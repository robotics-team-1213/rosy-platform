## D-994 N100·16GB Ubuntu 호스트에 통합관제 R을 두고 장치 owner와 공통 서비스의 책임을 구분한다

**Status:** Accepted (2026-11-08, 사용자 결정). 목표 하드웨어·역할 분담의 결정이다. Ubuntu 설치, 서비스 이전, N100 부하 시험과 DEVICE/FIELD 수용은 미수행이다.

### Context

사용자는 통합관제를 Intel N100·메모리 16GB 컴퓨터에 Ubuntu로 설치해 운영하기로 했다. D-960은 R의 목표를 상시 가동하는 저부하 전용 PC로 정했지만 구체 하드웨어는 정하지 않았다. D-893·D-974에 따라 물리 컴퓨터, 관제 단위, 프로그램, 장치 owner를 구별해야 한다. 같은 PC에 서비스를 모아도 그 서비스의 원장과 권한이 하나가 되지는 않는다.

### Decision

1. **N100·16GB 컴퓨터를 R의 목표 호스트로 채택한다.** 기본 OS는 Ubuntu Server 24.04 LTS amd64, 현장 서비스는 기존 서명 site candidate와 Docker Compose 경로를 쓴다. 운영 브라우저를 같은 컴퓨터에서 실행해야 하면 Desktop 설치를 허용하되 브라우저 부하까지 수용 시험에 포함한다. 유선 LAN을 기본으로 하고 SSD 512GB를 권장한다. 실제 배치와 이전 상태의 정본은 [관제 단위 배치표](../deployment/control-units.md#현장-배치표) 한 곳이다. PC의 물리 이름은 **N100 미니 PC**, 논리 단위 이름은 **통합관제 R**로 구별한다.
2. **이 호스트는 관제·공통 서비스·가벼운 업무 처리를 맡는다.** R의 Fleet·proxy·상태 저장, Account·Monitoring을 목표 범위로 삼는다. Harbor 웹·업무 실행기는 팀 저장소의 별도 Compose와 DB로 동거할 수 있다. Harbor의 입구는 R의 공개 HTTP 계약이며 팔 작업 승인은 해당 셀에 남는다(D-965). 이 결정이 미구현 팔 위임 wire를 활성화하지 않는다. AI 학습·무거운 추론·시뮬레이션·빌드·시험은 이 호스트의 운영 업무에 넣지 않는다.
3. **영상은 처리 위치와 비용을 확인한 뒤 배치한다.** R은 하위가 공개한 대표 영상을 볼 수 있지만 셀의 원본 카메라 전체와 장치 관측 처리를 중앙으로 이전하지 않는다. Media의 권한·세션 관리와 영상 전달·변환, Vision의 관측 계산을 구별한다. 기존 site Compose에는 `vision`·`media` 등이 있으므로 전체 스택을 그대로 복사하면 가벼운 관제 배치가 된다고 가정하지 않는다. 실제 설치 전 기존 서명 배포 경로에서 서비스 구성과 영상 경로를 확정하고, 그 구성을 부하 시험한다. 지원하지 않는 선택 배포가 필요하면 별도 구현·검증하고 현장에서 미서명 overlay로 우회하지 않는다.
4. **R·장치 owner·공통 서비스·사람 권한을 다음처럼 구별한다.**

   | 대상 | 의미와 책임 | 명령·원장 경계 |
   |---|---|---|
   | N100 미니 PC | 프로세스를 실행하는 물리 호스트 | 호스트 관리자 권한이 Fleet 작업 승인이나 장치 실행 권한을 대신하지 않는다 |
   | Rosy Fleet | 관제 단위가 사용하는 프로그램과 콘솔 | 제품 이름 자체가 단일 관제·단일 DB를 뜻하지 않는다 |
   | 통합관제 R | 루트 관제 단위. 자기 원장·직접 소유 자원, 하위 정보 집계·위임·취소·허용된 정지 요청 | 하위 원장·승인을 대신하지 않는다. 직접 소유 Pinky는 자기 Fleet→CORE 경로를 쓴다. R에도 직접 소유 장치가 있을 수 있다 |
   | 셀 관제 CELL-x | 같은 물체·공간을 다루는 암 세트의 원장·기명 승인·Task admission/dispatch·정지/복구 조정 | 자기 팔이 연결된 호스트에서 기존 local UDS 경로를 쓴다. R 연결이 끊겼다고 원장·승인 owner가 R로 넘어가지 않는다 |
   | 로봇 CORE | 로봇의 외부 API, 상태·안전 재검사, 최종 Base 명령 owner | 최종 `/cmd_vel`은 CORE가 단독 발행한다. R·Account·Monitoring이 대신 발행하지 않는다 |
   | OMX owner | 팔별 joint/action 실행·안전·정지·복구 책임 | 셀 Fleet의 업무 승인과 장치의 최종 수락을 구별한다. 팔 연결·local stop을 N100으로 옮기지 않는다 |
   | Account | 공통 사람 신원·로그인·권한·세션·회수 | 앱마다 사람 계정을 복제하지 않는다. 앱별 허용·장치 admission·기계 자격은 기존 owner에 남는다(D-807·D-955) |
   | Monitoring | 상태 수집·집계·읽기 | 복구·명령 권한을 갖지 않는다. 같은 호스트의 장애는 외부 관측·백업 없이 스스로 보장할 수 없다 |
   | Harbor | 항만 업무 장부·제안·업무 완료 판정 | R·셀·장치의 원장과 별도다. Account 연동은 공통 계약을 따르고 별도 사람 계정을 만들지 않는다 |
   | 모델 PC / AI PC | 각각 학습·독립 평가 / 승인된 고정 모델 추론·사실·후보 | Fleet 원장 쓰기·작업 승인·장치 명령 권한이 생기지 않는다(D-516) |
   | 기명 운영자 | 개인 계정에 허용된 작업 요청·승인·관리 | `owner`라는 공용 계정·새 역할을 만들지 않는다. D-968의 개인 계정과 기존 capability 검사를 유지한다 |

   이 문서의 **owner는 해당 자원·상태·명령을 책임지는 소프트웨어 주체**다. 사람 계정의 소유자 권한과 구별한다. DB·설정·자격·Compose project 격리는 유지하고, Account를 공유한다는 이유로 관제·업무 DB를 합치지 않는다. R과 하위 셀은 기존 직계 HTTP/TLS로 연결하며 공유 SQLite·직접 DDS 연결을 추가하지 않는다.
5. **성능과 장애 복구를 확인한 뒤 운영으로 전환한다.** R·Account·Monitoring·동거 업무 앱과 실제 대표 영상·동시 브라우저 접속을 함께 걸어 최소 24시간 관측한다. CPU·메모리·swap·디스크 증가량·발열·API 지연·관측 신선도를 기록한다. 최대 장치·사용자·영상 수와 허용 지연은 시험 전에 정하고, 기존 기능 계약을 충족하지 못하면 영상·보조 처리를 분리하거나 더 큰 호스트를 선택한다. N100·16GB라는 사양만으로 처리 용량을 보장하지 않는다.
6. **계획된 이전과 복구 경계를 유지한다.** D-893 §6에 따라 진행 중 작업·결과 불명을 조정하고 이전 owner의 실행 권한을 회수한 뒤 새 위치를 검증한다. R 원장·Account DB·Harbor DB의 기존 owner별 백업·복원과 외부 보관, 부팅 후 자동 시작을 확인한다. R 호스트 단절·재부팅 중에도 하위 셀의 기존 관측·정지·복구 경로를 확인한다. 공통 Account 장애 시에는 기존 세션·인증 계약대로 처리하며 신규 로그인·갱신·승인이 가능하다고 보장하거나 로컬 우회 계정을 만들지 않는다. 재접속·DB 복원으로 자동 재실행·정지 해제·재무장하지 않는다.

### Consequences

학습·개발 호스트 재시작과 R 운영을 분리하고, 한 물리 PC에서 관제·로그인·조회 서비스를 제공할 수 있다. 대신 같은 PC 장애가 R·공통 로그인·Monitoring·동거 업무 앱에 함께 영향을 준다. 프로세스·DB 분리는 전원·OS 장애 격리를 뜻하지 않는다.

이 변경은 결정과 배치 안내만 기록한다. 현재 배치표의 「지금 호스트」는 이전 증거 없이 바꾸지 않는다. 기존 관제 구성·자격 범위·문서 계약 시험은 소스 검증이고, N100 실측·서비스 이전·실제 R↔셀 연결·현장 수용은 별도다.
