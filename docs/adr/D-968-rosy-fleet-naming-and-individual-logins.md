## D-968 통합관제 고유명은 Rosy Fleet이고 사람 계정은 개인 로그인만 쓴다

**Status:** Accepted (2026-11-03, 사용자 결정. 명명·계정 모델 확정이며 코드 변경을 요구하지 않는다)

## Context

통합관제 PC 콘솔을 부르는 이름과 사람 계정 모델이 대화마다 다시 올라온다. 2026-10-22 인증 복구와 2026-11-02~03 콘솔 로그인 실패 관측 중에도 "rosy fleet owner" 같은 계정을 넣을지, 통합관제를 무엇으로 부를지가 다시 논의됐다. 정본 없이 반복되면 구현·문서·운영 대화가 어긋난다.

이미 정해진 구조: 사람 자격은 사이트 레지스트리 `site-users.yaml`(D-276 토큰, D-519 로그인)에서 D-962 독립 Account 서비스로 이행 중이다. 콘솔 화면은 `applications/fleet/web`(D-822)이고 로그인·프로필·관리 자산의 소유도 같다. 역할은 `operator`/`viewer`/`service`/`ai_observer`이고 운영자 위에 `policy_admin`(D-793)이 붙는다. "owner" 역할·계정은 존재하지 않는다.

## Decision

1. 통합관제의 고유명은 **Rosy Fleet**이다. 콘솔 제목·문서·발화에서 이 이름을 유지한다. "통합관제"는 이 콘솔을 가리키는 한국어 설명어로만 쓰고 다른 영문명을 새로 만들지 않는다. D-960의 통합관제 R(관제단위)은 장치 제어 계층의 이름이며 이 콘솔 이름과 별개다.
2. 사람 콘솔 계정은 **개인 계정만** 등록한다. "rosy fleet owner", "admin" 같은 직함·공유 계정은 만들지 않는다. 감사(`fleet_api_audit`, `rosy_account_audit`)가 개인 단위로 남아야 책임 추적과 자격 회수가 되고, 공유 계정은 비밀번호 회전과 세션 회수를 무력화한다.
3. 소유자 권한은 새 역할이 아니라 **`operator` + `policy_admin`(`fleet.policy`)** 조합으로 표현한다(D-793 유지). 화면과 검사는 이 조합을 "소유자 권한"으로 부른다. `owner` 문자가 들어간 역할·계정·principal을 새로 만들지 않는다.
4. 사람이 아닌 보안주체(서비스·점검·관제단위)는 용도 기반 `principal_id`와 login 없는 토큰·`machine: true` 자격만 쓴다(D-962 규칙). 사람 로그인 항목과 섞지 않는다.
5. 콘솔의 아이디·비밀번호 처리는 이미 구조화된 길만 쓴다. 로그인·변경·프로필 라우트(`rosy_account`), 레지스트리가 정한 초기 비밀번호와 첫 로그인 강제 변경, 재설정은 원자적 레지스트리 도구(`deploy/site/site_users.py`) 또는 Account 관리 UI로만 한다. 콘솔 코드나 일회성 스크립트가 새로운 비밀번호 경로를 만들지 않는다.

## 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| D-276 / D-519 | 레지스트리·로그인 형식은 그대로 두고 이름·계정 모델만 확정한다. |
| D-793 | `policy_admin` 조합을 소유자 권한 표현으로 계속 쓴다. |
| D-962 | Account 독립 서비스 이행 전후에 같은 이름·계정 모델을 적용한다. |
| D-960 | 통합관제 R은 관제단위 계층 이름이다. 이 ADR이 정하는 콘솔 이름과 섞지 않는다. |
| D-822 | Fleet UI 소유 구조는 그대로다. 부르는 이름만 Rosy Fleet으로 통일한다. |

## Consequences

- 새 화면·문서·대화는 콘솔을 "Rosy Fleet"으로만 부르고, 계정 요청·등록은 개인 단위로만 받는다.
- 계정 잠김 대응은 초기 비밀번호 재설정 → 첫 로그인 강제 변경 순서를 따른다. 2026-11-02~03 로그인 실패 사례도 이 경로로 해결했다. 실제 사람 로그인 관측은 배포 단계 증거와 분리해 기록한다.
- 기존 구조(역할·레지스트리·라우트)가 이미 이 결정과 일치하므로 이 ADR은 문서·명명 확정이며 코드 변경을 수반하지 않는다.
