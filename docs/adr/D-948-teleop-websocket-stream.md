# D-948 사람 조종은 `/ws/teleop` 스트림으로 보내고 REST `/teleop`은 대체 경로로 남긴다

**Status:** Accepted (2026-11-01, 사용자 지시 "WebSocket도 좋은 방향 — 처리해줘"). 장치·현장 수용은 별도다.

### Context

- 운용자가 "조종할 때마다 자주 끊긴다"고 보고했다(2026-11-01).
- Pilot은 hold-to-drive 명령을 100 ms마다 REST `POST /api/v1/teleop`로 보냈다. 한 번에 한 요청만 날아가고, 요청 시한은 400 ms, CORE 워치독은 500 ms다(SAF-002).
- 요청 하나가 Wi-Fi 지연으로 늦으면 다음 명령이 나가지 못한다. 시한에 왕복이 더해지면 워치독이 로봇을 세운다. 안전한 쪽으로 실패하지만 조종감이 끊긴다.
- 프로토콜 교체로 Wi-Fi 지연 자체는 사라지지 않는다. 바꿀 수 있는 것은 요청마다 기다리는 구조다. 같은 시기에 Wi-Fi 절전도 끈다(별도 변경).

### Decision

1. **`/ws/teleop`을 둔다.** 인증은 `/ws/state`와 같은 첫 메시지 방식이고 operator 이상이다. 프레임은 `{"type":"teleop","seq","linear","angular"}`, 답은 `{"type":"ack","seq","accepted","code"}`다.
2. **프레임마다 REST와 같은 검사를 한다.** trip lease, capability, 보정 소유, 유지, command manager, 녹화·영상 훅을 공용 함수 `apply_teleop` 하나로 거친다. REST가 409로 답하는 거절은 같은 code의 ack가 된다.
3. **최신 것만 적용한다.** seq가 앞서지 않는 프레임은 버린다. 적용을 기다리는 동안 새 프레임이 오면 앞 프레임은 실행하지 않고 `SUPERSEDED`로 답한다.
4. **끊기면 세운다.** 마지막으로 적용한 명령이 움직임이었으면 소켓이 닫힐 때 0을 적용한다. 같은 토큰의 새 소켓이 대신한 경우는 예외다. 워치독 500 ms는 바뀌지 않는다. 0 적용은 그 위에 더하는 장치다.
5. **REST는 대체 경로다.** Pilot은 소켓이 열려 있지 않거나 ack가 1 s 넘게 없으면 기존 REST 경로로 보낸다. 소켓은 토큰마다 하나, 전체 `teleop.max_ws_clients`(기본 2)개다.

### Consequences

- 요청마다 기다리지 않으므로, 한 프레임이 늦어도 다음 프레임은 나간다. 늦은 명령이 줄지어 실행되지 않는다.
- 경로가 둘이 된다. 같은 검사 함수를 공유하므로 판정은 하나다.
- Android Pilot 프록시가 `/ws/teleop`을 넘기지 않으면 REST 대체 경로로 동작한다. 장치에서 확인해야 한다.

### Alternatives

- **REST 유지, 동시 요청 허용:** 순서가 뒤바뀐 명령이 늦게 도착해 최신 명령을 덮을 수 있다. 기각.
- **WebRTC 데이터채널(비신뢰):** TCP head-of-line도 피하지만 연결 설정·NAT·인증이 무겁다. WebSocket 실측에서도 끊기면 다시 본다.
- **MQTT 등 브로커:** D-59·D-227 8. 기각.
