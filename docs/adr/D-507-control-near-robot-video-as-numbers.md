## D-507 제어 고리는 로봇 가까이 두고, 영상은 숫자로 바꿔 보내며, 사람이 볼 영상만 필요할 때 보낸다

**Status:** Proposed (2026-10-07, 사용자 요청 "속도나 이런걸 올릴 수 있는 영상 관련 부분도 더 생각해볼래", "그렇게 아예 ADR로 지정해봐"; 사용자 선택: 현장 도구를 현장 PC에서 먼저). 문서만. 코드·설정·네트워크 장비는 바꾸지 않는다.

잇는 결정: D-152 · D-257 · D-368 · D-375 · D-379 · D-399 · D-411 · D-429 · D-430 · D-468 · D-491 · D-500.

### Context

- **2026-10-07 현장 측정.** 운영자 노트북의 Wi-Fi가 끊겨 인터넷은 LTE(10.207.x)로, 로봇 LAN(192.168.1.0/24)은 Tailscale 서브넷 경로로 들어갔다. 왕복 시간: 노트북 → 공유기 532–678 ms, → 로봇 356–805 ms(최대 1.1 s). 같은 시각 현장 PC(robttt, 로봇 LAN Wi-Fi) → 로봇 7–10 ms. 로봇 송신은 2–8 KiB/s(미리보기는 요청 때만), Rosy Cam → 현장 PC 수신 약 512 KiB/s. 느림의 원인은 영상이 아니라 제어 명령의 경로였다.
- **같은 날 생긴 문제가 모두 이 경로에서 나왔다.** PC 스크립트가 명령마다 HTTPS 연결을 새로 맺어 명령 간격이 감시 타이머(300 ms)를 넘었고, 로봇은 명령 사이마다 멈췄다(회전 명령의 16 %만 실행). 여유 판정은 LiDAR 한 장에 0.22–1 s가 걸렸다. 보정 도구(`run_calibration.py`)도 같은 이유로 중단됐다(고침: `core_client.py`, 연결 유지). `docs/solutions/workflow-issues/field-scripts-driving-a-real-robot-need-clearance-identity-and-wall-pose-2026-10-07.md`.
- **이미 맞는 원칙이 있다.** 천장 카메라는 현장 PC에서 처리하고 Fleet에는 자세만 보낸다(D-257). 로봇 카메라의 차선·횡단보도 판단은 로봇 안에서 하고 근거만 보낸다(D-468, D-491). 녹화는 로봇 안에 남기고 나중에 가져온다(D-379, D-411). 운전자 스트림은 요청할 때만 있다(D-368). 여유 검사는 CORE 명령 입구에서 강제한다(D-500, Proposed). 빠진 것은 PC 쪽 현장 도구와 사람용 영상의 원칙, 그리고 무선망의 우선순위다.
- **현장 PC로 옮기자 바로 풀렸다.** 같은 도구(연결 유지 + 배경 여유 판정)를 현장 PC에서 돌리자 8kcn 여유 판정이 p50 0.032 s, 최대 0.086 s였다(노트북 0.42–1 s). 명령 간격이 감시 타이머 안에 들어온다.
- **운영자 경로를 도구가 모른다.** 오늘 도구들은 자기가 0.5–1 s 경로 위에 있는지 알지 못했다.

### Decision

1. **제어 고리는 로봇 가까이.** 로봇을 움직이는 고리(명령 → 센서 → 판단)는 로봇 안(CORE) 또는 로봇과 같은 LAN의 현장 PC에서 돈다. 운영자 PC는 시작·중지·결과 보기만 한다. 안전 정지는 운영자 연결과 무관하게 로봇 안에서 성립한다(D-500 결정 6, D-430).
2. **현장 도구는 현장 PC에서 실행.** 보정 주행(`run_calibration`), IR 교정 선 건너기, LiDAR-벽 자세, 현장 확인 스크립트는 현장 PC(robttt)에서 실행하는 것을 기본으로 한다. 노트북에서 직접 실행하는 것은 결정 5의 경로 검사를 통과할 때만이다. 도구는 저장소 코드(`core_common.robot_body`, 지도 번들, `tools/calibration`)를 그대로 쓰고 현장 PC 전용 사본을 만들지 않는다.
3. **영상은 숫자로 바꿔서 보낸다.** 판단에 쓰는 영상은 생긴 곳에서 처리하고 결과만 보낸다.
   - 천장 카메라: 바닥 정합(D-375)과 로봇 자세(바퀴·LiDAR 대조)는 Vision(현장 PC)이 계산하고 Fleet에는 자세·품질만 보낸다(D-257 확장).
   - 로봇 카메라: 차선·횡단보도·여유 판단은 로봇 안, 근거(`containment` 등)만 보낸다.
   - 원본 프레임을 판단 목적으로 원격에서 가져오지 않는다(오늘 PC가 로봇 프레임을 받아 판단한 방식은 현장 확인 전용 예외로 둔다).
4. **사람이 보는 영상은 필요할 때, 경로에 맞게.** 미리보기·운전자 스트림은 요청할 때만 열고, 받는 쪽 경로의 왕복 시간·대역폭을 보고 해상도·fps·JPEG 품질을 낮춘다(Rosy Cam의 품질 자동 조절과 같은 방식). 녹화는 장치 안에 H.265로 남기고 회수한다. 영상 스트림은 제어 명령과 같은 연결을 쓰지 않는다.
5. **운영자 경로를 알리고, 느리면 직접 제어를 막는다.** 운영자 도구와 콘솔은 로봇까지의 왕복 시간을 재서 보인다. p95가 감시 타이머의 절반(현재 150 ms)을 넘으면 "원격 경로"로 표시하고, 그 경로에서의 직접 조종(teleop)과 현장 도구 실행을 거절한다. 보기·결과 확인은 허용한다. 기준값은 D-500 `motion_response`의 `remote` 지연과 맞춘다.
6. **무선망에서 제어를 먼저.** 현장 공유기(OpenWrt)는 조종·정지·상태 트래픽을 높은 우선순위(DSCP/WMM voice)로, 영상은 video 등급으로 둔다. 로봇·카메라·현장 PC는 5 GHz 현장 SSID에 두고, 고정 주소 계획(현장 장비 .200 이상)과 같이 관리한다. 운영자 PC는 현장 SSID에 직접 붙는 것을 기본으로 하고 Tailscale은 보기·관리용이다.

### 기존 결정과 관계

| 결정 | 관계 |
|---|---|
| D-257 / D-375 | 천장 영상 처리는 현장 PC, Fleet은 자세만. 바닥 정합을 로봇 자세 계산에 씀 |
| D-399 / D-429 | 현장 층(Fleet·Vision·현장 PC)과 기기 처리의 경계를 유지. 현장 도구는 현장 층에서 실행 |
| D-368 / D-152 | 운전자 스트림·최신 프레임 계약은 그대로, 경로에 맞춘 품질 조절을 더함 |
| D-379 / D-411 | 녹화는 장치 안, 회수 방식 유지 |
| D-468 / D-491 | 로봇 카메라 판단은 로봇 안, 근거만 전송 |
| D-500 | 여유 강제는 CORE. `remote` 지연 기준과 결정 5의 경로 기준을 맞춤 |
| D-430 | 안전 정지는 운영자 연결과 무관하게 로봇 안에서 성립 |

### Alternatives

- **운영자 PC에서 더 빠른 코드로 버팀(연결 유지·스레드):** 오늘 그렇게 고쳤지만 경로가 0.5–1 s이면 감시 타이머를 맞출 수 없다. 기각(보조로만).
- **영상을 더 압축해 원격에서 판단:** 대역폭은 줄지만 왕복 지연은 그대로다. 기각.
- **감시 타이머를 늘림:** 정지가 늦어져 D-311 G4·D-500 간격이 커진다. 기각.

### Open questions

- 결정 5의 기준(감시 타이머의 절반)과 측정 창(최근 N초 p95).
- 현장 PC에서 도구를 실행하는 방법(SSH 명령, 현장 콘솔 작업, 컨테이너)과 권한·토큰 보관(D-226, D-418).
- OpenWrt QoS 설정의 소유자와 적용 순서, 5 GHz 분리 시 기존 장비(Rosy Cam 휴대폰, 태블릿) 호환.
- 2026-10-07 9dfk의 관측 노드·학습 차선 노드가 외부 Azure 주소(443)에 연결된 원인(대역폭·보안). 확인 전까지 열린 항목.

### Validation

1. SOURCE: 경로 측정·표시·거절(결정 5)의 시험, 현장 도구의 실행 위치 검사.
2. DEVICE: 현장 PC에서 실행한 IR 교정·보정 주행이 감시 타이머 안의 명령 간격(≤ 100 ms)을 유지함을 기록. 노트북 원격 경로에서 직접 조종이 거절됨을 확인.
3. FIELD: QoS 적용 전후 영상 재생 중 조종 왕복 시간 비교.
