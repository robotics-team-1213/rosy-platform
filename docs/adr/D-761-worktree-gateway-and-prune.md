## D-761 워크트리는 관문 도구로 만들고, 끝난 워크트리는 착지와 생성 때 손실 없이 치운다

**Status:** Proposed (2026-10-14). 사용자가 워크트리 증가를 글로 된 규칙이 아니라 프로그램 관문으로 관리하라고 요청했다. 이 결정 자체는 아직 승인되지 않았다. 독립 리뷰와 착지는 디스패처가 한다.

### Context

여러 에이전트 세션이 체크아웃 하나를 같이 쓰고, 세션마다 `.worktrees/<이름>`을 만든다(D-372). 만드는 절차는 있었지만 지우는 절차는 없었다.

- 2026-10-13에 워크트리가 279개, 로컬 브랜치가 1,246개였다.
- 그날 손으로 정리한 뒤 하룻밤 사이에 워크트리가 다시 124개가 됐다.
- 손 정리에 쓴 일회성 스크립트가 세 가지를 확인했다. 깨끗하고 main에 들어간 워크트리는 그냥 지워도 잃는 것이 없다. 커밋하지 않은 내용은 임시 인덱스로 커밋을 만들어 태그로 남기면 작업 트리와 브랜치를 건드리지 않고 보존된다. gitignore된 파일 가운데 캐시가 아닌 것(자격 정보, 수집 자료)은 git이 깨끗하다고 답해도 워크트리 삭제와 함께 사라진다.

`AGENTS.md` 「같이 하는 깃」 1번은 `git worktree add`를 직접 치게 했다. 그 문장만으로는 개수가 줄지 않았다.

### Decision

1. **만드는 관문은 하나다.** 워크트리는 `python tools/worktrees.py new <짧은이름> <type>/<topic>`으로 만든다. 도구는 `<type>`이 `feat`, `fix`, `refactor`, `docs`, `uiux` 가운데 하나인지(D-372), 경로와 브랜치가 아직 없는지 본 다음 `git worktree add --relative-paths .worktrees/<짧은이름> -b <type>/<topic> main`을 실행한다. `--relative-paths`를 모르는 git(2.48 미만)에서는 그 옵션 없이 다시 실행한다.
2. **손실 없는 청소는 자동이다.** `new`와 `tools/land.py`는 시작할 때 `prune --apply`와 같은 청소를 돌린다. 지우는 조건은 다섯 개를 모두 만족하는 것이다. 수정·스테이징·미추적 파일이 없다. HEAD가 `main`의 조상이다. 잠겨 있지 않다. 캐시가 아닌 gitignore 파일이 없다. 12시간 넘게 쉬었다. 지운 뒤 브랜치 끝이 여전히 `main`의 조상이면 브랜치도 지운다. main 체크아웃, 도구를 실행한 워크트리, 잠긴 워크트리, 캐시가 아닌 gitignore 파일을 가진 워크트리는 어떤 옵션으로도 지우지 않는다. `land.py`의 청소가 실패하면 경고만 찍고 착지를 계속한다. `--no-prune`으로 끌 수 있다.
3. **쉰 시간.** 다음 셋 가운데 가장 최근 시각부터 잰다. 브랜치 끝 커밋 시각, 워크트리의 `logs/HEAD` 수정 시각, `git status`가 보여 주는 파일의 수정 시각. 인덱스 파일의 수정 시각은 쓰지 않는다. `git status`만 돌려도 바뀌기 때문이다.
4. **커밋 안 된 작업은 태그로 남긴 뒤에만 지운다.** `prune --snapshot`은 쉬고 있는 워크트리 가운데 더럽거나 브랜치가 main에 들어가지 않은 것도 다룬다. 더러운 워크트리는 임시 인덱스(`GIT_INDEX_FILE`)에 `read-tree HEAD`, `add -A`, `write-tree`, `commit-tree`를 해서 워크트리의 HEAD를 부모로 하는 커밋을 만들고 `archive/<YYYY-MM-DD>/wip/<워크트리 이름>` 태그를 단다. 같은 이름이 있으면 `-2`, `-3`을 붙인다. 그 커밋과 작업 트리를 `git diff --stat`으로 비교해 차이가 없을 때만 `git worktree remove --force`를 한다. main에 들어가지 않은 브랜치는 지우지 않고 워크트리만 지운다. `--snapshot`은 사람이나 디스패처가 직접 돌릴 때만 쓴다. `new`와 `land.py`는 쓰지 않는다.
5. **상한은 40개이고 비상구가 있다.** `new`는 청소 뒤에도 `.worktrees/` 아래 워크트리가 40개 이상이면 exit 1로 거절한다. 가장 오래 쉰 열 개와 판정, 그리고 치우는 명령 `python tools/worktrees.py prune --snapshot --idle-hours 72 --apply`를 찍는다. `--force-over-cap "<이유>"`를 주면 상한을 넘겨 만들고 이유를 찍는다. 사고 대응 중에 막히는 것이 워크트리 하나가 더 생기는 것보다 나쁘기 때문이다.
6. **lint는 경고만 한다.** `python tools/harness/rosy_harness.py lint`는 워크트리가 상한 이상이거나, main에 들어갔고 12시간 넘게 쉰 워크트리가 있으면 `WARN`을 찍고 명령을 알려 준다. 오류가 아니다. 이 검사는 워크트리마다 `git status`를 돌리지 않는다. CI와 `.worktrees/`가 없는 체크아웃에서는 아무것도 찍지 않는다.
7. **절차 문서.** `AGENTS.md` 「같이 하는 깃」 1번과 6번, `docs/reference/shared-checkout.md`의 같은 절, `rosy-land-on-main` 스킬을 이 도구로 바꾼다. 실험실 PC 우산 문서는 저장소 밖이라 사람이 같이 고친다.

### 일부러 하지 않는 것

- 맨손 `git worktree add`를 막지 못한다. git에는 워크트리 생성 훅이 없다. 관문을 거치지 않은 워크트리도 청소와 lint 경고의 대상은 된다.
- 원격 브랜치를 정리하지 않는다.
- main에 들어가지 않은 브랜치를 지우지 않는다. 로컬 브랜치 수는 이 결정만으로는 main에 들어간 만큼만 준다.
- 설정 파일이 없다. 상한과 기본 쉰 시간은 `tools/worktrees.py`의 상수다.

### D-172와의 관계

D-172는 구조 개편 이전의 미병합 브랜치를 `archive/<YYYY-MM-DD>/<branch>` 태그로 보존하고 그 태그를 지우지 않는다고 정했다. 이 결정의 `archive/<YYYY-MM-DD>/wip/<워크트리 이름>` 태그는 같은 `archive/` 아래에 있고 같은 규칙을 따른다. 지우지 않는다. 차이는 가리키는 것이다. D-172 태그는 브랜치 끝 커밋이고, `wip` 태그는 도구가 만든 커밋 하나로, 부모가 그 워크트리의 HEAD이며 커밋되지 않았던 내용을 담는다. 그 내용을 main에 들일 때는 D-172와 같이 새 주제 브랜치에서 다시 만들고 독립 리뷰를 거친다. `wip` 태그를 그대로 머지하지 않는다.

### Consequences

- 착지한 워크트리는 12시간 뒤 다음 `land`나 `new`가 치운다. 더 일찍 치우려면 main 체크아웃에서 `git worktree remove`와 `git branch -d`를 한다.
- 커밋 없이 12시간 넘게 읽기만 한 워크트리도 깨끗하고 main과 같으므로 치워진다. 잃는 내용은 없지만 그 세션은 워크트리를 다시 만들어야 한다. 오래 둘 워크트리는 `git worktree lock`으로 잠근다.
- `.vscode/`나 `local.properties`처럼 캐시 목록에 없는 gitignore 파일이 있는 워크트리는 자동으로 치워지지 않고 `status`에 "holds ignored data"로 남는다. 사람이 확인하고 지운다.
- 청소는 `new`와 `land`에 `git worktree list`와 `for-each-ref` 두 번, 그리고 쉬고 있고 main에 들어간 워크트리마다 `git status` 한 번을 더한다.
- 상한 40은 측정으로 정한 값이 아니다. 동시에 일하는 세션 수보다 넉넉하게 잡은 시작값이고 상수 하나를 바꿔 조정한다.

### Validation

- `test/test_worktrees_tool.py`: 임시 저장소에서 실제 git으로 시험한다. 깨끗하고 main에 들어간 워크트리와 브랜치가 지워진다. 들어가지 않은 것은 `--snapshot` 없이 남고, 있으면 워크트리만 지워진다. 더러운 워크트리는 `--snapshot` 없이 남고, 있으면 태그에 수정·스테이징·미추적 내용이 들어 있다. 캐시가 아닌 gitignore 파일, 잠금, 쉰 시간 기준, 실행 중인 워크트리 보호, `new`의 상한·비상구·잘못된 type 거절, `land.py`의 청소와 실패 시 계속 진행을 본다.
- 변이 확인: gitignore 판정, 임시 인덱스의 `add -A`, 실행 중인 워크트리 보호를 지운 커밋에서 해당 시험 4개가 실패했다.
- 이 도구의 `prune`은 실제 저장소의 워크트리에 대해 아직 한 번도 실행하지 않았다. 다른 세션이 일하는 중이라 임시 저장소에서만 시험했다.
- `python tools/harness/rosy_harness.py lint`가 오류 0이다.
