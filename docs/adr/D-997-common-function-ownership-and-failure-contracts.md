## D-997 공통 기능은 실행 서비스·공용 코드·owner별 운영 어댑터로 나누고 기능별 소유와 장애 계약을 확정한다

**Status:** Accepted (2026-11-08, 사용자 결정: 혼합 구조를 기본으로 기능을 하나씩 구체화하고 ADR로 완전하게 결정). 아키텍처·분리 기준·목표 계약의 수락이다. 아래 신설·추출 대상은 아직 구현·배포된 것으로 간주하지 않는다. 기존 API·권한·프로세스·DB·폴더·서명·장치 수용을 이번 문서 변경으로 바꾸지 않는다.

### Context

Account만 공통으로 취급하면 등록·알림·설정·감사·백업·업데이트가 앱마다 중복된다. 반대로 이름이 같은 기능을 모두 중앙 서버로 옮기면 사람 자격과 장치 등록, 업무 원장과 감사 사본, 업데이트 계획과 실제 설치 권한이 섞인다.

D-987은 공통 서비스와 공용 코드를 정의했고 D-995는 관제·실행 owner·공통 서비스·호스트를 구별했다. 이 결정은 그 위에서 기능별 소유자·데이터·호출·장애·복구·전환 조건을 확정한다. 판단 기준은 코드 중복 개수가 아니라 같은 의미·권한·수명·장애 조건을 공유하는지다.

### Alternatives

| 대안 | 판단 |
|---|---|
| 모든 공통 기능을 라이브러리로 배포 | 단순하지만 독립 앱마다 신원·전달 원장·비밀을 복제하게 된다. 외부 앱의 플랫폼 내부 import 금지와도 맞지 않아 채택하지 않는다 |
| 모든 공통 기능을 하나의 중앙 서비스·DB로 통합 | 모든 복구·설정·장치 자격이 중앙 장애와 배포에 묶인다. 기존 owner·안전·독립 배포 경계와 충돌해 채택하지 않는다 |
| 기능별 실행 서비스 + 공용 코드 + owner별 운영 어댑터 | 상태·수명이 필요한 기능은 독립시키고 판단·최종 실행은 기존 owner에 둔다. 기존 소유·배포 구조를 유지할 수 있어 채택한다 |

### Decision 1 — 구조와 배치

네 영역을 유지한다. Harbor·Games 같은 업무 앱은 자기 업무를, Fleet·World·Decision·CORE·OMX는 플랫폼 업무와 장치 실행을, 공통 서비스는 여러 앱에 같은 기능을, 공용 코드는 동일한 처리와 계약을 맡는다. 여러 앱이 Fleet을 쓴다는 사실만으로 Fleet 원장·admission을 공통 서비스로 옮기지 않는다.

공통 제공물의 종류는 D-987대로 실행 서비스와 공용 코드 둘이다. 아래 owner별 운영 어댑터는 세 번째 중앙 서비스 종류가 아니라, 공통 도구를 쓰면서도 실행 권한을 기존 owner에 남기는 방식이다.

- 공통 **실행 서비스**는 여러 소비자에게 같은 기능을 제공하고 자기 상태·수명·독립 장애 처리가 필요할 때 둔다. 현재 Account·Monitoring·Media와 TLS 입구를 유지한다. 하나의 거대한 common 프로세스·DB를 만들지 않는다. 이미지 동반 배포는 각 기존 계약을 따르며 Account의 독립 이미지(D-962), Monitoring의 동반 배포(D-936)를 바꾸지 않는다. owner·프로세스·health·데이터 수명은 구별한다.
- **공용 코드**는 ROS-free 계약·검증·클라이언트는 `contracts/foundation`, 웹은 `shared/web`, Android는 `shared/android`를 사용한다. 업무 절차·파일 보관 정책·특정 앱의 상태를 전역 utils나 계약 wheel에 넣지 않는다.
- **운영 어댑터**는 공통 도구를 쓰되 자기 데이터·장치·프로세스의 특성을 아는 기존 owner에 둔다. 백업·복원·설정 적용·업데이트 활성화가 여기에 해당한다. 중앙의 임의 경로 접근·원격 shell·모든 장치 관리 토큰은 만들지 않는다.
- 기존 source holder·패키지·서비스 이름은 유지한다. 새 공통 최상위 폴더·통합 저장소를 만들거나 기존 폴더를 이동하지 않는다. 신설 알림 전달 모듈의 목표 소스는 `operations/notifications`이며 구현 변경에서 manifest·패키징·카탈로그를 함께 등록한다. 이 목표 경로는 현재 생성돼 있다는 뜻이 아니다.
- Harbor 같은 외부 앱은 공개 HTTP 계약을 소비한다. 이 분류 때문에 플랫폼 Python·DB·ROS를 가져오지 않는다. 내부 코드 공유와 외부 앱 계약 소비를 구별한다.

### Decision 2 — 기능별 확정표

| 기능 | 분리 형태와 정본 owner | 공통으로 제공하는 것 | 기존 owner에 남기는 것 |
|---|---|---|---|
| 계정·권한 | 독립 Account 서비스 | 사람 신원·로그인 수단·권한·세션·회수·프로필 | 대상 앱의 업무 허용, 기계 자격, 장치 admission·운전석 |
| 등록·목록·찾기 | Account 연동 등록부 + 장치/서비스 등록 owner + 공통 조회/클라이언트 | 승인된 등록 결과의 앱 목록·식별·접속 정보 소비 | 신원 증명·페어링·장치 역할·자원 할당·기계 자격 발급 |
| 설정 | 공통 검증·설정 transaction 코드 + owner별 저장·적용 | schema/version 검증·오류·동시 변경 거절·원자적 파일 교체 같은 기계 처리 | 설정 의미·유효 범위·활성화·장치 보정·비밀과 최종 writer |
| 알림 | 독립 알림 전달 서비스로 추출하는 목표 확정 | 등록된 채널의 전달·중복 접수 대조·전송 시도·전달 상태 | 알림 필요성·수신 범위·본문 정책·사건 인수/해결·발송 직전 유효성 |
| 감사 | owner별 정본 감사 + 공통 사건 형식/수집·마스킹 조회 | 최소 감사 계약·상관관계·검색 사본 | 업무 transaction·원본 감사·보존/복구 권한·완료 판정 |
| 백업·복원 | 공통 도구/receipt + owner별 실행 어댑터 | 무결성·버전/범위 검증·보관 상태·복원 검증 형식 | DB·키·첨부의 일관된 세트, 스냅샷/복원·writer 중지·재개 |
| 업데이트 | 공통 상태/검증 규약 + 배포 계열별 도구/활성화 owner | 산출물·설치 revision·검증/거절/rollback 상태 소비 | 서명 신뢰·호환성·다운로드/설치·hold·유휴 판단·재기동·안전 |

Monitoring은 이들의 허용된 상태·마스킹된 조회 사본을 읽는다. Media는 기존 영상 세션·위임·프로세스 관리 owner다. 둘을 알림 전달이나 범용 host 복구 서비스로 확장하지 않는다.

### Decision 3 — 계정·권한

Account는 사람 신원·로그인·권한·세션·회수의 단일 정본이다(D-757·D-807·D-962). 앱별 로그인 원장을 새로 만들지 않는다. 앱이 필요로 하는 로컬 업무 역할·감사는 중앙 신원에 결속하되 대상 자원의 허용 여부는 해당 서버가 요청마다 검사한다.

기계·장치·서비스·미디어 lease·외부 제공자 자격은 기존 owner에 남긴다. 사람의 로그아웃이나 중앙 공통 토큰으로 대신하지 않는다. Account 실패 시 새 로그인·발급·갱신·관리 쓰기는 닫고, 기존 자격은 원래 만료·회수·재검증·업무별 더 짧은 제한 안에서만 처리한다. 안전 정지·deadman·로컬 복구를 중앙 연결 유지에 의존시키지 않는다. Account DB 복원으로 정지 계정·소비한 refresh·회수 세션이 되살아나면 복원 실패다.

### Decision 4 — 등록·목록·찾기

등록을 하나의 범용 원장으로 합치지 않는다.

1. 사람 로그인 수신 client·callback·resource·앱 목록은 Account 연동 등록부가 소유한다(D-955·D-962). 승인된 원장을 소비하며 앱마다 별도 명단을 만들지 않는다.
2. 로봇/카메라 등록·장치 역할·workcell/직접 자원 할당·서비스 자격은 해당 Fleet·장치·서비스 owner가 검증하고 발급한다(D-302·D-807). Account client 등록 성공으로 기계 신원이나 장치 역할이 승인되지 않는다.
3. 공통 directory는 승인된 원본과 현재 연결 상태를 출처·시각과 함께 보여주는 조회다. writer 원장이나 자격 발급자가 아니다. 기존 앱 목록 API와 승인 directory를 재사용하며 별도 범용 Registry 서버를 신설하지 않는다.
4. mDNS 발견·주소·표시 이름은 신뢰나 접근 권한이 아니다. 승인된 identity와 transport의 결속을 유지하고, 단절·만료를 정상/등록 완료로 만들지 않는다. 모르는 주소로 자동 연결·자동 재등록하지 않는다. 동일 데이터의 여러 owner를 만들지 않고, 단계가 다른 등록 흐름은 기존 실패·보상·재시도 계약을 따른다.

### Decision 5 — 설정

중앙 Config DB/쓰기 서비스를 신설하지 않는다. 공유하는 것은 설정을 안전하게 읽고 검증·교체하는 코드이며 설정의 의미와 정본 저장·적용은 owner가 소유한다. 현재 기본값→사용자 overlay→명시 설정의 병합 순서와 각 서비스의 보호 설정·환경 규약을 유지한다.

- 설정 namespace는 기존 서비스·대상 identity를 따른다. 전역 dict에 모든 앱의 비밀·장치 보정을 섞지 않는다.
- 읽기, 초안 검증, 저장, 실행 중 적용을 구별한다. 오래된 revision이나 경쟁 변경은 거절하고 변경 전후 결과를 대조한다. schema가 모르는 값을 조용히 지우지 않는다.
- 장치 보정·한계·신뢰 anchor·등록 client·허용 callback은 해당 owner의 검증·권한을 통과한다. 공통 관리 화면은 owner의 허용된 계약을 호출하며 직접 파일·DB를 바꾸지 않는다.
- 단절 때 마지막 검증 설정의 사용 여부와 유효 기간은 기존 owner 계약을 따른다. 확인 불가 값을 기본 정상값으로 만들거나, 실패한 새 설정을 적용 성공으로 기록하지 않는다. rollback도 owner의 버전·신뢰·활성화 검사를 통과한다.

### Decision 6 — 알림 전달

알림 전달은 여러 앱이 HTTP로 소비하는 독립 공통 서비스로 추출한다. 현재 Fleet 사건 outbox·판단·인수·최종 검토는 Fleet에 유지하고, 전송 adapter와 전달 원장만 분리한다. 기존 구현은 이 전환을 검증하기 전까지 그대로 유지한다. 처음부터 새 메일·SMS·범용 메시지 브로커를 더하지 않고 기존 허용 채널 계약을 재사용한다.

**첫 전환의 생산자는 Fleet 사건 통지와 Harbor 업무 HOLD 통지로 고정한다.** 플랫폼 내부와 독립 업무 앱이 같은 전달 계약을 소비하는지 확인하기 위한 선택이다. Account 보안 알림은 첫 범위에 추가하지 않아 로그인·회수 흐름을 함께 변경하지 않는다.

| 생산자 | 첫 통지의 발생·수신 범위 | 발송 직전 유효성 정본 |
|---|---|---|
| Fleet | D-661의 기존 OPEN/CLOSED·명시 설정 운영 채널·본문/예산 | Fleet의 현재 case·의미 revision·최종 판단·인수/닫힘과 D-661 검사 |
| Harbor | 업무 장부의 기존 업무가 비-HOLD에서 HOLD로 들어가는 회차당 한 번. 해당 설치의 업무 조회 권한을 가진 운영자만 받도록 승인한 운영 채널 | 같은 원래 업무·HOLD 발생 회차가 여전히 유효하고 HOLD이며 현재 채널 수신 범위가 허용되는지 Harbor가 확인 |

Harbor는 업무 상태와 원본 알림 outbox·HOLD 발생 identity를 자기 업무 장부의 같은 transaction에 기록한다. polling으로 증가할 수 있는 `row_version`만으로 새 알림 identity를 만들지 않는다. 같은 HOLD 안의 재조회·같은 원인 갱신은 새 발송을 만들지 않고, HOLD를 벗어났다가 다시 들어갈 때만 새 발생 회차가 된다. 복원·재시작에서도 그 identity와 미해결 전달 상태를 보존한다. 이 원칙은 현재 `harbor.workflow.BusinessLedger`의 HOLD와 상태/row_version을 기준으로 구현하되 Django 업무 화면 DB와 분산 transaction을 만들지 않는다.

Harbor 첫 통지는 개입 필요 분류·불투명 업무/발생 식별자·시각·만료·token 없는 보호 업무 화면 링크만 포함한다. 원본 화물·재고·개인 정보·자유 텍스트·자격을 채널로 보내지 않는다. 승인 수신 채널이 없으면 외부 발송은 꺼져 있고 로컬 HOLD는 유지한다. 완료 통지·개인 연락처 자동 등록·자동 재개·채팅 승인·장치 명령은 첫 범위에 넣지 않는다. 이는 검증 대상 목표이며 현행 Harbor에 outbox나 통지가 이미 존재한다는 뜻이 아니다. 실제 Harbor 변경은 그 팀 저장소의 ADR/PR·계약 시험으로 반영한다.

- 생산자는 업무 상태와 알림 의도를 자기 DB의 같은 transaction에 남긴다. 전달 서비스의 접수/시도 원장은 그 업무 outbox의 대체가 아니다. 분산 transaction·물리 exactly-once를 약속하지 않는다.
- 전달 접수는 등록된 기계 신원과 생산자·대상 채널의 허용 범위로 검사한다. 발송지·webhook 비밀은 전달 서비스의 보호 설정에 두며 요청자가 임의 URL·수신자·redirect를 주지 않는다. 앱 사용자 토큰·장치 자격·Docker socket은 받지 않는다.
- 동일 생산자·알림 identity의 재접수는 같은 전달 건으로 대조하고 다른 본문은 충돌로 거절한다. 생산자와 서비스 모두 보관 용량·유효 기간·전달 예산이 유한해야 한다. 한 앱의 폭주가 다른 앱의 전달을 무한정 막지 못하게 한다.
- **발송 직전 현재 필요성은 생산자 owner가 재검사한다.** 서비스가 Fleet 사건 종료·인수·judgment revision 판단을 복제하지 않는다. owner에 확인할 수 없거나 통지 기한이 끝났으면 보내지 않고 대기/만료로 남긴다. 제출 여부가 불명인 외부 전송은 UNKNOWN이며 맹목 재전송하지 않는다. 새 owner 확인 계약을 마련하지 않은 채 기존 outbox를 원격 서비스로 옮기지 않는다.
- D-661의 Fleet 알림은 채널당 60초 간격·최대 3회·10분 expiry, 429/확실한 연결 전 실패만 제한 재시도, timeout/5xx/취소·재시작 뒤 제출 불명 UNKNOWN, 최소 본문·비밀/원본 영상 비노출을 그대로 유지한다. 다른 생산자에 이 숫자를 근거 없이 강제하거나 더 느슨하게 적용하지 않는다.
- 전달 접수·provider 수락·사용자 열람·담당 인수·사건 해소는 별개다. 채팅 응답·알림 확인으로 작업 승인·재무장·장치 명령을 수행하지 않는다.
- 전환은 원래 outbox/identity·진행 중 UNKNOWN을 보존하고 발송 owner를 하나로 바꾼다. 옛 발송기와 새 발송기를 동시에 활성화하지 않는다. 공통 서비스 단절 중에도 로컬 사건·원래 안전/운영 상태를 보존하며 통지 성공을 위조하지 않는다.

### Decision 7 — 감사

계정 변경은 Account, 업무·admission은 해당 앱/Fleet, 장치 실행·복구는 장치 owner가 원본 감사를 소유한다. 중앙 Audit DB를 모든 쓰기의 필수 경로로 만들지 않는다. 공통화 대상은 최소 사건 형식과 correlation, 비밀 마스킹·수집·조회 코드다.

최소 계약은 기록 owner·인증된 행위 주체의 종류/identity·대상·행위·요청/시도 상관관계·결과·관측/기록 시각·관련 revision을 구별하는 것이다. 사람이 아닌 주체를 사용자로 합성하지 않는다. 토큰·비밀번호·쿠키·원본 민감 자료는 넣지 않는다. 이는 목표 계약이며 새 공개 schema/endpoint를 설치했다는 뜻이 아니다.

감사가 필수인 보안·승인·설정 쓰기는 owner가 기존 transaction과 감사/outbox의 원자성을 보장하고, 기록할 수 없으면 성공으로 응답하지 않는다. 외부 수집 장애는 원본 감사를 지우지 않으며 Monitoring에는 권한으로 필터한 읽기 사본만 제공한다. 사본 누락을 사건 없음으로 해석하거나 사본으로 업무 원장을 재구성하지 않는다. 보관·삭제·복원도 원본 owner의 권한과 기존 보존 규칙을 따른다.

### Decision 8 — 백업·복원

공통 도구·무결성/신선도 확인·버전/범위/복원 receipt 규약을 재사용하되, 실행은 DB·첨부·키·현재 writer를 아는 owner별 adapter가 맡는다. 중앙 서비스에 모든 볼륨·키·임의 파일 경로를 연결하지 않는다. Account·Fleet·Harbor의 백업을 하나의 전역 DB나 파일 복사 작업으로 합치지 않는다.

각 owner는 일관된 백업 세트·schema/source revision·필요한 키 참조·검증 결과·보관 범위와 복구 절차를 관리한다. 백업 파일 존재·해시·DB 열림·복원 성공·업무 재개는 서로 다른 증거다. 키 원문을 일반 manifest나 조회 API로 내보내지 않으며 기존 민감 백업 보호·격리를 유지한다. 보관 개수·주기·RPO/RTO를 모든 owner에 같은 숫자로 새로 정하지 않는다.

복원은 원래 writer/실행을 정지·대조한 뒤 owner가 수행한다. 원장·identity·generation·회수 상태·미해결 요청을 검증하고 단일 writer와 기존 재개/재무장 절차를 거친다. Account 회수 역행, Harbor 복원 후 원래 요청 대조 없는 재제출, Fleet/장치의 자동 정지 해제·재실행을 허용하지 않는다. 백업 실패·신선도 초과는 실패/미확인으로 표시하고 마지막 검증된 복구본을 임의 삭제하지 않는다.

### Decision 9 — 업데이트

공통으로 제공하는 것은 제품별 desired/installed revision과 산출물 종류·검증·호환성·설치·건강·rollback 상태를 읽는 규약과 공통 검증/전송 도구다. 서명·호환성·실제 활성화는 각 배포 owner가 수행한다. 범용 중앙 업데이터나 임의 remote shell은 만들지 않는다.

ROSY site candidate·Pinky payload/OS·모델 산출물·Android·Harbor 이미지는 각자 기존 산출물·신뢰·설치·수용 경로를 유지한다. Harbor의 GHCR digest/CD를 ROSY의 수동 서명 site candidate와 동일한 신뢰로 취급하지 않는다. 공통 UI·설치 계획·HTTP 요청이 서명 키·업데이트 권한을 주지 않는다.

확인 실패는 새 산출물 적용을 거절하고 기존 검증 런타임을 유지하거나 기존 복구 절차를 따른다. D-985의 최신 payload 배달·유휴/배터리/명시 hold/claim·건강 검사·canary·rollback과 OS 수동 설치 경계는 유지한다. 공통 기능 분류를 이유로 새 봉인·승인 잠금·배달 중단 조건을 추가하거나 안전 검사를 없애지 않는다. 배포 성공이 보정·행동·업무·실물 수용을 대신하지 않는다.

### Decision 10 — 의존·저장·통신·장애의 공통 규칙

1. 서버 간에는 승인된 공개 HTTP/TLS 계약과 용도별 기계 신원을 사용하고, 내부 공용 코드는 기존 설치 묶음에 포함한다. 새 메시지 브로커·공유 SQLite·범용 비밀 저장소를 필수 인프라로 더하지 않는다.
2. writer·DB/schema·마이그레이션·보관/삭제·backup/restore는 기능 owner마다 명시한다. 상대 DB 직접 조회·수정이나 공통 관리자 권한으로 우회하지 않는다. 동일 호스트와 동일 이미지가 공유 writer를 뜻하지 않는다.
3. 업무/감사/알림 의도는 owner의 로컬 transaction을 우선한다. 외부 전달·수집은 durable 의도와 원래 identity로 대조하며 네트워크 timeout을 새 업무 key 재발급·자동 재실행으로 해결하지 않는다.
4. 중앙 서비스 실패는 새 권한·정상 상태·장치 가용성·완료 근거를 만들지 않는다. 안전 정지·watchdog·로컬 복구는 기존 장치 owner가 유지하고, 실행 중 작업의 계속/중단·새 작업 허용은 기존 계약을 따른다. 모든 장애에 전역 정지나 전역 계속 정책을 일괄 적용하지 않는다.
5. Monitoring과 알림 전달은 다른 서비스의 쓰기 경로에 필수적인 순환 의존을 만들지 않는다. 수집/전달 장애 자체는 각 owner의 로컬 기록과 상태로 남길 수 있어야 한다. 중앙 상태 조회 결과를 장치 실행 허가로 쓰지 않는다.
6. N100의 기본은 수용된 R·공통 서비스 구성이다. 새 알림 전달·영상 변환·백업·업데이트 작업은 자원 예산·동시 부하·장애 복구를 검증한 뒤 추가한다. 기능마다 하나의 상시 서버를 자동으로 늘리지 않는다.

### 적용 순서와 완료 조건

이 결정은 아래 순서와 통과 조건까지 확정한다. 단계별 구현은 별도 변경이며 문서 수락만으로 관문을 통과하지 않는다.

1. 현재 카탈로그와 실제 source/Compose·데이터/자격 owner를 연결한다. 기존 Account·Monitoring·Media·Foundation·웹/Android 모듈을 먼저 재사용한다.
2. 등록·설정·감사·백업·업데이트는 기존 writer·권한·프로토콜·수명·배포를 보존하며 같은 의미인 기계 처리만 추출한다. 동작이 다른 세션·origin 검사·독립 배포 proof helper를 억지로 합치지 않는다(D-841·D-987).
3. 알림은 위에서 고정한 Fleet 기존 profile과 Harbor 업무 HOLD를 실제 두 생산자로 구현해 목표 계약·기계 인증·접수 중복/본문 충돌·발송 직전 owner 확인·예산·UNKNOWN·단절·재시작·단일 발송 owner를 검증한 뒤 전환한다. Harbor의 같은 HOLD polling 중 무발송·HOLD 종료 뒤 대기 통지 거절·새 HOLD 발생·설치/수신 채널 권한 격리·원장/outbox 원자성도 확인한다. 전환 전까지 기존 Fleet 발송 경로가 정본이다. 새 HTTP 계약은 구현 변경에서 API reference·schema·버전을 같이 갱신하고 가짜 통과와 실제 채널 수신을 구별한다.
4. 각 추출은 caller·fixture·설치/import·데이터·키·기존 오류 의미를 함께 확인하고 커밋된 SHA의 원격 시험·독립 검토를 거친다. source manifest와 현장 Compose가 바뀌면 카탈로그·구조 시험·서명 packaging·rollback을 함께 검증한다.
5. 독립 앱은 고정 양 끝 SHA의 실제 HTTP 계약으로 검증한다. 실제 채널·N100 최대 부하·호스트 단절·백업 복원·업데이트 rollback과 DEVICE/FIELD는 각각 별도 수용한다. 기존 감사·회수·정지 한계를 낮춰 통과시키지 않는다.

### Consequences and evidence

새 공통 기능의 위치·데이터 주인·장애 처리를 앱마다 다시 정하지 않아도 된다. 대신 공통 알림 전달은 별도 수명·저장·인증과 owner 확인 계약이 필요하므로 단순 파일 이동으로 전환할 수 없다. 이 비용을 제외한 나머지 운영 기능은 별도 중앙 서버를 늘리지 않는 방향으로 확정했다.

조사 근거는 현행 [카탈로그](../reference/common-services.md), `core_common.config`·`config_transaction`, Account audit·독립 DB/backup 구성, Fleet `incidents/notifications.py`의 outbox와 채널 정책, 기존 site/robot updater와 Harbor ADR0021·0028이다. 이 변경은 문서·하네스·카탈로그 시험과 독립 검토로 검증하고 실제 원격 결과는 해당 SHA에 연결한다. 코드 추출·알림 서비스 신설·실제 채널 발송·서버/DB 이전·배포·실물 시험은 수행하지 않는다.
