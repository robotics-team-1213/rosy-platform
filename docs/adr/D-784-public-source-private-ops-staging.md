## D-784 공개 소스·비공개 운영 설정과 staging 경계

**Status:** Proposed (2026-10-17, Fleet·웹·시뮬레이션부터 적용하는 설계 초안)

## 배경

제품 코드는 공개 저장소 한 곳에서 유지하면서 팀 내부 설정과 개발 검증 환경을 공유해야 한다. 비공개 저장소는 비밀값 보관함과 구분한다. staging은 후보 버전을 운영과 분리해 확인하는 환경이며, 로봇 업데이터의 설치 전 번들 보관과는 다르다.

## 제안

| 위치 | 맡는 내용 |
|---|---|
| 공개 `rosy-platform` | 제품 코드·계약·ADR·합성 시험·비밀값 없는 설정 예제. 제품 코드의 단일 기준 |
| 비공개 `rosy-ops` | 환경별 설정·내부 운영 절차·배포할 전체 SHA와 산출물 digest·배포 및 롤백 기록. 제품 코드 복제본은 두지 않음 |
| 별도 저장소 | 토큰·비밀번호·개인키는 승인된 비밀 관리 수단, 원본 영상·MCAP·운영 DB는 접근 제한 자료 저장소. 오프라인 릴리스 서명키는 기존 D-437 절차 유지 |

비공개 운영 저장소의 첫 범위는 `README.md`, `environments/staging/desired.yaml`, `docs/staging.md`다. desired 파일은 공개 소스 SHA, 불변 산출물 참조와 digest, 이전 검증 버전, 검증 기록 참조를 선언한다. 실제 endpoint·운영자 정보는 비공개 범위에서만 관리하며 비밀값은 참조로 주입한다. 해시·대상·필수 설정이 비어 있으면 배포를 시작하지 않는다.

후보 빌드는 비공개 설정 없이 수행하고, 배포는 검증된 산출물과 설정을 결합한다. 공개 PR의 코드가 비공개 저장소 자격증명이나 배포 호스트에서 실행되지 않게 한다. 변경 가능한 branch·`latest`를 배포 신원으로 사용하지 않는다.

```mermaid
flowchart LR
    source["공개 소스 · 고정 SHA"] --> checks["CI · 산출물 검증"]
    checks --> staging["staging · Fleet·웹·시뮬"]
    ops["비공개 환경 설정"] --> staging
    staging --> result{"기능·격리·복구 확인"}
    result -->|실패| hold["승격 중단 · 이전 검증 버전 복구"]
    result -->|통과| receipt["SHA·digest·결과·롤백 기록"]
    receipt --> approval["운영 반영은 별도 승인·수용"]
```

### staging의 완료 조건

- 별도 호스트 또는 VM·DB·계정·인증 issuer·TLS 설정을 사용한다. 운영 DB·토큰·사용자 자료는 복사하지 않는다. 초기 데이터는 합성 자료를 사용한다.
- 실제 로봇과 운영 서비스로 향하는 네트워크 경로를 차단한다. ROS domain·namespace도 분리하되, 이것만으로 격리됐다고 판단하지 않는다. 운영 장치 자격증명과 USB·UART를 연결하지 않는다.
- Fleet 로그인·권한, 웹 표시, 시뮬레이션 작업·중단·재시작·연결 복구를 검증한다. 격리 실패나 비밀값 노출이 있으면 배포를 거절하고 해당 결과를 남긴다.
- 배포 전후 SHA·산출물 digest·설정 버전·검증 결과를 기록한다. DB 변경은 staging 백업과 복구 가능성을 확인한다. 불일치·검증 실패 시 마지막 검증 버전으로 복구하고 승격하지 않는다.
- 배포 대상 호스트, 접속 범위와 운영 담당자가 정해지기 전에는 실행 환경을 기동하지 않는다. staging 통과는 서명·제품 배포·DEVICE/FIELD 수용을 대신하지 않는다.

### GitHub와 승인

초기 비공개 저장소는 문서·설정 검토부터 시작한다. GitHub Free의 비공개 저장소에는 Environments 기능을 전제로 한 승인 관문을 구성하지 않는다. 지원 요금제와 실제 설정을 확인한 뒤 환경별 자격증명·브랜치 제한을 추가한다. 그 전의 배포는 명시적 대상과 고정 버전을 확인한 담당자의 수동 절차로 제한하며, 운영 자동 배포는 포함하지 않는다.

작성자·독립 검토자·게시 담당의 역할은 D-762와 PR 파이프라인을 따른다. 이 설계의 승인은 저장소 구성과 후속 구현 계획의 근거이며 실제 호스트 변경·장치 명령·서명을 승인하지 않는다.

## 대안과 기존 결정

공개 저장소만으로 환경을 관리하면 저장소 수는 줄지만 내부 설정을 함께 검토하기 어렵다. 제품 코드의 비공개 복제본은 동기화와 수정 경로를 늘리므로 채택하지 않는다.

| 결정 | 관계 |
|---|---|
| D-226·D-437 | 공개 자료·내부 자료·비밀값·오프라인 서명 경계를 유지 |
| D-427·D-429 | 공개 제품 소스의 책임·패키지·설치 경로를 이동하지 않음 |
| D-430 | CORE 최종 명령·안전 검토와 장치 수용 조건을 유지 |
| D-762·D-777 | 단일 게시 담당·독립 검토와 간결한 기준 문서 원칙 적용 |

초기 자료 이전은 파일별 소유·공개 권한·소비자를 확인한 뒤 수행한다. 이미 공개된 자료를 비공개로 옮겨도 과거 이력의 공개가 사라지지는 않는다.
