## D-757 Rosy Account 단일 신원과 모든 앱의 자동 인증 세션

**Status:** Accepted (2026-10-14, 사용자 요구: Rosy Account 하나로 모든 앱을 사용하고 로그인 후 권한 내 인증·세션 연결을 자동 처리한다. 설계 결정이며 구현·CI·배포·운영 계정 전환·사용자 수용은 별도)

### Context

Fleet은 D-519의 비밀번호·SQLite 세션과 D-686/689의 첫 변경·프로필을 구현했지만,
사람 계정/역할은 시작 시 YAML에서 읽는다. CORE의 장치 코드·토큰과 학습/검수의
접근 보호는 별개다. D-549는 Fleet 중심 Rosy Auth를 제안했으나 앱 전체의 자동 연결,
권한 회수, 프로젝트 협업과 전환 계약을 닫지 않았다.

사용자는 Fleet·로봇·Pilot뿐 아니라 모든 앱을 하나의 Rosy Account로 처리하고,
로그인 후 별도 코드 입력·토큰 복사·인증 세션 시작 없이 권한 내 기능을 바로
사용하도록 요구했다. D-755의 외부 계정 연결도 이 내부 신원에 결속해야 한다.

### Decision

#### 1. 사람 계정의 정본은 하나다

Rosy Account가 변경되지 않는 내부 account identity, 로그인 수단, 계정 상태,
프로필, 자원별 권한, 세션과 회수 revision을 소유한다. 앱별 사람 비밀번호 DB나
현장별 독립 복제 계정을 만들지 않는다. login/email/표시 이름이 바뀌어도 감사
주체는 유지하고 이메일 일치만으로 사용자를 합치지 않는다.

첫 구현은 기존 Fleet 프로세스의 auth holder와 SQLite를 사용한다. 운영 서버나
외부 IdP를 새로 요구하지 않는다. 여러 현장도 동일 논리 신원과 명시적 사이트
scope/trust로 다루며, 다중 현장 복제·federation 구현은 이 결정으로 완료되지 않는다.

계정 발급·정지/재개·권한 변경·비밀번호 초기화·세션 회수는 같은 원장과 서버 경로를
사용한다. 관리자 UI와 유지 도구의 정책을 일치시키고 서비스 재시작 없이 반영한다.
관리자 bootstrap/복구와 마지막 관리자 보호를 제공한다. 사용자 대신 최종 비밀번호를
정하지 않고, 기존 강제 첫 변경과 본인 비밀번호 확인을 유지한다.

#### 2. 어느 앱에서 들어와도 로그인 뒤 인증 세션을 자동 연결한다

`shared/web/surfaces.yaml`의 전체 사용자 표면과 API/WS/native 진입점을 대상으로 한다.
Fleet의 모든 문서, Dashboard, Pilot web/PWA/Android, Cam, 학습·리뷰·모델 관리,
Games 및 사용자 조작이 있는 도구를 빠짐없이 적용 목록에 둔다. 공통 라이브러리,
장치 Face 같은 비대화형 표면에는 로그인 창을 만들지 않지만 관리/조작 API가 있으면
같은 권한을 검사한다. PARKED 표면은 활성화 전 통합이 필요하다고 명시한다.

진입 흐름은 `Account 상태 확인 → 필요 시 로그인 → 대상 앱 세션 연결 → 현재
권한 조회 → 허용된 업무 복귀`다. 같은 브라우저의 유효한 Account 세션은 다른 앱에서
재사용하여 비밀번호를 다시 묻지 않는다. 새 기기/브라우저는 한 번 인증한다.
자격 교환·갱신·재연결은 앱이 처리하고 사용자에게 토큰 붙여넣기를 요구하지 않는다.

앱은 중앙 쿠키를 모든 호스트에 복사하지 않는다. 등록된 앱/복귀 주소와 결속된
일회용 교환으로 대상 자격을 얻으며 장기 비밀을 URL·로그·브라우저 localStorage에
남기지 않는다. 브라우저 쿠키는 HttpOnly/Secure와 CSRF 보호를 적용하고 native는
검증된 callback과 플랫폼 보안 저장소를 쓴다. 동일 origin만 가정하지 않는다.
구체적인 protocol·route·wire schema는 구현 전 API reference 및 shared schema에
명시하고, 검증된 표준 흐름/라이브러리를 선택한다. 이 ADR은 신규 endpoint를 확정하지 않는다.

갱신 경쟁은 하나로 모으고 만료·권한 거부·네트워크 불명을 구별한다. 자동 재연결은
이전 명령을 재전송하지 않는다. 사용자 전환 시 이전 사용자 응답·캐시·초안을
새 사용자에게 노출하지 않는다. 초안 복구도 같은 사용자·권한을 확인한 뒤 제공한다.

#### 3. 로그인은 신원이고 허용 여부는 자원별 권한이다

모든 허용은 account + action + site/device/project scope로 판단한다. 서버가 정본이며
UI 숨김만으로 보호하지 않는다. REST·WebSocket·장기 연결·다운로드·영상·worker 실행
경로에도 적용한다. 알 수 없는 권한/대상은 기본 거부한다.

| 기존 책임 | 유지할 경계 |
|---|---|
| viewer | 허용 자원 읽기; 로봇 명령 불가 |
| operator | 부여된 운용 행동; 계정 관리·정책 편집·학습 승인 자동 허용 불가 |
| policy-admin | 정책 관리; operator의 모든 행동을 상속하지 않음 |
| Account 관리 | 계정/권한 관리의 별도 명시적 부여; 로봇 조작으로 자동 확대 불가 |
| 학습/프로젝트 | 열람·가져오기·편집·검수·구성원 관리·외부 게시를 구분 |
| service/ai_observer/장치 | 별도 기계 신원; 사람 로그인이나 관리자 권한으로 승격 불가 |

기존 역할을 이름 순서의 권한 계층으로 합치지 않는다. 신규 capability 식별자와
기존 역할의 정확한 매핑은 구현 계약에서 allow/deny 표와 시험으로 고정한다.
타 사용자·프로젝트·로봇의 자격 재사용과 자기 권한 상승을 거부한다.

#### 4. 중앙 인증과 각 실행 주체의 권한은 분리한다

CORE는 대상별 짧은 서명 접근 자격을 검증한다. issuer·audience·용도·서명 알고리즘·
만료·신뢰 키·권한 revision을 검사하고 unknown key/타 대상/replay를 거부한다.
신뢰 키의 배포·회전·폐기는 기존 검증된 배포 경로를 사용한다. 정상 시계가 없거나
검증할 수 없는 자격을 유효하다고 간주하지 않는다.

Fleet은 사이트 transaction과 admission, CORE는 최종 Base 명령, OMX는 장치 action,
학습 owner는 검수/승격을 계속 소유한다. 자동화하는 것은 인증 세션이다. 운전석
점유·deadman·위험 작업 확인·장치 최초 등록·보정·자료 외부 게시 동의를 자동 승인하지
않는다. 이미 적법하게 허용된 업무에 중복 인증 단계를 추가하지도 않는다.

로봇 로컬 코드/관리자 자격은 AP·단독 장치·장애 복구 경로로 구분해 유지한다.
복구 신원을 중앙 사용자로 위장시키지 않고 감사 출처를 구분한다. 개발 모드도 기존
계약에 한정하며 운영 인증 실패의 자동 fallback으로 사용하지 않는다.

#### 5. 세션 종료와 권한 회수는 전 앱 계약이다

계정/권한 변경과 회수는 DB transaction으로 기록하고 세션/자격 revision을 갱신한다.
중앙 서버의 새 요청·발급·갱신은 변경 commit 이후 최신 권한으로 판정한다. 이미
실행 중인 작업은 owner가 정한 안전한 취소/checkpoint 경로를 따른다.

연결된 verifier의 회수 적용 상한은 **30초**, 단절된 verifier의 이미 발급된 자격
유효기간은 **최대 5분**으로 정한다. 이는 목표 계약이며 현재 달성한 성능이 아니다.
회수 snapshot의 신선도를 관측하고 갱신 실패 상태를 단절로 표시한다. verifier는
권한/회수 정보를 신선하게 확인하지 못하면 자격 수명을 연장하지 않는다. 기존
CORE watchdog·lease 등 더 짧은 안전 제한은 이 수치 때문에 늘리지 않는다.

기본 로그아웃은 해당 로그인 session family의 모든 앱 갱신 자격을 끝낸다. 관리자
계정 정지·비밀번호 초기화·전체 로그아웃은 모든 기기 세션을 회수한다. 본인 비밀번호
변경은 기존 D-689의 이전 세션 종료 후 현재 사용자 replacement session 발급을 잇는다.
이전에 나간 오프라인 접근 자격의 잔여 만료 한계는 동일하게 적용한다.
UI는 회수 요청/중앙 적용/장치 적용 대기를 구별하고 오프라인 회수를 즉시 완료라 하지 않는다.

중앙 장애 시 새 로그인·갱신·관리 쓰기는 거부한다. 기존 검증 가능한 자격은 남은
수명과 scope 안에서만 유효하고 만료 후 무인증으로 전환하지 않는다. DB 실패를 성공으로
표시하지 않으며 비상정지 및 기존 안전 제한은 보존한다.

#### 6. 외부 계정과 업무 자격도 Rosy Account에 결속한다

D-755의 검증된 provider issuer/subject 연결과 초대 사용자 첫 로그인은 유지하되,
결과는 하나의 Rosy Account identity다. Hugging Face 등 외부 계정은 연결된 로그인
수단 또는 데이터 접근 자격이고 별도 ROSY 사용자 원장이 아니다. 최초 동의/추가 scope는
사용자가 확인하며 이후 허용 범위의 자격 갱신·작업 연결은 자동화한다.

개인 연결과 프로젝트 자동 작업 연결을 구별한다. worker는 요청 account·project·
connection·credential generation을 보존하고 민감 단계에서 권한을 재검사한다.
연결 해제/권한 축소 때 다른 사람 자격으로 자동 재시도하지 않는다. 서비스 토큰,
장치 pairing, Discord identity 연결은 사람 로그인과 구별하여 각각의 trust를 검증한다.

#### 7. 이전은 현재 비밀번호와 감사 이력을 보존한다

YAML의 사람 계정과 SQLite의 변경 완료 비밀번호·프로필을 함께 이전한다. 초기 YAML
비밀번호로 회귀하지 않는다. 충돌은 자동 병합하지 않고, migration은 재실행 가능하고
transaction 실패 시 원본을 유지한다. 기존 기계/AI/업데이트 자격은 보존한다.

이전 완료 후 사람 계정의 YAML/DB 이중 편집과 파일 watcher 재시작 의존을 제거한다.
관리 변경의 actor·target·이전/이후 권한·revision·결과를 기록하되 비밀은 기록하지 않는다.
rollback은 정지 계정·이전 비밀번호·회수 세션을 부활시켜서는 안 된다. 혼합 버전은
지원 여부를 명시하고 호환되지 않으면 거부한다.

### Alternatives

- 앱별 계정/토큰 복제: 회수 불일치와 수동 연결을 남기므로 채택하지 않는다.
- 별도 IdP/인증 서비스부터 운영: 현 단계는 기존 Fleet을 재사용한다. federation이나
  가용성 요구로 분리가 필요하면 같은 논리 identity/계약을 유지하는 후속 결정으로 다룬다.
- 네트워크가 같으면 무인증: 계정·권한 요구와 맞지 않아 채택하지 않는다.

### Consequences and acceptance

실행 순서는 [통합 완성 계획](../plans/2026-10-14-rosy-account-completion.md)을 따른다.
이 ADR의 Accepted는 제품 요구와 architecture의 결정이다. 구체적인 protocol·API·
capability 이름·migration schema·key lifecycle은 구현 전에 API/SRS/shared schema와
검증 항목으로 구체화한다. 전체 Task 1이나 구현이 완료됐다고 보지 않는다.

최종 완료는 모든 적용 앱에서 `로그인 → 자동 인증 세션 → 권한 내 업무 → 영속 결과
재조회 → 로그아웃/회수`를 같은 identity로 확인하는 것이다. 실제 API 우회 거부,
WS 만료/회수, 계정 전환 격리, DB/네트워크 장애, 오프라인 5분 만료와 온라인 30초 회수,
키 교체, native 로그인 복귀, 외부 연결 해제 및 worker 중단을 측정한다.

SOURCE·원격 TEST·최종 SHA CI·설치·runtime·실제 사용자 수용을 따로 기록한다.
브라우저/시뮬 통과는 물리 주행 수용을 대신하지 않는다. 계정 검증을 위해 E-Stop을
해제하거나 운동 명령을 보내지 않는다. 구현/전환 중 한 앱이라도 예외가 남으면 전체
통합 완료를 선언하지 않는다.
