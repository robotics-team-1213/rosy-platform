## D-960 실제 제어는 암 세트마다 붙은 관제가 하고, 통합관제 R은 그 위에서 조정한다

**Status:** Accepted (2026-11-02, 사용자 결정: "rosy의 실제로 제어하는 쪽은 각각 세트의 암에 붙는 것", "그건 서로 통합관제와도 소통", "통합관제 PC는 지금은 이 관제 PC로", "모델 PC는 일이 많다"). 구조와 배치 원칙의 결정이다. R의 서명 스택 재구성, R↔CELL-A 실제 연결, 브라우저 접속은 이 결정 시점에 **미수용**이다(아래 「수용 조건」).

잇는 결정: [D-850](D-850-composable-control-units.md)(관제 단위) · [D-855](D-855-control-unit-wire-and-scoped-cancel.md)(위임 wire) · [D-862](D-862-integrated-control-information-and-stop-requests.md)(정보·정지 요청) · [D-893](D-893-control-unit-host-placement.md)(관제 단위와 호스트 분리) · [D-911](D-911-omx-native-reviewed-operating-envelope.md)(팔 감독 관문) · [D-932](D-932-field-runs-one-landed-revision.md)(착지된 코드만 현장 동작)

### Context

D-850·D-893은 관제 단위와 호스트를 나누는 원칙을 정했다. 하지만 어떤 단위가 실제 장치를 움직이는지, 통합관제를 어디에 두는지는 정하지 않았다.

2026-11-02 현장 확인 결과는 다음과 같다.

- OMX 관제 PC 한 대에 Fleet이 셋 있다.
  - 서명 이미지의 독립 `rosy-site`: 셀 화면·카메라·팔 관측을 받는다.
  - 검증용 `cell-a`(CELL-A): 개발 이미지다.
  - 검증용 `r-verify`(R): 개발 이미지이고, 브라우저 포트가 없고, cell-a의 인증서를 빌려 쓴다.
- 운영자는 어느 화면이 셀이고 어느 화면이 통합인지 구별할 수 없었다.
- 셀 Fleet manifest의 카메라 라벨·장치가 실제와 어긋나 있었다(같은 날 수정).
- 통합관제 후보였던 모델 PC는 학습으로 부하 약 22/24 코어이고, GPU·드라이버 작업으로 재시작된다.

### Alternatives

| 대안 | 판단 |
|---|---|
| 통합관제 한 곳이 모든 팔·로봇을 직접 제어 | 팔의 정지·재무장·관절 owner가 장치에서 멀어지고 통합관제 장애가 모든 장치를 멈춘다. D-429·D-430과 충돌. 채택하지 않는다 |
| 암 한 대마다 관제 단위 | 같은 컨테이너를 함께 다루는 두 팔의 공간·물체 승인이 단위 사이 위임으로 쪼개진다. 채택하지 않는다 |
| **암 세트(셀)마다 관제 단위 + 그 위에 R** | 장치 가까이에서 원장·승인·정지를 지키고, R은 공개 경로로만 조정한다. D-893 구성표의 "암별 제어 PC + 통합 PC"와 맞다. **채택** |
| 통합관제를 모델 PC에 둔다 | 학습 부하·재시작이 통합관제의 상시 접속·정지 요청 중계를 흔든다. 채택하지 않는다 |

### Decision

1. **실제 제어는 암 세트마다 붙은 셀 관제가 한다.**
   - 같은 물체·공간을 함께 다루는 팔들(암 세트)이 하나의 셀 관제 단위다. 지금은 CELL-A = `workcell:arm_a`, `workcell:arm_b`, `workcell:arm_s`다. arm_s는 arm_a와 같은 보드의 이전 이름이다.
   - 셀 관제는 그 팔이 연결된 PC에서 돈다. OMX 정지(StopLocal)가 같은 호스트의 local UDS를 쓰기 때문이다.
   - 셀 관제가 원장, 기명 승인, Task admission, 팔의 정지·해제·재무장, 셀 카메라 전체를 소유한다.
2. **통합관제 R은 계층의 꼭대기에서 조정만 한다.**
   - R은 직계 하위의 요약·신선도·Task·지도를 모은다. 위임·취소·명시 허용된 정지 요청은 `/api/fleet/control-unit` HTTP/TLS로만 중계한다(D-855·D-862).
   - 하위 장치에 직접 명령하지 않고 하위 원장을 덮어쓰지 않는다.
   - 하위의 승인·정지 해제는 하위 화면에서 그 관제의 기명 운영자가 한다.
   - R이 직접 소유하는 장치는 Pinky `rosy_40`·`rosy_41`이다. Pinky가 늘어 자기 원장·승인이 필요해지면 `PINKY` 같은 하위 단위로 옮긴다.
3. **새 암 세트는 R 아래 새 셀이 된다.** 예: R → CELL-B. PC가 늘었다는 이유만으로 단위를 만들지 않는다(D-893 §3). 한 셀이 둘 이상의 PC를 쓰면 실행 호스트만 나눈다.
4. **화면을 나눈다.**

   | 단위 | 보여 주는 것 |
   |---|---|
   | 셀 | 그 셀 카메라 전부(원본), 관절·고장, 작업 승인 |
   | R | 각 하위의 요약·신선도·고장, 위임·정지 요청 결과. 대표 영상은 하위가 공개한 것만 |

5. **호스트 배치.**
   - CELL-A는 OMX 관제 PC에 둔다.
   - R은 **임시로 같은 OMX 관제 PC**에 둔다. 포트·DB·인증서·계정·Compose project를 셀과 분리한다(D-893 §3).
   - 목표는 **상시 켜 두는 한가한 전용 PC**다. R은 GPU가 필요 없고 Fleet·proxy·DB면 된다.
   - 모델 PC는 학습·평가, AI PC는 고정 추론 역할을 유지한다.
   - R을 옮길 때는 D-893 §6의 계획된 전환을 따른다.
6. **R과 CELL-A는 서명된 site candidate로 돈다.**
   - 각자 자기 DB·포트·TLS 인증서·수신 service principal을 갖는다. 인증서를 빌려 쓰지 않는다.
   - 기존 등록을 다시 하지 않는 쪽으로 전환한다. Pinky 등록을 가진 운영 site 스택이 R이 되고, 셀 관측(팔·카메라 자격)은 CELL-A 인스턴스가 갖는다. 같은 workcell을 두 관제가 함께 소유하지 않는다.
   - 대체가 확인된 뒤 개발 이미지의 검증 인스턴스 `r-verify`를 은퇴한다(사용자 승인 2026-11-02). 인스턴스별 전환 절차는 handoff에 둔다.

### Consequences and validation

운영자는 셀 화면과 통합 화면을 구별할 수 있고, 통합관제가 멈춰도 각 셀은 자기 팔을 계속 운영·정지할 수 있다. 대신 셀마다 인증서·계정·peer 설정을 관리해야 한다.

**수용 조건.** 아래가 모두 실제 실행으로 확인되기 전에는 R 연결을 수용했다고 쓰지 않는다.

1. R이 서명 이미지로 자기 인증서와 포트에서 뜨고, 운영자 브라우저가 R에 로그인한다.
2. R `GET /overview`에 CELL-A의 요약·신선도가 나온다.
3. R에서 보낸 정지 요청이 CELL-A에 접수·기록되고, 해제는 CELL-A 화면에서만 된다.
4. CELL-A 셀 화면에 카메라 네 대(top·side·arm_a wrist·arm_b wrist)가 원본으로 나온다.
5. R이 멈춘 동안에도 CELL-A가 팔을 정지·접기·관측한다.
6. `r-verify`를 멈춘 뒤에도 1–5가 유지된다.
