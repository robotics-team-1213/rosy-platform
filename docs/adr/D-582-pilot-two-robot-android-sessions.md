## D-582 Pilot Android는 두 로봇의 세션과 화면을 따로 유지한다

**Status:** Accepted (2026-10-10, 사용자 요청; Android SOURCE와 실기 화면 확인, 동시 실물 주행 수용은 별도)

### 배경

Pilot Android는 로봇 한 대의 `LobbySession`·`PilotProxy`·WebView만 열었다. 다른 로봇을 보려면 목록으로 돌아가 첫 세션을 닫아야 했다. 사용자는 한 태블릿에서 로봇 두 대의 카메라와 조종 화면을 동시에 쓰려 한다. 같은 `127.0.0.1`의 서로 다른 프록시 포트에 같은 이름의 쿠키를 두면 Android 쿠키 저장소가 첫 프록시의 값을 덮어써, 첫 카메라 요청이 403이 되는 실기 반례를 확인했다.

### 결정

1. Android 셸은 인증한 로봇 두 대까지 독립된 `LobbySession`·`PilotProxy`·WebView를 연다. 두 번째 대상은 로봇 목록에서 사용자가 고른다. 인증된 `robot_id`가 같은 두 화면은 열지 않는다. 각 화면에 로봇 이름과 ID를 표시한다.
2. 각 프록시는 별도 loopback 포트·무작위 capability·서로 다른 `rosy-shell-<난수>` 쿠키 이름을 쓴다. `ProxyGuard`는 자기 쿠키만 인정한다. 브라우저 쿠키가 포트와 무관하게 두 프록시에 함께 실려도 서로의 capability로 입장할 수 없다. 로봇 토큰은 기존대로 각 origin의 `sessionStorage`에만 놓고, 요청은 해당 로봇의 CORE API로만 중계한다. CORS는 열지 않는다(D-343).
3. 두 화면의 `주행 시작`과 hold-to-drive는 각각 기존 Pilot 계약을 따른다. 화면을 열거나 두 번째 로봇을 붙이는 동작 자체는 움직임을 시작하지 않는다. 앱 배경 전환·화면 끄기·목록 복귀 시 두 프록시를 닫고 각 로봇에 0을 요청한다. 응답이 없는 로봇은 CORE watchdog이 최종 정지를 맡는다.
4. 두 카메라의 실시간 보기와 각 조종 화면의 장치·네트워크 여유는 태블릿과 로봇 두 대에서 따로 확인한다. 두 로봇의 **동시 실물 움직임**은 UI·모의 API 검증만으로 수용하지 않는다.

### 검증

- SOURCE: 서로 다른 두 mock CORE에 카메라·teleop 요청이 각자 도착하고, 두 쿠키가 함께 실려도 각 프록시의 경계를 지키며, 종료 시 두 CORE에 0이 가는지 시험한다.
- DEVICE: 실제 태블릿의 두 연결·두 카메라를 한 화면에서 촬영하고 각 로봇 ID를 확인한다. 화면 종료 뒤 두 로봇의 명령 만료·정지 상태는 별도 readback으로 확인한다.
- FIELD: 안전한 현장 절차로 두 로봇 hold 입력·해제·통신 단절과 물리 정지를 측정한 뒤 동시 주행을 수용한다.

**관련:** D-2, D-193, D-323, D-343, D-368, D-411, D-460, SAF-002.
