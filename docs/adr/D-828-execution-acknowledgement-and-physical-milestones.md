## D-828 작업 접수·진행·물리 완료·인계 근거를 구분한다

**Status:** Proposed (2026-10-21). 논리적 결과 의미와 검증 책임의 제안이다. 아래 개념은 새 wire enum·HTTP endpoint·장치 capability의 선언이 아니며 구현 전 기존 계약과의 매핑을 검토한다.

### Context

장치 요청 접수, 공정 단계의 준비, 물리 동작 완료와 목표 확인은 같은 사건이 아니다. 상위 앱이 어느 사건을 기다리는지 불명확하면 화물이 여전히 차량에 있는데 차량을 출발시키거나, 오래된 결과를 새 작업 완료로 반영할 수 있다.

현재 `rosy.execution.site.workflow`와 Fleet `missions/mission_progress.py`는 실행 진행과 근거를 보수적으로 투영한다. PlanBundle·공정 컴파일 결과는 실행 권한이 아니며, 장치 receipt만으로 모든 업무의 물리 완료가 증명되는 것도 아니다. 기존 어댑터에 논리 단계의 유예·병합이 있을 수 있으므로 성공 반환값의 의미를 호출자까지 추적해야 한다.

### Decision

1. 각 공개 작업에 접수·실행 진행·동작 결과·목표 검증의 의미를 문서화한다. 중간 milestone이 필요하면 공정이 조건을 선언하고 승인된 생산자가 근거를 발행하며 플랫폼이 시도·버전·유효성을 검증한다. 앱의 요청 자체가 근거가 되지 않는다.
2. 새 인터페이스에서는 실행 전 단계 유예나 계획 병합을 물리 완료로 표현하지 않는다. 기존 소비자 호환을 유지하면서 명시적 하위 단계 또는 기존 진행·근거 계약으로 표현한다. 호환 어댑터의 동작을 조용히 바꾸지 않는다.
3. 실제로 서로 다른 조건인 물체 보유, 운송 공간 퇴피, 차량 출발 허용, 목표 안착과 업무 완료는 구분한다. 모든 작업에 이 사건을 일괄 추가하지 않고, 필요한 공정의 전이 조건으로 선언한다.
4. 작업·시도·장치 identity와 사용한 계획·설정·관측 revision에 근거를 결속한다. 기존 식별·receipt·goal-evidence·cursor 계약을 먼저 재사용하고, 중복 결과는 재완료시키지 않으며 과거 시도·오래된 관측은 새 시도의 완료 조건으로 쓰지 않는다.
5. 근거 생산 실패·연결 단절·재시작·순서 역전에서는 완료나 자원 해제를 추정하지 않는다. 불명 상태와 차단 이유를 조회할 수 있어야 한다. lease 만료·시간 초과만으로 물리적 빈 상태를 확정하지 않는다.
6. 단순 단계 분리와 기존 상태 조회로 충분하면 새 이벤트 버스나 실행 엔진을 만들지 않는다. 비동기 작업이 필요한 범위만 기존 작업 조회·진행·이벤트 재연결 계약으로 확장한다.
7. 차량 출발이나 장치 동작의 실제 허용은 기존 admission과 장치 owner가 집행한다. 상위 공정 milestone의 선언은 정지·권한 검사를 우회하지 않는다.

### 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| D-427·D-429 | 관측 생산자·원장·실행 소비자의 소유와 API 방향을 유지하고 결과 의미를 명확히 함 |
| D-430 | 최종 장치 권한·정지 의미를 유지. 물리 근거 없이 정상 전이를 개방하지 않음 |
| D-657 | 순수 진행 투영·goal-evidence와 Fleet의 transaction·생산자 인증 분리를 재사용 |
| D-773·D-797 | Proposed 장치 포트·실물 dispatch를 이번 ADR로 활성화하지 않음 |
| D-827 | 업무 성공 판정과 공통 실행 근거의 책임 분리를 구체화 |

### Alternatives

- 모든 단계에 성공/실패 하나만 반환: 논리 유예와 물리 완료가 섞이므로 신규 인계 계약의 기준으로 채택하지 않는다.
- 모든 장치 신호를 앱에 직접 노출: 앱별 해석과 중복·재연결 처리가 퍼지므로 채택하지 않는다.
- 처음부터 범용 실시간 workflow 엔진 도입: 기존 진행·근거 계약을 대체할 필요가 확인되지 않아 보류한다.

### Consequences

구현 전 현재 상태·receipt·관측과 요구 milestone의 매핑표를 만든다. 새 필드가 필요한 경우에만 SRS·API reference·스키마·양 끝 시험을 함께 변경한다. API 버전은 기존 선점 절차를 따른다. 기존 장치·기존 앱에 없는 근거가 새로 생겼다고 가정하지 않는다.

### 검증 기준

- 접수 또는 유예 응답만으로 물리 목표나 자원 해제가 완료되지 않는다.
- 중복·지연·과거 시도 결과, 오래된 관측, 재연결·재시작을 처리해도 완료 횟수와 원장이 보존된다.
- 동작 성공 뒤 목표 근거가 없으면 보류하고, 해당 근거와 연결된 시도만 다음 전이를 허용한다.
- 장치 오류·근거 불명 상태에서 기존 정지·복구 경계를 유지한다.

구현 단위와 관련 시험은 [실행계획](../plans/2026-10-21-domain-neutral-application-phases.md)에 둔다.
