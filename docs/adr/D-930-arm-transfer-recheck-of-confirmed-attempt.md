## D-930 확인된 ARM 시도의 재관측

**Status:** Accepted (2026-10-30, 사용자가 Harbor 최종 완료 공백의 해결로 재관측 계약 추가를 지시). 계약과 simulation 구현의 결정이다. 원격 회귀·배포·실물·현장 수용은 각각 증거로 판단한다.

### Context

D-927 전체 흐름 회귀가 2026-10-30에 ①~④를 통과하고 ⑤에서 멈췄다. Harbor는 첫 흐름의 마지막 완료에 반출 이동 시도에 묶인 새 관측(반출 화물이 반출대에 있고 관련 팔이 모두 퇴피)을 요구한다(Harbor ADR 0005 결정 6). 복귀 이동이 반출 화물을 건드렸을 수 있기 때문이다.

Fleet의 물리 근거는 시도마다 한 번 저장되는 불변 기록이다(D-856, D-915). 확인된 뒤에는 같은 시도에 대한 새 측정 사실을 받을 경로가 없어서, 앱은 이미 쓴 근거를 다시 쓸 수밖에 없었고 Harbor 장부는 그것을 거절했다. 복구 경로(D-899)는 실패한 시도에서 새 시도를 만드는 흐름이라 맞지 않는다.

### Decision

**1. 확인된 시도에 재관측을 요청할 수 있다.** 작업을 만든 주체나 허가된 named operator가 `GOAL_CONFIRMED` 작업에 `POST …/jobs/{mission_id}/rechecks`로 재관측을 요청한다. 같은 `recheck_key`의 반복은 같은 기록을 돌려준다. 한 작업에는 기다리는 재관측이 하나만 있다.

**2. 관측은 기존 관측자와 경로로 받는다.** 기다리는 재관측은 다른 시도가 관측을 기다리지 않을 때 기존 observation context에 `phase=RECHECK`로 나온다. 관측자는 같은 observations 경로로 표본 두 개를 낸다. 별도 자격·producer를 만들지 않는다.

**3. 검사는 POST_ACTION과 같다.** 원래 시도·정책 binding, 목표 자세, 정지·그리퍼·zone clearance를 그대로 검사한다. 표본 시각은 요청 뒤여야 하고 모든 참여 팔의 측정 관절이 있어야 한다. 실패는 기록을 바꾸지 않고 재관측을 기다리는 상태로 둔다.

**4. 재관측은 권한을 만들지 않는다.** Action 제출, claim 획득·해제, 작업 상태·물리 영수증·v1.330 근거 변경이 없다. 결과는 앱의 업무 완료 규칙을 위한 새 측정 사실이며 업무 완료도, 현재 가용성 판정도 아니다.

**5. 읽기는 원본 바이트로 한다.** `GET …/rechecks/{recheck_key}`가 정본 문서 바이트·SHA-256·검증 시각·설치 zone ID를 물리 영수증과 같은 읽기 범위로 준다. 계약은 API reference v1.334다.

### Alternatives

- Harbor 최종 완료가 마지막 이동의 퇴피 근거와 반출 이동의 배치 근거를 함께 받는다: 복귀 이동 뒤 반출 화물을 다시 확인하지 않아 채택하지 않는다.
- 같은 POST_ACTION 근거를 새 ID로 다시 낸다: 새 측정이 아니므로 채택하지 않는다.
- 복구(D-899) 경로를 재사용한다: 새 시도와 재실행 승인을 전제로 해 채택하지 않는다.

### Consequences and verification

- 시험: `operations/fleet/test/test_physical_transfer_recheck.py`가 요청 반복·충돌·범위, 관측 맥락, 낡은·관절 없는·옮겨진·다른 요청 표본의 거절, 작업·영수증·v1.330 근거·claim 불변을 고정한다.
- Harbor 전체 흐름 회귀(D-927 결정 7)의 ⑤가 이 계약으로 닫혀야 착지한다(D-927 결정 8).
- 실물 관측자·현장 수용은 D-858 S4·S5와 DEVICE·FIELD 관문이 따로 판정한다.
