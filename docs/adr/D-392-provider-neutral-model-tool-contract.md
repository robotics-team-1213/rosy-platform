## D-392 Model tool calls use a provider-neutral message contract and Fleet-owned allowlist

**Status:** Accepted (2026-10-01, logical tool-call and result boundary). No new public endpoint, autonomous Mission admission, device Action, ROS control, stop operation, provider enablement, or physical acceptance is approved.

### Context

The official `google-gemini/robotics-samples` repo contains more than the ER 2 notebook's spatial outputs and mock pick-and-place loop. Its Live API Spot embodiment exposes an allowlisted subset of backend OpenAPI operations as model tools, dispatches calls through a FastAPI/Boston Dynamics client path, and returns correlated tool results. This is a useful real application-to-robot integration pattern. The starter notebook's `move(x, y, high)` and `setGripperState(opened)` functions remain explicitly mocked and return a hard-coded `{"status":"success"}`; that result is not physical execution evidence. The Spot sample's model-routed `stop`/HTTP stop also does not establish an independent local stop fence or physical E-stop path. Its post-action image check is useful feedback, but model visual judgment does not replace Rosy's registered independent goal-evidence verifier. The Spot detector currently defaults to ER 1.6, so its endpoint must be updated and verified before reuse with current ER 2. Google's separate `gemini-robotics-sdk` README says Safari SDK is not an officially supported Google product and notes that most functionality requires the Trusted Tester Program. See the pinned source review in [Gemini Robotics Samples research](../plans/2026-10-01-gemini-robotics-samples-research.md).

ROSY already has the necessary authority boundaries: D-331 parses ER 2 output into a proposal; D-333 separates Mission admission, device Action acceptance, stop, and independent goal evidence; D-334 limits model-visible tools and progress; D-357 defines a bounded Fleet-executed feedback loop; D-358 fences provider effects and ambiguous delivery; D-369 assigns command and stop authority; and D-376 keeps trajectory planning/execution on the robot side. The source now has Gemini-specific function declarations, `ER2ToolResult`, and a Fleet allowlist dispatcher. It does not yet state one model-neutral internal message contract for translating another provider's tool-call envelope into the same Fleet effect and result semantics.

### Decision

1. **Normalize provider-native calls at the Fleet adapter boundary.** Each model adapter converts a provider response to an internal `ModelToolCall` containing an opaque `provider_call_id`, allowlisted `tool_name`, bounded JSON `arguments`, and the trusted `turn_id` supplied by Fleet. Provider/model identity, principal, workcell, Mission, Action/attempt, dispatch generation, event watermark, deadline, and egress policy come from the durable Fleet turn scope, not model arguments. A provider call ID is scoped correlation metadata; it is never a Mission ID, Action ID, attempt ID, ROS goal UUID, permission, or idempotency key by itself.
2. **Treat a model tool call as a request message, not a device Action.** A validated call may read a scoped Fleet snapshot or create a typed, non-executable proposal candidate. Fleet alone resolves the call through a closed tool catalog and policy dispatcher. The result is a `ModelToolResult` correlated to that call, with a bounded outcome, reason code, and result payload. A result such as `accepted` means only that the Fleet-owned tool effect was durably accepted (for example, a candidate was recorded); it never means that a Mission was admitted, an Action was accepted by ROS, an object was grasped or placed, or a robot stopped.
3. **Keep the current capability allowlist and effect classes.** ER 2's existing `propose_pick_place`, `get_mission_status`, and `propose_replan` semantics remain as decided by D-331, D-334, D-357, and D-358. Read tools return only principal/workcell-scoped Fleet facts. Proposal tools record typed candidates under the current turn/generation/event fence. Future providers may use provider-specific function/tool schemas generated from the same internal catalog, but the catalog does not discover or expose arbitrary APIs. Unknown names, unsupported effect classes, invalid or oversized arguments, wrong-scope identifiers, duplicate call IDs with changed content, and calls beyond the turn budget fail closed.
4. **Do not expose actuation or safety operations as model tools.** `move`, joint or trajectory commands, raw gripper actuation, device Action submission, Mission admission, cancel, stop/E-stop, rearm, and ROS/driver APIs are not callable by ER 2 or another reasoning model. An admitted Mission may later cause Fleet to issue a separately authorized semantic Device Action through the existing Fleet/device contract. Only the device-local command owner sends ROS goals; local stop authority and the independent physical safety path remain outside model control.
5. **Use durable call identity for effect idempotency and explicit uncertainty.** Any tool with a durable write records the `(turn_id, provider_call_id)` correlation and content digest before returning a result. Repeating the same identity and content returns the stored result; reusing it with different content is rejected. Provider delivery remains subject to D-358: an exception after provider transport invocation is `UNKNOWN`, not an automatic retry. A tool effect with an ambiguous durable outcome returns or retains `UNKNOWN`/HOLD; it must not fabricate success or trigger physical-action replay.
6. **Separate canonical semantics from provider wire formats.** Gemini Interactions `function_call` / `function_result`, Gemini Live `tool_call` / `tool_response`, and other providers' tool envelopes are translated at their own adapters. The canonical call/result contract is internal to Fleet; this ADR does not select MCP, add a public REST/ROS protocol, add a provider dependency, enable streaming, or require multiple live providers. A VLA action chunk or low-level policy output is outside this tool-call contract and requires a separate controller/action-owner decision.
7. **Keep enablement and evidence gates unchanged.** `POLICY_DISPATCH_ENABLED` remains `False` under D-357/D-358; this ADR and its plan do not change the valve. Provider/API approval, data-egress approval, secret management, Linux ROS-SIM, artifact, device, independent E-stop, and field acceptance remain independent gates. Google sample success text, provider interaction status, and a tool result cannot satisfy any of them.

### Sample alignment

The architecture adopts two useful sample patterns: (a) model requests a named function and application returns a correlated result, and (b) a robot-specific backend translates an explicit allowlist into its native operation surface. Rosy deliberately stops execution authority at Fleet's approved read/proposal effects for this ADR. The sample's OpenAPI-derived operation list is not a grant source: Rosy's server-owned catalog must be derived from supported capability, principal/workcell scope, Mission policy, and device safety profile, never from arbitrary backend API discovery. The sample fits ER 2's spatial reasoning, task decomposition, tool orchestration, and robot-adapter concept while preserving the ROSY separation among provider turn, Mission, device Action, ROS goal, goal evidence, and stop. It also allows future model adapters without making Gemini's function schema the ROSY domain contract.

### Alternatives considered

- **Expose the sample's `move` and gripper functions directly:** rejected because the sample implementations are mocks and the model coordinates are not validated robot poses, collision-free plans, accepted ROS goals, grasp evidence, or stop authority.
- **Let each model provider define its own Fleet effect semantics:** rejected because different provider IDs, argument conventions, and result formats would leak into Mission/Action semantics and make authorization, idempotency, and audit inconsistent.
- **Adopt MCP as the required external model-tool protocol:** not selected. The current ER 2 Interactions and Live APIs use their own function/tool-call envelopes, and ROSY needs a small internal semantic contract rather than another network service or dependency.
- **Treat every model output as an Action message:** rejected because a provider tool-call message is a request to a Fleet-owned effect, while a Device Action is an admitted and identity-fenced execution lifecycle with local ROS ownership and separate terminal evidence.

### Transition and validation

1. Add strict internal `ModelToolCall` and `ModelToolResult` types at the Fleet adapter/dispatcher boundary; do not alter public API routes or ROS interfaces in this step.
2. Adapt the current Gemini standard Interactions path to the canonical call/result types without changing D-331/D-357 tool names, `store=false`, bounded tool budgets, D-358 outbox semantics, or disabled policy dispatch.
3. Add provider-independent contract tests for allowlisting, scope derived from trusted turn state, argument size/schema errors, call/result correlation, same-content replay, conflicting call-ID reuse, late generation/stop rejection, explicit unknown outcomes, and refusal of device/stop tool names.
4. Add adapter conformance tests that map provider-native function calls/results to the same canonical semantics. Keep standard Interactions and Live API feature profiles separate: the standard endpoint supports structured output, code execution, and function calling, while the streaming endpoint uses streaming/function calling and must not be assumed to support the same feature set. Use fake provider fixtures for non-Gemini adapters until a real provider is selected; do not add an unused SDK dependency.
5. Keep the Gemini Robotics official sample review as the research record. Run Fleet provider/tool/outbox suites, shared contract tests if any shared schema changes, API documentation tests if public surfaces change, `python tools/harness/rosy_harness.py generate`, `lint`, and `git diff --check`.
6. Do not claim ROS-SIM, device, physical-stop, or field acceptance from provider adapter tests. Those remain separate evidence gates.

**Consequences:** Gemini and future model adapters can share Fleet authorization, effect, result, and audit semantics while retaining provider-native serialization. Tool-call IDs no longer risk being mistaken for Action identity. The current Gemini capabilities and all controller/stop boundaries remain unchanged.
