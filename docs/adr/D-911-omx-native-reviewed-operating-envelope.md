# D-911 OMX native 셀의 검증된 작업 범위와 현재 실행 조건을 구분한다

**Status:** Accepted (2026-10-28, 사용자 설계·구현 지시). 소프트웨어 구조의 결정이며 장치 운용·배포·현장 수용은 별도다.

## Context

기구학적으로 목표에 도달해도 물체를 들거나 유지하지 못할 수 있다. 같은 모델에서도 장치·설치·보정·Z·자세·하중·속도가 다르면 같은 작업의 성공을 보장하지 못한다. adapter의 `TransferPreflight`는 시뮬레이션 계산이며 실물 파지 허용 근거로 사용할 수 없다. 현재 native 실물 셀은 `cell_pipeline` → 기존 FIFO → `chunk_runner` → 기존 `NativeJointMotion` 경로를 사용한다.

## Decision

1. 최대 도달범위는 기존 기구학 제약, 계획상 작업 가능성은 전체 경로 계획, 검증된 운용범위는 장치·조건·전체 작업에 묶인 실물 근거로 구분한다. 안전가동범위라는 표현은 운용 범위를 뜻하며 협업 안전 인증이 아니다.
2. 첫 적용은 native 셀의 **정확히 일치하는 작업 경로**다. 전체 library 내용, 실제 세션의 장치 설정/보정/구동 readback과 실행 코드, 설치·물체 질량/치수·환경 revision, 카메라/좌표 보정/계획 조건을 SHA-256으로 묶는다. 성공한 점 사이의 공간이나 다른 Z로 허용을 확대하지 않는다.
3. 자동 `run`/`transfer`는 유효한 현재 상태, 시작 home 오차 기준, 동일 scope의 감독 시험 기록과 명시적인 사람 검토를 요구한다. 반복 수·성공률·시작 오차 기준은 검토자가 정하며 기본 수치를 만들어 넣지 않는다. 성공률은 관측 비율이고 요구 신뢰도를 입증하는 통계적 보증이 아니다. 인양·유지·실제 물체 상태의 수용은 검토가 참조하는 별도 물리 관측 근거로 판단한다.
4. 시험 수집은 개별 stage의 `--commissioning --person-at-switch`로 구분한다. `run` 자동 순환에는 사용할 수 없다. 저장된 JSON은 현장 사람의 존재를 주장할 수 없다. 시뮬레이션 자료는 hardware 근거로 사용할 수 없다. 기존 low-level 수동 도구와 guard의 권한·보호 정책은 유지한다.
5. 자동 명령은 native runner가 처리하는 시점에 session과 library SHA를 확인한다. 다른 library의 로드나 unchecked 수동 개입은 기존 자동 명령 사슬을 무효화한다. 추가 검사는 새 드라이버나 외부 제어 API·실행 permit을 만들지 않는다. Fleet/CORE/OMX의 기존 권한 경계는 유지한다.
6. 자동 작업 전에 실제 기록 대상에 독점적인 pending intent를 내구성 있게 남긴다. 결과를 기존 `attempts.jsonl`에 기록한 뒤 자신이 만든 intent만 해제한다. 비정상 종료로 intent가 남거나 같은 작업의 자동 실행 실패가 관측되면 기존 검증만으로 재실행하지 않는다. 동작 후 관측/세션 상실은 실행 실패로 기록하고 동작 전 보류와 구분한다.
7. 검증 근거의 ledger는 현재 셀의 `work_dir/attempts.jsonl`과 일치해야 한다. 감독 시험의 실패·중단도 분모에 남기고, 중복 identity·부분 JSON·달라진 근거·관측 누락은 허용하지 않는다. 성공 자동 실행은 시험 근거를 스스로 승격하지 않는다.
8. 주소·시리얼·완성된 장치 설정과 실제 검증 자료는 공개 예제에 넣지 않는다. 기본 예제는 선언 조건이 비어 있고 reviews도 비어 있어 자동 작업을 허용하지 않는다. 설치 이동·물체 교체처럼 자동 검출할 수 없는 변화는 운영자가 해당 revision을 갱신해야 한다.

## Consequences

- 기존 셀 설정은 새 명시 조건과 검토 근거가 없으면 자동 파지를 보류한다. 새 코드를 장치에 배포하거나 runtime을 활성화하는 것은 이 결정에 포함되지 않는다.
- 카메라 추정의 작은 변화로도 경로가 달라지면 미검증이 된다. 좌표 허용 영역·높이별 연속 공간·보간은 후속 실측 설계와 검증이 필요하다.
- native 실행 문맥은 제어 루프 시작 전에 읽는다. 세션 중 구동 설정의 외부 변경은 지원하지 않으며 버스 단일 소유권을 유지해야 한다. 이 기능이 동적 힘/토크의 실측을 대신하지 않는다.
- 검사 결과·pending intent·통계는 기존 장치 보호와 복구 절차의 대체물이 아니다. pending 파일은 원인과 장치/하중 상태를 확인하고 해당 시도를 기록으로 보존한 뒤에만 사람이 정리한다.
- FIFO/카메라 통신과 stage receipt는 `cell_pipeline_io.py`로 분리하고 기존 `cell_pipeline.FifoCell`/`write_receipt` 이름은 유지한다.

## Validation

실물 검증은 미실시다. 소프트웨어 시험은 장치/보정/높이/속도/하중 불일치, 오래된 상태, 근거 손상, 동작 파일 교체, 중간 수동 개입, 인양 후 중단, pending intent와 분모 보존을 검증한다. 최종 커밋별 원격 시험 증거는 해당 작업 기록에 남긴다.
