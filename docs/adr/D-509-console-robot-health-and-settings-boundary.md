## D-509 관제는 Pinky의 충전·건강 근거와 다음 조치를 보여 주고, 장치 설정은 소유 화면에서 실행한다

**Status:** Proposed (2026-10-07, 2026-10-08 계약 점검; 구현·배포·장치 수용 별도)

잇는 결정: D-124(로봇 네트워크 카드) · D-368(운전자 전면 영상) · D-406(관제 카메라 운용·설치) · D-415(관제 진단) · D-499(사이트 경로·로봇 링크, Proposed) · D-502(배터리 E-Stop·근거) · D-508(영상·제어 경로, Proposed). CORE API Reference §5.2·§6.1을 따른다.

### Context

- Rosy Console은 사이트 로스터와 여러 로봇을 모은다. 현재 Fleet 로봇 카드는 `StateSnapshot`의 배터리 잔량과 안전 상태를 보여 주지만, 충전 확인의 신선도와 전원 health는 보여 주지 않는다. `battery_status.charging`만으로는 마지막 도크 래치가 현재 충전을 증명하는지 알 수 없다.
- CORE에는 이미 Viewer `GET /api/v1/power/health`가 있다. 배터리 표본과 충전 확인이 모두 5초 이내이고 충전 래치가 참일 때만 `charging_state: confirmed`이며, 결측·낡음·정책 권고도 구분한다. 다만 이 응답은 충전 확인의 센서 출처·근거 수(전류+전압 또는 전압만)를 제공하지 않는다. 현재 `DockingManager` 생성은 기본 `DockingConfig()`의 instrumented 경로이고, D-350의 Phase 1 전압 단독 경로가 실장·수용됐다는 근거가 아니다. `GET /api/v1/safety/state`는 배터리 단계와 E-Stop 해제 판단 근거를 제공한다(D-502). 전류·용량 계측이 없어 남은 시간은 알 수 없다.
- 관제의 천장 카메라, Pinky 전면 카메라, 로봇 Wi-Fi는 소유자와 자격이 다르다. 한 화면의 설정 버튼으로 모두 다루면 관제 토큰에 장치 관리자 권한을 실어야 하거나, 연결이 끊기는 변경을 원격에서 실행하게 된다.

### Decision

1. **관제는 여러 로봇의 판단 입구다.** 기존 Rosy Console 로스터에 로봇별 배터리 단계, 충전 확인, 안전 정지, 진단 요약과 마지막 관측 시각을 함께 보여 준다. 정상일 때는 짧게, 이상이 있을 때는 근거와 다음 조치를 펼친다. 별도 health 앱이나 로그인은 만들지 않는다.
2. **로봇이 판정하고 Fleet은 읽기만 한다.** 기존 상태 gather의 `battery`, `battery_status`, `safety`, `diagnostics_summary`, `evidence`를 사용한다. Fleet 서버는 등록된 로봇의 Operator 토큰으로 Viewer `GET /api/v1/power/health`를 제한된 주기로 조회한다. Fleet 로봇 행의 선택 필드 `power_health`는 기존 공유 `PowerHealthResponse` 또는 null이고, `power_health_age_s`는 Fleet이 관측한 경과 초 또는 null이다. 실패·구버전·오프라인·오래된 근거는 null로 둔다. 브라우저가 로봇 토큰으로 직접 접속하지 않고, CORE의 충전·배터리 정책을 Fleet에서 다시 계산하지 않는다. 상세 안전 해제 판단은 로봇의 기존 `GET /api/v1/safety/state`가 정본이다(D-18).
3. **결측을 정상으로 바꾸지 않는다.** 전원 health가 없거나 오래됐거나 로봇이 오프라인이면 `확인 불가`와 원인·마지막 관측 시각을 표시한다. `charging_state: unconfirmed`는 `충전 미확인`이지 `충전 안 함`이 아니다. 배터리 잔량과 전압도 stale이면 현재 값처럼 표시하지 않는다. `confirmed`와 배터리 표본·충전 확인 각각의 신선한 근거가 함께 있을 때만 `충전 확인`이다. Fleet 캐시 나이와 브라우저 수신 뒤 경과도 두 근거의 나이에 더한다. 도킹 상태, 충전 확인, 배터리 회복, E-Stop 해제는 서로 다른 사실로 표시한다. 남은 가동 시간은 추정하지 않는다.
4. **다음 조치가 실제 권한 경로로 이어진다.** 배터리 telemetry 결측·낡음은 센서/CORE 확인, 신선한 경고는 충전·절전 확인, 충전 확인 실패는 도크·전압 근거 확인을 안내한다. 배터리 E-Stop은 충전 또는 전압 회복으로 자동 해제하지 않는다(D-502). 관리자는 로봇 화면의 안전 상태를 확인한 뒤 기존 관리자 해제 경로를 사용한다. Fleet은 배터리 전용 해제 버튼이나 우회 명령을 만들지 않는다. 로봇 화면에 닿지 않으면 원격 처리 성공을 암시하지 않는다.
5. **health 범위를 분리한다.** 로봇 진단 요약은 CORE 관측, 사이트 경로는 프록시·Fleet·Vision 조회 결과(D-499), 관제 로그는 현재 클라이언트 이벤트(D-415)로 출처를 붙인다. 사이트 `/healthz`가 200이어도 Pinky 배터리·카메라·Wi-Fi가 정상이라는 뜻은 아니다. 센서 결측이나 단일 서비스 응답만으로 현장 운용 가능 판정을 만들지 않는다.
6. **영상 설정은 영상 소유자별로 둔다.** 천장 카메라의 선택·프리뷰와 설치 보정은 기존 관제 카메라 구역(D-406), Pinky 전면 카메라의 상태·인증된 미리보기/운전자 스트림은 로봇 화면과 CORE 계약(D-368)을 따른다. 관제의 기존 Vision 표시는 구성된 소스와 도착한 프레임의 신선도를 보여 준다. 이는 송신 기능이 켜져 있는지 또는 송신 품질 설정을 읽었다는 증거가 아니다. 송신 enable·fps·bitrate를 바꾸는 공통 스위치는 두지 않는다. 그런 설정은 D-508의 경로·대역폭 근거와 별도 API/장치 검증을 거쳐 결정한다.
7. **네트워크는 관제에서 진단하고 로봇에서 적용한다.** 관제에는 D-499의 링크 상태와 다음 확인 대상을 표시한다. SSID·AP 모드·프로파일 변경은 로봇 관리자 화면 → CORE → Host Agent의 D-124 경로가 맡는다. Fleet 서버에 PSK를 저장·전달하거나 `nmcli`·로봇 네트워크 POST를 추가하지 않는다. 네트워크 변경은 관리자가 현장 복구 경로를 확인하고 기존 확인 절차로 실행한다.

### Alternatives

- **모든 설정을 Fleet Console에 모으기:** 한 화면에서 끝나지만 장치별 관리자 자격, 비밀, 연결 단절 복구를 Fleet이 떠안는다. 현 계약에서는 채택하지 않는다.
- **상태도 모두 로봇 화면에서만 보기:** 여러 Pinky의 이상을 비교하고 먼저 조치할 대상을 고르기 어렵다. 관제 요약은 필요하다.

### Consequences and validation

- 이 ADR은 화면·권한·증거의 설계 결정이다. 로컬 구현이 있더라도 배포·장치 수용이 완료됐다는 뜻이 아니다. D-350 Phase 1, D-499와 D-508의 Proposed 범위도 이 문서로 구현 완료가 되지 않는다.
- 구현 검증은 충전 confirmed/unconfirmed, 전압·충전 증거 각각의 stale/결측, 오프라인·구버전 CORE, 배터리 회복 중 E-Stop 유지, viewer/operator/admin 권한, Fleet 토큰의 로봇 설정 경로 미접근을 포함한다. 두 대 이상 로스터에서 한 대의 health 조회 실패가 다른 로봇 상태를 숨기지 않아야 한다.
- SOURCE/LOCAL 검사는 표시와 API 계약만 증명한다. DEVICE에서는 충전기 연결·해제, 센서 표본 중단, 안전 해제 readback, Wi-Fi 변경 후 재접속을 확인한다. FIELD에서는 관제자가 실제 Pinky를 식별하고 해당 조치를 끝낼 수 있는지 확인한다.
