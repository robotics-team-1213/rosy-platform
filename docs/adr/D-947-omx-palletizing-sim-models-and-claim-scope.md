## D-947 OMX 적층 셀 시뮬레이션: 무엇을 어느 시뮬레이터로 어느 범위까지 모델링하고 무엇을 주장하는가

**Status:** Accepted (2026-11-03, 사용자 확인 「좋아」). 학습 정책이 아니라 정답 IK로 먼저 확인하고, 학습은 5의 순서(같은 카메라 추정 오차 → 새 그리퍼 시연으로 놓기 보정 재학습)에서만 좁게 쓴다는 단계와 아래 역할 분담을 받아들였다. 처음 제안은 2026-11-01(사용자 요청 「ADR에 미리 결정해두는 게 좋겠어 — 어떤 모델로 어떻게 어느 범위까지, MuJoCo 혹은 Isaac으로 나눠도 좋고 Gazebo가 필요하면 해도 좋고」). 구현·실물 수용은 별도다.

**관련:** D-866(Isaac 주, Gazebo 회귀) · D-877(세 백엔드 공통 층) · D-927(Harbor 시연 MuJoCo OMX·Gazebo Pinky) · D-911(실물 작업 범위) · D-434 · 계획 `Rosy/docs/superpowers/plans/2026-10-31-omx-palletizing-sim-rebuild.md`(작업 공간, Git 밖)

### Context

- 셀이 바뀌었다(2026-10-31): 조 v2.1(`learning/envs/isaac/assets/omx_f_palletizing_description/`, 좌우로 오므림), 남색 배 모양 판(5×5 돌기, 피치 35.1 mm, 정렬용), 컨테이너 90×30×30 mm(1칸 7.2 g, 2칸 11.79 g, 3칸 16 g), 카메라 다섯 대(위쪽 RealSense D435, 옆 Jieli, 손목 Innomaker 둘, 천장 Rosy Cam).
- Isaac 컨테이너 적층(`omx-map-container-stack`)은 조 v2.1·16 g·돌기 판에서 정답 위치 IK로 seed 42·43 9/9를 놓았다(2026-11-01). 학습 정책(BC v0·rl3)은 예전 손가락과 15 mm 놓기 높이를 배워 재사용할 수 없다.
- 지금 Isaac 그림(`stacking_scene.capture`)은 800×600 관찰용 임의 시점이라 실물 카메라와 자리·화각·해상도가 다르다. 그 그림으로 만든 추정 오차나 시각 학습은 실물로 옮길 근거가 없다.
- 모델 PC의 실제 Isaac SDK는 6.2.0.0이다(실행 영수증). D-434 §3의 5.1 표기와 다르다 — 버전 정본은 D-434 쪽에서 따로 고친다.
- 세 시뮬레이터가 이미 있다: Isaac(접촉·RTX 렌더링), MuJoCo(D-877 공통 층, CPU·headless, D-927 매일 밤 회귀), Gazebo(`gz_ros2_control`, ROS 실행 계약 회귀).

### Decision

1. **역할은 질문으로 나눈다.**

   | 질문 | 시뮬레이터 | 이유 |
   |---|---|---|
   | 놓기·끼움·옆 상자 밀림·돌기 정렬처럼 접촉이 결과를 정하는가 | **Isaac** | PhysX 접촉, 조 메시, 이미 9/9 경로가 있다 |
   | 실물 카메라 영상으로 위치를 추정·학습하는가 | **Isaac** | RTX 렌더링, 실물과 같은 카메라 다섯 대 |
   | 순서·도달·충돌·임시 칸 배분처럼 기하가 결과를 정하는가(많은 경우를 빨리) | **MuJoCo** | GPU 없이 병렬, 몇 초에 한 경우 |
   | ROS 실행 계약(궤적 Action·owner·관측)이 지켜지는가 | **MuJoCo**(OMX, D-927) · **Gazebo**(Pinky, `gz_ros2_control` 기준선) | 이미 매일 밤 회귀 |

   Gazebo에는 적층 접촉·카메라 모델을 새로 만들지 않는다. 같은 일을 세 번 만들지 않는다.

   **순서 (사용자 결정 2026-11-01 「MuJoCo로 먼저 하고 그다음 Isaac」):** 새 시험 조건(어긋난 놓기, 흔들기 범위, 임시 칸 배분)은 먼저 MuJoCo 적층 장면에서 넓게 훑어 실패 경계 후보를 찾고, 그 경계 주변만 Isaac에서 확인한다. MuJoCo 접촉 결과는 후보를 고르는 데만 쓰고, 보고하는 접촉 수치·성공률은 Isaac 확인값이다. 두 결과가 갈리면 갈린 사실과 조건을 기록한다.

2. **셀 모델은 원본 하나에서 만든다.** 팔은 `omx_f_palletizing.urdf`(조 v2.1), 작업대·벨트·팔 베이스는 `261026_World.STL`, 배 판은 잰 값(피치·지름·높이·5×5)에서 생성, 컨테이너는 치수와 사용자 무게, 카메라는 아래 3의 표. 이 값들을 저장소 대장 하나(제안 `learning/envs/isaac/cell_model_inventory.yaml`)에 출처와 함께 두고 Isaac·MuJoCo가 같은 대장을 읽는다. 시뮬레이터마다 숫자를 따로 적지 않는다.

3. **카메라는 실물과 같게 둔다(Isaac).** 위쪽 D435 컬러, 옆 Jieli 640×480, 손목 Innomaker 둘 640×480(조에 고정), 천장 1280×720. 화각은 제조사 값에서 시작하고 자세는 실물 영상의 돌기 격자·컨테이너 모서리로 PnP를 풀어 정한다. 같은 배치에서 시뮬레이션 그림과 실물 그림의 기준점 픽셀 오차를 기록하고, 오차 한계를 넘는 카메라 그림은 추정 학습에 쓰지 않는다. 관찰용 그림(`mapped-top/side/overview`)은 사람이 보는 용도로만 남긴다.

4. **불확실한 값은 사진·영상에서 정한 범위로 흔든다.** 범위의 정본은 재구성 계획의 「흔들기 범위」 절이다. 임의 범위를 쓰지 않는다. 마찰·여는 속도는 실측 영상(기울인 판, 조 여닫기) 뒤에 좁힌다.

5. **주장 범위.**
   - 시뮬레이션 통과는 「이 모델·이 범위에서 정답 위치로 놓았다」까지다. 실물 수용(D-911)이나 학습 정책 성능을 뜻하지 않는다.
   - 접촉 수치(밀림 mm, 미끄럼)는 Isaac 결과만 인용하고, 마찰을 실측으로 맞추기 전에는 「추정 범위」로 쓴다.
   - MuJoCo 결과는 기하 판정(도달·충돌·순서)으로만 인용한다. 접촉·놓기 성공률로 인용하지 않는다.
   - 실물로 옮기는 순서: Isaac 정답 IK 통과 → 실물과 같은 카메라로 추정 오차 측정 → 새 그리퍼 시연으로 놓기 보정 재학습 → arm_b 단독 실물 시험(arm_a는 모터 무응답 해결 뒤).

6. **범위 밖(지금).** 천장 Rosy Cam 실시간 중계, 사람·조명 변화 무작위화, Gazebo 적층 장면, Isaac Lab 병렬 RL(D-427 HOLD 유지). 필요해지면 새 ADR로 연다.

### Consequences

- 적층 접촉·영상 결과는 모델 PC의 Isaac 한 경로에 몰린다. GPU 한 대를 줄 서서 쓰므로 많은 경우를 훑는 일은 MuJoCo로 먼저 거른다.
- 대장 파일 하나가 생기고 두 시뮬레이터가 그것을 읽도록 고쳐야 한다. 그 전까지 Isaac 고정값(`mapped_stack_fixture.py`)이 사실상의 정본이며, 대장 도입 때 값이 같은지 시험으로 대조한다.
- 카메라 일치 오차가 기준을 넘으면 추정 학습(재구성 5단계)을 시작하지 않는다. 위쪽 RealSense가 USB 2.0(424×240)인 동안 위쪽 카메라 일치는 낮은 해상도 기준으로만 판정한다.
- Gazebo는 OMX 적층에서 실행 계약 기준선으로만 남는다.
