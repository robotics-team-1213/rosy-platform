## D-908 업무 앱의 중립 이송 제안과 별도 운영자 승인

**Status:** Proposed (2026-10-28). 계약 방향의 제안이다. path·schema·API 버전·구현·배포·현장 수용은 정하지 않는다.

**관련:** D-763 · D-836 · D-841 · D-856 · D-865 · Harbor ADR 0013·0015, Harbor 설계 18·27

## Context

Harbor의 업무 흐름은 양하 → 이송(Pinky) → 장치(팔 A·B)다. 팔 단계는 API v1.307의 중립 ARM 제안·조회·승인을 쓴다. 이 계약에서는 Harbor 서비스 신원이 제안하고, 제안자와 다른 명명 운영자가 승인한다(v1.312는 관측·receipt를 더했다).

이송 단계에는 같은 구조가 없다. 현재 계약은 아래와 같다.

- `POST /api/fleet/trip-jobs`(v1.242, 후보 형식 v1.292)는 **명명 운영자가 만들고 그 자리에서 승인·시작**하는 호출이다. 등록부 승인 값은 `one_person`이다.
- 이 호출은 simulation 프로필에서만 열린다.
- v1.298은 앱이 자기 key로 만든 TRIP을 조회하고 대조하는 경로만 더했다.

이 때문에 Harbor는 다음 둘 중 하나를 해야 한다. 서비스 신원으로 trip을 POST하면 운영자 승인을 사칭하게 되어 Harbor 설계 18·27과 D-856 §4를 위반한다. 사람이 Fleet에서 trip을 따로 만들면 Harbor의 업무 request key와 결속되지 않는다. 그 결과 Harbor 실행기는 이송 단계를 진행할 수 없고, 공급암 S 퇴피 확인(Harbor `DepartureIntent`)이 실제 출발과 이어지지 않는다.

## Decision

### 1. 이송도 "앱 제안, 운영자 승인"으로 나눈다

업무 앱의 서비스 신원(proposer 역할)이 이송 제안을 만든다. 제안은 durable 기록으로 남고, 승인 전에는 로봇·lease·차로 자원을 잡지 않는다. 제안자와 다른 명명 운영자가 승인한다. 승인 결과는 기존 TRIP 작업과 같은 실행 원장 행이다.

v1.307 ARM과 같은 규칙을 따른다.

- 승인 요청은 제안 digest와 generation을 함께 보낸다. 제안 본문이 승인 사이에 바뀌면 승인을 거절한다.
- 제안자는 승인하지 못한다. 서비스 신원에는 승인 권한이 없다.
- 자동 승인은 이 ADR의 범위가 아니다. D-865 정책 승인이 열린 뒤 그 범위에서만 가능하다.

### 2. 본문은 중립 이송만 담는다

제안 본문은 v1.292 후보 형식의 `candidate_robot_ids`·`request_key`·`steps`와 같은 범위다. 화물 ID·공정 어휘·업무 전제(공급암 S 퇴피 같은 것)는 wire에 넣지 않는다(D-856 §3).

업무 전제는 앱이 제안 전에 판단한다. Fleet은 그 판단을 해석하거나 안전 허가로 쓰지 않는다. 출발 인터록·차로 통행권·충돌 방지는 지금처럼 Fleet·CORE가 독립적으로 집행한다.

### 3. 식별·대조는 v1.292·v1.298의 key 규칙을 그대로 쓴다

같은 principal의 같은 key와 같은 본문은 기존 제안이나 작업을 돌려준다. 같은 key에 다른 본문이면 충돌로 거절한다. 응답이 유실되면 앱은 새 key를 만들지 않고 원래 key로 조회한다.

승인된 작업의 조회는 v1.298 경로와 같은 snapshot을 쓴다. READY·완료는 이송 수행 사실일 뿐이다. 화물 도착이나 업무 완료는 Harbor가 관측과 대조해 판단한다.

### 4. 기존 경로는 그대로 둔다

운영자가 직접 만드는 `one_person` TRIP POST는 의미를 바꾸지 않고 유지한다(D-856 §5). 첫 구현은 simulation 프로필에서만 연다. 현장 프로필 개방은 Pinky 주행 현장 수용과 별도 결정으로 한다.

## 기존 ADR과의 관계

| ADR | 관계 |
|---|---|
| D-856 (Accepted) | §4의 "승인·시작 의미가 있는 trip POST를 cell proposal과 같게 취급하지 않는다"를 지키면서, 이송에도 제안과 승인을 나눈 별도 경로를 더한다. |
| D-763 | TRIP 작업 종류·단계·lease 의미를 바꾸지 않는다. 승인 뒤의 작업은 같은 원장 행이다. |
| D-836 | 후보 형식과 request key 제한을 재사용한다. 기존 후보 접수를 유지한다. |
| D-841 | 외부 앱은 HTTP 공개 계약만 쓴다. Harbor는 ROSY 코드를 import하지 않는다. |
| D-865 (Proposed) | 자동 승인은 D-865의 정책 범위가 정한다. 이 ADR은 사람 승인만 정한다. |
| D-427·D-429·D-430 | 구조·폴더·safety 경로를 바꾸지 않는다. |

## 열린 질문

1. path 형태: v1.307처럼 별도 자원(`.../trip-proposals`)으로 둘지, 기존 `trip-jobs`에 상태를 더할지. 기존 시험의 의미를 바꾸지 않는 쪽을 우선한다.
2. 승인 화면: Fleet work 화면이 ARM 승인처럼 이송 제안을 보여 주고 승인하는 UI가 필요하다. 이 UI는 같은 구현 단계에 포함한다.
3. 취소: 승인 전 제안의 철회와 승인 뒤 기존 cancel 경로의 구분.

## 검증 기준

- 서비스 신원이 승인하거나 자기 제안을 승인하면 거절된다.
- 승인 전에는 로봇·lease를 잡지 않는다.
- 같은 key와 본문을 다시 보내면 중복 생성 없이 기존 기록을 돌려준다. 다른 본문은 충돌로 거절된다.
- 응답 유실 뒤 원래 key로 조회가 성공한다.
- 기존 `one_person` TRIP 시험(`test_trip_candidates.py` 등)이 수정 없이 통과한다.
- Harbor 고정 양 끝 HTTP 시험에서 제안 → 운영자 승인 → 조회 대조가 통과한다.
