## D-993 Account 가입·권한 요청

**Status:** Accepted (2026-11-07, 사용자 요청; 구현·시험의 수용이며 배포·현장 수용은 별도)

**관련:** D-757 · D-777 · D-807 · D-962 · D-987

## Context

Account에는 계정이 없거나 앱 권한이 없는 사람이 갈 곳이 없다. 앱 접근이 거부되면 로그인 화면이 "관리자에게 요청하세요"라고만 말하고, 요청할 방법은 없다. 요청을 받아 처리하는 일은 특정 앱이 아니라 사람 신원과 권한을 가진 공통 서비스(D-962, D-987)의 일이다. Fleet이나 앱에 두면 앱마다 따로 만들게 된다.

## Decision

1. **Account 원장에 요청을 둔다.** `rosy_access_requests` 표(요청 번호, 종류, 이름, 희망 로그인 ID, 대상 자원, 남긴 말, 시각, `pending/approved/rejected`, 처리자, 처리 시각, 사유)를 같은 계정 DB에 둔다. 종류는 계정이 없는 사람(`new_account`)과 로그인한 계정이 자원 권한을 청하는 경우(`grant`) 둘이다. 로그인한 요청은 세션이 이름과 로그인 ID를 정하며 폼 값은 무시한다. 대상 자원은 `site|robot|project:<id>` 형식만 확인한다. 앱 역할은 Account에 없고 자원별 capability가 권한이므로, 요청은 자원만 적고 capability는 관리자가 승인 때 고른다.
2. **요청은 권한을 만들지 않는다.** 자동 승인, 자동 grant, 요청자가 고른 capability는 없다. 승인은 관리자 양식에서 `AccountLedger.create`(새 계정) 또는 `AccountLedger.mutate`(기존 계정의 grants)를 호출하며, 요청 마감과 `rosy_account_audit` 기록을 같은 트랜잭션에 넣는다(`within`). 어느 한쪽이 실패하면 계정도 요청 상태도 바뀌지 않는다. 별도 사용자 저장소를 만들지 않는다.
3. **비밀번호는 요청 때 받지 않는다.** 선택지는 요청자가 비밀번호를 정해 해시를 보관하는 방식과, 관리자가 승인 때 기존 "임시 비밀번호 + 첫 로그인에서 변경" 흐름으로 정하는 방식이었다. 후자를 택했다. 로그인 전 공개 입력에서 scrypt를 돌리면 비용 공격 면이 생기고, 승인 전 자격 증거(해시)를 DB에 두게 된다. 후자는 이미 있는 `create`와 `change_required` 경로를 그대로 쓰며 요청 표에 비밀이 전혀 없다. 비용은 관리자가 임시 비밀번호를 신청자에게 직접 알려야 한다는 점이다.
4. **공개 입력의 경계.** `POST /api/fleet/auth/access-requests`는 인증이 없으나 (a) `Origin`이 `Host`와 같아야 하고(기존 로그인과 같은 `same_origin`) (b) 본문 4 KiB, 이름 64자, ID 32자, 남긴 말 500자 제한이며 (c) 대기 요청은 서비스 전체 200건, 한 주소당 5건(주소는 SHA-256 요약만 저장)까지다. 넘으면 429 `REQUESTS_FULL`이다. (d) 같은 대기 요청의 반복과 이미 있는 로그인 ID도 새 ID와 똑같이 202 `{"status":"received"}`로 답하므로 계정 존재 여부를 알 수 없다. 이미 있는 ID는 관리자 목록에만 `login_taken`으로 보이고 승인은 막힌다.
5. **관리자 처리.** 기존 `accounts.manage` 쿠키 세션 규칙(`manager`)으로 목록·승인·거절을 한다. 거절은 사유가 필수이며 화면에서 `거절…`과 확인 대화상자를 거친다. 모든 결정은 승인 시 `create`/`update`에 더해 `access-approve`/`access-reject` 행을 `rosy_account_audit`에 남기고 HTTP 감사 기록도 남는다.
6. **화면.** 로그인 화면에 "계정이 없나요? 가입 요청"을, 접근 거부 안내에 "이 앱 사용 권한 요청"을 둔다(같은 양식, 새 HTML·자산 없음). 관리 화면에는 요청 표를 두고, 승인은 기존 계정 양식을 채워 그대로 저장하게 한다. 애니메이션은 쓰지 않는다(D-220).
7. **범위 밖.** 기계·장치·서비스 자격(D-807), 신청자에게 보내는 알림, 요청 보존 기간·정리, 이미 만든 요청의 수정이다. 요청자는 처리 결과를 화면에서 확인할 수 없고 관리자에게 듣는다.

## Consequences

- API: `POST /api/fleet/auth/access-requests`(공개, 202), 관리자용 `GET .../access-requests`, `POST .../{id}/approve`, `POST .../{id}/reject`. Additive이며 기존 응답은 바뀌지 않는다. API 문서 v1.374.
- 계정 DB에 표 하나가 늘며 요청 자체가 만들어지는 곳은 Account뿐이다. `migrate_authority`의 열 개 권한 표 목록은 바꾸지 않는다(요청은 권한 상태가 아니다).
- 주소 요약은 5건 제한용이며 로그인 실패 제한(`ADDRESS_FAILURES_PER_MINUTE`)과 달리 시간 창이 없다. 거절·승인으로 대기가 줄어야 같은 주소가 다시 보낼 수 있다. 관리자가 오랫동안 처리하지 않으면 정당한 신청도 막히므로 알림과 보존 정리는 후속 결정이다.
- 신청자는 다른 사람의 로그인 ID를 청할 수 있다. 승인은 관리자 눈을 거치며 임시 비밀번호는 신청자에게 직접 전하므로 ID를 도용해도 계정을 얻지 못한다.
