## D-358 ER 2 feedback turns use trusted scope, fenced candidates, and explicit ambiguity

**Status:** Accepted (2026-09-30, D-357 implementation contract refinement only). Does not enable provider calls, Mission policy dispatch, ROS/OMX capability, device operation, or physical acceptance.

### Context

D-357 establishes that ER 2 may consume bounded Fleet feedback and return candidates while Fleet owns Mission policy and device owners retain command and stop authority. Review of the implementation plan against the current Fleet composition found four places where implementation could still diverge: the existing proposal-resolution path creates a new Mission rather than amending an existing one; stop generation and proposal visibility need one atomic fence; outbox uniqueness does not make an external provider POST exactly-once; and a background worker does not inherit REST principal authorization automatically. The provider egress contract also needs to distinguish `store=false` from provider-side data handling.

### Decision

1. **Keep authority local to each effect.** ER 2 emits bounded tool requests and typed candidates only. Fleet derives principal/workcell/Mission/action/attempt/generation/event scope from the durable turn record, validates tools, owns the Mission journal, provider scheduling, proposal resolution, and admission. A provider tool result never changes Mission or Action state. The device-local Action owner is the only ROS/driver writer; the independent registered verifier owns `GOAL_CONFIRMED`; device stop authority and the independent physical safety chain own stop action/readback. No model tool invokes Action submit, cancel, stop/E-stop, rearm, or direct actuator control.
2. **A replan is a linked successor proposal.** Bind each `propose_replan` candidate to immutable source Mission, Action/attempt, observation, generation, and event watermark. Resolving it creates a separately identified successor Mission draft linked by `supersedes_mission_id`; it never mutates or reopens the source Mission or Action. The existing operator resolution and Mission admission gates remain mandatory. Fleet must not dispatch the successor merely because ER 2 proposed it.
3. **One logical outbox row is not exactly-once provider execution.** The unique key is Mission, triggering event, dispatch generation, and model-policy revision. Persist `SUBMITTING` before invoking the provider transport. A local preflight failure before transport invocation may return to `PENDING`; any exception after invocation begins becomes `UNKNOWN` and is never automatically resubmitted. This permits at most one client submission attempt per logical turn and does not claim exactly-once provider execution. With `store=false`, do not assume a lost response can be retrieved. A fresh attempt requires a new eligible event/generation and a current policy check; the ambiguous attempt remains `UNKNOWN`. Provider-attempt state cannot alter Mission, Action, goal, or stop state.
4. **Fence candidate visibility atomically with stop and generation.** Before a model result becomes visible or resolvable, one shared SQLite transaction checks the current stop generation, turn generation, source Mission/Action/attempt, and event watermark, then inserts the candidate. A stop or generation change before that commit makes the response stale. The current Fleet app composition already requires Mission, proposal, audit, and dispatch-control stores to share one SQLite database; the implementation uses that common transaction boundary or an equivalent fenced compare-and-invalidate operation before exposure.
5. **Make event eligibility and tool permissions explicit.** Active stop or generation mismatch suppresses the provider turn. Action `UNKNOWN`/`HOLD` or stale readback suppresses it. A reconciled terminal Action with pending/unknown/rejected/stale goal evidence or unresolved object effects may receive status-only feedback through `get_mission_status`; it cannot propose a replan. Only a fresh independently verified unsatisfied goal with reconciled Action/object effects, no stop latch, and a fresh authorized post-action observation available to ER 2 may enable `propose_replan`. Candidate storage rejects frames older than 30 seconds at commit. The dispatcher accepts only an injected observation source and fails closed as unavailable when none is configured; Fleet currently has no production post-action frame reader wired to this dependency. A confirmed goal receives status-only feedback and cannot replan. Status reads and model-generated events do not trigger another turn.
6. **Gate all provider egress explicitly.** `store=false` is not a guarantee of provider-side non-retention or restricted human review. Before transport invocation, Fleet must verify approval for the configured provider project/service tier and each data class actually sent, including structured Mission progress and the full Mission instruction, scoped by workcell and task class. Missing approval denies the call. Credentials use the approved runtime secret-injection path with environment separation and rotation/restriction; they are never accepted from model or Mission input. Replay steps/bytes, context/result bytes, calls per turn, deadlines, response bytes, image bytes, and cost have named numeric limits, and missing limits fail closed.
7. **Keep enablement and evidence gates closed.** `POLICY_DISPATCH_ENABLED` remains `False`. SOURCE/LOCAL tests must cover the exact state transitions, cross-scope tool input, denied provider egress with zero transport calls, successor-Mission resolution, and a stop arriving between provider response and candidate commit. Passing host tests does not establish ROS-SIM, device stop, grasp/placement, goal success, or FIELD acceptance.

### Consequences

The source implementation has an honest at-most-once logical-turn attempt guarantee, explicit recovery behavior for ambiguous POSTs, a durable-cursor event-to-outbox scheduler, and an atomic stop-generation fence before provider submission and feedback-candidate visibility. The outbox is capped at 10,000 rows by default; at capacity, the scanner records a dropped enqueue attempt and advances its cursor, so operator configuration must raise the cap before future turns can be enqueued. Candidate metadata carries source Mission/action/attempt/generation/event/observation identity; resolution rechecks the stop and source-event fence and creates a distinct linked successor Mission. The feedback dispatcher accepts only an injected trusted post-action observation source, and otherwise returns `REPLAN_OBSERVATION_UNAVAILABLE`; no production Vision reader currently provides this correlation. A model replan must follow the existing new-Mission approval path without rewriting an in-flight or completed Mission. The Mission remains authoritative when the provider or worker fails. The app does not configure a provider worker, so no ER 2 request or user-visible model feedback is currently produced.
