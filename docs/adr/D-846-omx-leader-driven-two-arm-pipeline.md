## D-846 OMX Leader를 코드 구동 기준으로 삼는 두팔 파이프라인

**Status:** Accepted for implementation (2026-10-22). 구현 완료·실물 수용·Fleet 업무 권한·제품 capability 활성화를 뜻하지 않는다.

## Context

2026-10-22 사용자 지시: 팔로워만이 아니라 리더도 코드로 구동해 두팔을 코드로 다루는 파이프라인을 만든다.

현장 사실(2026-10-22, Fleet PC): 리더는 사람이 손에 잡는 장치이고, 팔로워는 어깨가 테이블에 닿은
상태에서 `shoulder_lift` 3~5° 차이를 따라잡지 못했다. 그 세션은 정렬 기한 초과로 안전 종료했고
(팔 전 모터 토크 0, 캡 복구, 하드웨어 오류 없음), 원인은 팔로워 하중으로 판단된다(미확정).

D-770의 자동 시연 파이프라인은 "사람이 리더를 움직이는 방식만 준비하는 것이 아니라 에이전트가 실제
OMX를 조작해 데이터를 수집하는 자동화"를 포함하지만, G1까지는 local owner·독립 stop·카메라 소유
경로의 공백이 열려 있다. D-823은 Leader를 운용 중 사람이 개입하는 **입력 장치**로 규정한다.

문제는 제어권이다. 리더를 구동하면 그 장치가 사람의 손에서 움직인다. 리더를 읽기 전용으로 두면
팔로워는 리더의 **절대 자세**를 따라가야 하고, 어깨에 하중이 걸린 팔은 그 자세를 따라갈 수 없다.
어느 쪽이든 "코드화된 두팔"이 되지 않는 이유는 팔로워가 처음부터 움직여야 하기 때문이다.

## Decision

### 1. 리더는 코드 구동 기준 장치다

리더는 손에서 떼어 둔 상태에서만 구동한다. 구동 전 `--attest "hands-off:<누가>:<시각>"`이 있어야
하며, 없으면 파이프라인은 거절한다. 이 확인은 소프트웨어가 검증할 수 없으므로 운영자 증언으로
기록하고 영수증에 남긴다. 집게는 구동하지 않는다.

리더 구동은 `deploy/robot/omx/leader_actuator.py` 한 곳에서만 한다. 그 모듈은 팔로워 가드와 같은
봉투를 쓴다: 팔로워 정렬 속도(1°/s)보다 빠르게 움직이지 않고, 가속도 상한을 두고, 관절별 PWM·전류
캡을 토크 OFF 상태에서 쓰고 되읽는다, 하드웨어 오류와 캡 고착(하중)을 중단 조건으로 삼고, 어떤
출구에서도 토크를 끄고 발견한 캡·프로파일을 되돌린다.

### 2. 팔로워의 최종 writer는 팔로워 가드다

파이프라인은 팔로워 목표를 직접 쓰지 않는다. 팔로워는 `guarded_native.GuardedMotion`이 소유하고
리더의 읽기값을 목표로 삼는다. 한 버스에 두 writer가 생기지 않는다. 관측 유닛처럼 버스를 점유하는
프로세스가 있으면 파이프라인은 실행을 거부한다(리더obot 버스는 독점 잠그지 않으므로 `fuser` 확인이
필요하다).

### 3. 팔로워는 리더의 절대 자세가 아니라 상대 움직임을 따라간다

팔로워 가드의 오프셋을 시작 시점의 팔로워−리더 차이로 고정한다. 그래서 팔로워는 자기 자세를
유지한 채 리더의 움직임만 따라간다. 시작 오차가 0이므로 정렬 단계에서 팔로워가 크게 움직일 일이
없고, 어깨에 하중이 걸린 팔에서도 파이프라인이 시작될 수 있다.

### 4. 파이프라인은 단계별 영수증을 남긴다

`deploy/robot/omx/two_arm_pipeline.py`의 단계는 `preflight`(정지 상태·정체성·버스 소유) → `gap`
(읽기 전용 간격) → `park`(팔로워 현재 자세를 자세 파일의 park 자세로 기록) → `align`(팔로워를
리더 자세로, 막힌 관절은 하중으로 진단) → `drive`(리더를 지정 자세로 구동, 팔로워는 미러) →
`verify`(구동 후 간격)다. 각 단계는 단독 실행 가능하고 결과를 JSON 영수증으로 남긴다. 설정·팔로워
캡·게인·리더 중력 편향은 `two_arm_config.py`가 소유하고, 파이프라인은 이를 읽어 단계에만 쓴다.

`align`이 멈추면 "기한 초과"만 말하지 않는다. 어느 관절이 어느 PWM에서 멈췄는지와 사람이 해야 할
다음 행동(팔 지지, 또는 리더를 팔로워 가까이)을 함께 적는다.

### 5. 권한은 늘리지 않는다

이 결정은 Fleet 업무 권한·admission·장치 capability·제품 이미지를 바꾸지 않는다. 새 API·mode·
schema를 만들지 않고, Fleet·CORE·Pinky의 명령 권한 경계는 그대로다. OMX 워크셀 도구 위치도
`deploy/robot/omx/` 그대로다. 이는 D-770의 G0–G1 앞 preparations에 해당하며, D-770의 실물 수집
완료 기준을 대신하지 않는다.

## Consequences

팔로워가 리더와 다른 자세에서 시작해도 파이프라인이 그 차이를 "오차"가 아니라 "시작 오프셋"으로
다룬다. 사람이 손을 떼고 리더만 움직이는 구간은 코드로 재현 가능해진다.

대신 리더는 사람이 잡는 장치이므로 구동 구간에는 사람의 개입이 필요하다. 증언 없이는 구동하지
않고, 구동 중에는 손이 Leader에 닿으면 안 된다. 이 파이프라인은 독립 정지가 아니다. 팔 전원
스위치에 사람이 손을 둬야 한다.

## Validation / implementation gates

구현 시험은 호스트 pytest(가짜 버스)이며 실물 동작을 뜻하지 않는다. 실물 시험 순서:

1. `preflight`와 `gap`을 토크 OFF 상태에서 확인하고, 팔로워가 정지 상태가 아니면 진행하지 않는다.
2. `park`으로 현재 자세를 기록한다(읽기 전용).
3. `align`에서 막힌 관절이 하중으로 보고되는지 확인한다.
4. `drive`는 손이 리더에서 떨어진 상태에서, 어깨처럼 테이블에 눌린 관절을 제외한 관절만 움직이는
   자세로, 작은 각도(수 도)로 먼저 확인한다.
5. 각 단계의 영수증과 하드웨어 오류·캡 복구·토크 OFF 확인을 남긴다.
6. 팔로워가 리더의 상대 움직임을 따라가는지, 팔로워가 리더의 절대 자세로 가지 않는지 확인한다.

실제 수용(DEVICE/FIELD)은 이 ADR의 승인만으로 성립하지 않는다.
