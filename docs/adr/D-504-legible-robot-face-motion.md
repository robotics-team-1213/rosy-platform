## D-504 로봇 얼굴 애니메이션은 작은 LCD에서 표정의 형태를 먼저 구별하게 한다

**Status:** Accepted (2026-10-07, 사용자 요청: 기존 표정을 평가하고 더 풍부한 애니메이션으로 처리). SOURCE/LOCAL 구현 결정이며 DEVICE/FIELD 수용은 별도다.

잇는 결정: D-280 · D-385 · D-394 · D-433. D-385의 모드별 표정 어휘와 빠른 깜빡임 금지, D-433의 단일 LCD 소유자와 상황표 우선순위를 유지한다.

### Context

기존 GIF 여덟 종은 1000×750, 40 ms 프레임이다. 제품 `rosy-face`는 매 두 번째 프레임만 320×240으로 줄여 10 fps(대기 백라이트에서는 5 fps)로 재생한다. 첫 프레임의 32×24 전경 실루엣에서 `basic`·`fun` 차이는 0.3%, `basic`·`interest`와 `basic`·`happy`는 각각 약 2%였다. `hello` 첫 프레임은 비어 있었다. 이 상태는 지나가는 사람이 약 0.5초 안에 의도를 읽어야 하는 얼굴 문법(concept 16 §7.4)에 미치지 못한다. 호스트 렌더와 GIF 열람은 실제 LCD의 거리·각도·조도 증거가 아니다.

### Decision

1. 기존 `hello/basic/angry/bored/fun/happy/interest/sad` 어휘와 CORE의 모드 매핑은 유지한다. 새 표정 이름, 외부 API, ROS 서비스, LCD 소유자를 추가하지 않는다.
2. 각 자산은 320×240 검정 바탕에 장미색 눈·입을 그린 20프레임, 프레임당 100 ms 루프다. 처음부터 얼굴이 보이고, 작은 주기적 위치 변화로 살아 있음을 보인다. 눈 깜빡임, 빠른 표정 전환, 경보처럼 보이는 섬광은 넣지 않는다. 재생에 필요한 프레임은 건너뛰지 않는다.
3. 운용 중 보이는 `basic/interest/happy/fun/bored`의 첫 프레임은 32×24 흑백 실루엣에서 서로 6% 이상 달라야 한다. 이는 소스 자산의 기계적 하한일 뿐 사람의 판독 수용 기준을 대신하지 않는다. 모드별 의미는 중립·관심·이동의 밝음·도킹의 즐거움·기다림이며, 정지·실패는 표정이 아닌 상황 카드가 우선한다.
4. `rosy-face`의 10 fps와 대기 5 fps, 전력·CPU 예산, 상황표의 정지·업데이트·실패·CORE 누락 우선순위, 20 s마다 5 s의 주행 카드는 그대로다. 표정 자산은 `emotion`의 기존 패키징 경로에 둔다.

### Alternatives

- 표정 이름을 늘리면 CORE 매핑·핸드오버·패키징 계약이 함께 커지고 지금의 구분 문제를 해결하지 못한다.
- 런타임에서 임의 깜빡임이나 전환 효과를 만들면 D-385의 절제와 D-433의 안전 카드 가시성을 해친다.
- 기존 큰 GIF를 더 빠르게 재생하면 Pi의 변환 비용을 올리고 첫 프레임 공백과 형태 중복을 남긴다.

### Validation / transition

- 호스트: 여덟 자산의 크기·첫 프레임·움직임·프레임 간격, 다섯 운용 실루엣의 차이, `FaceFrames`의 전 프레임 재생, 상황표의 카드 우선순위를 시험한다. 320×240 첫 프레임을 직접 열어 시각 점검한다.
- 장치: 실제 설치 릴리스에서 화면의 1.5 m 거리·각도·조도 판독, 정상→수동→내비게이션→도킹→막힘 전환, 비상정지·CORE 중단·주행 카드 후 얼굴 복귀, 프레임 끊김과 CPU·메모리를 확인한다. 테스트 호스트의 통과만으로 DEVICE/FIELD GO를 선언하지 않는다.
- 이 변경은 브랜치에서 검증한다. `main` 착지, push, 릴리스 적용은 공유 Git 절차와 별도 사용자 지시에 따른다.
