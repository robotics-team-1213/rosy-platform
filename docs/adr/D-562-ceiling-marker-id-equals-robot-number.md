## D-562 천장 마커 번호는 로봇 번호와 같다 — 로봇은 40–49번, 스티커는 40 mm, 검출기 둘레 하한 0.015

**Status:** Accepted (2026-10-09, 사용자 결정: 천장 ArUco 로봇 마커 id = Fleet 로봇 번호, 로봇은 40–49번을 등록 순서대로 받는다, 로봇 윗면에는 40 mm 스티커만 들어간다). SOURCE 변경과 호스트 테스트만이다. 기존 로봇 번호 바꾸기, 스티커 인쇄·부착, 현장 수용은 이 기록이 하지 않는다.

잇는 결정: [D-33](D-33-.md)(로봇 신원은 로봇 번호 하나, `ROSY_ROBOT_NUMBER`, `ROS_DOMAIN_ID = 40 + N`) · [D-457](D-457-overhead-marker-priority-and-markerless-fallback.md)(천장 마커 우선, 무마커 폴백) · [D-472](D-472-rosy-cam-map-and-lamp-identity.md)(Rosy Cam 지도 표시, 램프 신원 대조) · [D-361](D-361-site-console-enrolls-robot-by-screen-code.md)(화면 코드 등록, `robot_id`가 등록 키). 폴더 구조는 바뀌지 않으므로 D-427 3항은 해당하지 않는다.

### Context

- 천장 카메라는 DICT_4X4_50(id 0–49)을 읽는다(`operations/vision/rosy_vision/detect.py`). 현장 설정의 `robot_markers`는 로봇마다 마커 id를 손으로 적는다. 로봇 번호와 마커 id가 따로 놀면 운영자가 두 표를 맞춰야 한다.
- 로봇 번호는 SD 카드 준비(`deploy/robot/pinky_pro/sd/prepare-rosy-sd.ps1`)가 1–61 가운데 빈 번호를 무작위로 골랐다. 마커 사전은 0–49까지라 51번 이상의 로봇은 같은 번호의 마커를 붙일 수 없다.
- 예시 `deploy/site/site-cameras.yaml.example`의 로봇 마커 7은 로봇 카메라가 보는 도크 태그 7(`tag_size_m` 0.05)과 겹친다.
- 로봇 윗면에는 40 mm 스티커만 들어간다.

**시뮬레이션 근거(2026-10-09).** 실제 천장 프레임 1280×720 한 장과 승인된 보정으로 88개 위치에 마커를 합성했다(흐림 + JPEG 80, 어두운 로봇 윗면). 원본은 저장소 밖 작업 폴더에 있다(공개 저장소라 넣지 않는다).

| 스티커(흰 테두리 1칸, 검정 = 스티커의 6/8) | 기본 검출기 검출률 | 잘못된 id |
|---|---|---|
| 40 mm | 44% (39/88) | 0 |
| 45 mm | 64% | 0 |
| 50 mm | 80% | 0 |
| 55 mm | 90% | 0 |

- 흰 테두리를 2–3 mm로 얇게 하면 어두운 윗면에서 더 나빴다.
- `minMarkerPerimeterRate`를 0.03(기본)에서 0.015로 내리면 40 mm가 39/88에서 54/88이 된다. 실제 천장 프레임 124장에서 잘못된 id 수는 3으로 기본값과 같다(이미 있던 거짓 id 17: 바닥에 칠한 원과 케이블).
- 프레임을 1.5–2배 키우는 방법은 이득이 더 작고 CPU가 약 2–4배라 기각했다.

### Decision

1. **천장 로봇 마커 id = 로봇 번호.** `rosy_NN`의 마커는 DICT_4X4_50의 id NN이다. 현장 `robot_markers`는 `rosy_40: 40`처럼 적는다.
2. **로봇 번호는 40–49.** SD 준비 도구가 자동으로 고를 때는 레지스트리에서 40–49 가운데 가장 낮은 빈 번호를 쓴다(등록 순서). 40–49가 모두 쓰였으면 분명한 오류로 멈춘다. 운영자가 번호를 직접 주는 경우의 검증은 그대로 1–61이다(D-33). `ROS_DOMAIN_ID`는 80–89가 된다.
   - 레지스트리는 운영 PC마다 따로다. 무작위 선택은 두 PC가 같은 번호를 낼 확률을 줄이려던 것인데, 가장 낮은 빈 번호는 두 PC에서 같은 번호를 낸다. 사이트 전체의 유일성은 여전히 Fleet 등록의 `robot_id_conflict` 거절에 기댄다. SD 카드는 한 PC에서 만드는 것을 운영 규칙으로 한다.
3. **id 배치.**

| id | 쓰임 |
|---|---|
| 1, 2, 10–13, 20, 21 | 게임 |
| 7 | 도크 태그(로봇 카메라, `tag_size_m` 0.05). 천장 로봇 마커로 쓰지 않는다 |
| 30–33 | 천장 모서리(`corner_marker_ids`) |
| 34–38 | 장소 마커 예약: 34 출발-남, 35 출발-북, 36 충전, 37 주차, 38 정지. 예약만 한다. 읽고 쓰는 동작은 별도 ADR이다 |
| 40–49 | 로봇(= 로봇 번호) |

4. **스티커와 검출기.** 스티커는 40 mm에 흰 테두리 1칸(검정 30 mm)이다. 천장 검출기는 `minMarkerPerimeterRate = 0.015`를 쓴다. 40 mm의 검출률은 약 61%(54/88)로 낮다. 마커가 없거나 놓친 프레임은 D-457 무마커 폴백이 받는다. 더 큰 스티커가 들어가는 로봇은 50 mm 이상이 낫다.
5. **예시 고침.** `site-cameras.yaml.example`의 로봇 마커 예시는 `rosy_40: 40`이다(도크 태그 7과 겹치지 않게). `robots.yaml.example`도 같은 `rosy_40`을 쓴다.

### 기존 로봇 번호 바꾸기(이 브랜치 범위 밖, 운영 단계)

8kcn(rosy_60 → 40), 9dfk(rosy_26 → 41)는 따로 운영 단계로 한다. 지원하는 번호 바꾸기 도구는 없다. `PUT system/info`는 `IDENTITY_LOCKED`를 돌려준다. 바꾸기가 건드리는 것:

- 로봇 `runtime.env`의 세 키(`ROSY_ROBOT_NUMBER`, `ROS_DOMAIN_ID`, `ROSY_NAMESPACE`)
- `/var/lib/rosy/provisioning/complete.json`의 `dds` 블록
- Fleet 등록 해제 후 다시 등록. `robot_id`가 등록 키이고 토큰 AAD에 들어간다(D-361)
- TLS 묶음 지도(`--enrolled-tls-bindings-file`) — 등록되었던 binding이면 D-580 뒤로는 고치지 않는다
- 현장 `robots.yaml`, `site-cameras.yaml`의 `robot_ids`·`robot_markers`, `site-sightings.yaml` — `robot_ids: enrolled`이면 D-580 뒤로는 고치지 않는다
- G4 매핑 승인 다시 발급(묶음이 `robot_number`에 묶인다)
- 옛 이름 아래의 녹화·토픽

### Alternatives

| 대안 | 판단 |
|---|---|
| 마커 id를 로봇 번호와 따로 배정 | 기각(사용자). 표 두 개를 맞추는 일이 남는다 |
| 1–61 무작위 번호 유지 | 기각. 50 이상은 DICT_4X4_50에 마커가 없다 |
| 더 큰 사전(DICT_4X4_100 등) | 기각. 같은 40 mm에서 검출 이득이 없고 현장·게임 마커를 다시 찍어야 한다 |
| 프레임 1.5–2배 확대 | 기각. 둘레 하한 낮추기보다 이득이 작고 CPU 약 2–4배 |
| 얇은 흰 테두리(2–3 mm) | 기각. 어두운 윗면에서 더 나빴다 |

### Consequences

- 새 로봇은 마커 번호를 따로 정하지 않는다. 로봇 번호를 보고 그 id의 스티커를 붙인다.
- 한 사이트의 자동 배정 로봇은 10대까지다. 넘으면 SD 준비가 멈추고, 이 ADR을 다시 연다.
- 둘레 하한을 낮춘 만큼 작은 거짓 후보가 늘 수 있다. 실제 프레임 124장에서는 늘지 않았다. 현장에서 거짓 id가 늘면 이 값을 다시 본다.
- 기존 두 로봇은 번호를 바꾸기 전까지 이 규칙 밖이다(60은 사전 밖, 26은 40–49 밖).
