## D-852 실험실 PC 사용자 서비스 목록과 대조

**Status:** Accepted for implementation (2026-10-23)

### Context

host-state manifest(D-530)는 모델·AI·관제 PC의 root 시스템 설정만 역할별로 선언한다. 실제 업무를 하는 rosy·pinky 사용자 유닛(검수 앱, 학습 센터, OMX 카메라·관측, 업데이트 타이머)은 어디에도 선언돼 있지 않았다. 2026-10-19~23에 다음 문제가 모두 며칠씩 보이지 않았다.

- 관제 PC OMX 업데이터가 교체된 보드 시리얼을 가리켜 4일 동안 멈췄다(#156).
- AI PC 상황 서비스 업데이터가 남은 `shallow.lock` 때문에 3일 동안 멈췄다(#158).
- 모델 PC 검수 전달 유닛이 이동된 파일 경로를 가리켜 이틀 동안 실패했다.
- 검수 앱 업데이트 타이머가 계정 연동 뒤 꺼진 채 남았다(#165).
- 카메라 보정·뷰어가 `~/rosy-test` 사본에서 돌았다(#162).

`tools/remote/update_status.py`는 유닛 설정에서 경로를 추정했을 뿐, 무엇이 돌아야 하는지에 대한 기준이 없었다.

### Decision

- 역할(`model`·`ai`·`site`)별 사용자 유닛의 기준은 `deploy/hosts/services.yaml` 한 곳에 둔다. 항목마다 다음을 적는다.
  - `run`: `active`·`timer`·`oneshot`·`off`
  - `channel`: 코드 갱신 경로(D-805의 업데이터, D-446 서명, 검토 스냅샷, 커밋 고정 설치기, 복사, 외부 코드, 임시 `adhoc`, 폐기)
  - 근거 문서
  - 해당하면 코드 경로(`source`), 저장소 유닛 원본(`template`), 복사된 파일(`copies`), 허용 drop-in, 인스턴스, 당분간 허용하는 차이와 이유(`known_drift`)
- 실험실 PC에 유닛을 추가·변경·폐기하는 변경은 같은 커밋에서 이 항목을 고친다.
- `update_status.py`는 각 PC를 역할의 선언과 대조한다. 다음 경우 exit 1이다.
  - 선언에 없는 유닛(UNDECLARED)
  - 설치되지 않은 유닛(MISSING)
  - 멈춘 유닛(DOWN)
  - 꺼져 있어야 하는데 켜진 유닛(UNEXPECTED)
  - 유닛 파일·복사 파일·코드 경로·drop-in이 선언과 다른 경우(DRIFT)
- `known_drift`로 설명한 차이는 KNOWN, `adhoc` 항목은 ADHOC으로 이유와 함께 보이며 실패로 세지 않는다.
- 저장소 원본 비교는 origin/main의 파일 내용으로 하고 CR은 무시한다. 다른 저장소의 원본은 `rosy-ops:<경로>`로 적는다.
- 역할은 `private/lab-hosts.json`의 `site_host`(site)와 `sim_hosts` 항목의 `=model`·`=ai`에서 읽는다.

| 기존 결정 | 관계 |
|---|---|
| D-530 | root 시스템 기준은 host-state manifest가 그대로 소유한다. 이 목록은 사용자 유닛만 다룬다. |
| D-805 | 업데이트 경로와 동결 관문을 바꾸지 않는다. 경로의 이름을 `channel`로 적는다. |
| D-446·D-545·D-561 | 모델 PC 서명 코드와 검수 앱 릴리스 규칙을 그대로 따른다. |

### Consequences

선언과 실제가 다르면 다음 상태 확인에서 바로 보인다. 목록은 유닛을 설치·변경하지 않는다. 고치는 일은 각 경로의 소유 절차(업데이터, 설치기, 검토 스냅샷 수용)가 한다. 확인은 개발 PC에서 사람이 실행할 때만 돈다. 주기 실행이나 Fleet 화면 연결은 이 결정의 범위 밖이다. 새 PC는 역할을 정하고 그 역할의 항목을 채운 뒤 상태 확인이 0건일 때 연결을 마친 것으로 본다.
