## D-982 현장마다 다른 운영 규칙은 데이터 문서 하나로 두고, 가정 상태로 "감·대기·거절"을 미리 묻는다

**Status:** Proposed (2026-11-07, 사용자 요청 2026-11-06: 차례 출발·스테이션 복귀·상하차 대기가 현장마다 다르니 규칙을 유연하게 두고, 실물을 더 굴리지 않고도 계획·편대·따라가기가 가는지 바로 확인한다). 1단계(문서·검증·초안·활성화·감사, 병합 대기·블록 수·충전 %의 문서 값 대체)와 2단계(판정 API·경로 미리보기 연결)를 구현했다. 대형 한도는 판정만 하고 시작에는 아직 적용하지 않는다(3단계). 문서가 없으면 동작이 바뀌지 않는다. 시뮬·실물 수용은 없다.

잇는 결정: [D-941](D-941-track-platoon-hold-points-charge-bays.md), [D-829](D-829-domain-intent-and-resource-admission-boundaries.md), [D-928](D-928-fleet-per-robot-dispatch-serial-traffic.md), [D-865](D-865-fleet-policy-admission.md), [D-573](D-573-crosswalk-stop-look-cross.md), [D-780](D-780-workcell-coordinator-peer-stop-source-and-named-barriers.md). 계획: `Rosy/docs/superpowers/plans/2026-11-06-site-operating-rules.md`.

**Context:** 차례 출발의 병합 대기(`merge_max_wait_s` 20초), 한 로봇이 쥐는 블록 수(3), 충전 시작·나감 비율(15%·80%)은 코드 상수다. 현장마다 달라야 하는데 바꾸려면 코드를 고치고 착지해야 하고, 바꾼 값이 가는지는 로봇을 굴려 봐야 안다. 지도는 초안·활성화·버전·감사가 있지만 규칙에는 같은 틀이 없고 소유 ADR도 없었다.

**Decision:**

1. **규칙은 데이터다.** 현장 규칙 문서 `rosy.site_rules/1` 하나에 `departure`(병합 대기 초, 블록 수, 순서 `fair`), `return`(충전 시작·나감 %, 칸이 찼을 때 대기 장소 `when_full`), `stops`(장소·역할 `load`/`unload`/`wait`·해제 `external`/`timer`·시한·시한 뒤 `hold`), `formation`(선택 한도 `min_gap_m`·`max_speed_mps`)을 둔다. 장소는 지도 장소 id뿐이고 업무 의미는 문서에 없다.
2. **저장은 지도와 같은 틀이다.** 초안 한 개, 불변 활성 버전, 이름 있는 운영자의 저장·활성화, 지도 `site_map_events`의 감사 행, 활성화는 trip·대형·teach 중이면 거절. 같은 SQLite를 쓰고 `SiteMapStore.rules`로 붙는다. 활성 문서에 없는 장소는 활성화·저장에서 거절한다.
3. **문서가 없으면 지금과 같다.** 모든 기본값은 바꾸기 전 상수와 같다. 활성 문서가 없는 현장에서는 어떤 움직임도 바뀌지 않는다.
4. **규칙은 더 막기만 한다.** 검증이 안전 쪽 경계를 넘는 값을 거절한다: 충전 시작 15% 미만(CORE 위험 10% + 5%), 나감은 시작 위·50% 이상, 블록 수 3 미만(적게 쥐면 고리에 더 많은 로봇이 들어간다), 대형 최소 간격 0.4 m 미만, 최대 속도 0.15 m/s 초과, 시한 뒤 동작은 `hold`뿐(사람에게 넘기고 임의로 출발하지 않음). 규칙은 CORE의 최종 `/cmd_vel` 판단, 가드 한계, 사람 확인, [D-911](D-911-omx-native-reviewed-operating-envelope.md)을 완화하지 않으며 정지 경로를 건드리지 않는다.
5. **판정과 실행은 같은 순수 함수다.** `POST /api/fleet/site-rules/judge`가 가정 상태를 받아 `go`·`wait`·`refuse`와 이유를 답한다. 출발 순서는 `blocks.grant_order_key`(실제 표가 쓰는 정렬 키), 복귀는 `ChargeBays.plan`, 대형은 `slots`(시작 전 검사)와 문서의 선택 한도를 본다. 대형 한도는 아직 대형 시작에 적용하지 않는다: 시작 경로 `formation_control.py`는 safety 태그라 3단계에서 Safety-Review와 함께 바꾸고, 그때까지 판정 답에 `enforced: false`를 적는다. 답은 조언이고 로봇에 아무것도 보내지 않는다. 경로 미리보기 화면의 운행 카드가 이 API를 불러 보여 준다.
6. **플랫폼은 중립이다.** 플랫폼이 가진 것은 "어디서, 누가 풀 때까지, 얼마나 기다리는가"라는 틀이다. 적재가 끝났는가 같은 업무 판단은 앱이 하고 항만 정책을 바꿔도 플랫폼 diff는 0이다. `stops`는 3~6단계(대기 단계, 해제 API)가 쓴다. 이 결정은 저장·검증까지만이다.

**기존 결정과의 관계:**

| 결정 | 상태 | 이 결정과의 관계 |
|---|---|---|
| D-941 트랙 운행·충전 칸 | Proposed | 충전 칸 계획의 15%·80%를 문서 값으로 바꾼다. 칸 계획, 보기 전용(`dispatch: false`)과 후진 도킹 순서는 그대로다. 계획을 보내는 일은 하지 않는다 |
| D-829 업무 목표와 자원 배정 분리 | Proposed | 규칙은 업무 목표가 아니라 공통 자원(블록·칸·정류 장소)을 어떻게 기다리고 배정하는가의 값이다. 업무 의도와 배정 판단의 경계를 옮기지 않는다 |
| D-928 로봇별 발행·교통 판정 한 줄 | Proposed | 교통 판정이 한 줄이라는 설계를 바꾸지 않는다. 판정 안의 병합 대기 값만 문서에서 읽는다 |
| D-865 정책 승인 | Proposed | 승인 범위는 건드리지 않는다. 이 문서는 승인이 아니고 작업을 자동으로 보내지 않는다 |
| D-573 횡단보도 서고·보고·건넌다 | Proposed | 횡단보도 정지·건넘 조건은 규칙으로 완화할 수 없다. 이 문서에 해당 필드가 없다 |
| D-780 조율자 정지 출처·barrier | Proposed | 정지 출처와 barrier 해제 연산은 다루지 않는다. `stops`의 시한 초과는 사람에게 넘기며 barrier를 열지 않는다 |

**Validation:** 단위·HTTP 시험(문서 검증, 저장소, 판정 표), 기존 교통·충전 칸·대형 시험 그대로 통과, 문서 없는 현장의 `GET /traffic`·`/charge-bays` 동일. 시뮬 시나리오(구역 차례·대열·칸 찼을 때·대기)와 실물 수용은 후속이고 이 ADR로는 허가하지 않는다. `authority`를 켜는 일(블록 규칙이 로봇을 실제로 막음)은 실물 단계에서 따로 결정한다.

**Consequences:** 현장 Fleet이 구버전이면 착지만으로 나타나지 않는다. 게시·서명·배포는 별도다. 현장 카메라가 끊겨 위치가 UNKNOWN인 동안 판정은 가정 상태로 할 수 있지만 현장 수용은 복구 뒤다.
