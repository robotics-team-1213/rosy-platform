## D-866 VLA 주 시뮬레이터는 Isaac Sim, Gazebo는 실행 계약 회귀용. 모델 PC와 AI PC는 역할을 나누되 오프라인 일괄 작업은 병렬로 함께 처리한다

**Status:** Proposed (2026-10-25). 사용자 결정: Isaac을 VLA 주 시뮬레이터로, Gazebo는 회귀·CI용으로 둔다. PC 역할은 명확히 나누되 학습 등은 두 PC를 병렬로 써서 빨리 처리한다.

이 ADR이 바꾸지 않는 것:
- D-516의 실행 권한 경계: AI PC는 Fleet 원장, admission, ROS, 장치 Action 권한이 없다.
- D-793 실물 관문
- D-795(PC 간 DDS 금지)

Isaac 버전은 D-434 §3이 정한 5.1이다(D-322 개정 완료). D-434 §3이 유지하는 Isaac Lab 학습 HOLD(D-427)는 이 ADR로 풀지 않는다. Isaac Lab 병렬 환경과 RL은 그 HOLD가 풀린 뒤에 쓴다.

**관련:** D-854 · D-864(§4를 보완하고 §5.1의 학습 위치를 바꿈) · D-516(AI PC 역할을 넓힘) · D-527 · D-434 · D-322 · D-795 · 계획 `Rosy/docs/superpowers/plans/2026-10-25-omx-vla-pipeline-structure.md`(작업 공간 계획, Git 밖)

### Context

- VLA는 영상이 핵심 입력이라 렌더링 차이가 성능을 좌우한다. 파지는 접촉 물리의 영향을 받는다. Isaac Sim은 RTX 렌더링, Replicator 무작위화, PhysX GPU, Isaac Lab 병렬 환경을 준다. Gazebo는 렌더링이 단순하지만, OMX 장면, top·front 카메라, CORE·owner·Fleet lease 연결, `remote_sim` 시험 자산을 이미 갖고 있다.
- 저장소의 Isaac 경로는 OMX에 대해서는 OMX-F 가져오기와 관절 검사까지다. 카메라, 장면, 팔 제어 ROS 연결은 아직 없다.
- 두 GPU PC는 모두 RTX 5080 16GB다. 2026-10-24~25에 `nvidia-smi`로 본 사용량은 모델 PC 약 0.4GB, AI PC 약 10GB(ollama 등)였다. AI PC 지연 재측정에서는 전처리가 1차보다 느렸고, 기록은 원인을 CPU 공유 부하로 추정했다(`docs/validation/policy-latency-smolvla-2026-10-24b/`, 원인 미확인).
- D-516은 모델 PC를 학습·평가, AI PC를 승인된 추론으로만 나눴다. 한 PC로는 Isaac 구축, 데이터 생산, 학습, 평가가 줄을 서서 늦어진다.

**정정 (2026-10-25):** Context 첫 항목의 "top·front 카메라"는 틀렸다. 설치된 Gazebo world의 카메라는 작업대 카메라 1대(`workcell_camera`)다. D-866 P0 시험(`policy_chain_vla_gazebo.py`)이 이 카메라를 복제해 top 카메라를 덧붙이고 두 대로 실행한다.

### Decision

#### 1. 시뮬레이터 역할

- **Isaac Sim(모델 PC):** VLA 학습 데이터 생산과 닫힌 루프 평가의 주 시뮬레이터다. 아래 §2 적합성 시험과 전환 조건을 통과하기 전까지는 후보로 둔다. 닫힌 루프 실행 때 CORE와 owner는 Isaac과 같은 PC(모델 PC)에 둔다(D-795). 정책 추론은 그 PC에서 하거나 CORE HTTP로 AI PC 실행기가 붙는다. ROS·DDS는 PC를 넘지 않는다.
- **Gazebo:** CORE·owner·정지·lease 실행 계약의 회귀 시험과 CI 기준선이다. Isaac이 없어도 실행 계약 확인은 계속된다.
- 한 시뮬레이터 데이터로 학습한 정책은 다른 시뮬레이터에서도 평가한다(교차 평가).

#### 2. 시뮬레이터 백엔드 계약

owner와 CORE는 백엔드를 구분하지 않는다. 각 시뮬레이터는 실물 공식 스택과 같은 ROS 인터페이스를 낸다.

| 인터페이스 | 계약 |
|---|---|
| 관절 상태 | `/joint_states`: `joint1..5`, `gripper_joint_1`, `ros_joint_rad` |
| 제어 | 팔·그리퍼 `FollowJointTrajectory` Action |
| 카메라 | `top`, `front` 원본 프레임과 시각. 설치 정책과 같은 크기 |
| 시각 | `/clock` |

평가용 사실(물체 위치 등)은 정책 입력과 분리한다.

새 백엔드는 적합성 시험을 통과해야 쓴다. 시험 항목은 토픽 이름·형식·주기, 관절 순서, 카메라 크기, 시각 단조성, 정지 응답이다.

Isaac 전환 조건은 다음과 같다.
- 적합성 시험 통과
- 카메라 2대 640×480에서 10Hz 이상, 실시간 배율 1 이상
- 그리퍼 파지 반복 시험 통과
- 실물 프레임과 렌더링 분포 비교 기록

#### 3. PC 역할 — 기본 소유

| PC | 소유 | 하지 않는 것 |
|---|---|---|
| 모델 PC | Isaac Sim, 데이터 생산과 curation, 학습, 독립 평가, 승격 증거, registry 산출물 | 운영 추론, Fleet 판단, 장치 명령 |
| AI PC | 승인된 고정 버전 정책·VLM의 운영 추론(D-516, D-854 §2) | Fleet 원장 쓰기, admission, ROS·장치 Action, 승격 판정 |

#### 4. 병렬 일괄 작업 — 두 PC를 함께 쓴다

학습, 하이퍼파라미터·시드 탐색, 데이터 변환·렌더링은 두 PC 어느 쪽에서도 돌 수 있다. 이 확장은 OMX·VLA 정책 데이터에만 적용한다. Decision 모델의 D-527 전달 규칙은 그대로다.

- **GPU 단독 작업:** 지연 측정, SIM 닫힌 루프 정책 실행, 승격용 독립 평가는 일괄 작업이 아니다. 실행하는 동안 그 PC의 GPU를 다른 일괄 작업과 나누지 않는다. 측정 기록에는 같은 시간대의 GPU 사용 프로세스를 남긴다.
- **AI PC에서의 양보:** VRAM은 우선순위로 비워지지 않는다. 그래서 AI PC의 일괄 작업은 체크포인트에서 멈추고 다시 시작할 수 있어야 한다. 운영 추론이 시작되면 일괄 작업은 멈춘다. 확인된 중단 장치가 생기기 전에는, 일괄 작업이 돌 수 있는 동안 AI PC 현장 추론 경로를 켜지 않는다. 지금은 그 경로가 꺼져 있다.
- **작업 단위:** 일괄 작업은 입력 데이터셋 digest, 코드 커밋, 환경 잠금(venv 해시), 시드를 고정한 하나의 작업으로 정의한다. 같은 작업은 어느 PC에서 돌아도 같은 산출물 기록을 남긴다.
- **데이터와 결과:** 학습 데이터는 모델 PC에서 digest를 고정해 AI PC로 복사한다. AI PC는 registry에 쓰지 않는다. 모델 PC가 AI PC 산출물을 가져와 해시를 확인하고 받아들인다. 승격 판정과 승격 메타데이터는 모델 PC의 독립 평가만 만든다. AI PC에서 돈 평가 반복은 탐색용이며 승격 증거가 아니다.
- **나누는 방식:** 단일 PC에 맞는 작업은 PC별로 따로 돌린다. 예를 들어 Isaac은 모델 PC, 학습 시도는 AI PC, 시드 탐색은 둘로 나눈다. 두 PC를 묶은 분산 학습(DDP)은 망 대역과 운영 위험을 따로 확인한 뒤에만 쓴다.
- **자원 확인:** 시작 전에 두 PC의 GPU 메모리, 디스크(`rosy-ops/docs/lab-host-storage.md`), 실행 중인 프로세스를 확인한다. 다른 사람의 프로세스는 멈추지 않는다.

### Consequences

- 정책·실행기·owner 코드는 시뮬레이터를 바꿔도 그대로다. Isaac 백엔드 구축은 새 작업이다(적합성 시험, 카메라, 장면, ROS 연결).
- 학습과 Isaac 구축이 서로를 기다리지 않는다. 예를 들어 모델 PC에서 Isaac을 만들면서 AI PC에서 학습할 수 있다.
- D-516의 "AI PC는 추론만"은 "운영 권한은 추론만, OMX·VLA 오프라인 일괄 작업은 체크포인트 중단·재개 조건으로 허용(§4)"으로 넓어진다. 실행 권한 경계는 그대로다.
- AI PC 현장 운영 추론을 켜려면 일괄 작업 중단 장치를 먼저 확인해야 한다(§4).

### 구현 순서

1. P0: Gazebo에서 정책 실행기 → CORE → owner 실행 경로를 SmolVLA로 확인한다.
2. 시뮬레이터 백엔드 계약 문서와 적합성 시험을 만들고, Gazebo가 먼저 통과한다.
3. 일괄 작업 정의(입력 digest, 커밋, 환경 잠금, 시드)를 만든다. 실행은 기존 `tools/remote/remote_job.py`(분리 실행)와 `remote_omx_native.py`(커밋 고정 작업, D-786), Isaac은 `remote_isaac.py`를 재사용한다.
4. Isaac OMX 백엔드를 만든다(모델 PC).
5. 데이터 생산과 학습을 병렬로 진행한다(모델 PC Isaac, AI PC 학습).
