## D-827 도메인 중립 플랫폼·재사용 공정·업무 앱의 책임을 분리한다

**Status:** Proposed (2026-10-21). 사용자가 합의한 구조 방향을 구현 가능한 경계로 구체화한 제안이다. API 변경·코드 이전·배포·실물 수용 완료를 뜻하지 않는다.

### Context

도메인 앱은 업무 목적과 정책을 바꾸면서 ROSY의 관측·작업·실행 기능을 재사용해야 한다. 반대로 앱마다 장치 제어·실행 원장·자원 충돌 처리를 복제하면 유지보수와 권한 경계가 흩어진다. 재사용 가능한 공정까지 전부 앱에 옮기는 것도 같은 중복을 만든다.

현재 `operations/site_execution`은 PlanBundle·공정 컴파일러 포트·진행 투영을 제공한다. `operations/processes/palletizing`은 공정 계산을 소유하고, Fleet의 `cell/cell_compiler.py`가 이를 연결한다. 이것은 공통화의 출발점이며 이미 범용 외부 실행 API가 있다는 증거는 아니다. D-822의 `applications/fleet` 역시 기존 Fleet과 함께 조립되는 내장 제품 앱이다.

### Decision

| 영역 | 소유 책임 | 소유하지 않는 책임 |
|---|---|---|
| 업무 앱 | 업무 개체·장부·목표·우선순위·처리 전략·화면. 실행 결과를 업무 상태에 반영하는 규칙 | 플랫폼 실행 원장 직접 쓰기, 장치 최종 명령, 다른 앱의 업무 모델 |
| 재사용 공정·Skill | 절차 계산·입력 제약·기하·단계 선후관계·필요한 완료 조건의 선언 | 실제 승인·grant·dispatch, 업무 출고 우선순위, 관측 사실의 임의 확정 |
| 플랫폼 운영·실행 | 공통 작업 식별·시도·상태·근거·자원 경합·admission·dispatch | 특정 업무 개체명·업무 우선순위 알고리즘·사용자 앱 내부 구현 |
| World·관측 | 출처와 시간에 결속된 현재 관측·투영 | 업무 장부·계획 위치·명령 전송을 물리 사실로 확정 |
| 장치 owner | 로컬 실행·최종 명령·정지·설치 제한의 집행 | 업무 전략, 원격 앱이 주장한 성공의 무조건 수용 |

1. 업무 앱은 지원되는 버전의 공개 계약과 어댑터로 요청·조회한다. 내부 Python 모듈·DB·ROS topic을 외부 앱의 숨은 인터페이스로 사용하지 않는다. 실물 direct 경로 등 이미 승인된 기존 경로는 별도 개정 전까지 유지한다.
2. 공정이 플랫폼 저장소에 있다는 이유만으로 도메인 종속이라고 판단하지 않는다. 여러 업무가 사용할 수 있는 절차 계산은 선택 가능한 공정 구현으로 유지한다. 업무 전용 정책을 공통 실행부에 분기로 추가하지 않는다.
3. 컴파일러·공정 검증은 실제 조립 지점에서 선택하고 인터페이스로 주입한다. 장치가 승인된 공정 산출물·기하를 검증하는 기존 절차는 유지한다. 도메인 중립화를 이유로 장치 검증을 삭제하지 않는다.
4. 업무 장부와 실행 원장은 다른 사실을 소유한다. 앱은 업무 개체·업무 완료를, Fleet은 실행 요청·시도·admission·결과 근거를 기록한다. ID·버전·근거로 연결하되 같은 실행 사실의 독립 정본을 만들지 않는다.
5. `applications/fleet`의 내장 조립과 외부 업무 앱의 계약을 구분한다. 독립 저장소 여부는 공개 범위·배포·권한의 결정이며, 논리 계층의 수와 같지 않다. 이번 제안은 저장소 통합이나 새 최상위 폴더를 요구하지 않는다.
6. 공통화 전 현재 호출 경로와 실패·정지 동작을 추적한다. 기존 앱의 `core`라는 이름이나 import 검사 통과만으로 업무 중립성을 인정하지 않는다.

### 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| D-413·D-427 | 공정·연동·앱·프로필과 middleware/operations/learning 책임을 유지하고 외부 앱의 소비 경계를 구체화 |
| D-429 | 생산자·소비자·API/import 방향을 유지. 물리 폴더 이동으로 권한을 추가하지 않음 |
| D-430 | 단일 writer·장치 안전·독립 검토를 유지. 공정 교체는 안전 검증 우회가 아님 |
| D-657 | 이미 분리된 실행 계약·순수 계산·Fleet 소유 transaction을 재사용 |
| D-773 | Proposed DeviceControlPort나 장치별 연결을 구현된 범용 외부 API로 취급하지 않음 |
| D-822 | 내장 Fleet 앱의 소스 배치를 유지. 외부 앱의 독립 계약은 별도 검증 필요 |

### Alternatives

- 앱이 모든 조정을 구현: 초기 direct 시연에 유용하지만 공통 원장·장치 조정의 앱별 복제를 장기 구조로 채택하지 않는다.
- 모든 업무를 범용 workflow/플러그인 엔진으로 표현: 현재 검증된 사례보다 큰 실행 언어·확장 체계를 먼저 만들므로 채택하지 않는다.
- 폴더만 재배치: 소비 계약·결과 의미·데이터 소유권 문제를 해결하지 못한다.

### Consequences

일차 구현은 기존 모듈의 계약과 호출 방향을 좁게 보완한다. 범용 SDK·공통 앱 프레임워크·별도 서버를 선행 조건으로 두지 않는다. 업무 정책만 바꾸는 변경이 플랫폼 코드 변경 없이 가능한지 검증해야 한다.

후속 구현과 분할 검증은 [실행계획](../plans/2026-10-21-domain-neutral-application-phases.md)을 따른다. 이 ADR은 현행 API 필드·스키마 버전·배포 프로필을 변경하지 않는다.

### 검증 기준

- 외부 앱이 지원 HTTP 계약만으로 준비·요청·조회·결과 처리를 수행하고 플랫폼 내부 import와 DB 직접 쓰기가 없다.
- 공정 교체 시 플랫폼 원장·장치 owner의 기존 검증·정지 시험을 유지한다.
- 업무 정책 변경과 플랫폼 계약 변경을 별도 변경으로 검토할 수 있다.
