## D-640 Fleet 범용 문제 해결 오케스트레이션과 지속 개선

**Status:** Accepted (2026-10-12). 후보 전용 소스 경계를 수용한다. 유한 supervisor·CLI 번역·Fleet 원장·offline 비교는 구현했으며 실제 provider 호출·배포·독립 현장 수용은 HOLD다.

### Context

새 장애물이나 암 동작 실패는 안전 정지, 원인 판단, 복구 성공을 따로 평가해야 한다. 안전하게 멈춘 사건을 모두 모델 실패로 학습하면 위험한 계속 동작을 보상할 수 있다. D-608의 incident review와 녹화 결합은 검토 자료를 남기지만 자동 정답·학습·승격은 만들지 않는다. D-619는 mobility/manipulation 공통 상황과 처리 방향을 이미 정의한다.

사용자는 Fleet PC에서 Claude Code와 OpenCode를 통해 선택한 모델들이 상황을 토론하고 처리 후보를 내는 런 오케스트레이션 계층을 요청했다. CLI/agent host와 기반 모델은 다른 식별이며, GLM 5.x는 실제 제공자 ID·지원 기능·승인 프로파일을 확인하기 전까지 사용자 후보명이다.

### 책임·선행 관문
[D-647 공통 판단 책임·배포 0단계](../adr/D-647-shared-judgment-ownership-and-deployment.md)에서 World·공통 상황평가·후보·작업/자원 중재를 구별하고 초기 배포 위치를 결정한다. Fleet PC supervisor는 잠정 배치이며 공통 판단 전체의 Fleet 소유 확정이 아니다. D-642~D-646의 중앙 판단과 비개입·사람 처리 수용이 이후 모델 토론 구현의 선행 조건이다. 기존 `rosy.decision`은 deliberative 역할에 한정한다.

### Decision

2026-10-12 사용자 지시로 Discord를 제외한 후보 전용 소스를 선행 구현한다.
앞의 현장 receipt 관문은 실제 모델 활성화·운영 승격에 유지한다.
[실제 책임 경계와 검증 계획](../plans/2026-10-12-decision-deliberation-boundary.md)을 따른다.
현재 구현은 문/암 fixture와 고정 처리 방향의 텍스트 의견이다. 기존 빠른 규칙·사례 owner를
재구현하지 않으며 실제 영상 추론·정책 자동 개선·실행 연결은 완료로 표시하지 않는다.

1. **Fleet PC에 범용 문제 해결 런 supervisor를 둔다.** World 현재 관측, 목표, 제약, 허용 capability, 결과를 공통 문제 자료로 읽는다. 사건·정지뿐 아니라 주어진 작업과 목표 불일치도 입력이다. 논리 구현 소유자는 기존 `operations/decision/src/rosy/decision`이며 Fleet과 같은 배포 경계를 재사용한다. 무거운 로컬 추론은 기존 AI PC 배치 경계를 따른다. Fleet 원장/admission/dispatch와 모델 PC 학습/평가는 기존 소유자에 남는다. 새 최상위 폴더·범용 에이전트 프레임워크는 만들지 않는다.
2. **빠른 처리와 깊은 숙고를 계층화한다.** 검증된 규칙/사례와 빠른 전문 모델, 불확실하거나 새로운 문제의 복수 모델 숙고 순으로 라우팅한다. 문제 유형별 독립 평가로 모델 구성을 선택하며 모든 문제에 전 모델을 호출하지 않는다. 느린 숙고는 로컬 정지를 기다리게 하지 않는다. 한 문제에 활성 런 하나, 두 모델 토론은 최초 독립 의견과 한 번의 반론 반영으로 최대 세 호출이다. 첫 운영 후보는 보고/제안만 하며 실제 호출·시간·비용 예산은 승인 프로파일로 고정한다. 첫 설계값은 전체 30초이고 기존 D-619 10초 추론/12초 제안 TTL이나 영상 신선도를 늘리는 값이 아니다. 새 영상·현재 세대 확인 없이 긴 토론의 답을 실행 후보로 사용하지 않는다.
3. **모델은 제안자와 비판자로 참여한다.** 최초 의견에는 상대 답을 주지 않는다. 각 답은 원인 가설, 사건 근거 참조, 불확실성, 기존 D-619 처리 방향, 필요한 새 관측, 재개 전제와 중단 조건을 반환한다. 토론 합의·confidence·같은 모델의 재질문은 독립 검증이 아니다. 최종 선택은 결정론 검증기와 기존 Fleet 정책이 한다. 증거 없는 결론, 상충, 잘못된 식별, deadline 초과는 기존 HOLD/규칙/사람 경로로 끝낸다.
4. **코딩 에이전트를 제한된 추론 실행기로 사용한다.** supervisor가 정리한 사건 자료만 제공한다. 코드 쓰기·셸·배포·임의 MCP·원장 수정·장치 명령·정지 해제 권한을 부여하지 않는다. 호스트 설정/플러그인/메모리의 암묵적 상속을 막고 전용 계정과 파일·네트워크 경계를 검증한다. 외부 제공자에는 승인된 최소 비식별 자료만 전송한다. 모델·CLI·프롬프트·정책 버전은 기록하며 승인되지 않은 자동 모델 fallback은 없다.
5. **사건과 결과를 닫아 개선으로 연결한다.** 기존 incident/episode/attempt/generation과 녹화 lineage를 재사용한다. 정지 원인, 장치 정지 readback, 각 모델 의견, Fleet 선택·거절, 실제 실행 결과, 목표 검증, 사람 교정, 재발을 연결한다. 통신 장애·보정 오류·센서 stale·환경 변화와 인식/판단 실패를 구분한다. 모델 출력이나 API 수락을 학습 정답·물리 성공으로 사용하지 않는다. 반복 재시도의 예산은 사건 묶음 기준이다.
6. **모델·프롬프트·규칙·토론 정책은 각각 평가한다.** 모델 PC에서 세션/장소/시간 분리한 사람 정답으로 규칙만, 단일 모델, 두 모델 숙고를 동일 사건에 재생한다. 위험 후보·금지 효과·잘못된 근거/세대 수락은 평가 세트에서 0건이어야 한다. 이 수치는 실물 안전의 증명이 아니다. 유효 응답률·기권·지연·비용·원인별 복구와 재발을 별도로 보고한다. 표본/허용 한계가 미정이거나 독립 정답이 없으면 승격 HOLD다. 그림자→제한된 장치 수용→현장 결과 검증 뒤 고정 후보를 승인하며 악화 시 이전 승인 프로파일로 되돌린다.
7. **지속 개선은 모델 선택과 재사용 사례에도 적용한다.** 기대 결과와 실제 결과의 차이에서 상황별 실패를 분류하고, 검수된 해결 사례·라우팅 정책·프롬프트·모델/정책 후보를 개선한다. 해결 사례는 적용 조건과 버전을 가지며 재사용 시 현재 근거·capability를 다시 검사한다. 운영 중 새 사례를 수집하는 것과 그것을 자동 실행 정책으로 승인하는 것은 분리한다. 미지 문제는 HOLD/재관측/사람 검토로 범위를 명시한다. 행동 조건부 World 미래 예측은 D-630의 후속 계약이며 이 설계에서 구현된 것으로 표시하지 않는다.

### Consequences

규칙만 처리하면 비용·지연이 작지만 새 원인 해석이 제한된다. 단일 모델은 구현이 작지만 반론이 없다. 이 제안은 해결되지 않은 사건에만 두 모델의 제한 토론을 적용한다. 추가 모델은 고정 재생에서 단일 모델 대비 가치가 입증될 때 검토한다.

첫 구현은 사건 보고와 후보만 남긴다. 기존 자동 실행 밸브·Arm capability·E-stop 해제 조건을 변경하지 않는다. 공개 API 필드는 이 ADR로 확정하지 않고 producer/consumer 구현과 API Reference를 함께 변경할 때 정한다.
