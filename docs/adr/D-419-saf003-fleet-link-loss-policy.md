## D-419 SAF-003: Fleet 링크가 끊기면 진행 중이던 Fleet 주행 목표에만 정책을 한 번 적용한다

**Status:** Accepted (2026-10-02, 사용자 승인 "구현, 범위 한정" — 브랜치 `feat/d415-saf003-fleet-loss`).
- 처음 D-415 로 썼다가 main 에 다른 세션의 D-415(콘솔 운영 가시성)가 먼저 들어와 D-419 로 번호를 바꿨다(D-416·D-417 은 진행 중 브랜치, D-418 은 origin/main). 브랜치 이름은 그대로다.

### Context

- CORE SRS SAF-003은 "Fleet 연결이 끊겨도 CORE는 동작하고, Fleet 명령 수행 중 연결 장애가 나면 `STOP | HOLD | RETURN_HOME | CONTINUE_CURRENT_NAVIGATION`(기본 `STOP`)을 수행한다"고 적는다. D-12는 미션을 Fleet에 두고 Fleet 장애 때 로봇의 안전을 SAF-003에 맡겼다.
- 2026-10-02까지 정책은 **저장만** 됐다: `rosy_default.yaml` `safety.fleet_loss_policy: STOP`, `SafetyManager.fleet_loss_policy`, `GET/PUT /api/v1/safety/limits`, 대시보드 선택 상자. 링크 상실을 판정하거나 정책을 적용하는 코드는 없었다. API Ref §7.6의 "접속 단절 시 SAF-003 정책 적용"은 지켜지지 않은 약속이었다.
- 로봇 쪽 Fleet 링크는 FleetAgent의 WebSocket 하나다(`core_features/fleet_agent/agent.py`). Agent는 `fleet.pairing_token`과 `fleet.hub_url` 또는 `fleet.discovery`가 있을 때만 돌고, WS 오류·종료·송신 실패에 `connected=False`, 1→30 s backoff로 다시 붙는다. 하트비트는 1 Hz이고 앱 수준 수신 시한은 없다(반쯤 열린 TCP는 `websockets` keepalive가 닫는다).
- Fleet 명령은 REST로 온다. Fleet 주행은 `POST /navigation/goal`에 Fleet dispatch 시도 ID를 `correlation_id`로 싣는다(D-316). 대형 follow는 자체 스트림 침묵 HOLD(SWM-004)가 있다.
- `fleet.enabled`(`rosy_default.yaml`)는 어디서도 읽히지 않는다. 지금 페어링된 로봇은 기본값 `enabled: false` 위에 토큰만 얹어 Agent를 돌린다(`deploy/site/README.md`, D-361 `PUT /fleet/link` 계획도 `fleet.*`에 토큰·주소만 쓴다).
- 예약 waypoint `__home__`(WPT-004, NAV-003)은 대시보드에서 저장할 수 있고 SAF-005 배터리 복귀가 이미 `nav.home()`으로 쓴다. 다만 기본으로 만들어지지는 않는다(D-28).

### Decision

1. **적용 범위.** FleetAgent가 설정돼 돌고 있고(`enabled`), **링크가 끊긴 순간** Fleet 주행 목표 — `correlation_id`가 있고 아직 끝나지 않은 `goal()` 목표 — 가 진행 중이었을 때만 적용한다. Fleet 없는 로봇, teleop/MANUAL, 대시보드 로컬 목표, 도킹 스테이징, moving-goal(대형 follow) 세션은 대상이 아니다. 끊긴 **뒤** REST로 들어온 Fleet 목표도 대상이 아니다: 그 요청이 왔다는 것 자체가 Fleet이 로봇에 닿는다는 증거이고, SRS는 "수행 중 연결 장애"만 다룬다.
2. **판정.** "설정됨"은 기동 설정으로 한 번 정한다(빌드 때 Agent 가 켜졌는가 = 토큰 + 주소/discovery). 그 뒤 hello 거부나 `stop()` 으로 Agent 가 꺼져도 그것은 "Fleet 없는 로봇"이 아니라 끊긴 링크다(리뷰 I1). 링크 살아 있음 = Agent `connected`(허브 **WELCOME 뒤에만** True, 소켓만 열리고 hello 가 실패한 재접속은 살아 있지 않다) **그리고** 마지막 허브 수신(`last_rx`, monotonic)이 **링크 신선도** `1 s(하트비트 주기) + fleet.heartbeat_reply_timeout_s + 0.5 s` 이내. 신선도는 판정 시간과 따로다 — 둘을 묶으면 짧은 판정 시간에서 답과 답 사이의 건강한 링크가 끊김으로 읽혀 STOP 이 났다(재리뷰 HIGH). 세션마다 수신은 리더 태스크 하나가 맡아 모든 허브 메시지로 `last_rx` 를 갱신하고, 하트비트 답만 하트비트를 깨운다(EVENT ack 가 쌓이거나 하트비트 시한을 대신 채우지 않는다). 허브는 메시지마다 한 번, 순서대로 답하므로(`fleet/hub/server.py`) 하트비트에 대한 **ERROR 답도 답이다** — 이벤트 행 하나가 상한 허브가 하트비트마다 `TASK_PROJECTION_UNAVAILABLE` 을 돌려줘도 허브는 살아 있고 링크는 유지된다(경고는 60 s 에 한 번). 페어링·세션 오류(`PAIRING_INVALID`·`SESSION_NOT_PAIRED`·`DUPLICATE_IDENTITY`·`IDENTITY_DRIFT`·`PROTOCOL_UNSUPPORTED`)가 **하트비트에 대한 답**이면 세션을 즉시 끝낸다(`PAIRING_INVALID` 는 무엇에 대한 답이든). EVENT 에 대한 ERROR 는 이벤트 거부로 기록하고 세션을 이어 간다 — 허브는 검증하지 못한 EVENT 에도 `SESSION_NOT_PAIRED` 로 답한다(`hub.py` `_event`). 인코딩할 수 없는 이벤트(버스가 검사하지 않은 JSON 밖 데이터)는 로그를 남기고 버린다 — 버퍼 맨 앞에 남기면 모든 세션이 죽는다(라운드 4)(라운드 3 HIGH: ERROR 를 무시하면 허브 하나의 손상이 사이트의 모든 Fleet 주행을 STOP 시킨다). hello 답 시한은 D-407 의 5 s(`HELLO_TIMEOUT_S`) — 링크는 WELCOME 전까지 끊긴 것이라 SAF-003 판정에 영향이 없다. 착지 때 main 의 D-407 수신 루프(답마다 하나의 리더, 거부된 EVENT 는 `EVENT_NOT_AUDITABLE` 이면 버리고 다른 코드면 최대 3 번 재전송, 세션이 끝날 때 답 없는 이벤트는 버퍼 앞으로)와 합쳤다 — 이 ADR 의 답 시한·신선도·backoff·치명 코드 규칙은 그 리더 위에 있다. Agent 는 하트비트(1 Hz)의 답을 `fleet.heartbeat_reply_timeout_s`(기본 2.0 s, 0.5–10 s) 안에 받지 못하면 소켓 transport 를 즉시 끊는다 — 반쯤 열린 TCP 도 몇 초 안에 끊김이 된다(리뷰 I2). 재접속 backoff 는 세션이 하트비트 답 3 개를 연속으로 받은 뒤에만 1 s 로 돌아간다 — 환영만 하고 답이 늦는 허브에 1 s 간격으로 다시 붙지 않는다. 단절은 마지막 허브 수신 시각부터 잰다. 끊긴 첫 판정 때 진행 중이던 Fleet 목표를 기억하고, 같은 목표가 진행 중인 채로 `safety.fleet_loss_timeout_s`(기본 5.0 s, 4–60 s, 그리고 `1 + heartbeat_reply_timeout_s + 1` 이상 — 아니면 기동 실패) 동안 계속 끊겨 있으면 정책을 **한 상실에 한 번** 적용한다. 취소가 그 목표를 찾지 못하면(판정과 취소 사이에 끝나거나 바뀜) 아무것도 하지 않는다: `applied: NONE`, `reason: goal_changed`, 귀환도 HOLD 기록도 없다(리뷰 I3). 그 사이 목표가 끝나거나 바뀌면 아무것도 하지 않는다. 시계는 벽시계(monotonic)다 — 네트워크 단절은 sim time 에서도 실제 초로 잰다. 판정기는 ROS 무의존 `core_features/safety/fleet_loss.py` `FleetLossMonitor`이고, `ros_bridge`의 5 Hz power 타이머가 `tick()`을 부른다(50 Hz `select_output` 경로 밖).
3. **정책별 의미.** 모두 래칭 e-stop을 걸지 않는다(SAF-001과 구별).
   - `STOP`(기본): Fleet 목표를 취소한다(`nav.cancel(source="fleet_loss", correlation_id=…)` — 판정과 취소 사이에 바뀐 목표는 건드리지 않는다). 로봇은 선다. Fleet에게 그 시도는 끝난 것이다.
   - `HOLD`: 로봇 동작은 `STOP`과 **같다**(같은 취소). 차이는 기록뿐이라고 정직하게 정한다: 목표(`correlation_id`, x, y, yaw)를 `held_goal`로 보관해 `safety.fleet_lost`·`safety.fleet_restored`·`GET /safety/state`에 싣는다. **자동으로 재개하지 않는다** — 재개는 새 명령(Fleet이 같은 시도를 다시 보내거나 운영자가 목표를 다시 줌)뿐이다. Fleet에게 그 시도는 "멈춤, 재개 가능"이다. 보관은 재접속 이벤트를 낸 뒤 지운다.
   - `RETURN_HOME`: Fleet 목표를 취소하고 `nav.home(source="fleet_loss")`로 `__home__`에 간다. SAF-005 복귀와 같은 지역화 문(D-395: `LOCALIZED`가 아니면 내지 않음)을 지난다. `__home__`이 없거나 지역화가 안 됐거나 목표가 거부되면 **선 채로 남고**(`applied: STOP`, `reason: home_unavailable: …`) e-stop은 걸지 않는다. 귀환 목표에는 `correlation_id`가 없어 이후 판정 대상이 아니다.
   - `CONTINUE`(`CONTINUE_CURRENT_NAVIGATION`): 목표를 그대로 둔다. 이벤트만 낸다. 끊긴 동안 들어오는 새 Fleet 목표는 막지 않는다(결정 1과 같은 이유).
   - 알 수 없는 값: `STOP`으로 적용하고 `reason: unknown_policy`. 기동 때 저장값을 정규화한다(`CONTINUE_CURRENT_NAVIGATION`→`CONTINUE`, 모르는 값→`STOP` + 경고 로그).
4. **이벤트(API Ref §8).** 행동을 마친 뒤 낸다. `safety.fleet_lost`(warning) `{policy, applied, activity, correlation_id, goal, disconnected_s, reason}` — `applied`는 실제로 한 것(`STOP|HOLD|RETURN_HOME|CONTINUE`, 행동이 예외로 실패하거나 취소가 목표를 찾지 못하면 `NONE`). 같은 상실 뒤 링크가 돌아오면 `safety.fleet_restored`(info) `{applied, correlation_id, disconnected_s, held_goal}`. 취소는 기존 `nav.canceled {source: "fleet_loss", correlation_id}`로도 보인다. 끊긴 동안의 이벤트는 FleetAgent 버퍼에 쌓였다가 재접속 hello 뒤 재전송되므로 Fleet은 원인과 결과를 둘 다 받는다.
5. **상태.** `GET /api/v1/safety/state`에 선택 필드 `fleet_link` `{configured, connected, lost, timeout_s, applied, correlation_id, disconnected_s, held_goal}`. 상태 스냅샷(`StateSnapshot`)·하트비트에는 넣지 않는다 — 스냅샷 계약을 늘릴 근거가 아직 없고, 끊긴 링크로는 하트비트도 못 간다.
6. **`RETURN_HOME` 설정은 거절하지 않되 경고한다.** 권고안은 "home 이 정의돼 있지 않으니 PUT에서 거절하고 기존 값은 STOP으로"였다. 사실 확인 결과 home은 `__home__` waypoint로 **정의할 수 있고** SAF-005가 같은 경로를 쓴다. 그래서 PUT은 지금처럼 네 값을 모두 받고, home이 없을 때의 결과(선 채로 남음)를 적용 시점에 이벤트로 알린다. `RETURN_HOME` 을 고르는 PUT 은 로그 경고와 응답 `warning` 문구를 남긴다(아래 Consequences 의 공통 모드 위험). 저장 시점에 `__home__` 존재를 검사하지 않는다 — waypoint는 나중에 지워질 수 있어 그 검사는 거짓 안심을 준다.
7. **`fleet.enabled`는 고치지 않고 "읽히지 않음"으로 문서화한다.** 이 키를 존중하면 기본값 `false` 위에 토큰만 얹은 기존 페어링 로봇의 Agent가 모두 꺼진다. Agent의 스위치는 승인된 `pairing_token`(+ 주소)이고, 그 규칙은 API Ref §7.6이 이미 적는다. 키 제거는 설정 파일·예시 정리와 함께 따로 한다.
8. **계약 버전.** API Ref v1.86(additive; 처음 v1.80 으로 썼으나 main 이 v1.80(D-407 관제 재실행)·v1.81(D-421)·v1.82(D-403 정리)·v1.83(D-411 A)·v1.84(D-422)·v1.85(D-413 Cell 목표 증거)을 먼저 써서 착지 때 v1.86): §5.5 `safety/state`·`safety/limits` 설명, §7.6 판정 규칙, §8 두 이벤트, 변경 이력. envelope `protocol_version` 1.0 유지. SRS SAF-003은 문구를 두고 이 ADR을 가리키는 줄만 더한다.

### Consequences

- SAF-003이 처음으로 실제 동작을 갖는다. 기본(`STOP`) 로봇은 마지막 허브 수신 뒤 5 s 동안 Fleet 링크가 끊겨 있으면 Fleet이 보낸 주행만 멈춘다. 운영자가 대시보드에서 준 목표나 teleop은 영향이 없다.
- `HOLD`와 `STOP`은 로봇 위에서는 **물리적으로 같은 정지**다. 차이는 Fleet과 운영자에게 남는 기록(재개 가능한 시도인가)뿐이다. 둘을 물리적으로 가르려면(예: 끊긴 동안 새 로컬 목표 거절) 별도 결정이 필요하다.
- **`RETURN_HOME` 은 사이트 전체의 공통 모드 위험이다.** 사이트 Fleet 하나가 죽으면 이 정책을 가진 페어링 로봇이 **모두 동시에** home 으로 달린다 — Fleet 교통정리(교차로·양보·대형)가 없는 상태에서. 그래서 기본은 `STOP` 으로 두고, `RETURN_HOME` 을 고르는 PUT 에 경고를 붙인다(거절은 하지 않는다).
- 실제 판정 시간: 정책은 **마지막 허브 수신부터 `fleet_loss_timeout_s`**(기본 5 s) 뒤, 5 Hz 틱 한 번 안에 적용된다. 깨끗한 단절(소켓 오류·종료)은 곧바로 끊김이 된다. 허브가 말없이 사라지면(답 하나를 놓침) 다음 하트비트(마지막 수신 뒤 ≤ 1 s)의 답 시한 2 s 가 지나 transport 를 끊고 — 그 무렵 마지막 수신 뒤 약 3 s — 정책은 마지막 수신 뒤 5 s 에 난다. 예전 `websockets` keepalive 의 약 40 s 가 아니다. 건강하지만 느린 링크(답 1.8 s)는 판정 시간 하한 4 s 에서도 끊김으로 읽히지 않는다.
- D-407 차선 막힘의 `console_linked`(관제가 이어져 있는가)도 같은 신선도로 디바운스한다: D-407 의 `linked_within(line_follow.recovery_console_grace_s)`(연결 중이거나 끊긴 지 유예 3 s 이내)이거나 마지막 허브 수신이 링크 신선도 이내면 이어진 것이다. 재접속 깜빡임이 관제 답 대기를 건너뛰고 로컬 복구로 넘어가지 않게 한다.
- Fleet console v1처럼 FleetAgent 없이 REST 폴링만 하는 구성은 로봇 쪽에서 Fleet 링크를 알 신호가 없어 SAF-003 대상이 아니다. 그런 로봇의 안전은 Fleet 쪽 dispatch 제어(D-330)와 로컬 정지 경로에 남는다.
- 대형 follow는 계속 SWM-004 스트림 침묵 HOLD로 지킨다. Fleet이 시작한 follow를 SAF-003에 넣지 않은 이유: follow는 `correlation_id`가 없고, 상대 위치 스트림이 끊기면 이미 0.5 s 단위로 멈춘다 — 두 번째 판정기가 같은 세션을 다투게 하지 않는다.
- 증거: `src/runtime/services/test/test_fleet_loss.py`(판정·정책), `src/runtime/gateway/test/test_fleet_loss_wiring.py`(빌드·REST·상태). 실기·Gazebo 확인은 하지 않았다(호스트 pytest만).
- 검증 범위: 판정 시간·답 시한·둘의 관계를 어기면 **Fleet 링크가 설정된 로봇에서만** CORE 가 기동하지 않는다. Fleet 없는 로봇은 경고 한 줄을 남기고 기본값으로 부팅한다 — 적용 범위 약속(결정 1)대로 Fleet 설정이 Fleet 없는 로봇을 막지 않는다.
- SAF-003 은 **허브 건강이 아니라 링크 생존**을 판정한다. 하트비트마다 치명적이지 않은 ERROR 로 답하는 허브는 링크를 유지하고 SAF-003 은 발화하지 않는다; 그런 허브에서의 배차 실패는 Fleet 쪽 문제다(D-330).
