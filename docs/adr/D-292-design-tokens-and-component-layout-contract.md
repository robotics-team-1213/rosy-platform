## D-292 시각 토큰은 의미·기초 척도·컴포넌트 역할로 나누고 메뉴마다 다시 쌓지 않는다

**Status:** Accepted (2026-09-26). D-254의 닫힌 토큰 전집에 컴포넌트 역할별 간격 토큰 층을 명시한다. 적용과 검증은 웹 UI 범위이며 로봇·장치 수용을 포함하지 않는다.

잇는 결정: [D-82](D-82-oklch.md) · [D-92](D-92-l2.md) · [D-194](D-194-web-shared-components.md) · [D-254](D-254-design-philosophy-and-token-inventory.md) · [D-277](D-277-rosy-brand-colour-tokens.md) · [D-278](D-278-role-based-surface-ux-and-palette-review.md) · [D-280](D-280-calm-intelligence-product-design-philosophy.md) · [D-284](D-284-shared-role-surface-status-component.md) · [D-285](D-285-shared-role-form-layout-and-field-labels.md) · [D-286](D-286-shared-role-readout-layout.md) · [D-287](D-287-shared-role-readback-sections.md).

**Context:**

D-254와 `tokens.css`는 이미 닫힌 색 집합, 4px 기본 간격 척도, 네 모서리 단계, 세 조작 대상 크기, 여섯 글자 단계를 갖는다. 그런데 공통 컴포넌트는 각자 `--space-2`, `--space-3`, `--space-4`를 직접 골라 버튼 안쪽, 폼 사이, 읽기 영역 사이, 상단바 여백을 표현한다. 기초 척도는 통일돼도 그 선택의 의미와 변경 지점은 한곳에 모이지 않았다. 새 메뉴가 기존 컴포넌트를 쓰면서도 간격·패딩을 화면마다 다시 정할 여지가 있다.

동시에 모든 그리드·폭·브레이크포인트를 전역화하면 지도, 설정 절차, Fleet 예외 큐처럼 질문이 다른 표면의 작업 문법이 하나의 틀에 갇힌다. 색상도 장미색의 일관성만 강조해 위험·주의·포커스·작업 데이터를 재도색하면 D-82와 D-277 의미 계약을 깨뜨린다.

**Decision:**

1. 디자인 토큰은 세 층으로 관리한다. (a) 의미 토큰: ground, surface, status, series, brand, focus 등 색과 의미의 출처, (b) 기초 척도: 4px 기반 `space`, radius, target, typography, (c) 컴포넌트 역할 토큰: 버튼 안쪽 여백, 필드 안쪽 여백, 폼·액션 간격, 읽기 영역 간격, 셸 여백처럼 반복 컴포넌트가 소비하는 이름 있는 값이다. 컴포넌트 토큰은 기초 척도 또는 의미 토큰을 참조하며 새 원시 색·픽셀 값을 복제하지 않는다.
2. 색상 값의 유일한 출처는 계속 `src/hmi/web/tokens.css`다. D-277의 ROSY 장미색은 워드마크와 현재 위치 표식에만, 빨강은 위험·되돌릴 수 없는 행동에, 호박색은 주의에, 파랑은 포커스와 데이터 계열에 사용한다. 역할이나 메뉴 종류를 색으로 부호화하지 않는다. 색상은 아이콘·라벨·형태·문구와 함께 의미를 전달한다.
3. 기존 색·글자·공간·모서리·터치 크기 토큰을 기준으로 유지하고, 다음 컴포넌트 역할 간격 토큰을 추가한다: `--inset-button`, `--inset-button-primary`, `--inset-button-irreversible`, `--inset-field`, `--inset-tag`, `--inset-grid-cell`, `--inset-chip`, `--inset-evidence-unavailable`, `--gap-button-content`, `--gap-button-detail`, `--gap-grid-cell`, `--gap-actions`, `--gap-form`, `--gap-field-label`, `--gap-readout`, `--gap-readout-mobile`, `--gap-readback`, `--gap-heading`, `--gap-triage`, `--gap-topbar`, `--gap-brand`, `--gap-section`, `--inset-topbar`, `--inset-topbar-focal`, `--offset-readout-mobile`. 값은 현재 화면에서 검증된 값의 별칭이며, 이번 결정은 임의 수치나 새 색을 만들지 않는다.
4. 공통 컴포넌트 CSS만 이 역할 간격 토큰을 소비한다. 표면 레이아웃에서 반복되는 공용 버튼·필드·폼·읽기 영역의 재도색과 크기 재정의를 금지한다. 표면 소유자는 콘텐츠 순서, 지도·표·카드 그리드, 너비, 열 수, 위치, 오버플로우 처리 및 실제 작업에 맞는 반응형 전환을 유지한다. 1px 규칙·테두리는 선이며 공간 척도 대상이 아니다.
5. 새 메뉴/페이지는 메뉴 라벨부터 늘리지 않는다. 먼저 사용자 작업 질문, URL·역할 정책, 표면 소유 모듈을 정하고 기존 4문법 중 하나와 셸을 선택한다. 페이지는 tokens.css를 링크하고 기존 공통 컴포넌트/역할 토큰을 사용한다. 반복되는 표현이 둘 이상의 표면에서 필요해질 때에만 공통 API와 계약 시험을 함께 추가한다. 한 화면 전용 그리드나 넓이는 해당 표면에 둔다.
6. 토큰 집합은 닫힌 상태로 유지한다. 색 의미, 기초 척도 값/단계, 컴포넌트 역할, 크기 이름 또는 공통 부품 API를 추가·변경하려면 근거, 소비 표면, 접근성·반응형 검증, 회귀 게이트가 포함된 ADR을 먼저 추가한다. 기존 클래스에 이름만 다른 별칭을 무한 증식하지 않는다.
7. 접근성·안전 계약은 시각 통일보다 우선한다: 키보드 포커스 식별, 읽을 수 있는 대비, 명시적 비활성 사유, 최소 44px 일반 조작, 되돌릴 수 없는 행동의 구분, 라이브 상태 의미를 유지한다. 색만으로 상태·권한·선택을 전달하지 않는다.

**Alternatives:**

- 기본 `--space-*`만 쓰고 컴포넌트에서 직접 고른다: 값은 제한되지만 의미와 전체 조정 지점이 분산돼 같은 컴포넌트의 패딩이 쉽게 갈라진다.
- 모든 패널/그리드/열/폭/브레이크포인트를 공용 토큰으로 통제한다: 이름상 통일은 커지지만 서로 다른 작업 질문을 같은 레이아웃에 강제하고, 의미 없는 별칭을 늘린다.
- 메뉴마다 별도 색과 컴포넌트 세트를 만든다: 정체성은 구별되지만 역할·상태 계약이 약해지고 공통 개선이 중복된다.

**Consequences:**

`tokens.css`는 의미와 두 치수 층을 제공하고 `components.css`는 재사용 가능한 표현을 소유한다. 메뉴와 표면은 자기 작업 문법을 유지하되 공통 조작의 밀도·색 의미·타이포그래피는 함께 개선된다. 역할 간격 별칭이 실제 간격 변경을 대신하는 마법 값으로 쓰이면 안 되며, 모든 역할 토큰은 기본 척도에 연결돼야 한다. 새 표면을 추가하는 비용은 권한/라우트 등록과 공통 셸·토큰 계약을 함께 만족하는 비용으로 명확해진다.

**Validation:**

- 계약 시험은 역할 간격 토큰의 완전성, 별칭의 기본 척도 연결, 공통 컴포넌트의 역할 토큰 소비, 미정의 토큰 참조를 확인한다.
- 웹 UI 테스트와 dashboard 라우트/자산 시험을 실행한다. Chromium에서 운용·설정 화면을 데스크톱과 좁은 폭으로 확인하며 포커스, 터치 크기, 넘침, 브랜드/상태 의미를 검토한다.
- 이 결정이나 브라우저 검토만으로 ROS-SIM, ARM64 이미지, DEVICE 또는 FIELD 수용 상태를 바꾸지 않는다.
