## D-483 화면 입력이 없는 수신 장비는 요청마다 LCD에 승인 코드를 띄우고, 요청한 기기가 그 코드를 입력해 승인한다

**Status:** Proposed (2026-10-06, 사용자 결정: "승인 코드는 기기에서 보여 주고 태블릿에서 입력", 콘솔 승인과 둘 다 가능, 요청별 LCD 승인 코드)

잇는 결정: [D-456](D-456-lan-receiver-approval-and-persistent-pairing.md)(상대 화면 승인 기본·QR/코드 보조) · [D-193](D-193-login-code-and-credential-lifecycle.md)(로봇 화면 일회용 코드·물리 접근 증명) · [D-433](D-433-one-face-process-owns-lcd-buzzer-lamp.md)(LCD 소유자 rosy-face, CORE hand-over) · [D-361](D-361-site-console-enrolls-robot-by-screen-code.md)(로봇 화면 코드로 사이트 콘솔 등록)

### Context

1. **2026-10-06 실기(Lenovo 태블릿 → rosy-pinky-9dfk, 릴리스 2026.10.06-043).** Native Pilot의 D-456 요청은 태블릿에 4문자 표시 번호를 띄우고 "수신 화면에서 승인하세요"라고 안내한다. 승인은 `POST /api/v1/auth/peer-pairing/requests/{id}/decision`(관리자 세션)뿐이고, 그 화면은 로봇 대시보드(`middleware/ui/robot/peer-approval.js`)다. Pinky의 LCD는 표시 전용이라 로봇 앞에 선 운전자는 승인할 방법이 없다. 이번 시험은 노트북에서 SSH `sudo rosy-login-code --role administrator`로 관리자 코드를 받아 API로 승인해서야 통과했다.
2. **D-456은 이미 보조 경로를 열어 두었다.** 상태 문구에 "상대 화면 승인 기본·QR/코드 보조"가 있지만 코드 보조의 모양은 정하지 않았다.
3. **D-193 로그인 코드는 이 자리를 대신하지 못한다.** LCD 로그인 코드는 부팅마다 한 번(또는 SSH·관리자 발급)이고, 결과는 브라우저 Bearer(168 h)다. D-456 승인 관계(기기 키·재연결·폐기)를 만들지 않는다.
4. **만료된 승인은 다시 승인받아야 한다(D-456 4항).** 기간 제한 승인을 쓰는 현장 태블릿은 주기적으로 재승인이 필요한데, 매번 관리자 콘솔을 거치면 현장에서 못 쓴다.

### Decision

1. **승인 경로는 둘이고 같은 요청을 승인한다.** D-456 요청(`POST /requests`) 하나에 대해 (a) 관리자가 콘솔·대시보드에서 승인하는 기존 경로와 (b) 수신 장비 LCD에 뜬 승인 코드를 요청한 기기가 입력하는 새 경로가 둘 다 열린다. 먼저 끝난 쪽이 이긴다. 결과는 같은 승인 관계 행이며 `approved_by`의 출처만 다르다(`owner` / `screen-code`).
2. **요청마다 승인 코드를 하나 만들고 LCD에만 보인다.** CORE는 요청을 만들 때 승인 코드 6자(알파벳 `23456789ABCDEFGHJKMNPQRSTUVWXYZ`, 약 29.7 bit)를 함께 만들고, 원문은 요청 행의 메모리에만 두고 해시만 비교한다. 응답·상태·`pending` 목록·로그에 원문을 넣지 않는다. 요청 기기에는 기존 4문자 표시 번호만 간다.
3. **LCD hand-over.** CORE는 기다리는 요청이 있는 동안 `/run/rosy-peer-display/approval.json`(디렉터리 `rosy-core:rosy-display` `2750` setgid, tmpfiles 생성, 파일 `0640`)에 `{"requests": [{display_code, approval_code, expires_at}, ...]}`(label 없음 — 화면이 쓰지 않는다)를 쓰고, 기다리는 요청이 없으면(승인·거절·취소·만료·정리) 지운다. CORE가 시작할 때 남은 파일도 지운다. 기다리는 요청은 최대 3개이고(4항) 가장 최근 것부터 모두 함께 보인다 — 새 요청이 먼저 온 요청의 코드를 가리지 않게 한다(보안 검토 M1·R2). rosy-face는 이 파일을 읽어 "Pair request" 제목 아래 요청마다 "표시 번호  승인 코드" 한 줄을 그리고(LCD 카드 글꼴에 한글이 없어 ASCII), 원문을 로그에 쓰지 않는다. 요청한 기기는 자기 표시 번호 옆의 코드를 입력한다. 기존 `face-inputs.json`(`0644`)에는 넣지 않는다 — 승인 코드는 D-193 로그인 코드와 같이 읽는 쪽을 rosy-display로 좁힌다.
4. **입력은 요청 비밀로 묶는다.** 새 경로 `POST /api/v1/auth/peer-pairing/requests/{id}/confirm`(인증 없음, `X-Request-Secret` 필요, 본문 `{approval_code}`)가 상수 시간 비교로 맞으면 그 요청을 승인한다. 요청당 5회 틀리면 그 요청은 `rejected`가 된다. 기존 출처별 속도 제한(분당 30회)을 같이 쓰고, 요청 취소(`DELETE`)도 같은 한도에 센다. 살아 있는 pending 요청은 LCD 목록과 같은 3개까지만 받고(끝난 요청은 세지 않는다), 한 출처는 동시에 2개까지만 기다리게 한다(보안 검토 M1·R2). 알려진 한계: LAN 출처 둘이 3자리를 계속 채우면 새 요청은 받지 못한다 — 그 호스트를 찾아 막거나 콘솔에서 거절한다. 끝난 요청은 대기 한도에 세지 않으므로, 출처별 한도와 별도로 모든 출처를 합친 틀린 코드 예산을 둔다. 10분에 20회를 넘기면 그 창이 지날 때까지 `confirm`은 맞는 코드에도 429(콘솔에서 승인하라는 안내)를 돌려주고, 콘솔 승인은 그대로 된다(보안 검토 N1). 상태 조회용으로 보관하는 요청 행은 보관 시간(600초)이 끝나기 전에는 승인되지 않은 끝난 요청만 먼저 비운다. 요청 비밀이 없으면 코드를 맞혀도 다른 기기의 요청을 승인할 수 없다.
5. **화면 코드로 생긴 승인의 수명은 168 h, 지속 승인이 아니다.** 물리 접근 증명은 D-193 `pair-physical`과 같은 무게로 보고, 관리자 콘솔의 기간 제한 승인과 같은 168 h를 쓴다. D-456 4항(짧은 세션이 무기한 권한을 만들지 않는다)을 지킨다. 지속 승인은 지금처럼 카드·수동 관리자만 만든다. 만료 뒤에는 같은 경로로 다시 승인받는다(LCD 코드 한 번). 관계의 발급자 확인(`_grant`)은 출처 `screen-code`에 대해 발급자 토큰을 찾지 않고, 관계 자체의 만료·폐기·수신 키만 본다. 관계 행은 `approved_at`을 갖고, 모델이 `expires_at - approved_at ≤ 168 h`·`persistent=false`·수신 키 지문 `issuer_digest`를 강제한다. 토큰 id `screen-code`는 예약어라 수동·카드 토큰으로 읽지 않는다. 168 h 재승인이 관계 상한 128개를 채우지 않도록, 상한에 닿으면 만료되었거나 폐기되었고 살아 있는 자식 세션이 없는 관계를 지우고 감사 행(`relationship_pruned`)을 남긴다(보안 검토 M2).
6. **Pilot.** 수신 승인 대기 대화상자에 "로봇 화면의 승인 코드" 입력칸을 둔다. 입력하면 `confirm`을 부르고, 그사이 콘솔 승인으로 끝나도 기존 상태 폴링이 이를 받는다. 입력칸이 없는 옛 앱은 콘솔 승인만 쓴다. 옛 CORE(새 경로 404)에서는 입력칸을 "이 로봇은 콘솔 승인만 지원합니다"로 바꾼다.
7. **역할은 operator 고정.** 화면 코드는 요청에 적힌 역할 그대로 승인하며, 요청 역할이 `operator`를 넘으면 `confirm`은 403이다. 관리자 승격은 콘솔 경로로만 한다.

### 범위 밖

- 지속 승인을 화면 코드로 만드는 일. 사이트 콘솔(D-361)과 Rosy Cam 등 다른 연결 주체의 자격 수명은 각 ADR이 정한다. 이 경로는 D-456 요청을 쓰는 모든 앱(Pilot, 이후 Cam·Console 피어 요청)에 같이 적용된다.
- LCD가 없는 보드. LCD가 없으면 콘솔 승인만 남는다(콘솔 배너에 같은 코드 행을 띄우는 일은 후속).

### 검토한 대안

- **D-193 로그인 코드를 요청 때 다시 띄우기.** 8자 입력창은 이미 있지만 결과가 168 h Bearer라 D-456 관계(키 재증명·폐기·재연결)가 생기지 않는다. 요청과 코드가 묶이지 않아, 근처의 다른 기기가 먼저 입력할 수 있다. 사용자가 고르지 않았다.
- **LCD 버튼/터치로 승인.** Pinky LCD는 입력이 없다.
- **`face-inputs.json`에 코드 넣기.** `0644`라 로봇의 모든 로컬 사용자가 읽는다. 로그인 코드와 같은 수준으로 좁혔다.

### Consequences

- 현장 태블릿은 관리자 없이 로봇 앞에서 연결·재승인할 수 있다. 콘솔 승인은 원격·대량 작업용으로 남는다.
- CORE(요청 행·`confirm`·hand-over 파일), rosy-face(카드), tmpfiles, Pilot Android(입력칸), API Reference 행이 바뀐다. 로봇에 닿으려면 서명 릴리스가 필요하다.
- 롤백: D-483 이전 릴리스의 관계 모델은 `screen-code` 출처와 `approved_at`을 모른다(Strict, extra 금지). 소유자 승인 행에는 `approved_at`을 쓰지 않아 그대로 읽히지만, 화면 코드로 생긴 관계 행이 overlay(`auth.peer_pairing.grants`)에 남아 있으면 이전 릴리스가 관계 저장소 전체를 거부한다. D-483 이전으로 되돌릴 때는 그 행들(`issuer_source: screen-code`)을 overlay에서 먼저 지운다.
- 화면 코드 행의 `approved_at`이 지금보다 60초 넘게 미래이면 사용 시점(`_grant`·세션 발급·HTTP/소켓 세션 확인)에 거부한다.
- 수용 기준: SOURCE — 코드 원문이 응답·목록·로그에 없음, 틀림 5회 거절, 요청 비밀 없이 승인 불가, 콘솔·코드 경합에서 한 번만 승인, 만료·취소 때 hand-over 파일 삭제, 화면 코드 관계의 수명 168 h·`persistent=false`. DEVICE — 9dfk LCD에 코드가 뜨고 태블릿 입력으로 연결, 콘솔 승인도 그대로 동작.

### 2026-10-09 실기 보완 — LCD에 CA 확인 값, hand-over 디렉터리

1. **hand-over 디렉터리.** 릴리스 055의 9dfk·8kcn에 `/run/rosy-peer-display`가 없었다. 페이로드 릴리스는 이미지의 `/etc/tmpfiles.d`를 바꾸지 않고, 이미지 계층 동기화는 `/var/lib` 허용 목록만 만든다. 그래서 CORE는 `FileNotFoundError`를 한 번 경고하고 LCD에는 코드가 뜨지 않았다(화면 코드 경로 전체 불능, 콘솔 승인은 동작). `rosy-core.service`가 시작마다 root `ExecStartPre=+install -d -m 2750 -o rosy-core -g rosy-display`로 만든다. 단위 파일은 이미지 계층 동기화가 옮기므로 이전 카드도 다음 릴리스와 CORE 재시작 한 번으로 고쳐진다.
2. **LCD가 CA 확인 값을 보인다.** 처음 연결하는 태블릿은 승인 뒤 수신기의 TLS CA 지문을 사람이 대조해야 고정한다(D-456 2026-10-05 절, D-341). 콘솔 승인은 대시보드가 지문 전체를 보이지만 LCD 경로에는 대조할 화면이 없었다. 화면 코드만으로는 중간자가 자기 요청으로 바꿔 끼우는 것을 막지 못한다. CORE는 `approval.json`에 검증된 `tls_ca_sha256`을 함께 쓰고, rosy-face는 코드 줄 아래에 앞 16자리를 `CA xxxx xxxx xxxx xxxx`로 그린다. Pilot은 승인 대기 대화상자에 같은 16자리를 보이고 코드를 입력하기 전에 대조하게 한다 — 승인 뒤에는 LCD 카드가 사라지기 때문이다(검토 HIGH). 대시보드 승인은 전체 64자리를 대조한다. 한계: 지문은 고정·공개 값이라 공격자는 앞 16자리가 같은 CA를 오프라인으로 미리 만들 수 있고, 비용은 로봇당 약 2^64 SHA-256(GPU 수십 년)이다. 교실·현장 LAN 위협 모형에서 받아들인다. 더 필요하면 요청에 묶은 값(`SHA-256(ca ‖ request_id)` 앞자리)으로 바꾼다. 이 값은 공개 정보라 `0640` 규칙을 바꾸지 않는다. CA가 없거나 검증되지 않는 수신기는 줄을 쓰지 않는다.
3. **Pilot은 상태와 이유를 늘 보인다.** 찾는 중·발견·승인 대기(표시 번호·남은 시간)·승인됨·연결됨·연결 끊김과, 닿지 않음·승인 시간 만료·거절·로봇 소프트웨어가 오래됨·CORE 준비 안 됨 같은 이유와 다음 행동을 문구로 보인다. 로봇 화면에 `Pair request` 카드가 없으면 그 로봇 릴리스는 화면 코드를 보이지 못하므로 콘솔 승인을 쓰라고 안내한다. 보안 한도(코드 길이·5회·예산·168 h·operator)는 그대로다.
