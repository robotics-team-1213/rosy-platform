## D-446 팔레타이징 앱은 화면의 한 작업 흐름과 박스 전용 Gazebo 수용을 먼저 완성한다

**Status:** Proposed (2026-10-04, 사용자 현황 검토·문서 작성·목표 설정 요청; 완료 목표의 구체화 초안. 코드 구현·운영 배포·실물 구동 및 ROS-SIM 승격은 수행하지 않음)

## 배경

현재 main `f32643ffd`에는 팔레타이징 process wheel, Cell 호환층, Fleet Cell 제안·승인·원장·복구, OMX 로컬 owner와 실행 기반이 있다. 그러나 Rosy Cell 전용 서버·레시피 화면·셋업 마법사와 전체 레시피 종단 수용은 미완료다. 상세한 코드 근거와 검증 구분은 [현황 보고서](../assessments/2026-10-04-palletizing-app-completion.md)에 기록한다.

D-401은 앱의 형식, D-403은 Fleet Cell 경로, D-404는 시뮬레이션 티칭 경계를 정한다. D-413과 D-425/D-427은 책임·소스 구조를 규정한다. 오래된 C1–C6 계획의 초기 미구현 목록은 현재 코드와 다르며, 일부 host 시험의 통과는 현재 Gazebo 수용을 뜻하지 않는다.

현재 레이아웃 시험은 박스를 계획하면서 2 mm 슬립시트를 그리퍼 기하 때문에 거절한다. 이 제약을 완료 흐름 안에서 숨기면 앱을 완성했다고 말할 수 없다.

## 결정 제안

### 1. 최상위 개발 목표

**운영자가 Rosy Cell 화면에서 셀 준비 → 레시피 편집·검증·층 미리보기 → 작업 제안 → 별도 사람 승인 → 실행 상태 확인 → 중단·대조·복구까지 수행하고, Gazebo에서 박스 적재 완료를 독립 관측으로 확인한다.**

표시 이름은 기존 Rosy Cell을 유지한다. 새 포트·REST 경로·권한·프로토콜 필드는 이 ADR에서 만들지 않는다. 구현 전에 기존 API Reference와 D-427 목표 경로를 확인하고 누락 계약만 구체화한다.

### 2. 완료 목표를 세 단계로 나눈다

| 목표 | 완료 조건 | 남는 범위 |
|---|---|---|
| G1 앱 LOCAL | 설치된 앱의 실제 브라우저 흐름으로 셀·레시피 준비, 입력 오류 수정, 저장/재시작, 제안·별도 승인·진행·HOLD·중단·복구를 확인한다. 승인 전 하달, 자기 승인, 오래된 해시, 연결 상실 및 중복 제출이 시험에서 거절된다. | 실제 적재 성공을 주장하지 않는다. |
| G2 박스 ROS-SIM | 두 팔레트·두 층의 박스 전용 레시피가 정식 앱→Fleet→UDS→OMX owner 경로를 완료한다. 독립 최종 위치·오차가 프로파일의 합의된 허용치 안에 있고, stop/fence/seat/응답 유실/재시작/늦은 성공 장애에서 자동 재개·중복 실행·잘못된 점유 해제가 없다. | 원래 C6의 슬립시트는 미완료다. |
| G3 원래 C6·설치 수용 | 슬립시트 취급 도구/공급 방식을 결정하고 원래 두 팔레트·두 층·슬립시트 레시피의 독립 수용 및 실제 설치 산출물 검증을 수행한다. | DEVICE/FIELD는 별도 목표다. |

G2는 원래 C6를 대체하지 않는 중간 수용이다. 슬립시트와 실물을 빼고 전체 완료로 표시하지 않는다. G1·G2·G3의 최종 통과는 구현자 메시지 대신 별도로 지정한 검증 담당의 증거 확인을 필요로 한다.

### 3. 구현 순서와 책임

1. **기준선:** 설치 wheel 회귀, 실제 미구현 목록과 stale blocker 정리. 폴더 이전 wave와 겹치는 경로는 작업 시작 전에 확인한다.
2. **Cell 앱:** 최소 서버, 셀/레시피 불러오기·저장·편집·검증·2D 미리보기. 컴파일은 정본 process를 호출하고 동일한 형식과 해시를 유지한다.
3. **OMX 준비:** 기존 시뮬 pairing·seat·티칭 계약으로 home/프레임/스테이션을 준비한다. 브라우저가 사라져도 운전석을 계속 갱신하지 않는다.
4. **Fleet 연결:** 기존 제안·별도 승인·진행·자원 점유·reconcile/resume/cancel을 앱에 연결한다. UI가 원장이나 grant를 자체 생성하지 않는다.
5. **독립 판정과 장애 수용:** 실제 독립 관측기를 연결하고 정식 실행 경로의 중단·재시작·응답 유실을 확인한다. `SUCCEEDED`와 목표 확인을 구분한다.
6. **박스 종단 실행:** 정상 전체 레시피와 장애 사례의 한 실행 묶음을 남긴다. 이후 슬립시트·설치·실물 목표로 전진한다.

PROCESS는 계산, Cell 앱은 입력·제안 UX, Fleet은 승인·순서·점유·원장, OMX owner는 실행·로컬 정지를 소유한다. 앱 화면 작업과 독립 관측기 작업은 계약을 고정한 뒤 병행할 수 있지만 실행 writer·원장을 복제하지 않는다.

### 4. 증거 묶음

각 수용에는 후보 SHA와 설치 산출물 해시, recipe/cell 해시, Job/PlanBundle, Fleet Mission/Action/attempt 및 이벤트 watermark, OMX phase/readback, 독립 관측 ID·신선도·위치 오차, 장애 입력과 재시작 대조 결과를 함께 남긴다. 공개 기록에는 실제 자격·주소·개인 영상이 들어가지 않는다.

필요한 장애 행렬을 먼저 작성한다. 응답 유실, 중복 요청, seat 충돌, stop/fence 변경, 재시작, 늦은 terminal 결과, 오래되거나 위조된 목표 근거, 그리퍼/관측 실패를 포함한다. 물리 상태가 불명확하면 HOLD/UNKNOWN을 유지한다.

### 5. Gazebo는 모델 PC에서 실행한다

2026-10-04 사용자 지시에 따라 작업 PC 로컬/WSL에서 Gazebo를 돌리지 않는다. D-434에 맞춰 모델 PC를 우선 호스트로 하고 운영 관제 PC는 사이트 스택을 유지한다. 모델 PC의 Isaac 설치와 Gazebo 준비 여부는 서로 다른 사실이다.

첫 G2 수용은 모델 PC에 격리한 검증용 Fleet·Cell 앱·OMX owner·Gazebo를 함께 설치해 현재 같은 호스트 UDS와 literal-loopback Fleet-current 역조회 계약을 보존한다. 작업 PC는 원격 제어·브라우저·결과 열람만 한다. 검증용 원장/자격/소켓/식별자는 운영 Fleet 및 실물 로봇과 분리한다.

준비 단계에서 모델 PC 접속·신원·ROS/Gazebo 또는 시뮬 이미지·자원 여유·설치 후보 SHA·실행 격리·증거 회수를 확인한다. 운영 관제 Fleet에서 모델 PC owner를 직접 원격 하달하는 것은 현재 UDS를 넘어서는 별도 transport 설계가 필요하며, 가드를 완화해 달성하지 않는다. 관제 PC로 시뮬레이션 부하를 옮기는 대안은 역할·응답성 검토 후 결정한다.

## 대안

- **화면만 완성:** UX를 빨리 검토할 수 있으나 실행 결과가 없는 제품 완료로 오해하기 쉽다. G1 준비 단계로만 사용한다.
- **슬립시트까지 한 번에 완성:** 원래 수용 범위를 한 번에 달성하지만 현 그리퍼의 기하 제약과 새 도구 검증이 앱 완료를 막는다. G3으로 분리하는 안을 권고한다.
- **박스 전용 한 흐름 먼저:** 기존 구현을 재사용하고 앱·권한·실행·복구를 함께 검증한다. 이번 제안이다.

## 영향과 한계

- 기존 D-401/D-403/D-404의 형식·승인·시뮬레이션 범위를 유지하고 D-427 목표 경로를 따른다. 예전 `src/site/cell`에 새 process 구현을 되돌리지 않는다.
- 원래 C6를 조용히 축소하지 않는다. G2 완료 후에도 슬립시트 미수용 사실을 표시한다.
- 기존 호스트 시험, 집중 Linux 시험, vendor Gazebo, 설치 산출물, 실물 관측을 구분한다. 넓은 Linux 실패는 freshness/timeout 가드를 제거해 통과시키지 않는다.
- 구현 기간은 첫 실행과 남은 장애 원인을 확인한 뒤 추정한다. 이 ADR은 우선순위와 수용 조건 초안이며 동작 가능한 앱이나 실물 적재 완료를 선언하지 않는다.

## 사용자 결정이 남은 항목

G2를 첫 시뮬레이션 제품 수용으로 분리하는 범위와 G3 슬립시트 취급 방식은 아직 구체적 승인 전이다. 현재 요청에 따라 목표를 문서화했으며, 이 문서만으로 실물 구동이나 운영 배포를 시작하지 않는다.
