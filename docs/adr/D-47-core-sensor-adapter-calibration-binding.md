## D-47 CORE sensor adapter calibration binding

**Status:** Accepted (2026-09-13). This is a software startup contract; physical sensor and motion acceptance remain separate Device/FIELD gates.

**Context:** The absorbed `rosy_control` sensor worker must use the calibration record belonging to the mounted Rosy OS data generation. A ROS parameter readback alone cannot prove that the correct record was used, and silently combining explicit parameters with a record can create an unsafe split profile.

**Decision:** When `control.sensor_adapter.enabled` and `control.sensor_adapter.calibration.required` are both true, CORE loads the snapshot before constructing the worker. The loader requires the exact device, hardware, geometry, sensor, and data-generation context, validates the digest and generation-bound path, and accepts only the seven measured SafetyNode parameters. Explicit parameter values must match the snapshot; conflicts fail closed. The worker remains `sensor_only`, and the existing CORE policy remains the only command authority. The packaged default keeps both switches disabled.

**Consequences:** The Device runtime supplies `ROSY_DATA_GENERATION` and `ROSY_DATA_PATH`; a stale, missing, malformed, or cross-device record prevents worker startup before any ROS node is created. CORE exposes the loaded record's revision and digest for diagnostics, while the worker's applied policy revision continues to label observations. Calibration loading is not an acknowledgement of motor policy adoption.

**Validation / Transition:** Unit tests cover pre-construction loading, parameter conflict, generation mismatch, disabled-path non-access, and default YAML opt-in. Device commissioning must still capture the JSON readback, verify the immutable ARM64 manifest, and complete the stationary sensor and motion gates before enabling the switches.

**References:** [calibration binding plan](../plans/2026-09-13-rosy-os-device-validation-implementation-plan.md), [control absorption results](../plans/2026-09-12-control-absorption-results.md), [Device readback contract](../deployment/raspberry-pi-runtime.md).

### Addendum 2026-10-01 — versioned calibration store, camera and odometry fits, one LiDAR mount, protocol v1

**Status:** Accepted for source (branch `feat/camera-extrinsic-autocalib`). Nothing below is applied on a robot; every value is a candidate until an operator accepts it. Device/FIELD gates unchanged.

**Context.** Three independent measurements put the Pinky Pro C1 nose near scan angle 181–182°, not the 190° in `robot.yaml`/`auto_calib.yaml` (`lidar_yaw_offset: 3.31612558`, hand-tuned from US/LiDAR agreement in a narrow maze; the same 190° is `NOSE_YAW` in `sensing/lidar.py`). **The 190° value is suspect.** Evidence: (a) camera wall-edge fit on the D-379 track session `20260930T133221Z` (D-379 score, pitch 11.8° at 0.067 m): score 20.0 at 180° vs 8.9 at 190°; joint yaw×pitch×height grid peaks at 182°; (b) LiDAR travel direction on straight runs (this addendum's ICP): 8kcn 181.83° ± 0.35 (95 %, 3 runs), 9dfk 181.29° (8 straights, one run); (c) main's independent ICP 180.9° ± 0.4 on 8kcn. CORE line_follow meanwhile used its own hand value (`lidar_forward_deg`, 180 on the device), the D-379 labeller the URDF 180°, and nothing calibrated the camera extrinsics (`camera_height_m`/`camera_pitch_rad` default 0; the NOMINAL profile of D-364 §3 was estimated offline). The existing auto-calibration (calib_node `auto`, startup calibration, certificates) covers LiDAR yaw snap, IMU zero, motion sign, US/IR, radius and round trip — not the camera, not the wheels.

**Decision.**

1. *Versioned store* (`core_common/calibration_store.py`). One immutable JSON record per calibration run: kind (`camera_profile`, `wheel_odometry`, `lidar_mount`), robot (device hostname), created_at, source sessions, method version, values with intervals, content sha256 (`O_EXCL`, never overwritten). Status lives in an append-only `events.jsonl` (candidate → accepted/rejected; accepted but not current reads *superseded*). `current` = the pinned accepted record, else the newest accepted one. Pin = rollback; unpin follows the newest again; rejecting the newest also rolls back. A damaged record (sha or identity mismatch) never becomes current. Robot: `/var/lib/rosy/calibration/<robot>/<kind>/` (`ROSY_CALIBRATION_ROOT` overrides); PC mirror: `data/calibration/<robot>/` (gitignored). Only an operator accepts (`tools/calibration/store_cli.py accept|reject|pin`); no code path accepts.
2. *Consumers* resolve once at start and log the record id + sha or the static source: CORE line_follow LiDAR mount (`core/lidar_mount.py`: accepted `lidar_mount` record > `lidar_yaw_offset` bound through this ADR's sensor adapter > `line_follow.lidar_forward_deg` hand value); `line_observer_node` NOMINAL camera profile (accepted `camera_profile` > `nominal_camera_profile_path` file); bringup wheel geometry (accepted `wheel_odometry` > `rosy_params.yaml` 0.027/0.0961). The static files (`robot.yaml`, `auto_calib.yaml`, `camera_nominal.yaml`, `rosy_params.yaml`, `line_follow.lidar_forward_deg`) are seed and fallback, not a competing source. `camera_detect_node`/`road_observer_node`/`dock_observer_node` keep their explicit `camera_*` parameters (apply = set them from the record). The D-379 labeller (`tools/perception/dataset/geometry.py`) reads `lidar_yaw_offset` from `robot.yaml` instead of the URDF π; `autolabel.py --lidar-yaw-deg` overrides it and `meta.json` records which was used — pass the measured ~181.9° until the robot value is re-accepted.
3. *Stationary camera step* inside the existing startup calibration (`calibration/cmd` → `camera_extrinsic`, mixin `calibration_camera.py`): refuses during calibration motion or when odometry is stale/moving, holds zero, captures ≥10 scans and ≥5 frames for 3 s, aborts if odometry drifts > 5 mm / 1°. The fit (`sensing/perception/camera_extrinsic.py`, ROS-free) aligns LiDAR wall contacts (bright wall over carpet) and 0.155 m wall tops with the image's vertical brightness edges, using the configured `lidar_yaw_offset`; pitch and roll always, lens height only when its score band is narrower than 2 cm (else the base height is kept); an optimum on a search bound or a score not ≥ 2.0 above the base profile is *not recommended*. It also reports the yaw the camera prefers (`lidar_yaw_check`). Output: `<result_path>.camera_candidate.json` (the `camera_nominal.yaml` keys + `roll_rad`, revision, source, score, uncertainty) and a candidate `camera_profile` record. The node's parameter `camera_extrinsic_profile_path` must name the base intrinsics (installed `pinky_pro/config/camera_nominal.yaml`); empty refuses the step.
4. *Odometry against LiDAR* (`sensing/odometry_fit.py`, ROS-free): per constant-command segment, point-to-line ICP of every scan against the segment's first scan (the rest-phase scan), seeded by the LiDAR's own previous increment — never by the odometry under calibration, so a scaled or mirrored odom cannot bias it. A 360° LiDAR in a static room keeps the whole turn in view, so full pivots have no chained drift (the earlier chained correlative estimate, 0.984/1.032, drifted ~3 %; keyframe ICP gives odom/LiDAR 1.0048 and 1.0040 for the same pivots). Straight travel uses |t| (a wrong mount yaw cannot shorten it by the cosine; 190° under-read it by 1 %). Least squares through the origin: ds = r·(φR+φL)/2 on straights → `wheel_radius`; dθ = (r/b)·(φR−φL) → `wheel_separation`; standard errors from residuals; per-wheel radii from all segments; actual/commanded per speed; LiDAR nose from the travel direction; absolute rotation sign cross-checked between command, LiDAR, odometry and camera optical flow (a CCW pivot moves the image right).
5. *Protocol v1* (`tools/calibration/run_calibration.py`, one command, several robots in parallel, `--dry-run`, `--offline SESSION…`): pair by login code, MANUAL, optional CORE calibration-session start/stop (`--session-api`; 404/405/501 tolerated — `feat/calibration-session-mode` has no API yet), `~/rosy_rec.sh` recording over SSH, then at 10 Hz through `/api/v1/teleop` within the robot's limits:

   | step | motion | why |
   |---|---|---|
   | rest 8 s | none | static reference scan (keyframe), stationary camera views |
   | 4 × (+L, rest 2 s, −L, rest 2 s), L = 0.24 m at 0.03 m/s | straights | wheel radius, LiDAR yaw from travel, per-straight repeat spread |
   | +360°, rest 3 s, −360°, rest 3 s at min(0.2, limit) rad/s | full pivots | separation (angular, scale-free), left/right |
   | ±90° at 0.1/0.2/0.3 rad/s up to the limit | gain steps | speed-dependent angular gain (above the limit CORE clips; not sent) |
   | ±L at 0.06 m/s when the limit allows | fast straights | speed-dependent linear gain / slip |
   | rest 5 s | none | end reference |

   Guard: a straight aborts when a return within ±25° of its direction of travel is < 0.20 m; a pivot when anything (beyond the 8 cm chassis) is < 0.15 m; a scan older than 0.5 s aborts; zero is always sent last (CORE's 500 ms teleop deadman is the backstop). Scene: a static bay with ≥ 3 walls in LiDAR view, one perpendicular to the straights 0.3–1.2 m away, track walls (0.155 m, top in the image) in front of the camera at the rest poses; nothing moves during the run. Repeat rule: repeat the whole protocol when the per-straight radius spread > 1.0 % or the full-pivot turn-gain spread > 0.5 % (max 2 repeats), then report failure. Time: 4.3 min of motion at L0 (0.03 m/s, 0.1 rad/s) + ~1.5 min pairing/recording/pull ≈ 6 min per robot. The mount yaw for the guard is explicit (`--lidar-yaw-deg`) or the accepted `lidar_mount` record; `robot.yaml` only with a SUSPECT warning.
6. *Apply* (operator, per robot, after review): `store_cli.py list <robot>` → `accept <robot> <kind> <record> --actor <name>`; copy `data/calibration/<robot>/` to the robot's `/var/lib/rosy/calibration/<robot>/` (sudo); restart CORE/bringup/line_observer and read their start log line naming the record and sha. Rollback: `pin <robot> <kind> <older-record>` or `reject` the newest. The camera candidate of the stationary step is a JSON beside the calibration result and a store candidate; it never changes a running node.
