## D-543 UI는 화면의 목적과 작업 전환 이유를 먼저 설명하고 공간을 그 목적에 배분한다

**Status:** Accepted (2026-10-09, 사용자 요청으로 설계 기준 확정; 개별 화면 구현·G1/G2/G3 수용은 별도).

잇는 결정: [D-153](D-153-ui-ux.md) · [D-280](D-280-calm-intelligence-product-design-philosophy.md) · [D-396](D-396-uiux-consistency-goal-system.md) · [D-439](D-439-task-oriented-web-app-design.md) · [D-461](D-461-task-first-workspace-compositions-and-learning-ux.md) · [D-493](D-493-fleet-console-map-first-layout.md) · [D-501](D-501-fleet-document-tabs-and-operator-wording.md).

### Context

ROSY의 디자인 철학과 토큰·문법·상태 평가 체계는 있지만, **왜 이 작업들이 한 화면 또는 한 탐색 줄에 놓이는지**를 판정하는 규칙은 약하다. Fleet의 `/console`, `/console/install`, `/console/site-map`, `/console/cell`은 D-501에 따라 동등한 네 탭으로 보인다. 실제로는 관제, 설치, 현장 지도 작성, 팔레타이징 Cell 작업 준비라는 서로 다른 시간·역할·결과의 작업이다. `/console`과 설치 화면의 `설정`은 접속·역할·테마를 담아, 로봇 설정이나 사이트 설정으로 오해하기 쉽다. 기존 G1/G2/G3는 화면의 상태와 외형을 검증할 수 있지만 이런 정보 구조의 이유와 작업 완료 경로를 기록하는 필수 입력은 아니다.

### Decision

1. **작업 카드가 레이아웃보다 먼저다.** 모든 활성 화면과 주요 하위 작업은 대상 역할, 시작 상황, 첫눈에 답할 질문, 주 동작, 완료·실패의 확인 근거, 다음 안전한 작업, 복귀 위치를 한 장에 적는다. 이 칸이 비면 레이아웃을 승인하지 않는다. 등록부의 앱 단위 `grammar`만으로 서로 다른 문서의 목적을 대신하지 않는다.
2. **같은 제품과 같은 작업을 구분한다.** Fleet와 Cell은 같은 사이트 서비스·인증·작업 원장을 공유하므로 연결된다. Fleet 관제는 로봇과 현장 작업의 상태·예외를 판단한다. Cell 문서는 팔레타이징 구성·미리보기·제안·승인 후 진행을 다룬다. 연결은 `Cell 작업 준비 → 제안/승인 → Fleet 실행 상태 확인`처럼 실제 인계가 있을 때 목적과 가져갈 대상·상태를 함께 밝힌다. 동등한 탭을 유지하는 D-501 결정은 그대로이며, 탭만으로 이 인계를 설명했다고 간주하지 않는다. 탭 재구성은 별도 결정과 사용성 검증을 거친다.
3. **이동에는 이유가 있어야 한다.** 전역 탐색은 위치를, 맥락 링크는 작업의 다음 단계를 뜻한다. 둘을 섞어 보이지 않는다. 관련 기능을 옆에 나열했다는 이유만으로 연결하지 않는다. 이동 뒤 사용자가 기대하는 대상, 사라지거나 유지되는 입력, 돌아올 경로를 표시한다. 권한이 없거나 증거가 없으면 이유와 안전한 대안을 보인다.
4. **설정의 소유자와 범위를 이름에 담는다.** 계정·접속·역할, 화면 표시, 사이트 장치 설치, 로봇 로컬 설정은 다른 작업이다. Fleet 머리의 현재 `설정`은 접속·역할·테마가 섞인 메뉴라는 사실을 평가 결함으로 기록한다. 개편 시 실제 항목의 소유·효과를 드러내는 이름과 그룹을 쓰며, Fleet가 로봇 로컬 설정을 소유하는 것처럼 보이지 않게 한다. 새 API·권한은 이 결정으로 만들지 않는다.
5. **공간은 판단 비용에 비례한다.** 첫 화면에는 현재 상태·근거·가장 중요한 다음 동작·안전을 둔다. 지도·영상은 위치/경로 판단이 주 과제일 때만 큰 면을 차지한다. 목록은 선택·비교에 필요한 정보와 동작만 먼저 보이고, 설정·원시 진단·드문 동작은 문맥 안에서 펼친다. 나란한 영역은 같은 목적이면 동등한 폭, 다른 목적이면 목적과 주 동작에 맞는 비율을 쓴다. Fleet 관제의 지도:개입 3:2는 D-493의 현행 예외로 유지하되, 실제 첫 화면에서 지도와 개입이 모두 판단 가능한지 검사한다. 숫자 비율이나 카드 수를 새 공통 토큰으로 만들지 않는다.
6. **평가에서 수용까지 한 줄로 추적한다.** `docs/plans/2026-10-09-uiux-purpose-and-layout-pipeline.md`의 작업 카드·평가표로 목적과 경계를 먼저 진단하고, 한 작업 흐름씩 개선한다. SOURCE 진단, 로컬 브라우저 G1/G2/G3, 실제 설치 이미지, 현장 사용자 작업·장치 확인은 각각 구분해 기록한다. D-153의 UI/UX GO를 이 점수표가 대체하지 않는다. 안전·권한·증거 정직성 위반은 합계와 무관하게 HOLD다.

### Alternatives

- **기존 네 탭과 `설정`을 그대로 두고 색·간격만 조정:** 현재의 이동 이유와 소유 범위 문제를 풀지 못한다.
- **Cell을 별도 제품과 인증 체계로 분리:** 현재 사이트 작업 원장과 승인 흐름의 연속성을 끊고 새 권한·운영 부담을 만든다.
- **Fleet·Cell을 하나의 긴 대시보드로 합침:** 서로 다른 사용 상황을 한 첫 화면에 동시에 밀어 넣는다.

### Consequences and validation

이 결정은 화면 구조 심사의 입력과 우선순위를 정한다. D-501의 탭, D-493의 비율, 기존 API·권한·안전 동작을 즉시 변경하지 않는다. 첫 적용은 Fleet 네 문서와 `설정`의 작업 카드·SOURCE 평가를 남기는 것이다. 이후 화면 변경마다 대표 작업의 시작→행동→결과→복귀를 선언 폭과 상태에서 캡처하고, D-153 G1/G2/G3를 다시 판정한다. 사용자 작업 입회와 현장 설치는 별도 증거다.
