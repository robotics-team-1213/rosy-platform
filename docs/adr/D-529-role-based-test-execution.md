## D-529 시험 실행은 역할별 호스트에 배치하고 커밋별 증거로 판정한다

**Status:** Accepted (2026-10-09, 사용자 지시; 실행기와 현장 수용 증거는 별도 확인)

### Context

D-346과 D-436은 시험의 범위와 시점을 정했지만 실행 호스트는 개발 PC로 남겨 두었다. 원격 main과 차이가 큰 브랜치의 pre-push affected 검사는 이 Windows PC에서 수천 건을 실행하고, 다른 세션의 작업과 자원을 다툰다. 호스트 pytest 결과만으로 ROS 2, ARM64 설치물, Fleet 현장 상태나 로봇의 물리 동작을 입증할 수도 없다. D-527의 Decision 파이프라인 역시 첫 계약 시험을 개발 로컬 PC에 두었다.

### Decision

1. **개발 PC는 선택과 판정을 맡는다.** 변경 범위 산출, 문서 lint, 커밋·브랜치 정리, 원격 로그 수집을 수행한다. push·착지용 pytest는 개발 PC에서 자동 대체 실행하지 않는다. 원격 호스트가 없으면 해당 시험은 미실행으로 남고 push·착지는 멈춘다. 고장 재현을 위해 로컬에서 단일 시험을 명시적으로 실행한 결과는 보조 증거로만 적는다. D-346·D-436의 시험 목록과 CI 승격 규칙은 유지하고 실행 위치를 바꾼다. D-527의 개발 로컬 PC 계약 시험 위치도 이 결정으로 대체한다.
2. **호스트 소프트웨어 시험은 모델 PC를 우선, AI PC를 대체 실행기로 쓴다.** 착지 또는 push할 정확한 커밋을 격리된 체크아웃에 보내 pytest를 돌린다. Python·패키지 의존성과 자원 제한을 기록하고, 결과 로그에 커밋 SHA·호스트·호출·종료 코드·known_failures의 NEW 여부를 남긴다. AI PC GPU 추론 시험은 승인된 모델 버전과 별도 입력을 사용하고, 일반 pytest 통과로 대신하지 않는다.
3. **현장 서비스 시험은 현장 PC에서 한다.** Fleet·Rosy Cam·천장 카메라의 설치 버전, 실제 등록 DB, 인증·TLS, 영상 시퀀스와 지도 관측을 그 서비스의 실행 사용자와 환경에서 읽는다. 현장 설정이나 자격을 호스트 시험용 체크아웃에 복사하지 않는다. 브라우저 시험은 Chromium이 준비된 현장 PC 또는 모델 PC에서 수행하며, 화면 결과를 확인한다.
4. **로봇 시험은 각 Pinky에서 한다.** 서명된 ARM64 payload와 활성 릴리스 SHA, CORE API의 기체 ID·상태, 센서·정지·명령 응답을 각 장치에서 읽는다. 이동이나 LED를 이용한 몸체 식별은 현장 영상·장치 읽기와 연결된 별도 DEVICE/FIELD 증거로 기록한다. 호스트 또는 브라우저 시험의 녹색을 두 로봇의 설치·이동 수용으로 승격하지 않는다.
5. **릴리스 판정은 증거를 순서대로 결합한다.** 원격 호스트 시험과 CI → 서명된 ARM64 산출물 → 각 장치 설치·API 읽기 → 현장 Fleet·카메라 대조 순이다. 어느 단계에서든 커밋이나 기체가 달라지면 그 뒤의 증거는 같은 릴리스의 수용으로 세지 않는다. D-436의 full tier는 GitHub CI에서 유지한다.

### Consequences

- 원격 실행기의 SSH·의존성·자원 한도가 시험 가용성을 결정한다. 호스트가 모두 닿지 않으면 로컬 자동 fallback으로 녹색을 만들지 않고 사유와 마지막 성공 증거를 남긴다.
- 모델 PC와 AI PC의 pytest는 SOURCE/호스트 계약 증거다. ROS-SIM, ARTIFACT, DEVICE, FIELD는 해당 환경의 별도 결과가 필요하다.
- 진행 중인 원격 실행기 브랜치와 pre-push 훅은 이 결정에 맞게 적용·검증해야 한다. 이 ADR 자체는 실행기 착지, 원격 푸시, 로봇 배포의 완료를 뜻하지 않는다.
