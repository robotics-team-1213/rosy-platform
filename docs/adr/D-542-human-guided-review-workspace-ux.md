## D-542 객체·픽셀 검수는 사진 중심 작업대와 결과 피드백을 공유하고, 사람 표시를 AI 보완의 경계로 쓴다

**Status:** Accepted (2026-10-09, 사용자 지시: 현 화면을 조사한 뒤 배치·표시·조작·AI 보완 원칙을 먼저 결정한다. 이 ADR은 설계 결정이며 화면 구현·모델 PC 적용·사람의 라벨 수용은 별도다).

### 조사와 문제

2026-10-09 모델 PC의 같은 43장 검수 작업 공간을 실제 브라우저에서 객체 `/`와 픽셀 `/pixels`로 열었다. 운영 마스크나 박스를 수정하지 않고 1280×720, 390×800 뷰포트와 현재 소스(`review_app_web`)를 대조했다. 현장 `index.html`·`pixels.html`은 소스와 SHA가 같았고 `app.css`는 토큰 별칭 세 곳만 달랐다. 이 관찰은 현재 화면의 사용성 증거이며 새 정답의 품질 증거는 아니다.

| 관찰 | 1280×720 사진 캔버스 시작 y | 390×800 사진 캔버스 시작 y | 검수 영향 |
|---|---:|---:|---|
| 객체 검수 | 539px | 1,347px | 모바일 첫 화면에 사진이 없고, 박스보다 탐색·도구를 먼저 훑는다 |
| 픽셀 검수 | 610px | 2,153px | 원본·마스크를 보기 전에 선택·썸네일·도구·초안이 긴 열로 쌓인다 |

두 화면은 D-538의 공통 순서와 단축키를 이미 일부 구현했다. `←/→`, `N`, `1–9`, `C`, `A`, `X`, `?`가 코드에 있으므로 “단축키가 전혀 없다”가 정확한 진단은 아니다. 그러나 안내가 접힌 도움말이나 캔버스 아래에 있고, 객체 숫자 키는 박스 선택 전 비활성인데 그 이유가 바로 보이지 않는다. 객체는 자동 저장·박스 수, 픽셀은 255 수·승인 차단 사유를 표시하지만 결과가 사진·현재 행동과 떨어져 있다. 픽셀 AI 의견은 사진 1에서 `판단 보류`와 영어 문장을 보였고, 초안의 출처·적용 전후·남은 클래스별 영역을 한곳에서 설명하지 못했다. 255 색, 클래스 색, 상태 색, 선택 강조가 각각 다른 의미인데 가까운 범례와 글자 없이 색/아이콘만으로 읽어야 하는 순간이 있다. 객체의 `기타 장애물` 같은 현재 클래스 이름도 모델 클래스·검수 클래스·위치 판단을 혼동시키기 쉽다(D-514).

### 결정

1. **사진이 작업의 기준면이다.** 객체·픽셀 검수 모두 `현재 사진/상태 → 사진과 저장된 라벨 → 현재 도구와 초안 → 결과/결정`의 정보 위계를 사용한다. 너비가 충분하면 사진을 주 영역으로 두고 도구와 판단을 옆 칸에 둔다. 좁은 화면에서는 현재 사진과 최소 보기/이동 조작을 먼저 놓고, 클래스·세부 설정·긴 설명·이력·자료 준비는 아래나 접힌 영역으로 보낸다. 동일한 선택 기능을 큰 드롭다운과 43개 썸네일로 동시에 반복해 사진을 밀어내지 않는다. 썸네일은 한 줄 스크롤 또는 접힌 목록으로 제한한다.
2. **세로 공간을 검증 가능한 자원으로 취급한다.** 대표 1280×720과 390×800에서 초기 화면에 사진의 일부와 현재 상태가 동시에 보여야 한다. 목표는 사진 캔버스 상단이 화면 높이의 40% 이내이고, 사진 높이의 최소 3분의 1이 스크롤 없이 보이는 것이다. 접근성 글자 확대·화면 회전·긴 한국어에서도 사진이나 필수 조작이 잘리지 않아야 한다. 높이가 부족하면 보조 제어를 접거나 옆으로 보내며 사진 자체를 지나치게 줄이지 않는다. `compact/medium/wide`는 D-359의 범위를 쓰고, 표면별 CSS만 배치를 소유한다.
3. **같은 위치는 같은 종류의 행동을 뜻한다.** 사진 이동은 양쪽 화면의 같은 자리에서 `이전 / 다음 / 다음 대기`로, 보기 전환과 확대는 사진 곁에서, 클래스와 편집 도구는 캔버스 곁에서, 저장 상태와 승인/제외는 별도 판단 칸에서 보여준다. 객체의 박스 자동 저장과 픽셀의 명시적 초안 저장은 합치지 않고 항상 문장으로 밝힌다(D-538). 위험한 전체 교체·전체 채우기·제외·승인은 미리보기/부분 적용과 시각적으로 분리하고 영향 범위를 버튼 이름에 쓴다.
4. **색과 아이콘은 이름·형태·출처를 보조한다.** 픽셀 클래스 색은 바인딩된 `classes.yaml`, 객체 박스 색은 바인딩된 객체 클래스셋에서만 가져온다(D-485). 선택 색, 대기/승인/오류 상태 색, 미검수 255 색을 클래스 색처럼 재사용하지 않는다(D-359). 저장된 박스는 실선, 미적용 제안은 점선처럼 선 종류도 달리한다. 각 박스/영역의 클래스명·현재 번호 키·출처를 범례 또는 선택 시 근처에 표시하고, 색각·흑백·마스크 투명도 0에서도 의미가 남아야 한다. 아이콘만 놓인 주요 행동에는 보이는 동사와 접근 가능한 이름을 붙인다. `기타`는 현재 셋의 정확한 명칭과 검수용 범위를 설명하며 동일 SHA의 클래스 뜻이나 번호를 화면에서 바꾸지 않는다(D-514).
5. **한 행동 뒤 한 결과를 같은 시야에서 보여준다.** 사진 곁의 결과 줄은 현재 작업(객체/픽셀), 저장/미저장, revision, 초안/사람 수정/승인, 출처와 최신성을 구분한다. 객체는 저장 박스 수·미적용 제안 수·선택 박스 클래스/좌표, 픽셀은 클래스별 픽셀 수·255 수와 비율·방금 바뀐 픽셀 수를 보여준다. 적용 전후는 원본/저장 라벨/미적용 초안을 같은 좌표로 비교할 수 있게 한다. 차단된 승인·저장 실패·충돌은 일반 실패 문구 대신 해당 사유와 다음 행동(예: 255 잔존, 전체 확인 미체크, 오래된 버전, 차선 경계)을 현재 사진 가까이에 보여준다. 빈 박스와 AI의 빈 응답은 “물체 없음 승인”으로 표현하지 않는다.
6. **단축키는 보이는 조작 계약이다.** D-538의 공통 키 `←/→`, `N`, `V`, `1–9`, `C`, `A`, `X`, `?`를 유지하고 이전/다음 버튼과 각 클래스의 번호를 화면에 함께 표시한다. `1–9`는 현재 작업의 화면에 표시된 클래스 순서와 일치하며, 객체는 선택 박스가 없을 때 “먼저 박스를 선택”이라는 이유를 보여준다. 픽셀의 `B`, `T`, `P`, `Enter`, `[`/`]`, `Esc`도 실제 사용 위치에 짧게 표시한다. 되돌리기처럼 빈번한 행동은 키보드 경로와 범위(로컬 획 또는 저장 수정)를 구현 단계에서 정해 명시한다. 입력칸·IME 조합·수정 중 제스처·서버 대기·오래된 revision에서는 키가 예기치 않게 적용되지 않으며 비활성 버튼을 우회하지 않는다. 키보드만으로 사진 이동→라벨 수정→결과 확인→다음 대기를 완료할 수 있어야 한다.
7. **사람 표시가 AI 보완의 입력이자 보호 경계다.** 사용자가 먼저 핵심 박스·영역·차선 경계를 표시하거나 초안을 수정하면, 모델 PC 오프라인 작업은 원본 hash, 현재 클래스셋 SHA, 사람 라벨 revision/마스크 SHA를 묶어 *아직 검수되지 않은 부분*의 후보를 만든다. 픽셀은 검증된 255에만 클래스 후보를 제안하며 기존 0–254를 자동으로 덮지 않는다. 객체는 기존 사람 박스와 중복·충돌하지 않는 누락 후보를 제안한다. 모델이 판단하지 못하거나 출처가 충돌한 부분은 대기로 남긴다. 작업 결과는 `대기/실행 중/후보 있음/기준 변경/실패`와 클래스별 제안·잔여 수, 보호된 사람 라벨 수, 거절 이유, 모델/입력 출처를 보여준다. 현재 review 앱이 모델을 직접 실행하지 않는 D-459 경계를 유지하고, 구현 시 요청·작업 상태의 구체적 API는 별도 계약으로 정한다.
8. **AI 후보 적용과 사람 승인은 분리한다.** 후보는 원본/사람 결과와 비교하고 255만 보완 또는 객체 누락 후보만 선택 적용할 수 있다. 적용 후 남은 255·불일치·경계 위반을 즉시 다시 보여주며 되돌릴 수 있어야 한다. 기준 revision이 변했으면 오래된 후보를 조용히 합치지 않고 재계산 또는 명시적 재검토로 보낸다. AI 자기 평가나 “확신” 표시는 승인 근거가 아니다. 객체·픽셀 승인은 여전히 각각 사람이 전체를 확인해야 하며, 학습 수용과 로봇 주행은 별도 절차다(D-462, D-464, D-465).

### 구현 순서와 수용 기준

1. 공통 작업대 배치와 세로 예산을 먼저 고친다. 양쪽 화면의 사진 위치, 현재 상태, 이동, 도구, 판단 칸을 같은 원칙으로 만들고 desktop/compact/light/dark 실화면을 비교한다. 이 ADR 자체는 화면을 고치지 않는다.
2. 클래스 범례·상자/마스크 표기·키 안내·행동 결과를 붙인다. 객체 0개·선택 박스 없음·픽셀 255 잔존·미저장 획·오래된 초안·서버 충돌을 각각 확인한다. 색만 제거하거나 화면을 흑백으로 봐도 클래스와 상태를 구별할 수 있어야 한다.
3. 사람 표시→오프라인 AI 제안→원본/현재 라벨/후보 비교→부분 적용→남은 영역/실패 피드백→사람 승인 흐름을 별도 테스트 작업 공간에서 걷는다. 객체와 픽셀의 version CAS·독립 승인·클래스 바인딩을 검증하고 운영 데이터를 시험 승인하지 않는다.
4. 검증 증거는 SOURCE/호스트 테스트, 실제 브라우저(1280×720, 390×800 및 키보드), 모델 PC 설치·동작, 사람의 라벨 품질/수정 시간으로 구분한다. 사진이 첫 화면에 보이는지와 단축키가 작동하는지는 브라우저로, 후보 품질은 사람이 수정한 독립 표본으로 판정한다. ADR 또는 테스트만으로 현장 사용성 수용을 선언하지 않는다.

### 대안

- 기존 칸에 문구·버튼만 계속 추가: 일부 설명은 늘지만 사진의 첫 화면 가시성과 행동 위치 문제를 키워 채택하지 않는다.
- 객체·픽셀을 한 편집기로 합치거나 한 번에 승인: 클래스·revision·저장 방식이 달라 D-462/D-485를 깨므로 채택하지 않는다.
- AI가 사람 라벨과 255를 한 번에 덮고 자동 승인: 사람 근거와 불확실성·정답 책임을 잃으므로 채택하지 않는다.
