## D-432 모든 앱·장치는 공통 발견·연결 규약을 쓰고, 개발 모드에서는 코드 없이 연결한다

**Status:** Accepted (2026-10-03, 사용자 승인 — 공통 구조와 ADR 작성). 목표 계약·책임·이행 순서를 승인한 문서 결정이다. 개발 연결 모드, 새 wire 필드, CORE TLS, 주소 자동 전환은 아직 구현하지 않았다. ARTIFACT·DEVICE·FIELD 수용을 뜻하지 않는다.

### Context

앱·로봇·사이트 서버·도크·신호 장치는 상대 IP를 미리 입력하거나 고정하지 않고 연결되어야 한다. 개발 단계에서 연결할 때마다 코드 입력·재페어링을 요구하면 시험 흐름이 끊긴다. 사용자는 개발 모드에서 간단히 연결하고, 이후 코드 기반 상호 페어링을 도입할 수 있는 공통 구조를 요청했다.

현재는 mDNS 광고·검색과 연결 구현이 여러 곳에 나뉘어 있다.

| 경로 | 현재 근거 | 남은 공백 |
|---|---|---|
| 로봇 광고 | `deploy/robot/pinky_pro/native/rosy-boot-status.py`, `_rosy._tcp` | 광고는 실행 가능·신원 증명이 아님 |
| 로봇 → Fleet | `src/runtime/services/core_features/fleet_agent/{discovery,agent}.py` | 이름·CA·자격 선등록 필요; 재시도 무작위 분산 없음 |
| Cam → 사이트 수신 서버 | `src/site/cam/.../settings/{NsdSiteBrowser,OverheadServerDiscovery}.kt`, `link/SiteResolver.kt` | 최초 검색과 재발견의 OS 처리가 다름; 단순 개발 연결 정책 없음 |
| Fleet → 로봇 | `deploy/site/mdns-bridge.py`, `src/site/fleet/fleet/server/address_drift.py` | 평문 CORE에 자격을 보내므로 새 IP 자동 추종 금지 |
| 도크·신호 | `firmware/{dock,signal}`의 ESPmDNS, `core_common/discover.py` | 광고는 구현됨; 공통 유틸리티의 실제 소비 경로·갱신 처리가 미완성 |
| 브라우저 Pilot·대시보드·Console | 기존 same-origin API/WS | 브라우저 자체의 LAN mDNS 검색을 가정할 수 없음 |

D-354는 외부 장치 발견, D-370 §5는 TXT·주소·실패 어휘, D-391은 사이트 연결 저장 모양을 정했다. D-427·D-429의 목표 구조에 맞춰 이를 로봇과 사이트 장치·앱 모두의 공통 계약으로 확장한다. ROS/DDS discovery는 로봇 내부 통신이며 외부 앱 발견과 구분한다.

### Decision

#### 1. 공통 책임과 적용 범위

공통 흐름은 **발견 → 계약 호환성 확인 → 연결 승인 → 세션 수립 → 상태 감시 → 재발견·재연결**이다. 모든 새 연결 경로는 이 흐름을 구현하거나, 물리 링크·same-origin·중앙 디렉터리 예외와 그 근거를 명시한다. 연결 승인은 개발 모드와 운영 모드가 교체하는 정책이다. 앱별로 별도의 등록 체계를 만들지 않는다.

| 책임 | 목표 소유 | 현재 소스·이행 기준 |
|---|---|---|
| 서비스 종류·역할·호환성·신원·실패·연결 기록의 의미와 공유 벡터 | `contracts`, 통신 규약 관심사 | `src/contracts/foundation/core_common/protocol`; Python·Kotlin·JS·펌웨어가 같은 사례를 검증 |
| 로봇의 광고·로컬 연결 수명·외부 gateway | `middleware` | CORE와 robot deploy; 외부 앱이 ROS/DDS로 직접 붙지 않음 |
| 사이트 디렉터리·등록·연결 승인·자격 회수 | `operations`의 Fleet | `src/site/fleet`; 장치 제어 owner는 D-429대로 역할별 유지 |
| Avahi·Android NSD·Bonjour·ESPmDNS·HTTP/WS/TLS 구현 | `integrations` 및 장치별 전송 binding | 현재 위치에서 어댑터로 정렬; OS 구현이 연결 권한을 판정하지 않음 |
| 선택·상태·오류·재시도 표시 | 각 앱·표면 | 같은 의미·실패 분류를 사용; native는 OS discovery, 웹은 소유 서버의 디렉터리 사용 |

이는 논리적 소유권이다. 이 ADR만으로 폴더를 옮기거나 새로운 중앙 통신 프로세스·브로커를 설치하지 않는다. USB·serial·BLE 장치는 해당 링크 어댑터로 같은 연결 모델에 참여한다. 유선 연결에 mDNS를 억지로 추가하지 않는다. 제3자 장치는 전용 어댑터가 호환성과 역할을 확인한다.

#### 2. 주소 대신 장치·서비스의 정체성을 보관한다

- 주소·포트·인터페이스는 수명이 있는 **접속 후보**다. DHCP가 바뀌어도 장치 ID는 유지된다. 표시 이름, IP, 서비스 instance 이름만으로 장치 신원을 확정하지 않는다.
- 장치 ID와 서비스 역할을 분리한다. 한 호스트의 Fleet·Vision, 한 장치의 여러 endpoint가 서로 덮어쓰지 않는다. 사이트 소속과 실행 세대도 장치 영속 ID와 구분한다. 재설치·복제 때 영속 ID가 충돌하면 자동 연결을 멈춘다.
- 보관 기록은 기존 `site-link.v1.json`과 방향별 자격 모델을 우선 사용한다. 로봇·사이트 장치에 필요한 확장은 후속 구현에서 공유 벡터로 추가한다. 이 절은 논리 모델이며 새 JSON/TXT 필드 선언이 아니다.
- 광고의 role·proto·port·TLS 요구를 실제 endpoint의 기존 health/handshake와 대조한다. 발견은 호환성·실행 준비·제어권 확보를 대신하지 않는다.
- 호환성은 계약별 버전 정책으로 판정한다. 알 수 없는 필수 버전·역할은 연결하지 않고 사유를 표시한다. 기존 프로토콜 이름을 바꾸지 않는다.

#### 3. 같은 LAN의 기본 발견은 mDNS/DNS-SD다

기존 `_rosy._tcp`, `_rosy-fleet._tcp`, `_rosy-overhead._tcp`, `_rosy-dock._tcp`, `_rosy-signal._tcp`를 유지한다. 새로운 역할은 서비스 종류·소유·필수 TXT·전송·호환성 정책을 공통 계약에 등록한 후 광고한다. 통신 역할은 사용자 표시 이름과 별개다.

- SRV의 실제 대상·포트와 A/AAAA를 읽는다. instance에서 호스트명을 조합하거나 포트를 `80`으로 추정하지 않는다.
- TXT는 공개 식별·호환성 메타데이터만 담는다. 비밀번호·Bearer·개인정보·페어링 코드·인증서 원문·실시간 상태·영상·명령을 싣지 않는다. TXT 전체 목표는 400 bytes 이하이며 초과는 역할별 근거와 패킷 검증이 필요하다.
- 광고는 설치된 서비스와 실제 listener에 맞춘다. readiness는 기존 health/세션에서 판정한다. 갱신·정상 종료·인터페이스 변경을 반영하고 stale 주소는 세션 성공으로 오인하지 않는다.
- 동일 신원이 서로 다른 장치에서 나타나면 `conflict`다. 먼저 응답한 장치를 선택하지 않는다. 한 장치의 IPv4/IPv6·여러 NIC는 동일 신원 확인 뒤 같은 후보 묶음으로 처리한다.
- 다른 VLAN·WAN에는 사이트 DNS/디렉터리·승인된 overlay 또는 관리된 discovery gateway를 쓴다. 전체 VLAN 간 무차별 reflector와 IP 대역 전체 스캔은 기본값으로 두지 않는다. 수동 주소·QR은 실패 시 대체 경로로 표시하고, 고정 IP를 정상 연결의 전제로 만들지 않는다.
- DHCP·네트워크 가입은 별도 선행 조건이다. 동일 SSID가 동일 LAN을 보장하지 않는다. provisioning AP 노출 규칙은 기존 계약을 유지한다.

#### 4. 개발 연결 모드는 코드 입력을 생략한다

개발 연결 모드의 이름은 `development`, 운영 정책은 `paired`로 기술한다. 이는 **연결 승인 정책**의 논리 이름이며 기존 `ROSY_RUNTIME_MODE=core|motor|hardware`, MANUAL/AUTO, 학습 모드와 독립이다. 정확한 config 키·환경 변수는 구현 단계에서 정하며 현재 설정에 존재한다고 주장하지 않는다.

- 기본은 `paired`다. 배포 담당자가 개발 프로필을 명시적으로 켰을 때만 `development`를 허용한다. 제품 이미지와 운영 프로필은 이를 자동 상속하지 않는다. 발견 실패·인증 실패 때문에 개발 모드로 강등하지 않는다.
- 개발 프로필은 개발 사이트/망 범위와 역할별 연결 권한을 함께 지정한다. 같은 LAN에 있다는 이유만으로 모든 장치를 자동 등록하지 않는다.
- 최초 사용은 **개발 모드 켜기 → 발견 목록에서 장치 선택 → 연결**이다. 격리된 시험 설정이 장치 ID·역할·사이트를 명시했고 유일한 후보인 경우 선택도 생략할 수 있다. 코드 입력과 매 연결 재승인은 요구하지 않는다.
- 개발 자격은 도구가 준비한다. 사이트/작업공간별로 범위를 제한한 credential·신뢰 묶음을 제공하고 앱마다 사람이 토큰을 복사하지 않게 한다. 선택한 장치·역할에 묶어 저장하고, 다른 사이트로 이동하거나 신원이 바뀌면 조용히 신뢰를 바꾸지 않는다.
- 개발 단계의 최초 신뢰는 개발 프로필의 bootstrap/신뢰 설정이 제공한다. mDNS TXT가 인증 근거가 되는 것은 아니다. 연결 상대가 운영 모드라면 개발 모드 클라이언트가 코드 절차를 우회할 수 없다.
- 개발 모드 종료는 개발 연결·자격을 해제하며 운영 자격으로 승격하지 않는다. 정상 세션 수명은 공통 모델을 사용한다. 매번 앱을 켤 때 재페어링하지 않는다.
- 연결 성공은 모터 토크·출력·주행·안전 승인·E-stop 해제를 허가하지 않는다. D-2·D-400·D-419·D-430의 owner·watchdog·래치·수용 조건을 유지한다.

기존 `ROSY_DEV_AUTH`는 개발·시뮬의 공유 인증 설정이지 이 공통 연결 모드가 아니다. D-193의 장치 모드 공용 개발 토큰 거부는 유지한다. 실물 개발 장치용 credential 경로는 장치별/사이트별 범위로 후속 구현한다. 지금 공용 토큰 차단을 제거하거나 설치 장치를 개발 모드로 바꾸지 않는다.

#### 5. 운영 페어링은 같은 흐름의 승인 단계에 붙인다

운영에서는 기존 D-341·D-361의 코드·상호 확인·역할·감사·회수 흐름을 사용한다. 향후 공통 승인 정책을 구현하더라도 기존 페어링 엔드포인트를 새로 복제하지 않는다. 코드는 짧게 유효한 최초 신뢰 수립 수단이며 연결할 때마다 입력하는 비밀번호가 아니다.

확인 후 장치 신원·사이트 신뢰·권한을 보관하고 재연결 시 검증한다. IP 변경은 재페어링 사유가 아니다. 신원 교체·신뢰 회수·사이트 변경·자격 만료는 다시 승인할 사유다. 자격 갱신은 코드 재입력과 별도 정책이며 무기한 Bearer로 단순화하지 않는다. 개발과 운영은 연결 승인만 달라지고 발견·호환성·세션·재연결·실패 분류를 공유한다.

#### 6. IP 자동 추종에는 상대 신원 확인이 선행한다

TLS 채널은 발견한 새 주소로 접속하되 저장한 CA·서버 이름·장치 신원 binding을 확인한 뒤 credential을 보낸다. 필요 시 mTLS 또는 장치별 인증된 handshake를 사용하며 자세한 방식은 전송별 구현 ADR/계약에 고정한다. 인증서 이름은 DHCP 주소에 종속시키지 않는다.

**Fleet → CORE의 현재 평문 경로는 전환 전까지 주소 고정을 유지한다.** mDNS로 찾은 새 IP에 기존 Bearer를 보내는 우회는 개발 모드에서도 허용하지 않는다. 이 방향도 궁극적으로 고정 IP 없이 연결해야 하므로, 인증된 전송 또는 서버 신원을 검증하는 handshake와 연결 기록·세션 교체를 함께 구현한다. 개발 프로필은 최초 신뢰 설정의 수작업을 생략할 수 있지만 전송 인증 생략의 근거가 아니다.

Pilot·대시보드는 same-origin을 유지한다. 자동 발견 디렉터리에서 새 origin을 여는 기능을 추가할 경우 이전 origin의 token/sessionStorage를 그대로 넘기지 않고 새 상대 검증과 권한 binding을 거친다. 브라우저에 OS mDNS 권한을 요구하지 않는다.

#### 7. 트래픽과 재연결 수명은 공통 제한을 따른다

- 플랫폼당 상시 발견 cache/listener를 공유하고 필요한 서비스 종류만 구독한다. 앱별 새 검색기와 주기적인 전체 재검색을 계속 늘리지 않는다. Avahi·NSD 등 표준 구현의 TTL cache·known-answer/중복 억제·백오프를 사용한다.
- UI 최초 검색은 유한한 창, 새로고침은 제한된 재검색이다. 배경에서는 변경 알림·TTL·네트워크 변경·연결 실패로 재발견한다. 현재 Fleet의 검색 종료 후 15 s 재실행은 이행 중 호환 경로이며 완료 시 이벤트/cache 경로로 전환하거나 실측 근거를 남긴다.
- 재연결은 지수 간격과 무작위 분산(jitter), 최대 간격, 전체 시도 deadline을 둔다. 기존 Fleet 30 s/Cam 5 s 상한은 전송별 프로필로 보존·검증한 뒤 조정한다. 공통 계약은 알고리즘·자원 상한이며 모든 장치에 동일한 숫자를 강제하지 않는다. 안정된 세션 뒤에만 백오프를 초기화한다.
- 서비스 수·후보 수·동시 resolve·동시 handshake·대기 queue에 상한을 두고 초과를 진단한다. 기존 scanner 64개 제한을 기준선으로 유지한다. 안정 상태에서 재발견은 기존 세션을 끊지 않는다.
- 발견용 UDP 5353은 허용된 사이트 인터페이스로 제한한다. 로봇 내부 ROS/DDS가 외부 앱 발견용으로 LAN에 확장되지 않게 한다. 실제 DDS interface 설정과 패킷을 함께 확인한다.
- 영상·텔레메트리·명령은 역할별 API/WS/전송을 사용한다. 영상은 용량·FPS·최신 프레임 우선·queue 상한, 텔레메트리는 구독·빈도 제한, 명령은 기존 ID·중복 판정·결과 추적을 유지한다. 재연결 때 진행 중 명령을 무조건 재전송하지 않는다. ACK를 완료로 취급하지 않는다.
- 연결 복구는 자동, 동작 재개는 해당 owner·운영 계약이 판정한다. stale 세션·이전 세대의 응답이 새 세션을 갱신하지 못하게 하고, 안전 상실 타이머를 재검색으로 초기화하지 않는다. 네트워크·discovery thread가 제어/정지 경로를 막지 않게 한다.

#### 8. 공통 상태 의미와 실패 분류

발견됨·선택됨·승인 필요·연결 중·연결됨·재시도 중·차단/충돌은 서로 다른 사실이다. 발견 목록에 있다는 이유로 online/ready를 표시하지 않는다. 연결 모드와 사이트, 마지막 성공·관측 시각, 원인과 복구 행동을 노출한다.

기존 `discovery-txt.v1.json`, `site-link.v1.json`, `failure-classes.v1.json`, `pairing.v1.json`을 정본으로 쓴다. 광고 호환성·검색 실패·네트워크 불통·TLS 불신·자격 만료/회수·권한 부족·신원 충돌·과부하를 분리한다. 인증/충돌 실패에 무한 네트워크 재시도를 적용하지 않는다. 새 상태·사유는 벡터와 모든 소비자 대조를 같은 변경에서 추가한다. 로그·진단에 원문 credential을 넣지 않는다.

호스트 계약 시험은 SOURCE/LOCAL만 증명한다. 다음 수용은 별도로 수행한다.

- 실 AP에서 2대 로봇 + Fleet/Vision + Cam + dock/signal을 시작하고, 목표 설치 대수로 확장한다. 광고·명령·텔레메트리·영상 부하를 분리한 측정과 동시에 켠 측정을 모두 남긴다.
- 정상 10분, 동시 기동, AP 재시작, DHCP 재할당/서브넷 변경, Wi-Fi 전환, 멀티캐스트 차단·장치 격리, 중복/위조 광고, 서버 종료·회수 사례를 검증한다. 물리 출력 없는 상태부터 수행한다.
- discovery bytes/s·packets/s·Wi-Fi airtime, CPU/메모리/queue, 검색/복구 p50·p95·최대, 명령 응답/정지 관측·영상 지연·drop을 기록한다. wire byte만으로 Wi-Fi 부하를 판정하지 않는다.
- 첫 실측의 **초기 목표**는 정상망 최초 발견 p95 ≤ 5 s, 전체 handshake 포함 연결 p95 ≤ 10 s, 망 복구 이후 동일 신원 재연결 p95 ≤ 30 s, 안정 상태 discovery의 가용 airtime 비중 ≤ 1%다. 이는 측정 전 설계 목표이며 검증된 제품 SLA가 아니다. 발견 창/프로필을 목표에 맞춰 조정하고 변경 근거를 기록한다.
- 명령·정지 deadline은 기존 안전 계약을 넘지 않아야 한다. 네트워크 기준선 대비 지연 변화와 최대값을 남기고, 해당 deadline·queue 상한 초과 또는 잘못된 상대 연결/자격 유출이면 수용을 중단한다. 보이는 online만으로 물리 정지를 판정하지 않는다.

### 기존 결정과의 관계

- D-354·D-370 §5·D-391의 발견·공유 어휘·저장 모델을 확장한다. 기존 service type·proto·API 경로는 유지한다.
- D-341·D-361·D-391의 코드 기반 승인 기본을 **명시적 개발 프로필에 한해** 코드 없는 승인 정책으로 대체한다. 운영 정책·신뢰 회수·감사는 유지한다. 구현 전에는 기존 코드 절차가 계속 적용된다.
- D-352·D-361·D-370 §5.3·D-391의 평문 CORE 주소 고정은 §6/단계 3 수용 전까지 유지한다. 인증된 자동 추종 전환이 완료된 경로에 한해 이 예외를 대체한다. ADR 승인만으로 pin을 제거하지 않는다.
- D-193 공용 개발 토큰 장치 차단, D-2 단일 writer, D-18 wire 동시 변경, D-33 로봇 identity, D-419·D-430 상실/안전 책임은 변경하지 않는다.
- 이전 ADR 본문은 덮어쓰지 않는다. 이 기록과 색인이 부분 개정의 범위·시점을 명시한다.

### Alternatives

- **고정 IP/수동 주소를 표준으로 유지:** 개발·현장 이동 및 DHCP 변경마다 재설정이 필요해 기각. 진단용 대체 경로만 남긴다.
- **모든 장치에 ROS/DDS 또는 새 브로커를 직접 연결:** 외부 API/제어 owner 경계를 침범하고 필요하지 않은 LAN 트래픽·의존성을 늘려 기각.
- **발견한 모든 장치를 무인 신뢰:** 충돌·잘못된 사이트·credential 유출을 구분하지 못해 기각. 개발 편의는 명시적 정책과 bootstrap에 둔다.
- **개발 중에도 매 연결 코드 입력:** 개발 반복 작업의 비용이 커 기각. 운영 신뢰 수립 수단으로 유지한다.

### Consequences

앱·장치가 같은 발견·연결 수명·실패 의미를 사용하므로 지원과 시험을 공유할 수 있다. 개발 연결의 코드 입력을 생략하면서 이후 운영 페어링을 같은 구조에 추가할 수 있다. 인증된 경로에서 DHCP 변경은 재연결 사건이며 재등록 사건이 아니다.

이를 위해 신원 binding과 전송 인증, 개발 자격 도구, OS별 discovery adapter, 펌웨어 소비·실측이 필요하다. 문서 승인만으로 기존 장치의 고정 주소 예외나 개발 인증이 바뀌지 않는다. 코드 구현·릴리스·장치·현장 수용은 단계별 증거로 기록한다.

### 2026-10-03 추가 결정: 장비 목록에서 바로 접속

사용자 확인으로 앱의 필수 설정 파일 가져오기 흐름을 폐기한다. Pilot은 실행 즉시 같은 LAN의
켜진 장비를 DNS-SD로 발견하고 목록에 표시한다. 사용자는 장비를 선택한다. 주소·고정 IP·CA 파일·
JSON을 입력하지 않는다. 연결 설정 생성 도구는 설치 담당자의 내부 도구이며 앱의 선행 조건이 아니다.

Pilot은 독립 실행 Android APK다. 화면·JS·스타일·아이콘은 APK에 포함하고 로봇에서 화면을 내려받지 않는다.
기존 Pilot JS 소스를 build 시 패키징하여 UI 원본을 하나로 유지한다. Android shell은 발견·자격 보관·
로컬 화면 실행을 맡고, 선택한 CORE에는 API와 WebSocket만 전송한다. 앱의 로비는 로봇 없이도 실행된다.

장비의 기본 연결 모드는 `paired`다. `/api/v1/auth/connection`으로 모드와 로봇 ID·전송을 확인한 뒤,
필요할 때만 장비 화면의 기존 8자리 로그인 코드를 `/api/v1/auth/pair`로 교환한다.
4자리 숫자·영문 통합과 Cam의 짧은 표시는 아래 후속 결정에 따라 추후 적용한다.

개발 장비는 `network.connection_mode: development`와 `ROSY_DEPLOYMENT=development`를 함께
지정한 경우에만 `/api/v1/auth/development-session`으로 코드 없는 1시간 operator 세션을 발급한다.
이 경로는 기존 로컬 HTTP CORE도 지원하는 명시적 개발 예외이며, 앞 본문의 개발 연결 TLS·정책 파일
필수 조건을 이 범위에서 개정한다. 생산·기본·device 배포에서는 자동 발급을 허용하지 않는다.
LAN peer·Host·Origin 제한, IP별 시도 제한, 최대 8개의 살아 있는 세션, 모드 종료 즉시 자격 거부를 적용한다.
자동 접속이 administrator 권한이나 액추에이터 허용·안전 승인 조건을 변경하지 않는다.

TLS로 광고한 장비는 HTTPS로만 접속한다. 신뢰되지 않은 인증서는 연결 오류이며 HTTP로 내려가지 않는다.
HTTP 세션은 선택한 발견 주소에 묶고 주소 변경·서비스 소실 시 제어 연결을 닫는다. 이전 자격을 새 주소로
자동 전달하지 않는다. 설치·인증서 배포 자동화와 운영 TLS 최초 신뢰 수립은 별도 장치 검증이 필요하다.

SSH는 로봇의 관리자 코드를 기존 페어링 경로로 교환하고, HTTPS 관리자 승인으로 Ed25519 공개 키를
고정 운영 계정에 등록한다. 전용 opt-in 서비스는 SSH 등록 명령만 실행하며 CORE는 root 권한을 갖지 않는다.
ADB의 무선 디버깅 페어링은 Android 시스템의 규약을 따른다. 앱의 후속 4자리 규칙으로 시스템 ADB 코드를 바꾸지 않는다.

### 2026-10-03 추가 결정: 앱 실행 기기의 발열과 화면 끄기

앱이 실행되는 Android 기기의 열 상태와 배터리 온도를 로봇 온도와 구별한다. Cam은 촬영 시작 후
화면 끄기를 제공하고 OS thermal severe 이상에서 화면 보호를 자동 요청한다. thermal API가 없는
구형 기기는 배터리 45°C를 화면 보호의 보조 기준으로 쓰며 41°C 이하에서 재무장한다. OS 열 상태는
severe 이상에서 보호, light 이하에서 재무장한다. 알 수 없는 값은 온도 0이나 정상으로 표시하지 않는다.
이 기준은 화면 전력 절감을 위한 앱 정책이고 제조사의 안전 온도나 로봇 안전 임계값이 아니다.

Cam의 카메라·전송은 기존 foreground camera service가 계속 소유한다. 화면 보호에서는 미리보기를
제거하고 display keep-awake를 해제한다. 화면을 꺼도 전송 세션을 종료하거나 카메라를 activity로 재바인딩하지 않는다.
Pilot은 화면 끄기 전에 조작을 해제하고 bounded zero와 연결 종료를 수행한다. 숨겨진 화면에서 제어를 계속하지 않는다.

즉시 실제 화면 잠금은 Android의 force-lock 권한을 사용하며 수동 버튼에서만 시스템 승인을 요청한다.
receiver에는 force-lock 하나만 선언한다. 자동 발열 보호는 승인 화면을 띄우지 않는다. 승인이 없으면
최소 밝기·미리보기 제거·keep-awake 해제로 OS 자동 꺼짐을 허용하며 이 상태를 실제 패널 off로 주장하지 않는다.
사용자는 화면을 다시 볼 수 있고, 충분히 식기 전 반복 자동 잠금을 막는 latch를 적용한다.

근거: [Android Thermal API](https://developer.android.com/games/optimize/adpf/thermal),
[foreground camera service](https://developer.android.com/develop/background-work/services/fgs/service-types),
[DevicePolicyManager.lockNow](https://developer.android.com/reference/android/app/admin/DevicePolicyManager#lockNow()).
host/JVM 시험은 실제 기기의 화면 off 중 프레임 수신·온도 하강 증거를 대체하지 않는다.

### 2026-10-03 후속 결정: 접속은 지금, 4자리 통합은 추후 적용

사용자 보정에 따라 실제 Rosy Pinky의 앱 접속 수정·검증은 지금 진행한다. 4자리 숫자·영문 코드로
로봇·Cam·SSH 승인을 통일하는 규약 변경은 이 ADR에 기록하고 추후 적용한다. 기존 로봇 로그인
8자와 Cam 승인 6자리의 발급·검증·표시를 이번 구현에서 유지한다. 구형 로봇에 새 서버 API나

### 2026-10-04 추가 결정: Android 검색 고착의 독립 복구

실제 Android 12 태블릿에서 이전 서비스의 NSD resolve가 종료되지 않아, 새 로봇 광고를
발견해도 `FAILURE_ALREADY_ACTIVE`로 주소 해석을 진행하지 못했다. 앱 내부 2초 타이머는
OS의 활성 resolve를 취소하지 않는다. 앱 프로세스 재시작 후에는 현재 광고의 IPv4 주소가
154 ms 만에 해석되고 로봇 목록의 연결 버튼이 활성화됐다. 목록 표시는 CORE 접속 성공과 구분한다.

NSD와 multicast lock은 앱과 동일 UID의 private bound service `:discovery`가 소유한다.
서비스는 `exported=false`이고 Messenger로만 통신한다. 부모는 기존 64개·60초 후보 저장소와
주소/TLS/장비 식별 검사를 유지한다. epoch·query ID·presence generation·단조 시각으로
이전 바인딩, 제거 후 재발견, TTL이 지난 응답을 폐기한다. 격리 UID와 숨겨진 API는 쓰지 않는다.

한 번에 하나의 native resolve만 실행하며 bind/resolve 제한 시간은 12초다. 시간 초과나
활성 resolve 충돌이면 epoch를 무효화하고 STOP/unbind를 요청한다. 자식은 NSD와 multicast
lock을 해제한 뒤 자기 PID만 종료한다. 부모는 Binder death 확인 후에만 다시 바인딩한다.
자동 재시도는 1/2/4초 대기, 5분 동안 최대 3회다. 명시적 '다시 찾기'는 새 검색 예산을
시작한다. 빈 LAN은 재시작 사유가 아니다. 정리가 확인되지 않으면 오류와 복구 동작을 표시한다.
백그라운드 전환과 목록 종료는 기한·대기를 취소하며 제어 세션·주 프로세스·Cam을 종료하지 않는다.

JVM 결함 주입과 실제 태블릿의 자식 종료·재검색·백그라운드 정리를 별도로 검증한다.
부모 PID 유지, 새 자식 PID, 실제 로봇 목록 복구를 기록한다. 이 결정은 Android 발견 복구에
한정하며 로봇 CORE 프로세스 구조와 페어링 코드 규격을 변경하지 않는다. 후보·TTL·재시도
상한으로 multicast 및 IPC 부하를 제한한다.

근거: [Android bound services](https://developer.android.com/develop/background-work/services/bound-services),
[ServiceConnection](https://developer.android.com/reference/android/content/ServiceConnection).

### 2026-10-05 추가 결정: LAN 이름 조회의 대기·트래픽 상한

저장한 HTTPS 이름의 DNS-SD 광고가 없을 때 사용하는 호스트 Avahi 조회에도
발견부터 주소 해석까지 총 4초의 대기 상한을 둔다. 같은 이름·포트의 진행 중 조회는
공유하고, 완료한 성공·실패 결과는 2초만 보존한다. 작업 스레드는 4개, 진행 및
완료 캐시의 이름·포트 항목은 최대 64개다. 상한을 넘는 새 이름은 연결 실패로 남긴다.

NSS getaddrinfo는 호출자 시간 초과로 강제 취소할 수 없다. 따라서 시간 초과·호출자
취소·이벤트 루프 종료 후에도 해당 조회가 끝날 때까지 소유권을 유지한다. 같은 이름을
재요청해 새 스레드를 쌓지 않는다. 완료 캐시가 만료되면 새 DHCP 주소를 해석한다.
보존된 결과를 사용해도 매 연결의 등록 정책·만료·회수·HTTPS 이름·CA·상대 신원
검사를 생략하지 않는다. 잘못된 광고·주소 충돌·HTTP downgrade는 계속 거부한다.

이 결정은 연결 요청과 NSS 작업의 자원 상한이다. 운영체제의 멈춘 DNS 작업 종료나
실제 관제 컨테이너의 NSS 배선·현장 로봇 접속을 증명하지 않는다. 멈춘 조회가 모든
작업 슬롯을 차지하면 연결 실패를 유지한다. 실제 컨테이너 UID의 해석과 기기 연동은
별도 검증한다(D-427의 배치 경계와 D-430의 승인·제어 권한 경계를 유지).
