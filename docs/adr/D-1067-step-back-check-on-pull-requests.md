## D-1067 병합된 변경을 PR이 조용히 되돌리지 못하게 pr_land가 막는다(step-back 검사)

**Status:** Accepted (2026-11-21, 패널 3석(Codex, agy, Claude 감사)의 합의. 병합 차단은 `pr_land`만, 리뷰 게이트 작업은 보고만 한다.)

잇는 결정: [D-1052](D-1052-self-review-and-zero-full-ci.md) · [D-1055](D-1055-pr-merge-queue-only-merge-path-land-retired.md) · [D-1061](D-1061-records-fragments-merge-queue.md) · [D-1066](D-1066-browser-evidence-in-the-pull-request-ci-run.md).

### Context

- 열린 PR #378은 main에 이미 병합된 #311(d9e7aededa)의 줄을 지운다. 브랜치 안의 main 병합 두 곳(ce3d7f0e34, 53f2385327)이 main 쪽 `console.js`·`charge-bays-view.js` 줄을 버렸고, 최종 diff의 순삭제는 병합 때 조용히 적용된다.
- 리뷰 게이트(`review-gate.sh`)는 열린 PR의 파일 겹침만 로그인으로 본다(`window_days` 기본 0). 최근 300개 PR 중 287개가 한 로그인이라 세션끼리는 겹치지 않는다. 이미 병합된 PR의 줄을 되돌려도 게이트가 보지 못한다.
- 단순히 "최근 7일 안에 다른 PR이 넣은 줄을 지움"만 보면 최근 133개 병합 중 36개가 걸렸고 전부 의도한 다시 쓰기였다. 차단 근거로는 잡음이 크다.

### Decision

| 항목 | 결정 |
|---|---|
| 검사 | `tools/harness/step_back.py`. 병합 기준과 HEAD의 diff에서 지운 줄을 blame해 `Merge pull request #N` 첫 부모 병합으로 PR에 대응시키고 7일 안의 PR만 본다. 기록·생성 파일(logs, index, STATUS, ADR Log, API 참조, 조각, lock)과 옮긴 줄·빈 줄·주석 줄은 뺀다. |
| 차단(본문에 `Replaces: #N (이유)` 또는 `Step-Back: none (이유)`) | 브랜치 안의 main 병합이 main 쪽 최근 줄을 버리고 끝내 되살리지 않음 · 파일이 줄어드는데 그 경로에서 자체 비병합 커밋이 지우지 않은 최근 줄 · 검사하기엔 너무 큼(삭제 3000줄·150파일 초과) |
| 정보(차단 없음) | 그 밖의 최근 줄 다시 쓰기를 PR 번호별로 출력 |
| 실행 위치 | `pr_land.py preflight`가 랩 증거 전에 돈다. `review-gate` 작업은 같은 스크립트를 base 브랜치 사본으로 돌려 작업 요약에만 쓴다(실패 없음). |
| 크기 경고 | 바뀐 파일 30개 초과, 자체 비병합 커밋 20개 초과, 병합 기준 7일 초과면 `pr_land`가 숫자를 경고로만 출력한다. |
| 끄기 | `ROSY_STEP_BACK=off`(`pr_land`가 건너뜀을 한 줄로 알림). 개별 PR은 본문의 `Step-Back: none (이유)`. 리뷰 게이트의 보고 단계는 워크플로 단계를 지우면 된다. |

### 측정

- 최근 60시간의 병합 135개(각 병합 M: 기준 M^1, 머리 M^2): 차단 4개(3.0%), 정보만 78개. 차단은 `#253`·`#257` 게시 PR 두 개(너무 큼 포함)와 `#292`(`cell_jaw_side.py` 17줄, 같은 작업의 뒤 버전이 이긴 경우)와 `#281`(`cell_task_exec.py` 2줄)이다. 전부 설명 가능하다.
- #378의 머리는 #311과 #253의 줄을 지워 차단된다.

### 못 잡는 것과 덮는 줄

- squash 병합, 리베이스, 옛 파일을 보통 커밋으로 복사해 넣은 경우는 자체 커밋이 그 줄을 지운 것으로 기록되므로 정보로만 나온다. 7일보다 오래된 PR의 줄과 PR 병합이 아닌 경로로 들어온 줄도 대응하지 못한다.
- 차단 2는 경로와 지운 줄 단위로 자체 커밋의 삭제를 짝짓는다(같은 줄은 한 번만). 줄 번호까지 따르는 hunk 단위는 아니다.
- `Step-Back: none (이유)` 한 줄은 이름 있는 PR과 크기를 포함해 모든 차단을 덮는다. `Replaces:`는 적은 번호만 덮고 크기 차단은 덮지 못한다.
- git 호출이 실패하면 검사는 `scan incomplete`로 멈춘다(통과가 아니다). 파일 하나의 blame 실패만 경고하고 이미 확인한 차단은 남긴다.
- API 참조는 `**Version:**` 줄, `v1.next` 줄, 이력 표의 버전 행만 건너뛴다.

### Rejected

- **리뷰 게이트 작업에서 처음부터 차단:** 거짓 양성률을 아직 재지 못했다. 보고 단계에서 재고 다음 결정에서 필수로 올린다.
- **크기 한도를 차단으로:** 열린 PR이 이미 한도를 넘는다(#378은 680파일, 99커밋). 소유자 결정이 필요하다.
- **최근 줄을 지우는 모든 PR을 차단:** 133개 중 36개가 전부 의도한 다시 쓰기였다.

### Consequences

- 순삭제와 main 병합 때 버린 줄은 PR 본문에 번호와 이유가 남는다.
- 파일 단위로 보는 차단 2는 자체 커밋이 같은 줄을 지운 경우를 정당한 삭제로 본다. 전체 파일 복사 커밋은 이 기준을 통과할 수 있다(줄 단위 가림은 후속).
- 남은 확인: 리뷰 게이트 보고의 거짓 양성률, 필수 전환 시점.

### Amendment 2026-11-21: size limits block

소유자가 권고를 받아들여 큰 UI PR을 나눈 뒤 크기 한도를 차단으로 올린다. `pr_land`는 센 바뀐 파일 30개, 자체 비병합 커밋 20개, 병합 기준 7일 중 하나를 넘으면 PR 본문에 `Size-Exception: <이유>`가 없는 한 제출을 거절한다. 생성·기록 파일과 순수 이름 변경은 파일 수에 세지 않고, 브랜치 이름 면제는 없고(검토에서 임의 브랜치가 이름만 맞춰 우회할 수 있다고 지적해 뺐다), 150파일 스캔 상한과는 별개이며, `ROSY_STEP_BACK=off`는 전부 건너뛴다. 측정(최근 7일 병합 145개, 면제 7개 제외 138개, 이름 면제를 뺀 뒤 이 7개가 걸리는지는 다시 세지 않았다): 파일 한도 5개(3.6%: #284, #281, #344, #349, #382), 커밋 한도 1개(#281), 병합 기준 한도 0개(GitHub의 base.sha가 최신이라 나이는 하한이다), 합쳐 5개(3.6%, 10% 미만)라 숫자는 그대로 둔다. 위 「Rejected: 크기 한도를 차단으로」는 이 개정으로 대체된다.
