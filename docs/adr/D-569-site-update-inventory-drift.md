## D-569 사이트 코드 갱신과 로봇 등록 차이를 분리한다

**Status:** Accepted (2026-10-09, 사용자 요청; SOURCE·Linux 호스트 테스트. 관제 PC 설치와 로봇 재등록은 별도 검증).

잇는 결정: [D-361](D-361-site-console-enrolls-robot-by-screen-code.md)(화면 코드 등록), [D-441](D-441-site-stack-automatic-update.md)(서명 후보 갱신), [D-562](D-562-ceiling-marker-id-equals-robot-number.md)(번호 변경). D-565의 TLS 필수 로봇 재등록은 별도 작업이며, 이 결정은 그 등록 절차를 대신하지 않는다.

### 문제

관제 PC의 `_rosy._tcp` 광고에는 두 로봇이 보였지만 Fleet `/api/fleet/state`에는 한 대만 있었다. 현장 `autoupdate.conf`는 옛 `robot_id`를 필수로 요구해, 설치된 사이트 이미지가 정상이어도 D-441 갱신기가 매번 후보 선택 전에 중단됐다. mDNS의 이름·주소·TXT는 발견 후보일 뿐 등록 신원이 아니므로, 광고를 보고 `robot_id`나 자격을 자동 변경할 수 없다.

### 결정

1. 사이트 갱신의 기능 검사는 등록 목록의 **회귀**를 판정한다. 전환 전 인증된 Fleet 상태와 Vision source 목록을 읽어 비어 있지 않은 ID 집합을 기준선으로 잡는다. 응답 구조·인증이 실패하거나 목록이 비면 갱신을 거부한다. 전환 후 같은 API에서 기준선의 ID가 하나라도 사라지면 롤백한다. 새 ID가 추가되는 것은 허용한다.
2. `functional_checks.required_ids`의 누락은 `inventory-drift` 이벤트와 `last_run.inventory_drift`에 경고로 남긴다. 오래된 ID 하나 때문에 서명된 사이트 코드 배포 전체를 막지 않는다. 이 값은 운영자가 기대 목록과 Fleet 등록부를 대조하는 자료이며, 로봇의 온라인 상태·물리적 신원을 증명하지 않는다.
3. 전환 저널에 기능 기준선을 저장한다. 갱신 중 프로세스가 끊겨도 복구·롤백은 전환 전 목록과 비교한다. 옛 저널에는 기준선이 없으므로 기존 엄격 검사를 유지한다.
4. 등록은 D-361의 화면 코드와 신원 확인, TLS 필수 로봇은 D-565의 승인된 binding 절차를 따른다. mDNS 광고만으로 로스터·토큰·binding을 만들거나 옛 로봇 ID를 새 ID로 치환하지 않는다. `site_functional_setup.py`의 초기 설정 검사는 필수 ID 일치를 계속 요구한다.

### 대안

| 방법 | 판단 |
|---|---|
| mDNS 이름을 새 `robot_id`로 자동 사용 | 광고가 인증되지 않고 TXT에도 로봇 번호가 없다. 기각 |
| 옛 필수 ID가 돌아올 때까지 모든 사이트 코드 갱신 중단 | 로봇 재등록과 코드 배포를 묶어 놓아 별개 장애가 함께 지속된다. 기각 |
| 전환 전후 인증된 목록 비교와 별도 누락 경고 | 배포 회귀를 막으며 등록 차이를 숨기지 않는다. 채택 |

### 검증과 한계

Linux 호스트 테스트는 옛 ID 누락 상태에서 목록을 유지하면 갱신, 전환 뒤 기존 ID를 다른 ID로 바꾸면 롤백, 잘못된 응답·빈 목록은 거부함을 확인한다. 관제 PC의 root 소유 갱신기·I/O 모듈은 별도 설치가 필요하다. 이 변경만으로 현재 미등록 로봇이 Fleet에 들어오지 않으며, 실제 재등록과 현장 갱신 성공은 별도로 확인한다.
