## D-807 Account 인증 서비스의 자격 소유 책임과 운영 완료 기준

**Status:** Accepted (2026-10-19, 사용자 실행 계획 확인 및 구현·검증 진행 승인. 구현·CI·설치·실사용 수용은 별도)

### Context

사용자는 로그인과 기타 인증 기능을 실제 사용할 수 있는 서비스까지 구현하고,
어느 경로에 어떤 토큰을 사용할지 토론하여 ADR로 기록하도록 요청했다.
로그인 API나 토큰 발급 코드의 존재만으로 이 요구를 충족하지 않는다.

[D-757](D-757-rosy-account-unified-app-sessions.md)은 단일 Rosy Account 신원,
기존 Fleet auth·SQLite의 첫 배치, 전 앱 자동 세션 연결과 회수 경계를 이미 결정했다.
[Account protocol](../reference/rosy-account-protocol.md)은 PKCE, 대상별 Access Token,
Refresh Token 회전, 앱 쿠키 및 계정 관리 API를 명문화했다. 이 ADR은 그 결정을
대체하지 않고 자격별 책임과 운영 인수 단위를 보충한다. 신규 endpoint·claim·capability,
토큰 형식이나 수명을 추가하지 않는다.

### Decision

#### 1. 인증 서비스는 하나의 운영 책임으로 완성한다

Rosy Account가 사람 신원·로그인 수단·계정 상태·프로필·권한 원장·세션·자격 발급과
회수를 소유한다. 최초 배포는 D-757대로 기존 Fleet 프로세스와 영속 SQLite를 사용한다.
서비스라는 제품 책임을 별도 프로세스나 외부 IdP 설치 의무로 해석하지 않는다.
각 앱은 Account를 소비하고 자기 자원과 업무의 허용 여부를 서버에서 판단한다.

첫 운영 인수는 한 배포 단위에서 실제 등록된 앱·자원을 묶어 수행한다. 이를 현장별
독립 사람 계정 원장 생성이나 전체 제품의 통합 완료로 확대하지 않는다. 다중 현장
복제·federation·인터넷 단절 중 신규 중앙 로그인은 지원 완료로 간주하지 않는다.
해당 요구가 생기면 동일 논리 identity와 회수 계약을 유지하는 후속 결정으로 다룬다.

#### 2. 자격은 경계와 회수 단위에 따라 구분한다

아래 표는 기존 계약의 책임을 모은 것이다. 행이 다르다는 이유로 새 공통 토큰이나
범용 자격 저장소를 만들지 않는다. 같은 발급 라이브러리를 써도 자격의 대상과 용도는
섞지 않으며, login/email/표시 이름을 불변 account identity로 사용하지 않는다.

| 자격 | 원장·발급 책임 | 보관·검증 책임 | 종료·회수 단위 |
|---|---|---|---|
| 중앙 사람 로그인 세션 | Account 원장·Fleet 로그인 경로 | 브라우저는 보호 쿠키, 서버는 세션 해시·계정 상태 검사 | 기본 로그아웃은 해당 session family 전체. 계정 정지·초기화·전체 회수는 모든 기기 |
| 앱 웹 세션 쿠키 | 대상 앱 receiver가 중앙 인증 결과에 결속해 생성 | 브라우저는 opaque HttpOnly/Secure/SameSite 쿠키, 앱은 해시와 암호화된 중앙 자격 보관 | 로컬 삭제와 중앙 family 회수를 함께 처리. 중앙 실패는 완료로 표시하지 않음 |
| 일회용 authorization code | Account, 등록 client·redirect·PKCE·resource에 결속 | 앱이 state를 확인하고 서버 또는 native의 verifier로 교환 | 60초·단일 사용. 교환 뒤 callback URL에서 제거 |
| 대상 Access Token | Account가 단일 resource와 명시적 capability로 서명 | 대상 API가 issuer·audience·서명·키·만료·family·revision과 요청 권한 검사 | 최대 5분, 온라인 회수 적용 최대 30초. 더 엄격한 업무 계약 우선 |
| Refresh Token | Account가 난수 발급·원자적 회전, DB에는 해시만 저장 | 웹은 앱 서버의 암호화 저장소, native는 플랫폼 보안 저장소 | 매 사용 회전, 재사용은 family 회수. 중앙 세션 한계를 넘어 연장 불가 |
| 기계·장치·서비스 자격 | 기존 등록·페어링·서비스 owner의 전용 발급 경로 | 해당 장치·서비스의 보호 저장소와 수신 owner | 기존 장치·서비스별 회수 계약. 사람 로그인이나 사람 로그아웃으로 대체하지 않음 |
| 외부 제공자 자격 | 제공자가 발급하고 기존 연결 owner가 사용자·프로젝트에 귀속 | 기존 서버 연결 저장소. ROSY API 인증으로 받지 않음 | 연결 해제·권한·credential generation과 기존 worker 재검증에 따름 |
| 미디어 등 업무별 위임·lease | 해당 자원·업무 owner가 현재 허용 범위 안에서 발급 | 해당 소비자만 용도·대상·원본 권한·lease를 검사 | 해당 업무의 만료·철회·실제 연결 종료 계약. Account 토큰 수명과 구분 |

웹 앱은 로그인 뒤 일회용 코드와 S256 PKCE로 자격을 교환하고 앱 세션을 연결한다.
Access/Refresh Token을 브라우저 localStorage·URL·로그에 남기거나 사용자가 토큰을
복사하도록 요구하지 않는다. native는 기존 검증 callback과 OS 보안 저장소를 사용한다.
표의 쿠키 속성만으로 CSRF 보호가 끝난 것으로 보지 않고 기존 same-origin 검사를 유지한다.

외부 제공자 로그인 수단과 외부 데이터 접근 자격은 구별한다. 제공자 로그인은 D-755와
D-757의 검증된 identity 연결을 거쳐 Rosy Account로 귀결한다. Hugging Face 등의
데이터 접근 토큰 자체가 ROSY 사용자 세션이나 로봇 접근 권한이 되지는 않는다.
현재 authorization code 구현을 완전한 OIDC 제공자 구현으로 표시하지 않는다.

#### 3. 인증 성공과 업무 실행 승인은 별도다

Account는 누가 어떤 자원에 어떤 capability를 갖는지 증명한다. 대상 API는 요청마다
필요한 capability를 검사하며 관리자 역할에서 조작 권한을 추론하지 않는다.
Fleet은 transaction·admission, CORE는 최종 Base 명령, OMX는 장치 action,
학습 owner는 검수·승격을 계속 소유한다. 좌석 점유·deadman·실행 lease·외부 게시 동의를
로그인으로 자동 승인하지 않는다. 인증 갱신을 명령 재전송이나 업무 재승인으로 해석하지 않는다.

`로그인 성공`, `API 접근 허용`, `업무 접수`, `실행 완료`를 각각 기존 owner의 결과로
표시한다. 자격 발급 성공은 로봇 동작이나 학습 완료의 증거가 아니다.

#### 4. 회수·장애·복구의 완료 범위를 구분한다

D-757의 온라인 30초·기존 자격 최대 5분은 일반 Account 경계의 상한이다.
중앙 장애 시 새 로그인·발급·갱신·관리 쓰기를 허용하지 않고, 기존에 검증된 자격도
만료와 자원 scope 안에서만 사용한다. 확인하지 못한 자격을 캐시에 넣거나 단절을 이유로
수명을 연장하지 않는다. WS·worker·다운로드·영상도 각 owner의 재검증 대상이다.

이 상한은 모든 연결을 5분 유지하라는 정책이 아니다. 예를 들어
[D-789](D-789-six-robot-webrtc-camera-transport.md)의 미디어는 최대 60초 입장 자격과
활성 lease, 원본 권한 1초 재검사, 철회·CORE 단절 확인 후 실제 세션 5초 이내 종료를
따른다. CORE watchdog·좌석·명령 lease 및 기타 더 짧은 기존 제한도 그대로 우선한다.

회수는 중앙 원장 commit, 수신 verifier 반영, 업무 owner의 취소/checkpoint,
실제 연결 종료를 구분한다. 이미 실행 중인 업무의 처리 방식은 업무 owner가 결정한다.
중앙 로그아웃 실패 시 로컬 세션 삭제와 암호화된 회수 대기열을 유지하는 기존 계약을
따르고 503/미완료를 표시한다. 재접속으로 회수된 권한을 복구하지 않는다.

운영자는 issuer·TLS·등록 client·정확한 callback/resource·신뢰 공개키·비밀 파일 권한·
영속 DB를 하나의 배포 구성으로 관리한다. Account 접근 토큰의 서명 개인키는 Account만 보유하고 receiver에는
신뢰 공개키와 자기 세션 저장소를 배포한다. 프로세스 재시작 때 서명·암호화 키를 임의로
재생성하지 않는다. 키 교체는 기존 공개키 선배포·서명 전환·기존 자격 만료·옛 키 제거 순서다.

복구는 DB 파일이 열리거나 서명이 검증되면 끝나는 작업이 아니다. 이전 백업의 단순
복원으로 정지 계정·옛 비밀번호·회수 family·옛 revision·소비한 Refresh Token이 다시
유효해지는 롤백을 금지한다. 기존 migration·회수 계약을 유지하는 복구 검증을 남긴다.
로봇 로컬 복구 자격은 명시적인 기존 경로로 유지하고 중앙 실패의 자동 fallback으로 쓰지 않는다.

#### 5. 실제 사용자 흐름을 운영 완료 조건으로 삼는다

적용 목록은 `shared/web/surfaces.yaml`과 D-757의 API/WS/native/worker 범위를 따른다.
배포마다 surface·자원·owner·정확한 revision/빌드·시험 환경·증거 위치를 연결하고,
기존 완료 계획의 `SOURCE / REMOTE TEST / CI / INSTALLED / RUNTIME / USER ACCEPTANCE`
여섯 칸을 유지한다. 실행 명령·host 역할·수집/실행/skip/NEW 결과·로그/receipt를 연결하고,
실패·skip·미실행·비적용은 통과와 구분하며 비적용 이유를 기록한다.

| 수용 시나리오 | 필요한 확인 |
|---|---|
| 계정 발급·첫 변경·로그인·앱 이동 | 실제 등록 앱에서 같은 account_id로 복귀하고 수동 토큰 전달 없이 권한 내 기능 사용 |
| 허용 업무와 결과 | 업무 owner의 영속 결과 재조회. 허용·거부를 직접 API 호출에서도 확인 |
| 다른 사용자·로봇·프로젝트 | 타 대상 토큰 거부, 사용자 전환의 응답·캐시 격리, 관리자와 operator 권한 비상속 |
| 로그아웃·권한 축소·계정 정지 | 중앙 변경 시각과 기존 REST/WS/갱신 거부 시각을 연결. 영상은 D-789의 별도 종료 상한 확인 |
| 네트워크·DB 장애와 재시작 | 새 발급·갱신 거부, 일반 자격의 잔여 만료, 엄격한 업무 경로 차단, 회수 대기 상태 구분 |
| 키 교체·migration·복구 | 신뢰 키 순서, 현재 비밀번호·프로필 보존, 회수 자격·이전 비밀번호 부활 없음 |
| native·외부 연결·worker | 실제 단말 callback/보안 저장과 제공자 연결·해제, 현재 권한·generation 재검증 |

계정 관리자와 실제 사용자가 배포본에서 `로그인 → 자동 앱 세션 → 허용 업무 → 영속 결과
재조회 → 로그아웃/회수 → 기존 접근 차단`을 확인하고 운영자가 장애·복구 절차를 수행해야
해당 배포 단위의 인증 서비스를 완료로 표시한다. 미완료 앱은 이름과 사유를 남긴다.
전체 적용 목록의 예외가 해소되기 전에는 전 앱 통합 완료를 선언하지 않는다.

[기존 완료 계획](../plans/2026-10-14-rosy-account-completion.md)의 2026-10-14 기록은
여러 revision의 원격 시험과 남은 설치·실사용 경계를 구분한다. 이는 이번 문서 변경으로
재검증된 현재 배포 증거가 아니다. 실제 주소·계정·비밀은 공개 ADR에 기록하지 않는다.
인증 검증을 위해 E-Stop을 해제하거나 운동 명령을 보내지 않는다.

### Alternatives

- 별도 인증 서버·외부 IdP를 먼저 운영: 분리 장애 경계와 federation에는 유리하지만
  현재 요구에 배포·DB·키 운영 단위를 더한다. 우선 기존 Fleet을 사용하며 가용성·다중
  현장 요구가 구체화되면 후속 결정으로 비교한다.
- 앱별 계정 또는 하나의 공용 장기 토큰: 연결 구현은 단순해도 사람·기계·자원 경계를
  잃고 회수·감사를 일치시키기 어렵다. 기존 단일 신원·최소 자격 계약을 유지한다.
- 브라우저가 Refresh Token을 직접 관리: 기존 앱 서버 세션 경로가 있으므로 채택하지
  않는다. 서버 저장·쿠키 연결의 운영 비용을 감수하고 JS에 장기 비밀을 노출하지 않는다.
- 로그인과 토큰 API 시험만으로 완료: 설치 설정·열린 연결·실제 단말·운영 회수의 누락을
  발견할 수 없어 배포 단위의 실사용 수용을 완료 조건으로 둔다.

### 토론과 반례

동일 세션의 계약 검토 에이전트와 운영 증거 검토 에이전트가 독립 의견을 낸 뒤
상호 쟁점을 전달했다. 서로 다른 모델의 독립 검증이나 실행 시험으로 간주하지 않는다.
두 의견 모두 D-757 보충에 동의했고 다음 반례를 본문에 반영했다.

| 반례 | 합의한 처리 |
|---|---|
| 관리자이므로 로봇 조작도 허용 | 명시적인 자원 capability와 업무 admission을 각각 검사 |
| 중앙 장애이므로 영상도 5분 유지 | D-789의 엄격한 온라인 재검증·실제 세션 종료 우선 |
| 쿠키만 삭제한 뒤 전 앱 로그아웃 완료 표시 | 로컬 삭제와 중앙 회수를 구분하고 중앙 실패는 미완료 |
| 과거 백업이 열리므로 복구 성공 | 회수 세션·소비한 Refresh Token·옛 비밀번호 부활 여부까지 확인 |

### Consequences

기존 라이브러리·API·저장소와 실행 owner를 재사용하지만 인증의 운영 책임에는 TLS·키·
앱 등록·영속 DB·회수·복구 인수까지 포함된다. Fleet과 Account가 같은 프로세스여서
장애 영역도 공유한다는 비용을 수용한다. 웹 receiver는 세션 저장·암호화 키 운영을 맡는다.

이 ADR의 Accepted는 보충 설계의 수용이며 D-757의 Accepted 상태를 바꾸지 않는다.
문서 작성·검토는 제품 코드 구현, 배포 변경, 운영 계정 전환, 원격 시험 통과 또는
실사용 수용을 뜻하지 않는다. 구현 시 기존 SRS·API·schema를 변경해야 한다면 그 계약과
검증을 함께 갱신하며, 안전 경로 변경은 기존 독립 리뷰 절차를 따른다.
