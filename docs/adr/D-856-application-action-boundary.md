## D-856 업무 공정 해석과 로봇 동작 실행의 분리

**Status:** Accepted (2026-10-24, 사용자 결정). 업무·동작 책임 경계의 결정이며, 상세 wire 계약·기능 구현·배포·장치 수용은 완료되지 않았다.

**실행 계획:** [단계별 계획](../plans/2026-10-24-harbor-rosy-application-action-boundary.md).

## Context

Harbor는 이미 ROSY 내부 Python을 import하지 않고 Fleet HTTP를 사용한다. 그러나 현재 공정 compile/proposal 경로는 Fleet에 설치된 palletizing compiler를 요구하며, `CELL_TRANSFER` 본문에도 `pallet`·`layer` 등의 공정 어휘가 내려간다. 저장소와 전송 방식의 분리만으로 업무 의미와 실행 책임의 분리가 완성되지는 않는다.

사용자가 요구한 경계는 화물 도착·팔 퇴피·하역 등을 해석하는 애플리케이션과 로봇이 수행할 동작을 처리하는 미들웨어의 분리다. 이 업무 조건들을 새 미들웨어 공통 API로 올리는 방법은 요구와 맞지 않는다. 근거는 Harbor의 `harbor/process.py`·`workflow.py`와 플랫폼의 `cell_app_routes.py`·`cell_compiler.py`·`step_action_kinds.py`를 대조한 결과다.

## Decision

### 1. 업무 의미와 공정 변환은 애플리케이션 책임이다

Harbor는 화물·재고·회수 순위·임시 적치·복원·하역·업무 완료를 소유한다. 공정 변환부는 업무 계획을 지원되는 로봇 동작과 선후관계로 변환하고, 업무 요청과 실행 identity를 연결한다. 첫 구현에서는 Harbor 내부 모듈로 둔다. 별도 중계 서버·공통 SDK·workflow 언어를 선행 도입하지 않는다.

재사용 공정 라이브러리도 의미상 애플리케이션 계층이다. ROSY 저장소 안에 있다는 이유로 미들웨어의 필수 지식이 되지 않는다. Cell 같은 공정 앱이 기존 compiler를 사용하도록 유지할 수는 있지만, Harbor의 중립 동작 실행 경로가 그 앱이나 compiler의 설치를 요구해서는 안 된다.

### 2. ROSY는 지원 동작을 검증·접수·조정하고 실행 사실을 반환한다

공통 실행은 인증·승인·동작 버전·장치 능력·좌표계/단위·보정·자원 점유·action/attempt 식별·진행·취소·복구를 소유한다. 장치 owner가 로봇별 경로/궤적 계획과 최종 출력·안전을 소유한다. 앱이 관절 경로나 장치 SDK를 직접 다뤄야 하는 구조로 바꾸지 않는다.

동작은 자신이 약속한 물리 수행 조건을 가질 수 있다. 예를 들어 목표 자세 허용오차나 그리퍼 상태가 동작 계약에 포함될 수 있다. 이는 항만 화물의 출고·하역·복원 완료를 해석하는 것과 다르다. object ID는 불투명 참조로 전달할 수 있고 형상·하중은 물리 검증 입력으로 사용할 수 있지만, 공통 실행기는 화물 업무 정책을 분기하지 않는다.

Fleet Action과 장치 내부 Motion Intent를 구별한다. 외부 앱에 raw servo·ROS·장치 owner 호출을 개방하지 않는다. D-442의 장치 Action Gateway와 Arbiter/Safety Guard 경계를 유지한다.

### 3. 수행 결과와 업무 완료는 별도의 정본이다

ROSY는 해당 action/attempt의 접수·진행·성공·실패·취소·불명 결과와 측정/근거 참조를 반환한다. Harbor는 그 결과와 인증된 관측을 대조해 업무 단계와 최종 완료를 결정한다. 동작 성공만으로 화물 도착·팔 전체 퇴피·최종 하역을 모두 참으로 만들지 않는다.

현재 Harbor `MoveEvidence`의 업무 필드를 공통 wire로 복제하지 않는다. 기존 일반 관측 기능은 공개 계약으로 재사용하고, 업무에 필요한 판정과 ID 대응은 앱 측에서 수행한다. 원본 시각·출처·revision·시도 결속·불확실성은 유지한다. `source_id` 문자열 허용만으로 producer 인증이 성립하지 않는다.

업무상 “팔 퇴피 후 다음 단계”는 앱이 판단한다. 로봇의 충돌 방지·허용 영역·정지 인터록은 실행부가 독립 집행한다. 앱 판정은 안전 허가가 아니다.

### 4. 불명 접수와 복구는 공통 실행의 식별 계약으로 다룬다

같은 요청의 중복·본문 충돌·응답 유실·과거 attempt·재시작을 구분한다. 응답 유실 시 먼저 소유 실행 원장과 대조하고, 새 key 재발행·다른 장치 자동 재배정·점유 해제를 하지 않는다. 재연결만으로 다음 동작·래치 해제·rearm을 허용하지 않는다.

구체적인 요청 key scope·조회 방식·보존 기간·오류 코드는 후속 계약 산출물에서 확정한다. 현재 cell proposal과 승인·시작 의미가 있는 trip POST를 같은 의미로 취급하지 않는다.

### 5. 기존 공정 경로는 명시적 호환 경로로 유지한다

새 중립 경로가 계약·consumer 시험을 통과하기 전까지 기존 `cell-app`/`CELL_TRANSFER`를 삭제하거나 의미를 바꾸지 않는다. 공정 digest에 결속된 기하·보정·검증 보장은 새 경계에서도 소유자와 시험이 있어야 한다. 새 경로는 임의 JSON 실행 또는 검증 없는 좌표 실행이 아니다.

ADR 채택 당시에는 외부 동작 계약의 path·schema·종류·버전을 확정하지 않았다. 실제 구현과 등록 동작을 대조한 상세 설계에서 동작별 API reference·schema·양 끝 시험을 함께 정한다. 후속 API v1.298은 TRIP 조회/대조, v1.299는 중립 팔의 읽기 전용 사전검사를 등록했다. [실행 계획](../plans/2026-10-24-harbor-rosy-application-action-boundary.md)이 각각의 구현·검증 상태를 소유하며 팔 grant·중립 실행 완료로 확대하지 않는다. 기존 Motion Intent가 있다는 이유로 외부 앱 공개 기능이 있다고 주장하지 않는다.

## 기존 ADR과의 관계

구현 후속: API v1.312는 별도 관측자 context/raw facts·physical receipt와 취소 계약을 등록했다. 첫 simulation의 [독립 ARM HTTP 검증](../validation/harbor-arm-observer-http-2026-10-24/result.md)은 Harbor의 업무 binding·완료 gate, Fleet의 실행/claim, 독립 관측자, 장치 owner의 역할을 구분한다. 합성 facts의 HTTP/UDS 통과와 native actuator·실물 수용을 구별하며 최종 FULL 상태도 이 검증 기록을 따른다.

| ADR | 관계 |
|---|---|
| D-827 (Proposed) | 업무·공정·실행 분리를 구체화한다. 재사용 공정이 플랫폼 저장소에 있을 수 있다는 것과 공통 실행의 필수 의존성이라는 것을 구별한다. |
| D-828·D-829 (Proposed) | 수행 결과와 업무 완료, 후보와 실행 허가 구분을 참고한다. 이들의 상태를 Accepted로 바꾸지 않는다. |
| D-836 (Accepted for implementation) | 현재 simulation 공정·후보 접수의 호환 계약으로 보존한다. 설치 공정 경로를 모든 독립 앱의 영구 필수 경로로 확대 해석하지 않는다. |
| D-841 (Accepted for implementation) | 외부 HTTP 소비와 앱 장부 독립성을 유지하고 의미 계층의 분리까지 보완한다. |
| D-429·D-430·D-442 | 장치 owner·Arbiter·Safety Guard·Action/Intent 경계를 유지한다. |
| D-850·D-851 | 관제 계층 구성과 별개인 앱–실행 경계다. 위임 트리 전체를 이번 구현의 선행 조건으로 만들지 않는다. |

기존 Accepted ADR 전체를 폐기하지 않는다. 후속 구현에서 특정 조항을 실제 대체할 때만 새 ADR에 대체 범위를 명시하고 기존 기록의 상태/링크를 해당 절차로 갱신한다.

## Alternatives

기존 HTTP 공정 API만 고정하면 변경량은 작지만 공정 compiler 결합이 남는다. 앱이 장치를 직접 제어하면 공통 안전·admission·복구를 다시 구현해야 한다. 앱의 공정 변환과 중립 실행 계약을 나누는 방식을 선택한다. 초기 계약·호환 시험 비용을 들여 업무 정책 변경이 미들웨어 변경으로 퍼지는 것을 줄인다.

## Consequences and acceptance

첫 적용은 simulation의 한정된 이동/조작 흐름으로 한다. 실물 개방·자동 충전·병렬 운행·AI 정책 실행기 통합은 범위 밖이다. 정확한 동작 종류는 상세 계약 검토에서 결정하며, 미지원 기능은 접수 전에 거절한다.

완료 기준은 다음과 같다.

- Harbor 업무 규칙을 바꿔도 ROSY 공통 실행 소스를 바꾸지 않는다.
- Harbor와 palletizing 앱/패키지가 없는 서버 구성에서 채택한 중립 동작을 접수·검증·조회할 수 있다.
- 다른 최소 HTTP 소비자가 같은 동작 계약을 사용하며 항만 업무 타입을 요구받지 않는다.
- 기존 공정 소비자의 승인·digest·장치 안전·복구 시험이 유지된다.
- 동작 성공과 관측 미확인을 함께 주면 Harbor 업무가 완료되지 않는다.
- 중복·충돌·응답 유실·재시작·늦은 결과에서 중복 실행·과거 시도 완료·불명 점유 해제가 없다.

현재는 위 기준의 기록이며 통과 증거가 아니다. 로컬 lint와 문서 계약 원격 시험 결과를 별도로 기록하고, 구현·HTTP 통합·장치 수용을 각각 별도 증거로 닫는다.
