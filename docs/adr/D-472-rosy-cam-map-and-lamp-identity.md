## D-472 Rosy Cam 현장 영상을 지도에 표시하고 후면 LED 점멸로 로봇 신원을 대조한다

**Status:** Accepted (2026-10-08, 사용자 결정 "LED 대조 구현도 해 adr로 해서 해"; 아래 addendum 2026-10-08이 3·7항을 고친다). 설치·배포·현장 식별 완료를 뜻하지 않는다.

잇는 결정: D-136, D-257, D-260, D-375, D-395, D-433, D-455, D-457.

### Context

- 사용자는 Fleet 현장지도가 실제 Rosy Cam 데이터를 가져와 보여 주고, 로봇 뒤쪽 LED 색으로 이름을 구별하기를 원한다.
- 현재 콘솔에는 Vision의 프레임 미리보기와 Fleet의 지도·추적 레이어가 따로 있다. 브라우저는 Fleet이 발급한 짧은 Vision lease로 `/api/vision/sources/{source_id}/frame`을 읽는다. Fleet 서버는 영상 바이트를 중계하지 않는다(D-136).
- `ceiling_north`의 실제 프레임과 `map_v2_fleet`의 승인된 paint-fit 보정은 조회됐다. 그러나 최근 현장 조회에서 두 로봇의 추적은 `NO_POSE`였고, 상단 신원 마커도 아직 부착되지 않았다. 외관의 청록색은 두 대 모두 비슷하다. 정적인 색 한 프레임이나 odom (0, 0, 0)으로 이름을 붙일 수 없다.
- 후면 WS2812는 안전·운행 상태 표시다. D-433의 `rosy-face`가 단독 소유한다. 현재 실기 조회에서 두 기기의 `rosy-face`는 active이고, 26번은 이전 `lamp_pattern ready` 종료 후 램프를 제외했으며 60번에는 `lamp_pattern booting`이 남았다. 두 기기의 하드웨어 보고는 `lamp: needs_human`이다. 현재 릴리스에는 신원 점멸 요청 경로가 없다.

### Decision

1. **현장지도 화면.** Fleet 콘솔의 현장지도에서 선택한 Rosy Cam source의 *실제 최신 프레임*을 배경으로 보여 준다. 브라우저가 기존 Vision lease와 프레임 경로로 Vision에서 직접 읽고, source·캡처 시각·프레임 나이·신선도와 보정 revision을 함께 표시한다. Fleet 서버에 이미지 저장·중계 경로를 추가하지 않는다. 스트림이 끊기거나 오래되면 마지막 프레임을 현재 현장처럼 표시하지 않는다.
2. **좌표와 레이어.** 승인된 source/map/lens/영상 비율 보정으로 영상 픽셀과 `map` 좌표를 연결한다(D-375·D-457). 같은 화면에 차선 그래프·주차·시작점·마커 및 익명 관측을 올리되 영상과 오버레이의 출처를 구분한다. `map_v2_fleet`의 차선/점유 지도는 경로와 좌표의 기준이다. Rosy Cam 영상은 시간에 따라 바뀌는 관측 배경이지 경로 지도의 자동 수정본이 아니다. 보정이 없거나 달라지면 영상은 별도 미리보기로만 보이고 지도 좌표 오버레이와 클릭 목표는 결합하지 않는다.
3. **기본 신원.** 로봇 상단의 고유 ArUco ID와 사이트 `robot_markers` 대응을 우선한다(D-457). 색 띠는 사람이 확인하는 보조 표지다. 신원 마커가 없으면 카메라 blob은 `unknown`으로 남긴다.
4. **LED 폴백.** 등록된 `robot_id` 한 대에 인증된 단기 식별 요청을 보낼 수 있게 *별도 구현*한다. Fleet은 동시에 한 대만 요청하고 6초 이내에 끝낸다. `rosy-face`만 후면 램프를 구동한다. 예정 패턴은 26번 파랑, 60번 주황의 1초 켬 → 1초 끔 → 1초 켬이며, 색은 현장 조명과 카메라에서 실측 후 조정한다. 초록 ready 표시나 기존 하드웨어 자가 시험을 신원 신호로 재해석하지 않는다.
5. **안전 우선.** E-Stop·고장·주의·운행 상태 표시는 식별보다 우선한다. 그러한 표시 중에는 식별 요청을 거절하거나 즉시 취소하고 원래 상태 표시로 돌아간다. 점등은 바퀴, 모드, E-Stop, localization을 바꾸지 않는다. `rosy-face` 밖에서 `lamp_pattern`을 직접 시작하거나 장치를 두 프로세스가 동시에 열지 않는다. LED 드라이버가 정지·오류·미확인 상태면 요청은 실패로 기록하고 신원을 추측하지 않는다.
6. **영상 대조.** Rosy Cam의 요청 전후 연속 프레임에서 *한* 익명 로봇의 후면 LED가 요청한 색·켜짐/꺼짐/켜짐 시퀀스와 시각적으로 일치하고 다른 blob에는 일치하지 않을 때만 해당 `robot_id`를 임시 표시한다. source/map/보정 revision·프레임 순서·시각이 모두 신선해야 한다. 가림, 반사, 다른 조명 변화, 로봇 이동, 프레임 누락, 중복 후보, 재보정이 있으면 즉시 `unknown`으로 돌린다. 카메라에 후면 LED가 보이지 않으면 이 폴백은 성립하지 않는다.
7. **권한 경계.** 이 연결은 Fleet 표시와 현장 확인에만 쓴다. 신원 점멸이나 영상 좌표만으로 `initialpose`, 귀환, 경로, 주차, 대형 또는 `cmd_vel`을 실행하지 않는다. 그런 동작은 별도의 CORE map localization·navigation capability·안전 게이트를 통과해야 한다(D-395·D-455). 현재 `/api/fleet/start-points`는 source별 참조점 하나이며 로봇별 귀환 슬롯을 뜻하지 않는다.

### 구현과 현장 검증 순서

1. 현장 카메라에서 후면 LED가 각 로봇에 대해 실제 보이는지, 광량·색 분리·프레임 시간 오차를 측정한다. 보이지 않으면 LED 폴백을 채택하지 않고 상단 마커를 사용한다.
2. 단일 소유 `rosy-face`의 제한 시간·안전 선점 신원 점멸 계약과 인증 요청 경로를 API reference 및 프로토콜에 정의한 뒤 구현한다. 현재 릴리스의 하드웨어 자가 시험을 운영용 식별 API로 쓰지 않는다.
3. Vision/Fleet의 연속 프레임 검출과 만료, 콘솔의 실제 영상 지도 합성을 구현하고 source·보정·신선도 불일치와 거절을 시험한다.
4. DEVICE/FIELD에서는 두 로봇을 한 대씩 점멸시키고 실제 `ceiling_north` 프레임으로 대응을 확인한다. 램프 오류 복구, 안전 표시 선점, 익명 복귀, 두 대 동시 시야와 가림, 좌표 실측 오차를 기록한다. 호스트 테스트만으로 식별 성공이나 지도 현장 수용을 선언하지 않는다.

### Consequences

영상 지도가 현재 장면을 보여 주더라도 로봇의 이름과 위치에는 각각 별도의 신원·보정 증거가 필요하다. LED 요청 경로가 설치되고 실제 영상에서 시퀀스가 검증되기 전에는 두 로봇의 카메라상 ID는 미확정이다.

### Addendum 2026-10-08 — 마커 없는 현장, D-511 입력

사용자 결정(2026-10-08): 모서리 마커는 쓰지 않는다("모서리용은 없이 할거야"). 로봇 신원은 상단 마커 대신 LED 대조로 한다("LED 깜빡임(D-472) 구현"). D-511(Fleet 차로 준수 감시)의 입력을 만들기 위한 것이다.

1. **보정.** 지도 좌표는 D-484 필드 경계 보정(`calibration_source: field_boundary`)으로 얻는다. 모서리 마커를 요구하지 않는다.
2. **3항 수정.** 상단 ArUco가 있으면 여전히 우선한다. 없으면 LED 대조가 기본 신원 경로다(폴백이 아니라 이 현장의 주 경로).
3. **7항 수정 — D-511 입력 허용.** LED로 확인된 트랙(이하 *확인 트랙*)의 지도 좌표는 D-511 차로 준수 감시의 입력이 될 수 있다(관측·콘솔 알림, D-511 M2 가장자리 신호). 다음에는 여전히 쓰지 않는다: D-494 `arbitrated_pose`와 trip 루프, `initialpose`, 귀환·경로·주차·대형, `cmd_vel`.
4. **확인의 수명.** 확인은 그 트랙이 끊기지 않는 동안만 유효하다. 트랙 손실·가림, 다른 트랙과 `0.30 m`(D-457 gate) 안으로 겹침, source·map·보정 revision 변경, 확인 후 `identity_ttl_s` 경과 중 하나면 `unknown`으로 돌아가고 다시 요청한다. `identity_ttl_s`는 현장 설정이며 초기값은 실측 후 정한다.
5. **요청 순서.** Fleet은 신원이 없는 움직이는 로봇에 한 대씩만 요청한다(4항 유지: 동시 한 대, 6초 이내). 운행 중 점멸은 운행 상태 표시를 그 시간 동안 대신한다. 5항(안전 표시 우선, E-Stop·고장·주의 중 거절·취소)은 그대로다.
6. **실측 먼저.** 구현 1단계는 `ceiling_north`에서 두 로봇의 후면 LED가 보이는지, 색 분리와 프레임 시각 오차를 재는 것이다. 보이지 않으면 이 addendum의 3항을 쓰지 않는다.
7. **안전 검토.** `rosy-face` 신원 점멸 경로는 운행 상태 표시를 잠시 대신하므로 구현 브랜치에서 D-430 `Safety-Review:`를 받는다. API는 API Ref에 버전을 올려 정한다(D-18).
