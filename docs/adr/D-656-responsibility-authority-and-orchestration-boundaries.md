## D-656 상황 판단·작업 실행·모델 숙고의 책임과 권한 경계

**Status:** Accepted (2026-10-11, 사용자 합의에 따른 책임 계약과 단계별 진행 원칙). 수용 범위는 논리 책임·권한·이행 순서다. D-652 내부 shadow 외의 구현, 공개 API 변경, 모델 호출, 외부 발송, 운영 활성화, 서비스 분산 및 장치/현장 수용을 승인하거나 완료했다는 의미가 아니다.

### Context

사용자는 로봇·암·문 등 다양한 문제를 빠르게 처리하고, 비개입 상황까지 평가하며, 실제 결과에서 지속적으로 개선하는 구조를 요구했다. Fleet의 현장 의사결정과 공통 상황평가, 모델 후보, 작업 실행을 구별해야 범용 판단을 재사용하면서 실제 실행 책임을 추적할 수 있다.

D-648은 목표 소스 구조를 Proposed로 기록했고 D-652는 Situation 공통 필요성 평가·CORE snapshot 변환·Fleet 내부 소비·최소 설치를 구현했다. 현재 `rosy.decision.tool_dispatch`는 Fleet Mission/proposal 저장소를 참조한다. `mission_service`, `mission_progress`, `step_dispatcher`에는 작업 의미와 I/O가 함께 있으며 기존 `rosy.execution.site`는 전체 Mission 실행기가 아니다. World는 현재 관측 projection이며 행동 조건부 미래 예측은 후속이다.

### Decision

#### 1. 책임은 입력·출력·변경 권한·결과 확인으로 정의한다

| 소유자 | 입력과 책임 | 출력과 변경 권한 |
|---|---|---|
| World | 출처·관측 시각·revision을 가진 장치/공간 상태와 불확실성 | 현재 상태 projection. 관측 누락을 추정 성공으로 채우지 않음 |
| Situation | 현재 상태, 도메인이 확인한 condition, 목표 진척·대기 기한·정책 | 개입/비개입/보류와 근거·유효기간. 공통 평가 자체는 원장·장치 요청을 쓰지 않음 |
| Decision | 유효한 문제 자료, 허용 후보, 추가 관측 필요와 예산 | 해결 후보·반론·불확실성. 후보는 실행 권한이나 완료 증거가 아님 |
| execution/site 순수 규칙 | 목표·현재 진행·실행 결과·복구 예산 | 작업 순서·재시도/보류·목표 근거 검증의 계산. DB/HTTP/claim/stop fence는 소유하지 않음 |
| Fleet 현장 어댑터 | 현재 권한·owner·사건/작업·자원·정책과 유효 후보 | 기존 transaction에서 승인/거절·기록·조치 제출·결과 추적. 로봇 배정·교통·공유 자원 coordination 유지 |
| CORE/장치 owner | 승인된 요청과 현재 장치 상태·안전 조건 | Base 최종 출력은 CORE, Arm 출력은 OMX. 실행/정지 readback과 로컬 보호 유지 |
| 평가·학습 | 사건 lineage, 정상/비개입 표본, 실제 결과와 독립 정답 | 교정·모델/프롬프트/규칙 개선 후보와 평가 receipt. 운영 정책을 자동 덮어쓰지 않음 |

책임 분리는 같은 배포 안의 코드 경계부터 시행한다. Fleet `server`라는 현재 위치를 공통 작업 의미 전체의 소유권으로 해석하지 않는다. 단일 셀·단일 장치·관측-only에서도 공통 평가를 재사용하고 로봇 집합 coordination을 필수로 강제하지 않는다.

#### 2. 모델 숙고와 작업 실행의 오케스트레이션을 구별한다

Decision의 모델 런은 모델 선택·호출·시간/횟수/비용 제한·취소·후보 검증을 맡는다. 실제 사건/작업 owner는 자원·담당·진행·재시도 예산·조치 접수·결과를 맡는다. 모델 런은 기존 사건/작업을 참조하며 두 번째 Mission/claim 원장이나 별도 실행기를 만들지 않는다.

D-640의 제한된 모델 토론을 재사용한다. 정상 작업, 빠른 현장 규칙, 안전 정지·로컬 복구는 느린 모델을 기다리지 않는다. 토론 실패·timeout·상충·늦은 결과는 현행 보류/규칙/사람 경로로 끝내고 실행 권한을 넓히지 않는다. 모델 합의·confidence는 신선한 관측이나 독립 목표 검증을 대신하지 않는다.

#### 3. 사건 처리 owner와 종료 책임을 하나로 묶는다

사건/작업별 활성 조치 결정 owner를 기존 원장에 명시한다. 사람 인수, lease/claim 상실, 재시작·취소·재시도는 현재 owner와 generation으로 대조한다. 대상·사건/작업·attempt·상태 revision·owner·정책 revision·유효기간 중 해당 계약의 binding이 달라지면 과거 권고/모델 결과를 재사용하지 않는다.

판단 → owner 채택/보류 → 조치 제출 → 수락/거절/응답 불명 → 실행 terminal → 목표 근거 확인 → 사건 해소/종료를 구별한다. 종료 상태의 writer는 기존 사건/작업 owner 하나이며 독립 goal verifier의 결과를 소비한다. 모델·알림 adapter·UI는 종료 상태를 직접 쓰지 않는다. 자연 해소는 현재 근거로 기록하고 조치 성공의 공로로 집계하지 않는다.

정상 비개입은 신규 조치/문제 알림 zero-send와 정상 평가 표본을 남긴다. 보류는 비개입과 구별하고 필요한 관측·다음 확인·담당 상승 조건을 둔다. 공통 평가의 `ABSTAIN`을 정상/안전/작업 완료로 표시하지 않는다. D-652의 line-follow OFF는 해당 감시의 비개입이며 전체 Mission 성공이 아니다.

#### 4. 범용 계약과 실제 도메인 증거를 함께 검증한다

문·Arm·로봇의 정상/대기/막힘 condition은 해당 producer와 domain adapter가 실제 관측에서 확인한다. 공통 평가 시험만으로 문 닫힘·Arm 대상 누락의 실제 검출 정확도를 주장하지 않는다. CORE revision·시각이 없는 legacy 가설 초안은 `needs_review`를 유지하며 공통 평가의 신선한 동일 사건 근거로 승격하지 않는다.

문 앞 정지 사례는 상태 관측 → 안전 대기/지속 장애/근거 부족 평가 → 재관측·허용 문 요청·우회·사람 호출 후보 → 현재 권한/자원 검사 → 장치 실행 → 통과/진척 확인으로 검증한다. 문 제어 capability가 없으면 문 요청 후보를 실행 가능한 것으로 승인하지 않는다.

#### 5. 알림과 개선은 같은 사건/결과를 소비한다

Discord·Slack·Telegram은 D-645의 outbox와 인증 Console 인수 경로를 따른다. 발송·읽음·사람 인수·조치 수락·실제 해소는 각각 기록하며 채널을 장치 writer로 만들지 않는다. 정상 신규 알림 zero-send와 기존 사건 종료 알림을 구별한다.

평가에는 장애뿐 아니라 정상·허가 대기·비개입·보류·자연 해소를 포함한다. 독립 정답으로 불필요 개입률·개입 누락률·보류율·해소율·처리 지연·재발을 비교한다. 분모, 관측 구간, 도메인, 버전, 표본 수를 고정하고 안전 정지를 실패로 보상하지 않는다. 모델 합의와 채널 ACK를 학습 정답으로 쓰지 않는다.

규칙·단일 모델·제한 토론을 같은 독립 평가 세트로 비교한다. 평가 허용 한계·정답·표본이 미정이면 운영 승격 HOLD다. 학습 데이터 분할, 고정 산출물, shadow·제한 장치·현장 수용, 이전 승인 버전으로의 rollback은 D-640/D-646/D-527 관문을 따른다.

#### 6. 설치 및 배포 경계는 논리 책임과 별도로 관리한다

빌드 소스 구성은 `tools/packaging`, 이미지/서비스 설치는 `deploy`, 실제 역할 코드는 해당 operations/middleware/learning holder가 소유한다. D-652 순수 세 파일 closure와 checkout 밖 wheel/sdist 검증을 유지한다. 폴더 이동으로 장치 token·원장·실행 호스트 권한을 이동하지 않는다.

최초 실행 경계는 현재 배포를 유지한다. 별도 서비스는 실제 복수 소비자, 자원 경합·장애 격리, 지연 예산과 운영 비용이 검증되고 API/version/auth/timeout/restart 관문이 정의된 뒤 별도 ADR로 결정한다. Fleet PC의 제한 supervisor 배치와 AI PC 고정 추론, 모델 PC 학습/평가 역할은 기존 호스트 계약을 따른다.

### Alternatives and consequences

Fleet 서비스에 모든 의미를 계속 모으면 현재 연결은 단순하지만 단일 셀 재사용과 모델·작업 권한 분리가 어려워진다. 즉시 독립 서비스를 만들면 장애 격리는 가능하지만 새 인증·원장·재시작·지연 문제가 생긴다. 같은 배포에서 순수 규칙과 현장 어댑터를 먼저 추출하는 방식을 채택한다. 설치 mapping과 Python 소비자도 함께 고쳐야 하며 경로 이동만으로 완료라 하지 않는다.

### 이행과 기존 ADR의 관계

| ADR | 관계 |
|---|---|
| D-427/D-429/D-430 | 소유 분류, 후보/중재/장치 writer와 Safety gate 유지 |
| D-647/D-648 | 책임/초기 배포의 잠정 방향을 이 ADR의 논리 계약으로 구체화. 기존 Proposed 문서 전체를 소급 수용하지 않음 |
| D-652 | 현재 내부 shadow와 최소 설치의 수용 범위 유지. 운영 소비/새 도메인 활성화는 별도 검증 |
| D-642~D-646 | 현재/당시 근거, 필요성, owner/결과, 사람 처리와 독립 수용은 모델 토론의 선행 관문 |
| D-640 | 모델 런과 개선 상세 설계를 재사용. 이번 ADR로 provider 호출/자동 조치를 활성화하지 않음 |

후속 작업의 통합 순서는 [책임 분리 실행 계획](../plans/2026-10-11-responsibility-authority-orchestration.md)으로 관리한다. 기존 단계별 계획의 파일/시험 세부를 재사용하고 완료·진행·미착수와 SOURCE/설치/CI/배포/DEVICE/FIELD 증거를 구별한다.
