## D-544 천장 카메라(Rosy Cam)는 나쁜 조명을 스스로 재고 노출 보정만 한정된 범위에서 고친다 — 기본 꺼짐, 폰이 닫는 고리, 기하 보정은 건드리지 않는다

**Status:** Proposed (2026-10-09, 사용자 요청: 강한 빛·눈부심·날아간/너무 어두운 프레임에서도 추적이 유지되도록 천장 카메라가 조명을 감지해 설정을 스스로 고치고 ADR로 남긴다). 1단계(폰 측정 + 한정된 로컬 노출 보정, 기본 꺼짐)만 이 ADR과 같이 구현한다. 2단계 이후는 이 문서의 조건이 채워진 뒤 Accepted로 올린다.

잇는 결정: [D-257](D-257-site-lane-map-and-overhead-sightings.md)(관측은 표시 전용) · [D-261](D-261-overhead-camera-app-skeleton.md)(앱, 프레임 선로) · [D-341](D-341-overhead-console-approved-pairing.md)(페어링) · [D-425](D-425-app-surface-ownership-shared-boundaries-and-source-layout.md)(앱 표면 소유·공유 경계) · [D-484](D-484-field-boundary-auto-calibration.md)(필드 경계 자동 보정) · [D-513](D-513-demo-start-places-fixed-heading.md) · [D-515](D-515-fleet-camera-top-down-site-picture.md)(수락된 보정으로 편 그림). 로봇 카메라의 AE/AWB 재잠금(`camera_controls.RelockWatch`, `camera_visibility.road_clip_stats`)의 발상을 가져온다.

### Context

- 천장 폰은 CameraX 자동 노출로 돈다. 창가 직사광이나 조명이 바뀌면 흰 경계선·로봇 마커가 날아가거나(clipped) 그늘이 뭉개져(crushed) Vision의 마커·로봇 검출과 D-484 경계 찾기가 떨어진다. 지금은 사람이 폰을 보고 알아채야 한다.
- 앱에는 이미 밝기 표본(`YPlaneLuma`, 0.25 s 간격 Y 평면 평균)과 어두움에서만 켜지는 손전등 정책(`AutoLightPolicy`, 기본 꺼짐)이 있다. 둘 다 "너무 어둡다"만 보고 "날아갔다"는 보지 못한다.
- 프레임 선로(`rosy-overhead/1`, 20바이트 `ROF1` 헤더)는 공유 벡터(`overhead-ingest.v1.json`)가 양쪽에서 읽는 동결 표면이다. 헤더의 `reserved` u16은 쓰지 않는다.
- 로봇 카메라 사건(rosy_26, 2026-10-06)이 보여 준 것: 한 번 잠근 노출은 방이 밝아지면 47–71 %가 날아가도 그대로다. 반대로 재잠금이 잦으면 암전 반복이 된다. 그래서 dwell과 최소 간격이 필요하다.

### Decision

1. **누가 결정하나: 폰이 닫는 고리(1단계).** 측정과 조정은 폰 안에서 끝난다. 이유: (a) 지연이 짧고 Wi-Fi가 끊겨도 동작한다, (b) 프레임 선로와 Vision·Fleet에 새 제어 채널을 넣지 않는다(동결 표면 유지, 새 채널은 정당화가 필요하다). Vision이 추천을 돌려보내는 방식은 2단계 후보로만 적고, 채택하려면 별도 ADR에서 검출 신뢰도 추세가 폰 측정보다 나은 신호임을 녹화 프레임으로 보여야 한다. Vision/Fleet은 폰의 노출 설정을 "바꾸라고 명령"하지 않는다. 운영자 수동 지정은 4항의 표시·덮어쓰기 경로만 쓴다.
2. **무엇을 재나(폰, 필드 영역).** Y 평면의 가운데 영역(가장자리 렌즈 모서리·창틀 제외, 전체 프레임의 가로·세로 각 10 % 안쪽)을 성기게 표본한다. 값은 셋이다.
   - `clip` = 휘도 ≥ 247 비율(로봇 카메라 `CLIP_LEVEL`과 같은 문턱).
   - `crush` = 휘도 ≤ 16 비율.
   - `mean` = 평균 휘도.
   깜빡임(플리커)과 검출 신뢰도 추세는 1단계에서 재지 않는다. 플리커는 아래 3항의 안티밴딩 문제이고 Camera2 `CONTROL_AE_ANTIBANDING_MODE`는 지금 기본(자동)이다. 검출 신뢰도는 Vision 소유 신호라 2단계다.
3. **폰이 바꿀 수 있는 것(Camera2 허용 목록).** 1단계는 **AE 노출 보정 지수(`setExposureCompensationIndex`) 하나**만 바꾼다. 이유: CameraX가 재바인딩 없이 지원하고, 자동 노출의 잠금·해제·시간·ISO 로직을 우리가 대신 쥘 필요가 없으며, 초점·배율·해상도·스케일러 크롭·손떨림 보정에 손대지 않는다. 지수는 카메라가 보고한 범위 안에서 `±2` 단계(`EV_LIMIT_STEPS`)로 제한한다. 다음은 **1단계에서 하지 않는다**: AE 잠금/해제, 수동 노출 시간·ISO, AWB 잠금, 50/60 Hz 안티밴딩 고정. 이들은 2단계 이후 후보이고, 각각 녹화 프레임으로 이득을 보인 뒤 올린다. 렌즈 선택·배율·해상도·`bind()`는 어떤 경우에도 조명 때문에 바꾸지 않는다.
4. **운영자가 보는 것.** 1단계는 폰 화면(스트림 화면)에 현재 판정(정상/과노출/저노출), `clip`·`crush`·`mean`, 현재 보정 지수를 보이고 설정의 스위치로 켜고 끈다. Fleet 경고·현재 설정 표시·수동 덮어쓰기는 폰에서 Fleet으로 올라가는 상태 필드가 필요하므로 2단계다. 2단계의 선로는 `hello`의 선택 필드 `exposure`(렌즈 `lens`와 같은 방식: 선택, 알 수 없는 키 무시, 다음 hello에 반영)와 상태 변화 시 한 번 보내는 JSON 텍스트로 하며, **바이너리 프레임 헤더는 바꾸지 않는다.** 이 ADR이 Accepted가 되기 전에 그 필드를 공유 벡터에 먼저 넣는다.
5. **흔들림 방지(히스테리시스·한도).** 판정은 문턱 두 쌍이다: 과노출 진입 `clip ≥ 0.25`, 해제 `clip ≤ 0.10`; 저노출 진입 `mean ≤ 40 또는 crush ≥ 0.40`, 해제 `mean ≥ 60 그리고 crush ≤ 0.20`. 나쁜 상태가 `DWELL_MS = 3000` 동안 이어져야 한 단계를 움직이고, 한 단계 뒤 `MIN_INTERVAL_MS = 4000` 동안은 다시 움직이지 않는다(자동 노출이 수렴할 시간). 좋은 상태가 `RECOVER_MS = 10000` 이어지면 지수를 0 쪽으로 한 단계 되돌린다. 과노출은 지수를 내리고 저노출은 올린다. 손전등 정책과 겹치지 않게 손전등이 켜진 동안(`torchOn`)은 조정하지 않는다. 한도에 닿아도 계속 나쁘면 더 하지 않고 판정만 남긴다.
6. **프레임이 쓴 설정을 어떻게 알리나, 보정이 유효한 이유.** 노출 보정은 밝기만 바꾸고 기하(화각·왜곡·해상도·회전)는 바꾸지 않으므로 `map_to_image` 같은 기하 보정(D-484·D-375·D-457)은 노출 변경으로 무효가 되지 않는다. 이를 보장하기 위해 1단계는 위 3항의 금지 목록(배율·크롭·해상도·렌즈·재바인딩)을 지키고, 단위 시험으로 정책이 지수 외 어떤 출력도 내지 않음을 고정한다. 프레임별 메타데이터는 1단계에서 선로에 싣지 않는다(헤더 동결). 폰 로그에 지수 변화를 `exposure_ev` 한 줄로 남기고, 2단계 `hello.exposure`가 `ev_index`·`state`·`clip`·`crush`·`mean`을 싣는다. 색 기반 검출(D-484 흰 경계)은 노출 지수가 바뀐 직후의 몇 프레임을 다시 수렴시킬 수 있다는 점을 DEVICE 단계에서 확인한다.
7. **안전한 기본값.** 설정 `auto_exposure_assist`는 **기본 꺼짐**이다. 꺼짐이면 측정도 하지 않고(CPU 포함) 지수를 0으로 되돌리며, 켜졌다가 꺼질 때와 카메라 바인딩이 바뀔 때 지수를 0으로 되돌린다. 열 차단(`thermalBlocked`) 중에는 조정하지 않는다. 설정은 DataStore에만 있고 선로·페어링·사이트 링크에 들어가지 않는다.
8. **수락 단계.**
   - **SOURCE:** 정책(`ExposureAssistPolicy`)과 측정(`LumaStats`)의 JVM 단위 시험 — 문턱·히스테리시스·dwell·최소 간격·한도·되돌림·시계 역행·꺼짐 동작.
   - **LOCAL:** 녹화된 프레임(밝은/어두운/정상)을 같은 측정 함수에 먹여 판정이 맞는지, 그리고 지수 조정 전후 프레임에서 Vision 마커·경계 검출이 떨어지지 않는지 확인한다(비공개 증거). 2단계 선로 필드는 `overhead-ingest.v1.json` 벡터와 Python 쪽 시험을 함께 갱신해야 통과다.
   - **DEVICE:** Galaxy S21에서 강한 빛 아래 켠 채 (a) 판정이 과노출로 바뀌고 지수가 한도 안에서 내려가며 진동하지 않는지, (b) 끄면 지수 0으로 돌아오는지, (c) 조정 전후 Vision 검출이 유지되는지, (d) 열·배터리 영향이 없는지 본다. 이 ADR의 구현 시점에는 DEVICE를 하지 않았다(다른 세션이 장치와 스트림을 점검 중이라 설치하지 않았다). DEVICE가 GO가 되기 전에는 Accepted로 올리지 않고 기본 꺼짐을 유지한다.

### Consequences and verification

- 1단계 코드: `camera/LumaStats.kt`(clip·crush·mean), `camera/ExposureAssistPolicy.kt`(순수 정책), `CameraController`(표본→정책→`setExposureCompensationIndex`), `SettingsStore`·설정 화면의 스위치. 선로·Vision·Fleet·보정 설정은 바꾸지 않는다.
- 되돌리기: 설정을 끄면 동작 전체가 사라진다. 코드 되돌림은 위 파일 삭제와 `CameraController` 호출 한 곳이다.
- 열린 것: Fleet 경고·수동 덮어쓰기(2단계), 안티밴딩·AWB·수동 노출(3단계 후보), Vision 신뢰도 추세 귀환 채널(별도 ADR), 문턱값 실측 조정(DEVICE).
