## D-876 ROSY Monitoring — 사이트 독립 감시와 통합 집계

**Status:** Accepted (2026-10-25, 사용자의 구조·명칭 결정 및 ADR 우선 기록 지시). 모듈의 목표와 책임 경계를 수용한다. 구현·배포·장치·현장 수용을 뜻하지 않는다.

### Context

ROSY에는 CORE 진단·metrics, 호스트 감시와 복구, Fleet 로봇 연결 상태, 관제 단위 정보 수집이 이미 있다. 사용자는 관제 간 네트워크 문제와 다른 시스템 장애를 전체 연결 관계와 함께 확인하고, 개별 사이트와 통합관제 양쪽에서 사용할 수 있는 독립 모듈을 요청했다.

현재 관제 간 정보 수집은 여러 예외를 `CONTROL_UNIT_PEER_INFORMATION_UNAVAILABLE`로 합친다. 업무에서 보수적으로 정보 부재를 처리하는 데에는 유효하지만, 인증 실패·시간 초과·응답 계약 오류를 진단하는 근거로는 부족하다. Fleet 안에서만 감시하면 Fleet 프로세스가 종료됐을 때 상태 조회도 함께 잃는다.

| 기존 구현 | 유지할 책임 |
|---|---|
| [CORE observability API](../../middleware/core/api/core_api_web/api/v1/observability.py) | 로봇 진단·이벤트·감사 조회와 Prometheus metrics |
| [host-guard](../../deploy/site/rosy-host-guard)·[SSH watchdog](../../deploy/hosts/common/rosy-ssh-watchdog) | 호스트 감시와 기존 정책에 따른 복구 |
| [Fleet 호스트 조회](../../operations/fleet/fleet/server/host_control_routes.py) | guard·호스트 상태 조회와 별도 권한을 요구하는 제어 |
| [관제 정보 수집](../../operations/fleet/fleet/server/ledger/control_unit_collection.py) | 관제 범위 검증, 정보 신선도와 수집 불가 처리 |
| [로봇 연결 판정](../../operations/fleet/fleet/server/console/console_view.py) | 로봇 도달 불가·인증 거부 등 기존 연결 근거 |

### Decision

#### 1. 이름과 소유권

정식 모듈명은 **ROSY Monitoring**, 한국어 표시는 **ROSY 시스템 모니터링**, 모듈 식별자는 **`rosy-monitoring`**으로 통일한다. `ROSY Observability`는 검토 당시 이름이며 별도 모듈이나 제품으로 만들지 않는다.

ROSY Platform 안에서 Fleet과 독립된 운영 모듈로 둔다. 수집·집계 런타임의 목표 소유 경로는 `operations/monitoring/`, 독립 상태 화면의 목표 경로는 `applications/monitoring/`이다. D-427의 operations·applications 경계를 따른다. 이번 ADR은 디렉터리·패키지·서비스를 생성하거나 소유권 manifest에 구현 완료를 등록하지 않는다. 구현 착수 시 `platform_parts.yaml`에 실제 소유 영역을 등록한다. 별도 Git 저장소를 만들지 않는다.

#### 2. 한 모듈의 사이트 수집과 통합 집계

| 역할 | 담당 내용 | 독립 동작 조건 |
|---|---|---|
| 사이트 수집 | 등록된 CORE·PC·Fleet·AI 서비스의 기존 상태를 읽고, 구성 요소와 연결의 관측을 제공 | 통합관제 연결이 끊겨도 로컬 수집·조회가 계속된다 |
| 통합 집계 | 허용된 사이트 수집기의 결과를 모아 사이트 간 연결과 영향을 표시 | 하위 일부가 끊겨도 나머지를 조회하며, 끊긴 범위의 신선도를 낮춘다 |
| 중앙 단독 실행 | 하위 수집기 없이 명시적으로 등록한 대상을 직접 관측 | Fleet이나 관제 계층의 존재를 실행 필수 조건으로 삼지 않는다 |

사이트 수집과 통합 집계는 같은 구현의 배치 역할이다. 사이트별로 독립 실행·조회할 수 있어야 하며, 모든 앱마다 별도 수집기를 두지 않는다. 같은 사이트의 중복 실행 방지와 저장 책임은 구현 계약에서 정한다.

Monitoring은 Fleet과 별도 프로세스로 실행할 수 있어야 한다. CORE 내부 진단은 기존 단일 프로세스 계약을 유지한다. 별도 Monitoring 프로세스가 로봇 CORE를 분리하거나 ROS 직접 접근 경로를 추가하지 않는다.

#### 3. 상태 원천과 공통 관측 계약

기존 소유자는 자신의 상태 판정과 근거를 제공한다. Monitoring은 그 출처·시각·정보 나이와 관계를 보존하고, 수집 경로의 상태를 추가한다. 원천의 상태 판정과 수집 정보의 신선도를 하나의 값으로 덮지 않는다.

공통 관측에는 다음 의미를 담는다. 이 표는 외부 API 필드명이나 신규 URL을 정의하지 않는다.

| 대상 | 필요한 의미 |
|---|---|
| 구성 요소 | 안정적인 식별자, 종류, 소유 사이트, 원천, 관측 시각과 정보 나이 |
| 연결 | 출발·도착, 방향·프로토콜, 설정상 기대 관계와 실제 관측 관계 |
| 통신 결과 | 마지막 성공, 요청 소요 시간, 확인된 실패 단계·이유, 근거 참조 |
| 이력 | 장애 발생·변화·회복 관측, 재접속 시 유실 구간과 출처 |

DNS·접속·TLS·인증·응용 응답·계약 검증·시간 초과는 실제 확인된 단계까지만 구분한다. 판별하지 못한 원인은 확인 불가로 남긴다. HTTP 시간 초과만으로 물리 단절이나 패킷 손실률을 확정하지 않는다. 그래프는 서비스·논리 연결을 표현하며, 설정만으로 실제 정상 연결을 표시하지 않는다.

상위 집계가 다시 수신했다고 원천 관측을 새 표본으로 바꾸지 않는다. 전달 지연과 PC 시각 차이를 고려해 정보 나이를 보존한다. 중앙이 사이트에 연결할 수 없으면 중앙에서의 수집 불가를 표시하고, 현장 전체가 정지했다고 단정하지 않는다. 오래된 로봇 값·상태는 현재 값처럼 표시하지 않는다.

외부 API·인증·envelope와 구체적인 시간 전달 방식은 구현 전 API reference와 스키마에 함께 등록한다. 이 ADR만으로 기존 API나 관제 wire 계약을 변경하지 않는다.

#### 4. 화면과 도구

개별 관제는 담당 범위, 통합관제는 허용된 여러 사이트의 관측을 표시한다. 별도 상태 화면은 Fleet 업무 화면을 거치지 않고 조회할 수 있어야 한다. 각 화면이 같은 관측 계약을 사용하며 별도의 정상·오류 판정을 복제하지 않는다.

Grafana는 연결 그래프·지표 이력 분석 도구 후보로 둔다. 설치·의존성·도입 결정은 이번 ADR에 포함하지 않는다. 기본 수집과 상태 조회가 Grafana의 가용성에 의존해서는 안 된다. 기존 CORE metrics를 재사용하고, 자체 시계열 DB·그래프 DB를 새로 만드는 것은 첫 범위에서 제외한다.

#### 5. 명령·복구·권한 경계

- CORE·OMX의 안전 판정과 최종 장치 명령, World의 현재 사실, Fleet의 업무 원장·admission·dispatch 소유권을 유지한다.
- 첫 범위는 상태·원인·이력·복구 안내다. Monitoring은 재시작·재부팅·네트워크 설정 변경·안전 해제를 직접 실행하지 않는다. 실제 조치는 기존 담당 기능의 권한·확인 경로로 연결한다.
- host-guard·watchdog의 기존 자동 복구는 담당 소유자에게 남긴다. Monitoring이 이를 복제하거나 새 조치 루프를 추가하지 않는다.
- 사이트·대상은 명시적으로 등록하고 인증된 허용 범위만 수집·공유한다. 임의 네트워크 탐색을 하지 않는다. 기존 operator 전용 상태를 viewer에게 확대 공개하지 않는다.
- 토큰·내부 설정·원본 예외 본문을 상태 응답·그래프·공유 이력으로 전달하지 않는다. 근거 참조도 같은 접근 범위를 적용한다.
- 수집의 시간·동시성·응답 크기·재시도·보존량을 제한한다. 제어의 동기 이벤트 경로에 외부 전송을 붙이지 않는다. Monitoring 장애로 로봇 명령을 발생시키거나 제어 가용성을 막지 않는다.

#### 6. 구현 전 확정과 수용 기준

구현 계획에서 최초 수집 대상, 읽기 인증·권한, API 계약, 시각 차이·정보 나이 전달, 이력 저장·보존 한도, 실행·업데이트·수집기 자체 장애 감시를 확정한다. 수집기 자신의 정상 판정만으로 수집기 가용성을 증명하지 않는다.

소프트웨어 수용에는 다음 증거가 필요하다.

1. Fleet 종료 중에도 독립 수집기와 상태 화면이 동작하고 Fleet 장애를 표시한다.
2. 중앙 단절 중 사이트 수집·조회와 기존 감시·복구가 계속된다. 중앙에서는 단절 범위와 오래된 근거를 구분한다.
3. 인증 실패·시간 초과·잘못된 응답·stale을 주입해 확인 가능한 원인과 출처를 표시한다.
4. Monitoring 중단·지연·잘못된 입력이 로봇 명령이나 안전 해제로 이어지지 않는다.
5. 권한 밖 사이트와 비밀값이 응답·로그·그래프에 노출되지 않는다.
6. 재시도·이력은 유한하고, 중복·역순·재전송 표본이 기존 표본을 새 정상으로 승격시키지 않는다.

실제 PC 배치, LAN·TLS 단절 및 복구, 장치 운전 중 영향은 소프트웨어 회귀와 분리해 현장 수용한다. 문서 수용·호스트 pytest 통과·화면 표시만으로 운영 완료를 선언하지 않는다.

### Alternatives

| 대안 | 판단 |
|---|---|
| Fleet 내부 감시 기능만 확장 | 기존 UI 연동은 쉽지만 Fleet 장애 시 독립 조회를 잃고 다른 ROSY 소비자와 결합된다 |
| 기존 감시 출력을 연결하는 독립 Monitoring | 선택. 기존 소유권과 복구를 유지하면서 사이트 독립 동작과 통합 집계를 제공한다 |
| Grafana 중심으로 상태·권한·복구까지 일괄 구성 | 도구 평가 전에 제품 구조를 특정 도구에 고정하며, ROSY 명령·복구 권한까지 섞일 수 있다 |

### Consequences

독립 실행 단위와 읽기 권한·배포 관리가 추가된다. 대신 Fleet 장애를 외부에서 관측하고, 사이트 독립 실행과 통합 조회를 같은 계약으로 지원할 수 있다. 도구 선택과 런타임 구현은 후속 작업이며 이번 변경은 ADR과 문서 등록에 한정한다.

### Related decisions

- D-175: 기존 장치 진단 번들·증거 수집을 재사용하며 대체하지 않는다.
- D-415: 기존 관제 진단 패널과 연결하고 업무 화면의 책임을 유지한다.
- D-427: 플랫폼 소유 영역과 설치 경계를 따른다.
- D-530: Proposed 호스트 관리 설계의 수용 상태를 변경하지 않고 현재 감시·복구 구현을 재사용한다.
- D-850·D-855·D-862: 관제 구성·wire·정보 수집 계약을 유지한다. Monitoring의 정보 수집은 위임·정지 권한을 만들지 않는다.

CE: 해당 없음 — 기존 구현 조사에 근거한 구조 결정이다. 새로운 런타임 장애 해결이나 장치 수용을 주장하지 않는다.
