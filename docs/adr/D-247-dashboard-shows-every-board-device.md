## D-247 대시보드는 보드의 모든 장치가 붙어 있고 응답하는지를 보여준다 — 장치 관측과 제품 기능을 가른다

**Date:** 2026-09-25

**Status:** Proposed

**Context:** 2026-09-25 `rosy_18`(`rosy-pinky-e4us`, 네이티브 이미지 release 012)을 원격으로 점검했다.
대시보드만으로는 아무것도 알 수 없었고, 모든 판단을 SSH와 커널 로그로 했다.

1. **운용자는 왜 못 움직이는지 모른다.** operator로 로그인하면 조작이 전부 막혀 있었다. 이유는 역할이
   아니라 `ROSY_RUNTIME_MODE=core`였다(capability 5개 `withheld: runtime_mode:core`). 화면에는
   "현재 하드웨어 프로필에서 teleop을 사용할 수 없습니다" 한 줄뿐이라, 사용자는 권한 문제로 읽었다.
2. **부품이 붙어 있는지 화면에 없다.** 점검 결과는 다음과 같았다.
   - 모터 XL330 ×2, LiDAR, 휠 오도메트리, LCD: 정상이었다.
   - IMU BNO055: 칩은 정상(ID `0xA0`)이다. 이미지가 `/dev/i2c-0`을 켜지 않아서 기본 상태에서는 보이지
     않는다.
   - ADC MCU(`i2c-1` 0x08; 배터리, IR ×3, 초음파): 13:39에는 8.49 V로 정상이었다. Pi를 재부팅한 뒤로는
     `controller timed out`만 난다.
   - 카메라 OV5647: 두 포트 모두 `-121`이다.
   - LED 램프(WS2812): 하드웨어는 있다. `rp1_ws281x_pwm` 커널 모듈이 이미지에 없다.
   - 부저: 핀이 확인되지 않아 꺼져 있다(D-190). 사람은 부팅할 때 소리를 들었다.

   대시보드는 이 가운데 어느 것도 구분해 보여주지 않았다. LCD는 배터리 칸에 `--`만 띄웠다.
3. **capability는 다른 질문에 답한다.** capability는 "제품이 이 기능을 약속하는가"다(D-11, D-169).
   D-169는 IMU·램프·LED·emotion을 벤치 전용으로 정했다. 그래서 이 장치들은 capability에 영원히 없다.
   붙어 있는지, 응답하는지, 고장인지를 볼 자리가 없다.
4. **측정 방법에도 함정이 있다.** 죽은 I2C 버스를 주소마다 훑으면 주소 하나에 1초씩 걸려 2분이 넘는다.
   0x08은 IR·배터리 판독과 flock을 공유한다(D-192). UART는 `rosy-io`가 이미 열고 있을 수 있다.

**Decision:**

1. **질문을 둘로 나눈다.**
   - *장치 관측*: 이 장치가 보드에 붙어 있고 지금 응답하는가.
   - *제품 기능*: 제품이 이 기능을 제공하는가. 이것은 capability(D-11)와 D-169가 계속 정한다.

   대시보드는 앞의 질문을 새로 보여준다. 이 ADR은 D-169의 제품 장치 표면을 바꾸지 않는다.
2. **점검 뷰에 "장치" 카드를 둔다.** 이 카드는 보드 목록(`deploy/robot/config/board.yaml`)의 모든 장치를
   한 줄씩 보여준다. 대상은 모터 ID 1·2, LiDAR, IMU, ADC 채널 다섯 개(배터리·IR 0–2·초음파), 카메라,
   LCD, 부저, LED 램프, Pi 전원과 온도다. 벤치 전용 장치도 빠짐없이 나오고 `벤치 전용` 표지를 단다.
3. **상태 어휘는 여섯 개로 고정한다.** 각 행에는 근거 한 줄과 측정 시각이 붙는다. 근거는 칩 ID, Hz, 전압,
   커널 오류 코드처럼 측정한 값이다.

   | 상태 | 뜻 |
   |---|---|
   | `정상` | 측정값이 기대 범위 안이다 |
   | `응답 없음` | 버스는 있는데 장치가 답하지 않는다(`-121`, `ETIMEDOUT`) |
   | `버스 없음` | 이미지가 버스를 켜지 않았다(`/dev/i2c-0` 없음) |
   | `드라이버 없음` | 커널 모듈이나 장치 노드가 이미지에 없다 |
   | `사람 확인 필요` | 소리나 빛처럼 기계가 스스로 판정할 수 없다 |
   | `측정 안 함` | 다른 서비스가 장치를 쥐고 있어 이번에 열지 않았다 |
4. **측정은 root 쪽 읽기 전용 probe가 한다. CORE는 장치를 열지 않는다(D-161).**
   - `rosy-hw-probe`는 systemd oneshot이다. 부팅 뒤 한 번, 그리고 관리자가 요청할 때 돈다.
   - 결과는 `/run/rosy-boot/hardware.json`(root:rosy-core 0640)에 쓴다. CORE는 이 파일을 읽기만 하고,
     `GET /api/v1/host/hardware`(viewer 이상)로 내보낸다. 로그인 코드 파일과 같은 방향이다(D-193).
   - `rosy-io`가 돌고 있으면 그 장치를 다시 열지 않는다. 대신 CORE가 이미 가진 토픽 신선도로 판정한다.
     대상 토픽은 `scan`, `odom`, `joint_states`, `battery/voltage`다.
5. **probe가 지킬 규칙.**
   - 알려진 주소만 읽는다. 버스 전체를 스캔하지 않는다.
   - 장치마다 시간 제한을 둔다. 첫 요청이 시간 초과면 그 버스의 나머지 장치는 `측정 안 함`으로 끝낸다.
   - 0x08은 D-192 flock을 잡는다.
   - BNO055는 칩 ID와 상태 레지스터만 읽는다. 동작 모드를 바꾸지 않는다.
   - 모터는 `rosy-io`가 꺼져 있을 때만 토크 없는 ping을 한다.
   - 카메라는 커널 probe 결과(dmesg)와 CSI 상태만 읽는다.
6. **사람 확인 장치는 관리자 전용 시험 동작으로 확인한다.** 부저는 짧게 한 번 울리고, LED 램프는 한 번
   켰다 끈다. 관리자가 들림·보임을 누르면 누가 언제 확인했는지 기록한다.
   - 기록이 없으면 상태는 `사람 확인 필요`로 남는다.
   - 부저를 기본으로 켤지(D-190 `ROSY_BUZZER_ENABLED`)는 이 기록을 근거로 정한다.
   - 시험 동작은 모터와 `cmd_vel`에 닿지 않는다.
7. **운용 뷰는 왜 못 움직이는지를 사람 말로 한 줄 보여준다.** 원천은 `host/commissioning`의
   `runtime_mode`와 hold 목록이다. 예: "모터가 꺼진 CORE 전용 모드입니다. 관리자가 모터 모드로 올려야
   움직입니다." 이 문장은 권한 부족 문구와 구별된다.

**Alternatives:**

- **SSH 점검 스크립트만 둔다.** 운용자는 볼 수 없고, 결과가 터미널에서 사라진다. 이번 점검이 그랬다.
- **CORE가 장치를 직접 연다.** D-161 경계를 깨고 CORE에 I2C·UART·GPIO 권한을 준다. 장치 하나가 멈추면
  API가 같이 멈춘다.
- **capability에 합친다.** 벤치 전용 장치가 제품 기능처럼 보이고 D-169가 흐려진다. capability는 정적
  YAML이라 "지금 응답하는가"를 담지 못한다(D-11).
- **`rosy_control` 진단 화면을 되살린다.** 운용자 콘솔이 둘이 된다(D-77).

**Consequences:**

- **새 구성요소.** root probe 하나, `/run/rosy-boot/hardware.json` 스키마, API 하나, 점검 뷰 카드 하나,
  운용 뷰 문장 하나가 생긴다.
- **이미지 결함이 화면에 드러난다.** 대상은 `i2c-0` 미활성, `rp1_ws281x_pwm` 부재, `i2cdetect`·`rpicam`
  도구 부재다. 이것들을 고칠지는 이미지 쪽 후속 결정이다(D-165, D-192). 이 ADR은 보이게만 한다.
- **Pi 재부팅으로 풀리지 않는 MCU 멈춤도 보인다.** 2026-09-25 ADC 사례가 그렇다. 이 경우 화면은
  "전원을 완전히 껐다 켜세요"를 안내한다.
- **측정 간격.** 장치 카드는 실시간 원격 측정이 아니다. 측정 시각이 오래되면 흐리게 보인다.

**Validation / Transition:**

- **호스트 시험.** probe를 가짜 `/dev`·sysfs·dmesg로 돌린다. 여섯 상태가 모두 나오는지, 죽은 버스에서
  시간 제한 안에 끝나는지 확인한다.
- **스키마 시험.** `hardware.json` 스키마와 API 계약을 시험한다.
- **브라우저 시험.** 점검 뷰 장치 카드와 운용 뷰 이유 문장을 시험한다(D-201 적합 계약).
- **DEVICE.** `rosy_18`에서 결과가 2026-09-25 수동 점검과 행마다 같아야 한다. 부저·램프 시험 동작은
  사람이 확인한다.
