## D-263 메뉴는 사용자의 질문을 찾는 길이다 — 화면 책임과 확장 규칙

**Status:** Accepted (2026-09-26). 문서 결정이며 화면 이관이나 기기 수용을 뜻하지 않는다.

잇는 결정: D-72(표면별 문법), D-75(로봇 로컬 정적 웹), D-77(운용 콘솔 하나),
D-157(공유 headless 상태), D-193(인증), D-204(역할별 화면·패널 계약, 별도 작업 브랜치),
D-233/D-254(디자인 시스템), D-243(화면은 `hmi`, API는 `runtime`).

**Context:** CORE `/dashboard`의 `운용`·`점검` 두 뷰는 상태 확인, 운전, 작업 준비,
설치·정비를 담는다. `app.js`가 로그인·상태 연결·조작·진단·호스트 카드를 조정하고,
`settings.js`가 웨이포인트·도크·토큰·안전 설정을 함께 맡는다. WEB-002는 메뉴 이름을
나열하지만, 새 기능을 상단 메뉴·기존 화면의 섹션·패널·동작 중 어디에 놓을지 정하지 않는다.
그 결과 기능을 추가할수록 단일 화면과 셸이 계속 커질 수 있다. D-204는 세 화면과 패널
조립을 정했으나, 메뉴 추가의 판단·표시·이름·탐색 계약은 별도로 고정할 필요가 있다.

**Decision:**

1. **메뉴의 첫 단위는 기능 모듈이 아니라 사용자의 질문이다.** 로봇 로컬 화면은
   `/console`(지금 이 로봇을 운용할 수 있나), `/setup`(작업을 시작할 준비가 됐나),
   `/device`(기기와 호스트가 정상인가)를 기준으로 한다(D-204). 메뉴 이름은 각각
   `운용`, `작업 준비`, `장치·정비`다. Fleet은 사이트 관제 PC의 별도 표면이고,
   게임 호스트·센싱 진단도 각자의 표면이다. 로봇 메뉴 안에 다른 서버의 기능을
   복제하지 않는다. `/dashboard`의 호환 경로와 이관 시점은 D-204 단계가 정한다.

2. **상단 메뉴는 화면만 가리킨다.** 하나의 화면에서 끝나는 새 기능은 그 화면의
   섹션/패널로 넣는다. 새 상단 메뉴는 (a) 독립적인 사용자 질문과 담당자가 있고,
   (b) 기존 화면의 문법·작업 흐름으로 설명할 수 없으며, (c) 독립 URL·접근권한·
   상태/오류 처리가 필요할 때에만 ADR로 화면 책임을 정한 뒤 추가한다.
   ROS 패키지·API 라우터·센서가 하나 늘었다는 이유만으로 메뉴를 만들지 않는다.
   버튼 같은 개별 동작은 메뉴 항목이 아니다.

3. **화면 탐색 정보는 화면 레지스트리 한곳에서 나온다.** D-204의 화면 메타데이터
   (`id`, 제목, 정렬 순서, 최소 역할, 문법, URL)를 메뉴의 단일 출처로 쓴다.
   셸·HTML·API에 별도 메뉴 배열을 복사하지 않는다. 패널 레지스트리는 화면 내부의
   슬롯·순서·기능 요건을 선언한다. 패널 하나를 추가해도 상단 메뉴가 자동으로
   증가하지 않는다. 현재 D-204 브랜치가 `title`과 화면 목록을 이미 내주는 만큼,
   이 결정은 별도의 메뉴 서비스나 두 번째 레지스트리를 요구하지 않는다.

4. **노출은 역할과 제공 기능을 구분한다.** `whoami`의 역할은 볼 수 있는 화면과
   동작을 결정한다. CAP-001과 inventory는 설치된 로봇이 실제로 제공하는 패널과
   현재 이용 가능 상태를 결정한다. 제공하지 않는 기능(`not_provided`)은 메뉴와
   패널에서 빠진다. 제공하지만 일시적으로 막힌 기능은 자리와 이유·증거 시각을
   남긴다. 역할이 낮으면 권한 밖 동작은 보이지 않는다. 메뉴 숨김은 보안 경계가
   아니며 API의 `require_role`이 최종 판정한다. URL 직접 접근도 401(미인증),
   403(권한 부족), 404(없는 화면)를 구별해 안내한다.

5. **화면의 최소 역할과 동작별 역할은 다를 수 있다.** 읽을 수 있는 지도는 Viewer에게
   보이고 목표 지정은 Operator에게만 보인다. `/setup`에 도크 등록을 배치해도
   도크 유형·도크 생성/삭제는 현재 API대로 Administrator만 실행한다. 동작을
   옮길 때마다 실제 엔드포인트 역할·사전 조건·실행 결과를 대조한다. UI는 API보다
   권한을 넓히지 않는다.

6. **셸은 모든 페이지에 필요한 것만 소유한다.** 인증/로그아웃, 현재 화면 표시,
   로봇 연결의 공통 상태, 전역 E-Stop을 셸에 둔다. 패널별 조회·렌더·명령·타이머는
   해당 패널이 맡고 셸의 인증된 API·공유 상태 인터페이스를 이용한다. 안전 정지는
   세 로봇 로컬 화면에서 같은 위치와 어휘로 남으며 페이지·패널 실패와 별도로
   접근 가능해야 한다. 안전 해제는 Administrator 전용 동작으로 분리한다.

7. **각 페이지는 자신의 문법으로 말한다.** `운용`은 위치·상태·다음 동작을
   즉시 찾는 공간형 화면이고, `작업 준비`와 `장치·정비`는 순서와 결과를 읽는
   절차형 화면이다(D-72, interface principles §4). 공통 색·타입·간격·버튼·증거
   어휘는 `web_common`에서 가져오되, 레이아웃·문장·우선순위는 대상 역할이 정한다.
   상단에는 현재 위치를 명확히 표시하고, 키보드·터치·좁은 화면에서도 메뉴 이름과
   E-Stop 접근이 유지되게 한다. 오류·지연은 조용한 성공 표시로 바꾸지 않는다.

8. **메뉴 추가는 선언과 검증을 함께 낸다.** 새 화면 제안에는 한 문장 질문,
   대상 사용자, 기존 화면에 넣을 수 없는 이유, URL/화면 ID, 최소 역할, 패널과
   CAP-001 조건, 읽기·쓰기 API와 권한, 빈/지연/단절 상태, 이동·되돌리기 경로,
   모바일·키보드 검증을 적는다. 새 패널에는 화면·슬롯·순서·역할·기능 조건과
   소유 모듈을 적는다. 이 정보가 없으면 메뉴 항목을 추가하지 않는다.
   URL은 북마크할 수 있고 새로고침 뒤에도 같은 화면을 연다. 라벨 변경에는
   기존 URL과 문서/테스트의 영향 확인이 따른다.

**Alternatives:**

- 기존 `/dashboard`에 모든 기능을 계속 붙이는 안은 작업 준비와 정비의 질문을
  운용 화면에 섞고 셸의 책임을 늘린다.
- ROS 패키지마다 상단 메뉴를 자동 생성하는 안은 사용자 과업보다 구현 폴더를
  탐색 구조로 노출하고, 장치별 capability 차이를 설명하지 못한다.
- 사용자별 자유 배치·원격 플러그인 메뉴는 현재 요구가 없다. 화면의 안전 위치와
  검증 가능한 자산 목록을 흔들므로 이 결정에서 채택하지 않는다.

**Consequences:** D-204의 화면·패널 조립은 그대로 쓰되 메뉴는 화면 메타데이터에서
만든다. `src/hmi/dashboard`가 로봇 화면 자산을, `src/runtime/api_web`이 매니페스트와
API 권한을 소유한다(D-243). D-204 브랜치는 구조 이동 전 `core_api_web/web` 경로를
기준으로 작성됐으므로 통합 전에 이 소유 경계를 반영해야 한다. 이 ADR만으로
`/console`·`/setup`·`/device`가 구현됐다고 보지 않는다.

**Validation / Transition:** 먼저 D-204의 S1을 현행 디렉터리에 맞춰 옮기고,
메뉴가 화면 레지스트리에서만 생성되는지 검사한다. 이후 각 이관 단계에서
Viewer/Operator/Administrator × 로봇 capability 조합의 메뉴·패널 노출,
직접 URL 접근, API 401/403, 새로고침/뒤로가기, 390px 모바일과 키보드 탐색,
E-Stop의 지속 접근을 브라우저로 확인한다. 호스트 테스트는 화면 계약의 증거이며
실기 안전·설치 수용 증거는 아니다.
