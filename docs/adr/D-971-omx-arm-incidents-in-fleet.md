# D-971 OMX 팔 사건은 Fleet이 기록하고, AI PC가 설명하고, 사람이 Fleet에서 해제한다

**Status:** Accepted (2026-11-03, 사용자 요청 "Fleet이 AI PC와 연동하고 역할을 명확히 나눈다". 구현·시험은 증거가 있고, 실물 수용은 별도)

## Context

2026-11-03 13:27 arm_b의 팔꿈치(ID 13)가 과부하로 잠겼다. 원인은 집게가 문 상자가 홈 자세를 막은 것이었고, 로그·사진·레지스터를 사람이 직접 읽어 한 시간 걸려 밝혔다. 같은 날 그 과정을 제어 PC의 `omx_incident.py`로 옮겼지만, 이 모듈은 사건 원장(`agenda.md`)과 세션 보류(`HOLD-<arm>.json`)를 제어 PC에 두고 모델을 제어 PC에서 직접 불렀다. 이는 D-681(Fleet이 사건·원장·처리 파이프라인, Decision이 판정 계약, AI PC가 추론)과 어긋난다. Fleet의 기존 사건 원장(D-608, D-684)은 Pinky 라인 정체 전용이고, 팔 고장은 Fleet 메모리에만 최근 20건이 남는다.

## Decision

1. **역할.**
   - 제어 PC는 측정·보고·장치 안전 조치만 한다. 세션이 끝나면 측정 사실과 고장 사진을 Fleet에 사건으로 보고한다. 원본(`faults/*.json`, 사진)은 제어 PC에 남는다.
   - Fleet은 팔 사건의 식별·상태·원장·화면·해제를 소유한다. 사건과 보류는 Fleet SQLite에 남는다.
   - AI PC는 열린 사건의 사진과 사실을 받아 설명만 만든다. 설명은 저장·표시만 하고, 처리 행동을 고르지 않는다.
   - Decision의 판정 계약은 바꾸지 않는다. 이 설명은 판정이 아니라 관측 보조다.
2. **사건 보고.** 제어 PC가 `POST /api/fleet/workcell-observations/arms/{source_id}/incidents`로 보낸다. 내용은 세션 ID, 측정 사실(잠긴 오류와 비트 해석, 종료 후 토크, 홈 접힘, 출력 상승 감지, 실행기 표시 행, 측정 판단), 사진 최대 2장(JPEG, sha256, 장당 상한)이다. 같은 `session_id`의 재보고는 같은 사건이다.
3. **보류와 해제.** 해제되지 않은 사건이 있으면 그 팔은 보류다. 제어 PC는 세션을 시작하기 전에 `GET .../arms/{source_id}/hold`로 확인하고, 보류면 시작하지 않는다. 해제는 Fleet 화면에서 이름 있는 운영자만 한다(`POST .../incidents/{incident_id}/clear`, 확인 내용 필수). 해제는 사건에 기록되고 지워지지 않는다.
4. **Fleet에 닿지 않을 때.** 제어 PC는 보고하지 못한 사건과 마지막으로 받은 보류를 로컬에 둔다. Fleet에 닿지 않으면 로컬 보류가 있을 때만 세션을 막는다. 보고하지 못한 사건은 다음 세션 시작 전에 다시 보낸다. Fleet이 해제를 알려야 로컬 보류가 풀린다.
5. **인증.** 보고와 보류 조회는 그 팔의 관측 토큰을 다시 쓴다(D-963 선례). 이 토큰은 여전히 명령 권한이 없다. 사건 쓰기와 보류 읽기만 더한다. 해제는 운영자 세션만 할 수 있다.
6. **AI PC 설명 경로.** D-610의 당겨 가기 경로를 쓴다. AI PC 상황 서비스가 `ai_observer` 토큰으로 설명이 없는 열린 팔 사건을 가져가서 로컬 Ollama 시각 모델로 설명하고, `POST .../incidents/{incident_id}/explanation`으로 돌려준다. Fleet은 AI PC로 밀지 않는다. 제어 PC는 모델을 부르지 않는다.
7. **장치 안전 조치.** 과부하·입력 전압 오류로 잠긴 모터의 Dynamixel 재부팅은 장치 주인의 안전 조치로 제어 PC에 남긴다. 조건은 세 가지가 모두 맞을 때다.
   - 모든 팔로워 모터가 토크 0이다.
   - 팔이 홈에 접혀 있다.
   - 잠긴 오류가 과부하나 입력 전압뿐이다.

   재부팅은 움직임을 만들지 않고 토크를 켜지 않는다. 결과(전후 레지스터)는 사건에 붙여 보고한다. 보류는 재부팅 뒤에도 남는다. 원인이 남아 있을 수 있기 때문이다.

### 2026-11-09 보완: 측정으로 판정되는 소프트웨어 정지는 보류하지 않는다

사용자 결정: 판정 모델과 근거가 이미 있는데 사람이 해제할 때까지 팔을 묶으면 병목이 된다. 11-09 02:21 두 팔이 가드의 시작 정렬 시한 초과로 멈췄고, 접힌 채 아무것에도 닿지 않았는데도 사람을 기다렸다. 공통 규칙 `core_common.protocol.arm_incidents.software_stop`이 측정 사실로 판정한다: 안전 종료, 접힌 자세, 걸린 하드웨어 오류·감김 없음, 표시된 행이 모두 가드 자체의 정지(`SOFTWARE_STOPS`)이고 모든 관절이 명령값 2.5° 안(따라갔다, 밀린 것이 없다). 제어 PC는 이 사건을 보류 없이 원인 표시용으로 보내고, Fleet의 보류 계산도 저장된 사실에 같은 규칙을 적용한다. 사건은 목록에 남아 원인 표시를 기다린다. 명령을 못 따라간 팔, 접히지 않은 팔, 접촉·감김·하드웨어 오류는 그대로 보류다.

## 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| D-681 | 역할 배치를 그대로 따른다. 팔 사건은 Pinky 처리 루프(D-684)를 쓰지 않는다. 자동 처리 행동이 없고, 사람이 해제하는 보류뿐이다. |
| D-963 | 관측 토큰으로 보고하고 운영자가 Fleet에서 결정하는 같은 모양이다. |
| D-610 | AI PC가 Fleet에서 당겨 가서 설명을 돌려주는 같은 경로다. 설명은 행동을 만들지 않는다. |
| D-779, D-403 | Cell Job의 팔 claim `HELD`와는 별개다. 이 보류는 세션 시작을 막고, Cell Job은 자기 미션의 팔을 막는다. 둘 다 풀려야 팔이 일한다. 하나로 합치는 일은 D-773 §2가 정해질 때 다시 본다. |
| D-777 | 짧은 문서. 정본은 이 결정과 API 참조다. |
