## D-886 워크트리 도구 차단값을 15개 예산과 맞추고, 착지한 브랜치를 prune이 지운다

**Status:** Accepted (2026-10-26, 사용자 지시). D-824의 상한 숫자를 대체한다. 기존 워크트리·미커밋·미착지 브랜치를 지우거나 착지·푸시를 승인하지 않는다.

## Context

2026-10-21 사용자 지시로 운영 예산은 main 포함 15개가 되었지만 `tools/worktrees.py`의 `CAP`은 50(D-824)으로 남았다. shared-checkout은 "도구 상수는 바꾸지 않는다"고 적었다. 그래서 문서 예산을 넘겨도 `new`가 막지 않았고, 2026-10-26에는 워크트리가 22개였다. 에이전트는 문장보다 도구의 거절을 더 확실하게 따른다.

같은 날 로컬 브랜치는 488개였고, 그중 132개는 이미 `main`에 들어간 상태였다. D-372 결정 2는 착지한 브랜치를 지우라고 하지만, `prune`은 자신이 지우는 워크트리의 브랜치만 지웠다. 워크트리 없이 남은 브랜치를 지우는 경로가 없었다. 브랜치 이름은 접두어만 검사했다. 그래서 `test/`·`land/`·`backup/` 같은 종류도 게이트웨이 밖에서 생겼다.

조사: 업계의 Conventional Branch 관례는 `<type>/<소문자-하이픈-설명>`, 약 50자 이내, 이슈 번호는 설명 안에 둔다. 병렬 에이전트 작업 관례는 작업 1개 = 브랜치 1개 = 워크트리 1개, 머지 후 즉시 정리다. 동시 개수 상한은 정해진 값이 없어 각 팀이 정한다. 팀 Git-flow 규칙(develop·task·release·작업자 이름 브랜치)은 여러 사람이 원격에서 통합할 때의 구조다. 이 저장소는 로컬 `main` 하나에 `tools/land.py`로 착지하는 trunk 방식(D-868)이고 작업자는 세션이다. 그래서 그 구조에서 '작업 전 기준·이름·대상 확정', '종류별 역할·수명 표', '완료 브랜치 정리'만 가져온다.

## Decision

1. `CAP`을 14로 둔다. `.worktrees/` 아래(orphan 포함)가 14개, main을 더해 15개이면 일반 `new`를 거절한다. `--force-over-cap "<이유>"`와 감사 기록은 유지하고, 사고 대응·사용자 승인에만 쓴다. 지금 15개를 넘은 상태도 지워서 맞추지 않는다. 신규 생성을 멈추고 기존 슬롯 회수 순서로 줄인다.
2. `new`는 topic이 영문 소문자·숫자를 `-`로 이은 48자 이내일 때만 만든다(`[a-z0-9]+(-[a-z0-9]+)*`). 기존 작업 브랜치 447개가 모두 이 형식이라 기존 관행을 굳히는 것이다.
3. 모든 `prune`(드라이런은 개수만)은 `main`에 들어갔고, 어느 워크트리에도 체크아웃되지 않았고, reflog가 1시간(`LANDED_IDLE_HOURS`) 넘게 그대로인 로컬 브랜치를 `update-ref -d <ref> <sha>`로 지우고 `branch.<b>` 설정도 지운다. `main`과 `archive/*`는 지우지 않는다. `main`에 없는 브랜치, 원격 브랜치, `refs/wip`는 다루지 않는다. 내용이 모두 `main`에 있어 손실 없는 청소이므로 소유자를 가리지 않는다.
4. 브랜치 종류·이름·수명의 정본은 `docs/reference/shared-checkout.md` 「브랜치 이름과 수명」 한 곳이다. AGENTS.md·git-workflow·명령 카드는 그 절을 가리킨다.

## Alternatives

- 경고만 추가하고 50 유지: 22개 상황이 그대로 되풀이된다. 사용자가 거절했다.
- Git-flow(develop/release/task, `feature/<작업자>/...`) 도입: 원격 통합 브랜치가 없는 trunk 착지 흐름과 맞지 않고 브랜치 수를 늘린다. 작업자는 소유자 기록으로 이미 구분된다.
- 맨손 `git worktree add`·`git branch`를 git 훅으로 막기: git에는 생성 전 훅이 없고 `post-checkout`은 사후 경고만 된다. 이번에는 보류한다.

## Consequences

현재 22개라 정리될 때까지 모든 세션의 `new`가 거절된다. 거절 문구가 지금 치울 수 있는 워크트리와 소유자를 보여 준다. `rosy_harness.py lint`도 상한 경고를 낸다. 착지·`new --prune`·`prune --apply` 때마다 착지한 브랜치가 정리되어 `git branch`가 진행 중 작업에 가깝게 유지된다. 지운 브랜치는 `main`의 커밋에서 다시 만들 수 있고, reflog가 남아 있는 동안은 sha도 찾을 수 있다.

개발 협업 도구와 안내만 바꾼다. 제품 폴더·호스트·권한(D-427·D-429)과 safety 체인(D-430)은 바꾸지 않는다.

## Validation

`test/test_worktrees_tool.py`: 기본 상한 14에서 orphan 13개를 포함한 14번째 생성 성공, 다음 일반 생성 거절, 사유 있는 예외 생성. 대문자·밑줄·하위 경로·앞 하이픈·49자 topic 거절. 착지한 브랜치는 1시간 안에는 남고, 드라이런은 개수만 세고, `--apply`는 그것만 지운다. 체크아웃 중인 브랜치·`archive/*`·`main`에 없는 브랜치·`main`은 남는다. 시험 결과는 커밋에 결속된 원격 로그로 확인한다.
