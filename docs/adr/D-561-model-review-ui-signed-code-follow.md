## D-561 모델 PC 검수 UI는 승인된 서명 코드 릴리스를 따라간다

**Status:** Accepted (2026-10-09, 사용자 요청. 모델 PC 자동 전환과 현장 화면 확인은 별도 증거로 기록한다.)

## 배경

D-446의 모델 PC 코드 타이머는 승인된 서명 후보를 자동 적용하지만, D-545의 검수 UI는 별도 릴리스 링크를 사용한다. 따라서 코드가 갱신되어도 검수 화면은 이전 릴리스에 남았다. 관제 PC의 D-441 사이트 스택 갱신과 모델 PC 검수 UI 갱신은 서로 다른 대상이다.

## 결정

1. 모델 PC의 별도 사용자 타이머가 D-446의 적용 상태와 `current` 링크를 확인한다. 설치 시 기록한 기준 sequence보다 **큰** 승인 후보만 처리한다. `pending`, 적용 실패 또는 상태·링크 불일치에서는 전환하지 않는다. `main`이나 작업 checkout을 직접 가져오지 않는다.
2. D-446 서명 payload의 `learning/training/perception/`과 `shared/web/`에서 전체 검수 앱 소스를 준비한다. 외부 `data` 링크는 복사하지 않는다. D-545 설치기로 불변 릴리스를 만들고 `/api/workspace`, `/pixels` 확인 후 전환한다. 실패하면 D-545의 이전 화면 복구를 따른다. 검수 DB, 영상, 가중치, 비밀은 릴리스 밖에 둔다.
3. 이미 활성화한 동일 sequence는 재설치하지 않는다. 검수 UI 적용 실패는 모델 코드·학습 작업을 중지하거나 모델 승격으로 연결하지 않는다. 오류는 사용자 서비스 journal에 남기고 다음 주기에 재시도한다.
4. 관제 PC는 D-441 서명 사이트 후보 자동 설치를 유지한다. D-530에 따라 중복된 옛 `rosy-site-update.timer`는 관리자 권한으로 비활성화한다. D-441의 릴리스 발행·서명과 모델 PC의 D-446 후보 승인·서명은 별도 단계다.

## 검증

호스트 테스트는 이전 후보 무시, 상태와 링크 불일치 거절, 새 후보의 UI 설치, 중복 실행 무동작을 확인한다. 모델 PC에서는 타이머 활성 상태, 새 서명 후보 적용 뒤 UI 릴리스 링크와 두 HTTP 경로를 확인한다. 브라우저의 실제 검수·승인 저장, 학습 반영, 로봇 주행 권한은 각각 별도 검증한다.
