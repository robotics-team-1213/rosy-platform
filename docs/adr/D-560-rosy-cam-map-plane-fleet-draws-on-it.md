## D-560 Rosy Cam이 지도 평면 영상을 펴서 내고, Fleet은 그 영상 위에서 점을 잡고 지도를 그린다

**Status:** Accepted (2026-10-09, 사용자 지시 "rosy cam 에서 사각형으로 왜곡된 걸 펴서 주고, fleet은 그걸 받아 조금 더 조정하거나 포인트를 잡고 지도를 그린다 — adr로 기록해서 해"). 구현·배포·현장 확인은 아래 단계마다 따로 증거를 남긴다.

잇는 결정: D-318, D-375, D-457, D-472, D-484, D-513, D-515, D-544.

### Context

- 2026-10-09 현장(`ceiling_north`, 승인 보정 `paint-7b220d432c2a`)에서 Rosy Cam 원본은 비스듬한 사각형이다. 이것을 펴는 곳이 지금 Fleet 브라우저에 세 군데 따로 있다.
  - 관제 현장 지도의 위에서 본 그림: D-515 `camera-backdrop.js`, 576 삼각형.
  - 현장 지도 탭의 "직사각형 평면 영상 불러오기": `site-map.js` `warpImage`.
  - 설치·보정의 확인 그림: `field-view.js`.
- 셋 다 원본(`X-Frame-Rectified: false`)만 받고, 이미 편 프레임은 지도에 쓰지 않는다(`camera-backdrop.js` `cameraMapCalibration`).
- Rosy Cam 계통에서 펴기는 이미 Vision(현장 수신기)에 있다. D-318 `rectify.py`가 lease의 보정 프로필로 미리보기만 편다. D-484 `mode: auto`는 경기장 네 모서리가 화면에 다 보여야 하는데, 이 현장은 먼 쪽이 화면 밖으로 나가 쓸 수 없다.
- 폰 앱은 노출 자동 보정(D-544)과 원본 송출만 한다. 앱에는 펴기 코드와 OpenCV가 없고, 와이어 `rosy-overhead/1`은 고정이다(D-374, D-484).
- 사용자 결정: 펴기는 Rosy Cam 쪽이 한 번 정확하게 한다. Fleet은 받은 평면 영상 위에서 점을 잡고 지도를 그리며, 필요하면 조금 더 맞춘다.

### Decision

1. **누가 펴나.** Rosy Cam 계통의 Vision이 원본을 한 번 편다.
   - 폰 앱은 지금처럼 노출(D-544)과 원본 송출을 맡는다. 와이어는 바꾸지 않는다.
   - 원본 프레임은 추적·마커·관측용으로 그대로 둔다(D-318). 평면 영상은 그 원본에서 만든 표시용 사본이다.
2. **지도 평면 영상.**
   - **요청.** Fleet lease의 `rectification`에 `{"mode": "map"}`을 더한다. Vision은 추적이 이미 Fleet에서 읽는 승인 보정 기록(D-457: `map_to_image`, `track_bounds_m`, `lens`, `calibration_revision`)으로 원본을 편다.
   - **영역과 방향.** `track_bounds_m`에 여유 `0.15 m`를 더한 직사각형을 위에서 본 그림이다. 지도 `+x`가 오른쪽, `+y`가 위다.
   - **축척.** 고정 `px_per_m` 400이고, 긴 변 1920 px를 넘으면 그 안으로 줄인다. 화면 밖이었던 부분은 바탕색으로 둔다.
   - **응답 헤더.** `X-Frame-Rectified: map`, `X-Frame-Plane: <min_x>,<min_y>,<max_x>,<max_y>,<px_per_m>`(미터, 여유 포함), `X-Frame-Calibration: <revision>`. 기존 `X-Frame-*` 헤더(Seq, Age-Ms, Captured-At)와 `X-Source-Lens`는 그대로 붙는다.
   - **못 펼 때.** 승인 보정이 없거나 source·map·렌즈·영상 비율이 기록과 다르면 `409`와 `X-Frame-State: plane-unavailable`을 돌려준다. 원본으로 몰래 대신하지 않는다.
   - **렌즈 왜곡.** D-515와 같이 모델로 다루지 않는다.
3. **자동 보정.** 평면의 근거는 설치·보정의 기존 흐름(`맵 자동 맞춤` → `맞춤 수락` → `추적 보정 적용`, D-375·D-457)이다. 적용한 revision으로 바로 평면 영상이 나온다. 새 보정 저장소는 만들지 않는다. 보정이 바뀌면 revision이 바뀌고, Fleet은 그 revision으로 평면을 다시 받는다.
4. **Fleet은 받은 그대로 쓴다.**
   - 관제 현장 지도, 현장 지도 탭의 평면 영상, 설치·보정 확인이 모두 `mode: map` 평면을 받는다.
   - 받은 평면은 `X-Frame-Plane` 사각형에 그대로 그린다.
   - 픽셀↔지도는 축척과 원점만으로 바꾼다: `x = min_x + u / px_per_m`, `y = max_y − v / px_per_m`.
   - 같은 좌표로 차선·주차·시작점·로봇·관측을 그 위에 그리고, 평면 지도 좌표 확인(점 잡기)도 이 식을 쓴다.
   - 브라우저 펴기(D-515 삼각형, `site-map.js` `warpImage`)는 Vision 평면을 받을 수 없을 때의 대체 경로로만 남긴다. 화면에 어느 경로인지 적는다.
5. **조금 더 맞추기.**
   - 운영자가 평면 위에서 지도상 위치를 아는 점(차선 교차, 시작 자리 등) 둘 이상을 찍으면 Fleet이 작은 닮음 변환(이동·회전·축척)을 구한다.
   - 그 변환은 보정 revision에 묶어 저장하고 표시와 점 잡기에만 적용한다. 보정 revision이 바뀌면 버린다.
   - 이동 `0.10 m`, 회전 `3°`, 축척 `5 %`를 넘으면 맞추기 대신 `맵 자동 맞춤`을 다시 하라고 안내한다. 큰 어긋남은 보정 자체의 문제다.
6. **화면 방향.** 사이트 지도의 `view_turn_deg`(D-513 7)는 Fleet이 평면 영상째 돌려서 적용한다. Vision 평면은 항상 지도 `+y` 위다.
7. **용도와 권한.** 평면 영상과 그 위의 좌표는 표시와 좌표 확인용이다. 평면 좌표만으로 `cmd_vel`·경로·`initialpose`·주차를 실행하지 않는다(D-472 7). 평면 lease는 기존 Vision lease와 같은 권한·수명을 쓴다. Fleet 서버는 영상을 중계하지 않는다(D-136).

### 단계

| 단계 | 내용 | 끝난 기준 |
|---|---|---|
| S1 | Vision `mode: map`, 헤더, 409, API Reference | Vision 호스트 테스트, 실제 현장 프레임으로 평면 영상 한 장 확인 |
| S2 | Fleet 세 화면이 평면을 받아 그대로 그림, 픽셀↔지도 식, 대체 경로 표시 | 호스트·브라우저 테스트, 실제 프레임으로 차선이 도로 가운데에 놓임 |
| S3 | 점 둘 이상으로 닮음 변환 맞추기, revision별 저장, 한도 안내 | 호스트·브라우저 테스트 |
| S4 | 현장 배포 뒤 관제·현장 지도에서 확인 | 현장 화면 증거 |

### D-318·D-472·D-484·D-515와의 관계

| 결정 | 이 ADR 뒤 |
|---|---|
| D-318 Vision이 미리보기만 펴고 원본은 그대로 | 그대로. `mode: map`도 미리보기 사본이다 |
| D-472 1·2 현장지도는 최신 실제 프레임, 승인 보정으로 좌표 연결 | 그대로. 연결을 Vision이 펴서 하고 Fleet은 축척 식만 쓴다 |
| D-484 `mode: auto`(경기장 모서리) | 그대로 남는다. 모서리가 화면 밖인 현장은 `mode: map`을 쓴다 |
| D-515 브라우저가 원본을 삼각형으로 편다 | 대체 경로로 내려간다. Vision 평면이 있으면 쓰지 않는다 |

### Consequences

- 펴는 곳이 Vision 하나가 되어 세 화면의 그림과 좌표가 같아진다.
- 브라우저의 프레임당 펴기 비용(D-515 576 삼각형)이 사라진다.
- 평면 영상의 정확도는 승인 보정의 정확도와 같다. 보정이 어긋나면(카메라 재조준) 평면도 어긋난다. D-457의 교정 낡음 경고가 그대로 그 신호다.
- Vision은 평면 요청마다 원본 한 장을 편다. lease당 요청 빈도는 지금과 같다.
