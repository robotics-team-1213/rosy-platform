# D-686 Fleet 초기 계정과 첫 로그인 비밀번호 변경

**Status:** Accepted (2026-10-12, 사용자 지시: 팀원 네 ID에만 계정/권한, 초기 ID와 비밀번호 일치, 로그인 후 필수 변경. 구현·설치·계정 발급 별도)

### Context

D-519는 읽기 전용 site-users.yaml과 기존 SQLite 세션을 사용한다. 비밀번호 변경 API와 초기 계정 권한 제한은 없다. D-683의 전용 로그인·업무 복귀에 첫 로그인 단계를 추가한다. 실제 팀 명단과 자격은 공개 저장소에 기록하지 않는다.

### Decision

1. 확인된 네 팀원의 Gmail 앞부분을 로그인 ID, 전체 메일을 principal로 발급한다. 역할은 기존 현장 운용 `operator`다. 새 관리자/정책 권한이나 SSO를 만들지 않는다. 사람 로그인은 이 명단으로 제한하되 기존 기계·AI·서비스·업데이트 토큰은 보존한다.
2. 사용자 요청대로 초기 비밀번호는 ID와 같다. 서버가 초기 해시를 ID와 대조하여 `password_change_required`를 판단한다. 초기 자격으로 발급한 쿠키는 auth/session, 로그아웃, 비밀번호 변경에만 쓰며 기존 Fleet API의 읽기·쓰기 권한은 부여하지 않는다. UI만으로 차단하지 않는다. Bearer/CORE의 기존 계약은 유지한다.
3. GET `/api/fleet/auth/session`은 초기 쿠키에 `password_change_required` 필드를 참으로 제공한다. POST `/api/fleet/auth/change-password`는 같은 출처의 유효한 초기 쿠키와 JSON `password`를 요구한다. 새 비밀번호는 8~1024자이고 ID/현재 초기 비밀번호와 달라야 한다. 변경 대상 principal/역할은 요청 본문으로 받지 않는다.
4. 새 비밀번호는 D-519 scrypt로 해시하고 기존 Fleet SQLite에 보관한다. YAML은 계정 존재·principal·역할·초기 자격의 원본이고, SQLite의 변경 해시는 그 원본 자격 지문에 결합한다. 원본 계정이 제거되거나 자격/역할이 바뀌면 기존 세션은 무효다. 다른 계정의 비밀번호로 적용하지 않는다.
5. 변경은 원자적이며 그 계정의 기존 세션과 캐시를 무효화하고 새로운 쿠키를 발급한다. 동시 변경·이전 비밀번호 확인과 세션 발급의 경쟁은 오래된 검증으로 새 세션을 발급하지 못하게 한다. DB 실패는 성공으로 표시하지 않고 원래 제한 상태를 유지한다. 재시작 후 새 비밀번호가 유지되고 초기 비밀번호는 거절된다.
6. 전용 로그인은 초기 쿠키를 확인하면 비밀번호/확인 입력 단계로 전환한다. 새 비밀번호와 확인이 일치해야 제출하며 중복 제출·오류 때 비밀 입력을 지운다. 변경 후 세션 조회에서 제한 해제를 확인한 뒤 허용된 원래 업무로 복귀한다. 보호된 화면의 초안을 자동 저장·재실행하지 않는다.
7. 공개 저장소에는 실제 명단/비밀번호/해시를 넣지 않는다. 현장 발급은 기존 원자적 site_users 유지 도구와 검증된 새 서버를 사용한다. 기존 사람 로그인은 확인된 팀 명단으로 교체하고 서비스 자격·파일 권한을 보존한다. 설치와 실제 네 계정 readback은 소스 검증과 구분한다.

### Existing contracts

| 계약 | 관계 |
|---|---|
| D-519 | 인증·scrypt·쿠키·CSRF·속도 제한 재사용. 런타임 비밀번호 변경과 초기 쿠키 제한, SQLite 해시 보관을 추가 |
| D-683 | 전용 로그인에서 필수 변경을 마친 뒤 세션 확인·업무 복귀 |
| D-427, D-429 | 기존 Fleet 서버/콘솔/SQLite와 배포 closure 재사용; 새 서비스 없음 |
| D-430 | 초기 쿠키가 운용 API에 도달하지 못함을 독립 검토. CORE/정지 권한과 기존 유효 자격은 보존 |

### Consequences

초기 로그인→운용 API 거절→CSRF/입력 검사→변경→새 세션→업무 복귀, 이전 쿠키 거절, 초기 비밀번호 거절, 재시작 유지, DB 실패·경쟁 조건, 320px 키보드/중복 제출을 원격 검증한다. 실계정과 private 명단은 별도 기록하고 해당 SHA의 CI·서명·설치 뒤 발급한다. 예측 가능한 초기 자격의 첫 변경은 팀원이 직접 완료해야 한다.
