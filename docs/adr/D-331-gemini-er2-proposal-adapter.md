## D-331 Gemini Robotics ER 2 is integrated as a stateless, proposal-only Fleet provider

**Status:** Accepted (2026-09-29, provider boundary and source adapter only). Runtime wiring, automatic Mission admission, robot actuation, production use, and device acceptance remain HOLD.

### Context

The previous ER 2 notes correctly separated image-space coordinates from robot control, but did not specify the live Gemini API request/response boundary. Google's current public API exposes two distinct endpoints: `gemini-robotics-er-2-preview` through the Interactions API and `gemini-robotics-er-2-streaming-preview` through Live API. Both accept user-declared function tools, but their surrounding API capabilities differ. Google's pick-and-place sample uses mock `move` and gripper functions and runs an application-owned loop; it is not a ROS/Franka adapter. The model card also says not to use Robotics Models for safety-critical work.

Rosy already has a proposal-only Mission service, an independent goal-evidence contract, and Fleet-side action/stop admission decisions (D-326, D-328, D-330). A provider adapter must create a typed candidate that can be reviewed and resolved; it must not execute a tool call, create physical authority, or promote an image coordinate to a robot pose.

### Decision

1. **Start with the standard ER 2 Interactions API for one-shot Fleet proposals.** Use `POST https://generativelanguage.googleapis.com/v1beta/interactions` with model `gemini-robotics-er-2-preview`. The Fleet adapter uses the repository's existing `httpx` dependency and the documented REST contract. It sends one image frame and one instruction, sets `store=false`, makes one request without automatic retry, and does not continue with `previous_interaction_id`. One-shot proposals do not need retained provider conversation state. The documented 20 MB inline request ceiling includes prompt and encoded image, so the adapter limits source image bytes to 14 MiB to leave room for base64 expansion and request text.
2. **Expose one inert semantic function: `propose_pick_place`.** Its arguments select a target and destination by a label plus exactly one normalized image point `[y,x]` or image box `[ymin,xmin,ymax,xmax]`, each in the documented 0–1000 range. Do not declare `move`, joint/trajectory, gripper, ROS, stop, E-stop, Mission admission, or device-status mutation functions. The application parses the function call into `PickPlaceProposalCandidate`; it never dispatches it as an SDK callback or sends a function result back to the model.
3. **Keep the output as an unresolved proposal candidate.** Preserve caller `request_id`, provider interaction/call IDs, model ID, source observation/camera/frame/time, and image SHA-256. The stable local proposal key is derived from the caller request ID; provider call IDs remain provenance, not Action IDs. Image points/boxes remain in image coordinates. Fleet/device-local code must resolve object identity, calibration/TF, depth, workcell, collision-free grasp/place, capability and admission before creating an executable Mission or ROS goal. Unresolved, malformed, ambiguous, text-only, unknown-tool, or multi-call output yields no candidate.
4. **Do not treat model text or a tool call as execution or success.** No model summary confirms physical possession, placement, action completion, cancellation, stop, or E-stop. Mission admission still passes through the D-330 Fleet owner, the device-local Action owner remains the only physical command submitter, and Mission completion requires D-328 independent goal evidence.
5. **Defer the streaming endpoint.** Streaming is a separate Live API protocol and model ID; the current public guide limits image input to JPEG at no more than 1 FPS and streaming has a different output/capability profile. It is not required for a one-shot task proposal and must not be treated as a servo/control-rate feedback loop. A future streaming adapter needs its own design, cancellation/session behavior, and tests.
6. **Constrain use to non-safety-critical proposal work pending policy review.** The ER 2 model card explicitly excludes safety-critical applications and calls for discretion before production, commercial, or public use. No production enablement is authorized by this source adapter. API-key restriction, provider-data handling, and deployment review are required before any approved non-safety-critical pilot.

### Alternatives considered

- **Coordinate-only `generateContent` call:** useful as a vision probe, but does not express the multi-step task proposal or caller-visible function-call identity needed by this Fleet boundary.
- **Streaming ER 2 first:** useful for low-latency continuous interaction, but has a distinct Live API session, different capability matrix, and a documented JPEG input cap. It adds state and cancellation concerns without serving the current one-shot proposal.
- **Expose the official mock `move` and gripper tools:** rejected because these are app-defined demo functions, image-space coordinates lack a robot-frame transform, and neither driver execution nor safety/readback is supplied by ER 2.
- **Install a general-purpose SDK agent loop:** rejected for the first slice. The provider response is parsed as candidate data; any future tool execution loop must be a separate Fleet admission decision, not SDK automatic function execution.

### Verification and limits

The source adapter is exercised with an HTTPX mock transport and response fixtures. This checks the REST request shape, image encoding, stateless request flag, proposal allowlist, coordinate validation, provenance, and failure behavior without a credential or physical robot. It does not verify live API compatibility, model accuracy, image calibration, runtime wiring, network latency, robot stop, ROS execution, or production policy approval.
