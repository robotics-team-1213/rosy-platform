## D-357 ER 2 receives bounded Fleet feedback while Mission and device control remain independent

**Status:** Accepted (2026-09-30, Fleet/provider feedback-loop contract). SOURCE implementation, automatic policy dispatch, ROS/OMX enablement, device and field acceptance remain separate gates.

### Context

D-326 assigns high-level reasoning to Fleet and keeps execution authority out of the model. D-330 makes Fleet the shared admission/dispatch arbiter while local device owners retain command and stop authority. D-333 closes the first ER 2 `PICK_PLACE` candidate, operator admission, local Action, and independent goal-evidence boundary. D-334 establishes a durable progress snapshot and cursor, while explicitly deferring a provider tool-result loop. The current `GeminiER2StandardAdapter` still sends one `store=false` request, parses one `propose_pick_place` candidate, and executes no tools. Fleet can project Mission/Step/Action/goal/stop state and create a bounded, owner/workcell-scoped model context, but that context is not returned to ER 2.

As a result, an operator can inspect progress and Fleet can record controller readback, but ER 2 cannot yet consume a structured result to inform its next proposal. The provider interaction, Mission, and physical Action have different lifetimes: a completed provider call is not a completed Mission; a disconnected model session does not cancel an accepted Action; and a model statement cannot prove goal completion or physical stop.

### Decision

1. **Fleet's durable Mission journal is the source of truth.** Model turns, tool calls, candidate proposals, middleware admission, device Action state, independent goal evidence, and stop readback remain separate correlated records. Model output can create a typed proposal only. It cannot write Mission/Action terminal state or declare a physical result.
2. **Use bounded, middleware-executed tools.** The first provider loop may expose only (a) `get_mission_status`, a read-only snapshot scoped to the authenticated principal and workcell, and (b) `propose_replan`, which records a typed candidate tied to the current Mission, latest eligible event, observation, and dispatch generation. The existing `propose_pick_place` remains candidate-only. Fleet validates every call, enforces per-turn call/time/cost budgets, executes calls serially, and returns a bounded structured result. No model tool submits a device Action or invokes ROS/CORE/driver, cancel, stop/E-stop, rearm, or direct gripper/motor control. `request_observation` is deferred until camera authorization, freshness, payload, and provider data-handling limits have an explicit contract.
3. **Keep the ER 2 interaction stateless and bounded.** Use the standard Interactions API only, with `store=false`. For synchronous read/proposal tool exchange, the adapter may replay the complete documented function-call history required by the provider, including opaque provider step/signature material, only in bounded process memory for the lifetime of one turn. It must not persist that transcript, signatures, raw image, credential, or provider session in SQLite or logs. Enforce a finite turn/tool budget and response-size limits. If the adapter cannot safely validate or replay a required provider step, terminate the turn fail-closed. Do not use `previous_interaction_id`, provider-side stored conversations, background interactions, or Live/streaming sessions in this decision.
4. **Deliver long-running Action feedback as a new model turn.** A device Action remains asynchronous and belongs to Fleet/OMX, not to an open provider request. After an eligible terminal Action/goal event is durably recorded and reconciled, Fleet may enqueue one bounded ER 2 follow-up turn containing the latest sanitized progress context and event watermark. The durable outbox key binds Mission, event, generation, and model-policy revision so duplicate delivery cannot create duplicate proposals. Provider outage or ambiguous timeout leaves the Mission and Action intact; Fleet reconciles readback and does not blindly replay a provider POST or physical Action. A replan remains a candidate subject to the existing admission and human-confirmation rules.
5. **Keep completion axes separate.** Tool-call completion and provider `Interaction.status` describe only model work. `ACTION_SUCCEEDED` requires terminal device Action readback; `GOAL_CONFIRMED` requires the independent registered goal-evidence verifier; stop success requires its own controller/physical readback. Missing, stale, conflicting, or late evidence is `UNKNOWN`/`HOLD`, not inferred success. The model receives source, observation time, freshness, active attempt/generation, and bounded reason fields with the snapshot; it does not receive another principal's Mission or unrestricted raw journal/evidence.
6. **Stop and fencing override model continuity.** A stop latch or newer dispatch generation invalidates outstanding provider turns and makes late tool results/proposals stale. E-stop and local safety action never wait for, invoke, or depend on ER 2. Stop/cancel acknowledgements remain distinct from physical stop readback. No provider reconnect, tool retry, restart, or replan automatically rearms or reissues an Action.
7. **Do not open autonomous dispatch.** `POLICY_DISPATCH_ENABLED` remains `False`. The first implementation supports feedback and candidate creation around existing explicitly admitted Missions; existing D-332/D-333 admission rules, D-330 arbitration, and OMX disabled state remain in force. Any policy-driven admission, autonomous replan execution, streaming control, or expanded tool allowlist requires a later decision and evidence.
8. **Resolve only the deferred part of D-334.** This ADR supersedes D-334's one-tool-only/future-tool and deferred-provider-loop clauses for the bounded standard-Interactions feedback loop above. D-334's Fleet progress meanings, authorization/freshness limits, no-direct-control boundary, and rejection of model-derived physical completion remain in force.

### Alternatives

- **Keep ER 2 strictly one-shot:** safest and simplest, but it cannot use controller readback and goal evidence to improve its next candidate. Rejected as the final architecture.
- **Use provider-stored conversation IDs:** simpler continuation, but it changes the existing `store=false` data-retention boundary and couples provider state to Mission recovery. Not selected.
- **Expose motor/arm/stop functions directly to ER 2:** rejected because it bypasses Fleet admission, device ownership, and independent stop/readback.
- **Hold a provider request open until the Action finishes:** rejected because provider turn lifetime and physical Action lifetime differ, and a network timeout must not own or interrupt device work.
- **Start a fresh bounded turn from a durable event/outbox:** selected because it carries controller feedback into reasoning while Fleet retains durable state, explicit admission, and recovery authority.

### Transition / validation

1. SOURCE/LOCAL: contract and schema tests prove principal/workcell scoping, bounded model context, event/action/generation correlation, provider budget enforcement, `store=false`, no persisted provider transcript, serial allowlisted tool execution, idempotent outbox delivery, and rejection of late-generation tool results. Inject provider timeout, duplicate event, process restart, stale readback, conflicting goal evidence, and stop during a turn. Assert no physical Action replay and `POLICY_DISPATCH_ENABLED is False`.
2. ROS-SIM: fake controller readback and goal evidence drive event-triggered follow-up turns; compare proposal-before/after feedback, disconnect and reconnect, action terminal result arriving before/after provider timeout, and stop-generation races. Simulation does not prove physical stop, grasp, placement, or goal success.
3. ARTIFACT/DEVICE/FIELD: separately verify deployed provider policy, secret/data handling, controller ownership, independent stop path, action and goal readback, latency, restart reconciliation, operator admission, and physical acceptance. No source or simulation result opens a live capability.

**Consequences:** ER 2 can reason over durable Fleet feedback and return a new typed proposal without becoming a controller. Fleet gains a bounded provider tool runner and durable follow-up scheduling contract. The Mission outlives provider sessions; device safety and physical truth remain local and independently evidenced.
