## D-425 앱·웹의 작업 소유권과 공유 경계를 고정하고 실행 조합 apps와 사용자 화면 ui를 분리한다

**Status:** Accepted (2026-10-03, 사용자 승인 — 역할·공유 범위·목표 폴더 구조를 ADR로 먼저 기록). 구조 결정의 수용이며 코드 이전·설치·브라우저·장치 수용 완료를 뜻하지 않는다. 이번 변경은 문서뿐이다.

**부분 대체 (2026-10-03):** [D-427](D-427-platform-three-parts-middleware-operations-learning.md)이 §4의 최상위 `apps/`·`ui/`를 각 파트 안(`middleware/apps/device`, `operations/apps`, `middleware/ui`, `operations/ui`)으로, `ui/shared/web`을 최상위 `shared/web/`으로 대체한다. §1~§3의 화면 소유·공유 경계는 유지한다. 최상위 `apps/`·`ui/`로의 새 이전은 동결한다(D-427 이전 동결).

### Context

사용자는 각 앱·웹의 역할을 명확히 하고, 공유할 것은 공유하되 책임을 나누며, 폴더명 변경까지 고려한 구조를 요청했다. 현재 main의 코드·배포 설정과 D-370·D-410·D-413을 대조했다.

- Robot·Pilot은 CORE가, Console은 Fleet이 정적 웹을 제공한다. Vision은 FastAPI가 아닌 Python WebSocket 수신 서비스이고 Cam은 Kotlin/CameraX 앱이다. 화면 파일의 위치와 실행 서버는 다른 개념이다.
- Console 운용과 설치는 D-410에 따라 문서가 분리됐지만 인증·요청 래퍼가 각각 남아 있다. Robot·Pilot도 별도 API 래퍼와 연결 관리가 있다.
- `src/runtime/gateway`는 Pinky CORE지만 `apps/gateway`는 Fleet 실행 조합이다. `apps/agent`도 로컬 실행 조합과 특권 Host Agent를 이름만으로 구분하기 어렵다.
- D-340은 설치형 웹 셸을 `apps/`에, D-413은 서버·로컬 실행 조합을 `apps/`에 두므로 같은 루트가 다른 뜻으로 읽힌다. D-413의 기능 추출은 시작됐으며 기존 `src/` 경로와 새 경로가 공존한다.
- `web_common/surfaces.yaml`과 `test_app_roles.py`는 화면 소유권을 일부 검사한다. 화면 소유, API 소유, 상태 정본과 최종 실행 권한까지 연결해야 후속 메뉴·앱 확장에서 경계를 지킬 수 있다.

### Decision

#### 1. 화면의 작업 소유와 실행 권한을 각각 기록한다

각 사용자 작업은 다음 다섯 항목을 가진다.

| 항목 | 기록할 내용 |
|---|---|
| 화면 소유자 | 요청·편집·확인 절차를 제공하는 앱/표면 |
| API 소유자 | 인증·권한을 검증하고 요청을 받는 서비스 |
| 상태 정본 | 요청·실행·관측의 사실을 소유하는 원장 또는 생산자 |
| 최종 실행 권한 | 실제 장치 명령을 중재·발행하는 로컬 owner; 표시 전용 작업은 없음 |
| 소비자·이행 조건 | 다른 화면이 읽거나 링크할 범위, 임시 중복의 제거 조건 |

화면 소유자와 API 소유자는 같을 필요가 없다. Console의 Mission 입력은 화면이 소유하지만 승인·순서·공유 자원·원장은 Fleet이 소유한다. 장치 Action의 수락·취소·복구는 장치 owner가, Pinky 최종 `cmd_vel`은 CORE가 소유한다. OMX 최종 팔 명령은 별도 수용된 OMX 로컬 owner가 소유한다.

브라우저는 요청과 상태 표시를 맡는다. Mission 다음 Step 진행·권한 발급·완료 확정은 서버가 맡고, 브라우저의 폴링·연결 수명주기에 의존하지 않는다. 사이트 MissionStore와 장치 ActionStore는 별도 사실의 정본으로 유지한다(D-413). 장치 상태는 장치가, 파생 관측은 해당 생산자가 소유하며 Fleet의 집계는 그 정본을 대신하지 않는다.

#### 2. 앱·표면의 사용자 작업을 고정한다

| 앱/표면 | 소유 작업 | 경계·연결 |
|---|---|---|
| Rosy Console 운용 | 사이트 감시, Mission 요청·진행·개입, 사이트 정지 요청 | 장치 상세 정비와 직접 조종은 Robot/Pilot 링크. 명령·원장은 Fleet API 경유 |
| Console 설치 | 사이트 기기 등록·승인·회수, 카메라 연결과 사이트 좌표·영상 보정 | D-410의 별도 문서. 운용과 같은 Fleet 로그인·공통 자산을 소비하며 별도 서버를 만들지 않음 |
| Rosy Robot | 한 로봇 상세 상태, 작업 준비, 기본 로컬 조작, 영구 설정·정비·로봇 자격 관리 | 로컬 목표·도킹 등 기존 Local-First 범위 유지. 사이트 Mission을 구현하지 않음 |
| Rosy Pilot | 한 장치 직접 수동 조종, 운전 영상, 현재 조종 세션과 그 세션의 기록 | 영구 설정·정비는 Robot 링크. 입력 감도·서버 한도 이내의 세션 프리셋은 Pilot 소유. Fleet Mission·사이트 등록을 구현하지 않음 |
| Rosy Cam | 카메라 캡처·송신, 물리 설치와 연결 상태 안내 | 사이트 승인·좌표 보정은 Console 설치가 소유. 카메라 자격만 가지며 로봇 조종·정지 권한 없음 |
| Rosy Face | 부팅·이름·연결 코드·상태 표시 | 표시 전용. 입력·토큰 원문·실행 권한 없음 |
| Rosy Vision | 프레임 수신, 관측 생성, 허가된 미리보기 제공 | UI가 아닌 서비스. Fleet에는 파생 관측만 전달하고 로봇 명령을 만들지 않음 |
| Games 보드 | 경기 상태·경기별 사용자 작업 | 게임 호스트 계약을 유지하며 사이트 Mission·장치 최종 명령을 소유하지 않음 |
| 제어 진단·시뮬 뷰어 | 개발·진단·시뮬 상태 표시 | 운영 화면과 구분하고 기존 PARKED/개발 범위를 유지 |

같은 생산자의 데이터를 여러 화면이 서로 다른 목적에 사용하는 것은 허용한다. 배터리는 Console 요약·Robot 진단·Pilot HUD로, CORE 카메라는 Robot 저주기 미리보기·Pilot 운전 영상으로 소비할 수 있다. 같은 설정 변경·등록·조종 절차를 두 벌 구현하지 않는다.

정지는 예외다. 운용 중 개입이 필요한 표면은 자기 대상의 정지 버튼을 직접 제공하며 링크로 대체하지 않는다. 사이트 전체와 개별 장치의 대상·범위를 표시하고, 정지 요청·응답·로컬 래치·물리 정지 확인을 구별한다. Cam과 표시 전용 LCD에는 정지 자격을 주지 않는다. 기존 비상 정지와 주행 취소의 서로 다른 의미도 유지한다(D-421).

Robot의 기존 `console.teleop`은 Pilot DEVICE 수용 조건을 만족하기 전까지 이행기 표면이다(D-370). 신규 조종 기능은 Pilot에서 개발하며, 조건 충족 뒤 Robot 패널을 Pilot 링크로 전환한다. 이번 ADR로 기존 조종 경로를 제거하거나 실기 수용을 선언하지 않는다. OMX Pilot 기능도 현재 격리된 시뮬레이션 범위를 유지한다.

#### 3. 공유는 UI·통신 도구·소유 모듈의 계약으로 나눈다

| 층 | 공유하는 것 | 소유자에게 남기는 것 |
|---|---|---|
| UI | 디자인 토큰·테마·기본 컴포넌트·대화상자·접근성·증거 표시 | 화면 구성, 메뉴, 작업 절차와 사용자 판단 맥락 |
| 통신 도구 | 인증 헤더 처리, 요청 취소·시간 제한, 오류 표현, WS 연결·백오프 도구, 폴링의 시작·종료 관리 | 자격 발급자·저장 정책·권한 범위, 조종 세션, Mission 복구·재제출 판단 |
| 계약·기능 규칙 | 소유 모듈의 버전 있는 API·타입·공정·Skill 규칙, 언어 간 적합성 벡터 | 서비스·장치별 원장, 승인 정책과 최종 실행 권한 |

공통 통신 도구 위에 계약별 클라이언트를 둔다. CORE 클라이언트는 Robot/Pilot이, Fleet 클라이언트는 Console 운용/설치가 소비한다. CORE 오류 `error`와 Fleet 오류 `detail` 등 실제 계약 차이는 각 클라이언트가 해석한다. 공통 도구에 모든 서비스 경로·도메인 규칙을 넣거나 서버 wire 형식을 이번 이전에 통합하지 않는다.

공유하는 것은 코드와 계약이다. 대상 서비스·장치·origin별 인증 상태와 store 인스턴스는 분리한다. Console 운용/설치는 기존 same-origin 세션을 공유하지만 CORE·Fleet·Vision 자격을 합치거나 모든 앱이 사용하는 전역 토큰/store를 만들지 않는다. 권한 숨김·비활성 표시는 UX이며 최종 검증은 API가 한다.

연결 재시도와 명령 재전송을 구별한다. 공통 도구는 이동·집기·Mission 요청을 자동 재전송하지 않는다. 작업 ID·수락·현재 결과를 확인한 소유자가 계약에 따라 조회·복구를 결정한다. Pilot의 누름 해제·탭 이탈·충돌 후 재개와 Fleet의 UNKNOWN/HOLD·재시작 조정은 각 소유자에게 남긴다. 연결 복구가 실행 재개를 뜻하지 않는다.

폴링·구독은 화면/패널 scope를 가지며 내려간 뒤의 타이머·늦은 응답이 화면을 갱신하지 않게 한다. 생산자의 freshness 판정과 출처·관측 시각을 보존하고, 통신 도구가 센서의 유효성 문턱을 별도로 정의하지 않는다.

Python·Kotlin은 동일 wire 규칙과 수용/거절 벡터로 동등성을 검증한다. 언어가 다른 코드를 한 런타임 라이브러리로 합치지 않는다. mDNS는 주소 후보를 제공하며 신원·자격 신뢰를 대신하지 않는다. 서비스별 TLS·주소 고정 정책과 자격 수명은 유지한다.

공유 UI는 실제 두 소비자가 필요로 하는 좁은 기능부터 추출한다. 공정·권한·장치 규칙을 `shared`에 쌓지 않고 소유 모듈 API로 소비한다. 프레임워크·번들러·별도 프론트엔드 서버 도입은 이 결정에 포함하지 않는다.

#### 4. apps는 실행 조합, ui는 사용자 화면으로 구분한다

목표 소스 분류는 다음과 같다. 아래 트리는 책임 예시이며 비어 있는 미래 폴더를 만들라는 목록이 아니다.

```text
apps/
  site/
    fleet/                  # Fleet API·조합·프로세스 수명주기
    vision/                 # 영상 수신·관측 worker 조합
  device/
    pinky/                  # CORE 로컬 실행 조합
    omx/                    # OMX 로컬 실행 조합
ui/
  console/
    operate/
    install/
  robot/
  pilot/
  cam/
  face/
  shared/
    web/                    # 공통 UI·통신 도구·계약별 클라이언트
modules/                    # 실행·관측·Skill·공정의 소유 규칙
integrations/               # ROS·장치·외부 기술 연결
profiles/                   # 선언형 선택·버전·설정 참조
deploy/                     # 설치·서비스·릴리스
```

`apps`는 모듈·연동·API를 조합하고 프로세스 수명주기를 소유한다. `ui`는 사람에게 제공하는 화면·입력과 그 화면의 패키징을 소유한다. 설치형 셸이 필요해지면 해당 `ui/<앱>` 아래에 두며 기존 웹 화면을 감싸는 D-340의 단일 화면·PWA 우선 원칙을 유지한다. 셸 생성·스토어 배포·새 origin 허용은 별도 작업이다.

`modules`, `integrations`, `profiles`의 의미와 단계적 기능 추출은 D-413을 유지한다. API의 HTTP 경계는 실행 앱이 조합하되 승인·공정·원장 규칙을 API 파일에 중복 구현하지 않는다. `ui/shared/web`은 브라우저 라이브러리이며 범용 도메인 저장소가 아니다.

기존 Games·진단·시뮬레이션·드라이버·MCU 경로는 자기 수명주기와 설치 단위를 유지한다. 이번 표에 없는 패키지를 전부 `apps`나 `ui`로 밀어 넣지 않는다. 실제 소유자·소비자·설치 경로가 확인된 단위만 후속 이전표에 추가한다.

#### 5. 이름 이전과 실행·설치 이전을 구분한다

| 현재 경로 | 목표 책임 경로 | 이전 범위 |
|---|---|---|
| `apps/gateway` | `apps/site/fleet` | 기존 Fleet 실행 조합; 새 Fleet 서버를 만들지 않음 |
| `apps/agent` | `apps/device/<대상>` | 현재 OMX 시뮬 조합은 omx, 후속 Pinky 조합은 pinky; 공통 agent 골격을 먼저 만들지 않음 |
| `src/runtime/gateway` | `apps/device/pinky`와 소유 기능 모듈 | CORE 조합과 기능 규칙을 분리한 뒤 이전; 폴더 전체를 즉시 옮기지 않음 |
| `src/runtime/api_web` | Pinky 실행 앱의 API 경계 | 기존 `core_api_web` 라이브러리·DI·권한 검사를 보존하고 의존 소비자를 확인 |
| `src/hmi/dashboard` | `ui/robot` | Robot 화면·패널·자산 |
| `src/hmi/pilot` | `ui/pilot` | 조종 웹/PWA와 현재 시뮬 화면 |
| `src/site/fleet/fleet/server/web` | `ui/console` | 운용·설치 문서와 화면 모듈 |
| `src/hmi/web_common` | `ui/shared/web` | 공통 자산·라이브러리; 등록 메타데이터의 설치 위치는 이전 시 명시 |
| `src/site/cam` | `ui/cam` | Kotlin/Gradle 앱과 해당 UI 패키징 |
| `src/hmi/face` | `ui/face` | LCD 표시·패키징 |

위 표는 목표 매핑이다. `src/` colcon 경로와 실제 설치 경로는 해당 단위의 호출자·설치 검증 전까지 유효하다. 디렉터리·Python import·wheel 이름·ROS 패키지명·URL·토픽·Android applicationId·서비스명은 별도 식별자이며 한 번에 바꾸지 않는다. Host Agent는 특권 호스트 관리 역할로 남으며 장치 실행 조합과 합치지 않는다.

소스 이동이 실행 서버를 추가하지 않는다. Robot/Pilot은 CORE의 in-process 정적 서빙, Console은 Fleet 정적 서빙, Cam은 Android, Face는 LCD를 유지한다. CORE의 한 프로세스 안 rclpy+uvicorn 구조와 단일 최종 `cmd_vel` writer도 유지한다. 사이트 브라우저·Fleet은 장치 ROS/DDS에 직접 참여하지 않는다.

후속 이전은 자산 manifest/allowlist, ament share 경로, wheel·Gradle 설치, CI·harness·문서 참조를 함께 확인한다. 운영용 UI 자산을 역할별 최소 설치에서 누락하지 않고, 로봇 이미지에 사이트 서버·불필요한 Android/학습 의존성을 포함하지 않는다. 새 경로로 이동한 앱의 설치형 셸 도구 검사도 그 새 경로를 기준으로 조정한다.

기존 ADR의 역사 본문은 보존하고 부분 대체 범위만 표시한다. 기존 v0.2 설계·이전 계획에서 위 배치와 충돌하는 후속 단계는 이 ADR을 반영한 별도 실행 계획으로 구체화한다. 이미 진행 중인 고정 셀 흐름을 UI 이전 작업으로 중단하거나 이번 기록을 구현 완료 근거로 쓰지 않는다.

### Alternatives

- **기존 경로를 유지하고 역할표만 강화:** 즉시 변경은 작지만 gateway/agent/apps의 중의성이 남는다. 이전 중의 호환 경로로는 허용하며 목표 구조로는 선택하지 않는다.
- **제품마다 UI·서버·규칙을 모두 모음:** 제품별 탐색은 쉽지만 공유 기능·원장·통신 규칙이 제품 아래로 흩어진다. 기능 소유 모듈과 실행 조합을 분리하는 현재 방향을 선택한다.
- **전역 common 패키지·전역 로그인/store로 통합:** 서로 다른 자격·상태 정본·조종과 복구 규칙을 결합하므로 선택하지 않는다.
- **새 프론트엔드 서버나 동일 역할 API를 병렬 생성:** 기존 정적 서빙과 실행 owner를 유지하고 소비·조합만 이전한다.

### Consequences

- 앱 이름과 목표 경로가 사용자 작업과 실행 위치를 설명한다. 새로운 기능은 화면 소유·API·정본·writer를 정한 뒤 추가한다.
- Console 운용/설치는 한 Fleet 클라이언트를, Robot/Pilot은 한 CORE 클라이언트를 소비할 수 있다. 통신 코드 공유가 인증 상태·행동 정책 공유를 뜻하지 않는다.
- UI 위치가 서버 패키지와 분리되므로 정적 자산의 설치·서빙 manifest를 명시적으로 관리해야 한다. 소스 위치만 바꿔서는 설치가 완성되지 않는다.
- 기존 import·ament·Gradle·배포 계약은 이행 기간에 공존한다. 호환층은 단방향이며 호출자와 설치 검증이 끝난 항목만 제거한다.

### Validation and Follow-up

이번 문서의 수용 조건은 새 ADR/색인·부분 대체 표기의 일치, 번호 충돌 부재, 문서 계약 시험과 harness lint다. 런타임 코드·wire·등록부·폴더의 이전은 수행하지 않는다.

후속 실행 계획은 다음 순서와 출구를 기록한다.

1. **소유권 표:** 작업별 화면/API/정본/writer/소비자/이행 조건을 현재 구현과 대응. 등록부의 `owns`와 실제 API 호출·쓰기 경계를 함께 검사하고 선언만 검사하는 가드에 의존하지 않음.
2. **통신 추출:** Console 운용/설치부터 Fleet 클라이언트를 공유하고 Robot/Pilot의 CORE 클라이언트를 연결. 자격 격리·오류 계약·timeout·명령 자동 재전송 금지 검증.
3. **화면 책임 정리:** 영구 설정/세션 입력과 사이트 설치/운용 경계를 확인. 기존 운용 경로는 이행 수용 조건이 만족된 뒤 전환.
4. **소스 이전:** 한 단위씩 호출자·import·manifest·CI·harness·서빙·설치를 연결. 저장소 밖의 설치 환경에서도 엔트리포인트와 UI 자산을 확인.
5. **브라우저 검증:** 권한 부족·빈 상태·연결 상실·재연결·화면 이탈·폴링 종료·정지 요청의 결과 불명 표시, Console 두 문서의 세션 연속성과 Pilot 세션 중단 검증. 연결 복구 때 조종·작업이 자동 재개되지 않음을 확인.
6. **호환 제거:** 이전된 호출자와 설치 증거를 확인한 범위만 제거. SOURCE/LOCAL/ROS-SIM/ARTIFACT/DEVICE/FIELD를 구분하며 문서·호스트 브라우저 결과로 실기 gate를 올리지 않음.

새 관측·AI·공정 앱은 실제 사용자 작업이 생겼을 때 이 역할표에 소유자와 연결을 추가한다. 메뉴나 폴더만 먼저 만들지 않는다.
