## D-889 CI/CD 흐름: 통합 열차·정기 게시·잠금 밖 FULL

**Status:** Proposed (2026-10-26, robot-71 초안, 5개 세션 1차 검토 반영)

잇는 결정: [D-868](D-868-local-main-first-merge-commit-publish.md)(로컬 main 먼저, merge commit 게시. 이 ADR이 2항 5단계를 고친다) · [D-803](D-803-landing-queue-before-delta-rerun.md)(착지 대기열, 이 ADR이 처리 단위를 바꾼다) · [D-762](D-762-main-gateway-pull-request-merge-queue.md)(PR·merge queue로 가는 끝 상태) · [D-584](D-584-tests-never-run-on-operator-laptop.md)(노트북에서 시험하지 않음) · [D-568](D-568-compute-pool-headroom-placement.md)(계산 PC 풀) · [D-571](D-571-sim-ready-hosts-load-aware-placement.md)(sim 호스트).

### Context

지금 흐름은 "세션마다 `tools/land.py`를 돌려 한 줄로 선다 → 가끔 origin에 거대한 게시 PR"이다. 2026-10-25~26 측정:

- 처리 능력은 시간당 약 2.5건(잠금 안에서 시험해 착지당 평균 약 24분)인데, 몰릴 때 4건/시간이 들어와 대기 12건이 쌓였다. 대기 45~137분에 실제 차례는 4~8분으로, 대기가 90% 이상이었다. FULL 차례 하나(약 63분)가 뒤의 affected 11건을 붙잡았다.
- 첫 착지 전 재시작이 최대 16회였다(main 이동 6, NEW 7, 크기 규칙·트레일러·lint·호스트 재부팅 각 1). 기록 파일(`logs.md`·`index.md`·`adr_gaps.txt`) 때문에 멈추고 맨 뒤로 다시 선 경우가 3~4번이었다. 10-26 07:18에는 대기열 시간 초과로 자리를 잃었다(열차 전까지는 `--queue-timeout`을 늘려 줄인다).
- 착지 코드가 착지하는 브랜치의 사본으로 돌아, 오래된 브랜치가 옛 판정으로 멈췄다. `65cd2e6764`(`land_checks.landed_copy`가 main의 `land.py`로 다시 실행)가 고쳤다.
- 시험 PC의 디스크 부족(MAIN-RED)과 I/O 압력(fsync 굶음)이 시간 제한 시험의 거짓 실패를 만들었다.
- 게시가 정기적이지 않아 로컬 `main`이 `origin/main`보다 2,700커밋 넘게 앞섰다(10-16 분리의 일회성 밀림, PR #210으로 해소 예정).

몰릴 때 무너지는 원인은 셋이다. 시험이 잠금을 쥔다. 넓은 착지와 작은 착지가 한 줄에 선다. 게시가 정기적이지 않다. 흐름 자체를 단계로 나눈다(근거: 저장소 밖 작업 계획 `docs/superpowers/plans/2026-10-26-landing-throughput-design.md` 0~0.5절).

### Decision

**1. 단계 흐름.**

1. **작성:** 세션은 자기 워크트리에서 커밋하고 자기 브랜치를 원격 시험한 뒤 "준비됨" 파일을 쓴다.
2. **통합:** 전용 워크트리 `.worktrees/integration`에서 통합 스크립트가 준비된 브랜치를 착지한다. Claude 세션이 아니라 Windows 예약 작업으로 N분마다 도는 멱등 스크립트다. 한 번 실행이 한 사이클이다. 사람 판단이 필요한 충돌이나 MAIN-RED면 멈추고 사유 파일을 남긴다. git은 작업 폴더 밖에서 `-C`로 부른다(빈 폴더 위험, `5743aef1ee`).
3. **게시:** `origin/main`을 포함하는 커밋 가운데 녹색 FULL 착지 기록이 있는 가장 최신 커밋을 게시한다. 최소 하루 1회, 팀원 PR이 로컬 main을 기다리면 수시로 한다.
4. **릴리스:** 페이로드·모델 릴리스는 녹색 FULL 기록이 있는 SHA에서만 한다.

**2. main에 쓰는 쪽.**

- 통합 스크립트를 켜기 전에는 지금처럼 세션마다 `land.py`가 기본이다.
- 켠 뒤에는 통합 스크립트가 main에 쓰는 유일한 쪽이다. 세션은 `land.py`를 직접 돌리지 않는다. 사고 대응 착지는 통합 잠금을 같이 쓰는 우선 차선으로 간다. 대체 경로의 `land.py`는 그 잠금을 잡지 못하면 거부한다.
- ff 직전에 main이 후보의 기준 커밋과 같은지 본다. 다르면 그 후보를 버리고 다음 사이클에 다시 만든다.
- 통합 잠금에 pid가 없거나 N분 동안 갱신이 없으면 낡은 잠금으로 보고 지운다(D-803 대기열과 같은 방식).

**3. 열차 규칙.**

- 통합 워크트리에서는 코드 충돌을 풀지 않는다. 기록 파일만 자동으로 맞추고, 코드 충돌 브랜치는 열차에서 빼 주인에게 돌려보낸다.
- 안전 경로 여부와 "작은 affected 브랜치" 여부는 통합 스크립트가 diff에 `is_safety`와 선택기를 돌려 정한다. 준비 파일의 선언을 믿지 않는다. 안전 경로 브랜치와 사고 대응 착지는 묶지 않고 단독 serial FULL로 간다.
- **묶음 시험은 후보 트리에서 `시험한 main..후보`에 대한 선택기의 합친 affected다.** 브랜치 사이 import 결합(A의 새 시험과 B 모듈의 역의존)이 함께 선택된다. 선택기가 FULL로 올릴 때만 FULL을 돈다. 같은 모듈을 양쪽에서 건드린 브랜치가 자동 병합되면, 선택은 병합된 트리에서 양쪽 시험을 모두 포함해야 하고 트리 전체 크기 검사를 반드시 돈다(10-26 동기화의 실패 유형).
- 후보 트리마다 트리 불변식을 모두 다시 돌린다: 크기 `ratchet_problems` 전체, `safety_review`(시험한 main..후보), lint, generate, 짝 검사. 이분 탐색으로 쪼갠 하위 후보에도 다시 돌린다. 구성원별 결과를 합쳐 판단하지 않는다.
- 빨강의 귀속은 먼저 직접 귀속(실패 경로나 크기 단위를 바꾼 브랜치를 준비 기록과 대조)이다. 크기·safety처럼 결정적인 불변식을 빼면, 그 브랜치를 뺀 후보가 녹색인 것을 확인한 뒤에야 나머지를 착지한다. 그다음은 브랜치 단위 이분 탐색이다. 반쪽씩은 통과하고 합치면 실패하는 조합 실패는 순차로 처리한다(앞쪽 반만 넣고 나머지를 새 후보로).
- 시간 제한 시험도 판정에 들어간다. 실패하면 serial 호스트에서 단독으로 다시 돌려(`land_checks.load_flaky`) 분류한 뒤 귀속한다. 판정에서 빼는 것은 `known_failures`·`flaky_quarantine` 절차로만 한다. sim 회귀는 착지 관문에 넣지 않는다.
- **단독 재실행의 전제:** 귀속과 early-stop 확정이 이 재실행에 기대므로, node id를 저장소 경로로 되돌리거나 고정 rootdir로 돌린다. "no tests ran"·파일 없음은 통과가 아니라 쓸 수 없는 결과다. 10-26 `feat/update-view` 3회차에서 진짜 NEW 둘이 틀린 루트로 보고되어 재실행이 시험 0개를 돌았고, 분류가 소리 없이 빠졌다.
- 묶음은 측정한 새 실패율 p가 0.1 이하일 때만 켜고 k는 p로 정한다(p≈0.3, k=4면 성공 24%; p=0.1, k≤4면 66%). 그 전에는 묶음 크기 1로 돈다.
- 열차가 D-803 계획의 "준비 순서 대기열"을 대신한다. 둘 다 만들지 않는다.

**4. 준비·결과 파일.** `<git-common-dir>/rosy-ready/<branch>.json`:

| 필드 | 뜻 |
|---|---|
| head SHA | 검토·시험한 커밋. 준비 뒤 head가 바뀌면 준비는 무효이고 통합은 착지를 거부한다 |
| 증거 | 통과 기록(tree, 시험한 main, 선택 결과, 로그 경로). 참고용이다. 통합은 후보를 늘 직접 시험한다 |
| 의존 대상 | 브랜치, 또는 `{"sha", "why"}`. `merge-base --is-ancestor <sha> main`으로 판정 |
| 낮 필요 | 실물 확인이 필요한 착지. `deploy/**` 경로가 있으면 통합이 스스로 켠다 |
| 세션 이름 | 알림 대상 |

`<branch>.result.json`은 착지 SHA 또는 돌려보낸 이유, 자동으로 맞춘 파일 목록, `next` 힌트를 담는다: `retry`(호스트 끊김, 통합이 스스로 재실행), `fix`(NEW, node id·로그 경로), `rebase-needed`(코드 충돌), `gate`(`size-range`·`safety-review` 등 관문 이름). 알림은 결과 파일과 doctor의 한 줄 요약이 맡고, 세션 이름이 있으면 메시지도 보낸다.

**5. 게시 규칙.**

- 게시 전에 게시할 범위 전체(`origin/main..SHA`, 첫 게시는 약 2,700커밋)에 비밀 검사(IP·호스트·토큰·sha256 행 규칙)를 돌린다. 걸리면 게시하지 않는다. merge commit 게시는 마지막 트리가 아니라 이력 전체를 내보내므로, 검사는 범위 안 모든 커밋이 추가한 줄(커밋별 diff)을 본다. 중간 커밋에서 들어갔다가 지워진 비밀도 공개된다. 공개 저장소라 이 구멍이 열차보다 크다.
- origin→로컬 동기화는 충돌이 기록 파일뿐인 깨끗한 경우만 자동이다. 코드·add/add·이름 변경·삭제 충돌이면 멈추고 동기화·게시 담당에게 알린다.
- push는 게시할 SHA로 체크아웃한 임시 워크트리에서 한다(pre-push가 push SHA 기준으로 고를 때까지).
- 병합 전에 PR의 병합 가능 상태를 확인한다. 충돌이면 동기화로 넘긴다. PR을 닫았다 다시 열지 않고 force-push하지 않는다. 매번 날짜 붙은 새 브랜치를 쓴다.
- **역동기화(D-868 2항 5단계를 고친다):** 게시 PR이 병합되면 로컬 main에서 딴 워크트리에 `origin/main`을 병합해 `land.py`(켠 뒤에는 통합)로 착지한다. 그사이 origin에 아무도 push하지 않았으면 빈 병합이나 기록 파일만이다. `main` 체크아웃에서 `git merge --ff-only origin/main`은 하지 않는다.
- 첫 정기 게시는 `origin/main`이 로컬 main의 조상이고 직전 게시 PR(#210)의 역동기화가 착지한 것을 확인한 다음이다.

**6. 안전 장치.**

열차보다 먼저 들어갈 것:

- 안전 경로 FULL 트리거는 `FULL_TRIGGERS`에 접두를 복사하지 않고 `safety_review.is_safety(path, roots, safety_modules)`를 부르는 훅으로 둔다. "가장 깊은 루트가 이긴다" 경우와 `is_safety`가 False인 변형에서 시험이 빨개지는지를 시험한다.
- 안전 경로 브랜치의 단독 FULL에 더해, 주행·계획·제어 안전 루트를 건드리면 관련 sim 회귀 녹색을, 그 밖의 안전 루트는 사람의 명시 승인을 요구한다.

열차 뒤에 들어가도 되는 것:

- 넓은 FULL 착지는 FULL을 잠금 밖 준비 단계로 빼서 푼다. 잠금 안에는 병합 확인만 남긴다.
- 야간 FULL이 빨강이면: (1) 실패 id를 serial 호스트에서 단독 재실행해 확정한다. (2) 빨강인 동안 새 착지는 affected에 더해 빨간 id를 직접 다시 돌려 녹색이어야 허용한다. (3) 되돌림 제안이 4시간 안에 처리되지 않으면 동결 범위를 넓힌다. (4) 빨강 이후 SHA로는 릴리스·게시하지 않는다.
- "묶음을 되돌린다"는 그 merge commit의 revert를 우선 차선으로, 불변식과 시험을 거쳐 착지하는 것이다. main을 reset하거나 force하지 않는다(ruleset `non_fast_forward`).

기록: 착지한 구성원마다 후보 트리 SHA, 선택기 버전, 시험 환경 해시, `known_failures`·`flaky_quarantine` 해시, 시험 호스트를 사건 기록 jsonl에 덧붙인다. 열차 사이클은 `train` 사건(`branches`, `k`, `result`, `bisect`)으로 남긴다. merge commit을 보존해 구성원 단위로 되돌릴 수 있게 한다. 사건 기록은 정기적으로 `Rosy/artifacts/` 아래에 백업한다.

**7. 시험 PC 규칙.**

- FULL 묶음과 serial 단독 재실행은 gpu 예약이나 remote_sim sim lock이 있는 호스트에 넣지 않는다.
- 단독 재실행은 실행 폴더의 write+fsync p90과 잰 파일시스템을 함께 기록한다. p90이 20ms를 넘으면 판정하지 않는다.
- 현장 PC는 sim을 받지 않고(D-571), pytest는 다른 PC가 찼을 때만 받으며, 부팅 전 busy도 무시하지 않는다(`435401b133`). 그래서 열차는 FULL 묶음을 현장 PC에 넣지 않는다.
- gpu 예약(`.resv`)은 첫 필드에 만료 epoch를 쓰고 최대 2시간이며 갱신할 수 있다. 예약은 호스트에 묶인다(Isaac은 모델 PC, SmolVLA GPU는 AI PC). GPU 입장은 다른 ROSY GPU 예약이 없고 사용률·여유 메모리가 맞을 때다. ollama 같은 상주 서비스는 제외 목록에 둔다.
- 열차가 묶음을 띄울 때 예약 크기는 메모리 이력으로 정한다: 4GB를 넘은 적이 있거나 이력이 없으면 6GB, 아니면 3GB.
- 밤 창은 05:20에 끝난다(05:30 정리 타이머, 06시 재부팅). 밤에도 호스트별로 FULL 다음 sim 순서로 직렬 예약한다. 낮의 개발용 sim·GPU 시간대는 예약으로 남긴다.

**8. 측정이 먼저다.** `<git-common-dir>/rosy-land-events.jsonl` 사건 기록과 `tools/land_stats.py` 요약(`feat/land-events` `39108c0b53`)이 착지한 뒤 p를 재고 묶음을 켠다. early-stop은 첫 NEW를 단독 재실행으로 확정한 뒤에 남은 묶음을 취소한다.

| 순서 | 구성 요소 | 담당 |
|---|---|---|

| 2 | early-stop 연결(단독 재실행 확정 뒤 취소) | 착지 도구 담당 세션 |
| 2 | 안전 경로 FULL 트리거, pre-push의 push SHA 기준 선택 | 원격 시험 담당 세션 |

| 2 | 게시 비밀 검사, 게시 스크립트 | 원격 시험 담당 세션 초안 → 동기화·게시 담당 세션 |
| 3 | 통합 열차(`land.py` 루프 재사용), 통합 잠금·우선 차선 | 착지 도구 담당 세션, `remote_pytest`·doctor는 원격 시험 담당 세션 |
| 4 | 정기 게시·역동기화 | 동기화·게시 담당 세션 |
| 5 | FULL 잠금 밖 준비, 야간 빨강 동결 | 착지 도구 담당 세션 |

### Consequences

- 착지 처리 능력이 "잠금 안 시험 시간"에서 "병합 확인 시간(몇 분)"으로 바뀐다. 대신 잠금 밖 준비가 시험 PC 부하를 늘리므로 7항이 함께 들어가야 한다.
- 켠 뒤에는 main에 쓰는 쪽이 하나라 진행 상황이 통합 한 곳(결과 파일·사건 기록)에서 보인다.
- 묶음의 YAML·토픽 결합은 affected 선택이 놓칠 수 있다. 다른 착지와 같이 야간 FULL이 뒤를 받친다.
- 통합 스크립트는 이 노트북의 사용자 로그온 세션에서 돈다. 노트북이 잠들면 멈춘다(AC 대기·최대 절전 0 확인).
- 로컬 `main`과 `origin/main`의 차이가 하루치 착지 이하로 유지된다. 저녁 팀원 PR 병합 마감은 팀 운영 규칙이라 사용자가 정한다.
- Proposed다. 구현·측정 전이며, 묶음은 p ≤ 0.1을 확인하기 전에는 켜지 않는다.

### Alternatives considered

- **묶음마다 FULL:** 기각(검토에서 동기화·게시 담당과 한 세션이 제안). 사이클마다 약 60분 FULL이 지금의 병목을 다시 만든다. 브랜치 사이 import 결합은 합친 affected가 잡고, YAML·토픽 결합은 야간 FULL이 받친다.
- **넓은 FULL 착지를 밤 창(00~05시)으로 미루기:** 기각. 지연이 최대 하루다. 밤의 빨강을 볼 사람이 없다. 노트북이 잠든다. 밤에도 시험 PC가 학습·GPU 작업과 경쟁한다(릴리스 37이 9시간 보류된 전례). 밤 창은 동기화·게시와 sim 회귀 감시에만 쓴다.
- **세션마다 `land.py`(현재):** 잠금 안 시험으로 시간당 약 2.5건이 한계다. 통합 스크립트를 켤 때까지 기본이고, 그 뒤에는 통합 잠금을 잡을 때만 도는 대체 경로다.
- **GitHub merge queue(D-762 방향):** 지금은 하지 않는다. D-868이 로컬 `main`을 통합 브랜치로 남겼고, 시험은 GitHub 러너가 아니라 실험실 시험 PC(D-568)에서 돌며, GitHub CI 대기는 head당 50~60분이었다. 로컬 열차가 같은 규칙(후보 트리 시험·이분 탐색)을 먼저 검증한 뒤 다시 본다.
