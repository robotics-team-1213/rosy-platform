# PR 게시·검토 파이프라인

2026-10-16 사용자 결정: GitHub에서는 한 사람이 게시·병합하고, 에이전트 작업은 작성자와 독립 검토자 두 역할로 확인한다. GitHub 사람 승인 수는 0이며 필수 검사는 `ci-result`다. 이 절차는 현재의 PR 게시 기준이고, 공유 체크아웃의 로컬 착지 도구를 PR 도구로 바꿨다는 뜻은 아니다.

## 1. 작성 에이전트가 검토할 커밋을 만든다

1. 작업 이슈·담당 경로·완료 조건을 확인하고 전용 주제 브랜치에서 작업한다. 실험실은 [공유 체크아웃 절차](shared-checkout.md), 개인 클론은 [팀 가이드](team-guide.md)를 따른다.
2. 관련 계약과 해당 경로의 `AGENTS.md`를 읽고, 생성 기록을 갱신한 뒤 자신의 파일만 커밋한다. 관련 시험은 그 커밋을 대상으로 실행하고 실제 결과·건너뛴 검사·기존 실패 비교를 남긴다. 실험실 세션의 pytest는 원격 시험 PC에서만 실행한다.
3. 검토할 base SHA와 head SHA를 고정한다. `git log --oneline origin/main..HEAD`와 `git diff --stat origin/main...HEAD`로 공개할 범위를 확인한다. 로컬 `main`에만 있는 다른 작업까지 섞였으면 자신의 변경을 원격 기준 브랜치로 분리한 뒤 검토를 요청한다.

## 2. 독립 검토 에이전트가 읽기 전용으로 확인한다

작성자와 다른 에이전트에게 목적·완료 조건·변경 경로·base/head SHA·관련 계약·검증 결과를 전달한다. 전체 대화 기록 대신 검토에 필요한 근거를 전달한다. 검토자는 파일을 수정하거나 게시하지 않고, 실제 변경과 생산자·소비자 경로, 실패 시 동작, 시험 누락을 확인한다.

검토 결과는 `수정 필요` 또는 `수정 필요 사항 없음`으로 남기고, 발견 사항에는 경로·위치·영향·근거를 적는다. 작성자가 발견 사항을 수정하면 변경된 SHA와 해당 수정 범위를 다시 검토받는다. 검토자를 만들 수 없으면 혼자 검토하고 두 명이 확인했다고 적지 않는다. 그 상태를 보고하고 검토를 확보한다.

안전 경로의 독립 리뷰와 `Safety-Review:` trailer는 기존 D-430 규칙을 따른다. 일반 독립 검토 기록이 이 요구를 대신하지 않는다.

## 3. 게시 담당 한 명이 PR을 올린다

작성 에이전트가 게시 담당을 겸해도 된다. 같은 브랜치의 push·PR 수정·병합은 게시 담당 한 명만 수행한다. 검토 에이전트는 GitHub에 별도 승인이나 댓글을 작성하지 않는다. 외부 게시·병합은 사용자가 허용한 범위에서만 한다.

게시 전 커밋 상태와 pre-push 검사를 확인한다. 원격 브랜치가 이미 공유됐다면 최신 `origin/main`은 merge로 반영하고 force-push하지 않는다. 생성 기록·문서·코드 수정이나 merge 충돌 해결로 head가 달라지면 모든 파일 종류의 변경분을 독립 검토받고 새 head를 검증한다. 최종 게시 head는 검토 기록의 head와 같아야 한다. PR에는 아래 검토 기록과 검증 결과를 남긴다.

```text
작성자 / 게시 담당:
독립 검토자:
검토 base SHA / head SHA:
검토 결과와 발견 사항 처리:
시험 SHA / 실행 위치 / 명령 / 결과:
건너뛴 검사와 이유:
```

## 4. 최신 SHA의 CI를 확인한 뒤 병합한다

```bash
gh pr checks <PR번호> --required --watch
gh pr view <PR번호> --json headRefOid,statusCheckRollup,mergeable
gh pr merge <PR번호> --squash --match-head-commit <확인한-head-SHA>
```

`ci-result` 성공과 PR head SHA를 직접 확인한다. 비게이팅 잡도 읽고, 실패·수집 오류·미실행을 전체 통과로 보고하지 않는다. 이 변경에서 새로 드러난 실패는 원인을 확인하고 해결하며, 기존 실패라고 판단하려면 변경 전 기준선의 같은 실패 근거를 남긴다. 시험을 숨기거나 freshness·안전 기준을 느슨하게 바꿔 통과시키지 않는다.

head가 바뀌면 새 SHA의 관련 시험·독립 재검토·CI가 필요하다. 문서·생성물·merge 해결도 같은 규칙을 따른다. 관리자 예외로 적색 CI를 넘기지 않는다. 사람 승인 0명은 혼자 게시할 수 있다는 뜻이고, 독립 에이전트 검토와 검증을 생략한다는 뜻은 아니다.

## 5. 병합 후 확인하고 종료한다

GitHub의 병합 상태·병합 SHA와 변경 파일을 확인한다. 기본 브랜치에만 적용되는 양식·문서는 그 브랜치의 파일로 확인하고, 로그인 등으로 실제 화면을 확인하지 못했으면 그 한계를 남긴다. 병합 후 CI의 상태와 남은 후속 작업도 기록한다. CI 확인까지 요청받은 작업은 결과를 확인한 뒤 완료로 보고한다.

공유 로컬 `main`을 임의로 reset·stash·clean해 맞추지 않는다. 다른 세션 변경을 보존하고, 작업 브랜치와 워크트리는 현재의 손실 없는 정리 규칙을 따른다.
