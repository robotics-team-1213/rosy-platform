## 02 제품 정체와 실제 구성

본 보고서의 OMX-AI는 ROBOTIS의 입문형 Physical AI 리더·팔로워 세트입니다. OMX-L은 사람이 손으로 조작하는 입력 장치이고, OMX-F가 실제 물체를 다루는 팔입니다. **팔 5자유도와 그리퍼 1축**을 임의의 위치·자세를 모두 지정하는 6축 산업용 팔과 혼동하면 안 됩니다. \[01\]\[03\]

| **항목** | **OMX-L 리더** | **OMX-F 팔로워** |
| --- | --- | --- |
| 자유도 | 팔 5 + 그리퍼 입력 1 | 팔 5 + 그리퍼 1 |
| 전체 도달거리 | 335mm | 400mm |
| 본체 질량 | 360g | 560g |
| 동작 전압 | 5V DC | 12V DC |
| 호스트 / 내부 통신 | USB-C / TTL, 1Mbps | USB-C / TTL, 1Mbps |
| 구동기 구성 | XL330-M288-T ×5<br>XL330-M077-T ×1 | XL430-W250-T ×3<br>XL330-M288-T ×3 |
| 공식 가반하중 | 작업 하중의 기준 장비가 아님 | 완전 신장 100g / 일반 도달 250g |

위 사양은 공식 하드웨어 문서 \[03\]. “일반 도달”의 정확한 거리·자세와 연속 운전 조건은 공개 표만으로 확정할 수 없어 공급사 확인이 필요합니다.

### 세트에 포함되는 것과 별도 준비할 것

공식 공통 구성표에는 OpenRB-150 2개, DYNAMIXEL 12개, SMPS·SMPS2DXL, USB-C 케이블 2개, 클램프 4개, DC 컨버터와 출력 부품이 기재되어 있습니다. 카메라·호스트 PC는 이 구성표에 없습니다. **카메라까지 포함된 완성 시스템 가격이 아닙니다.** \[03\]

국내 구매 기준 SKU는 905-0047-000입니다. 공식몰은 2026년 5월부터 Link-U 및 DC 컨버터 변경을 공지하고 있어, 발주서에는 최신 리비전·전원·케이블·조립 상태·카메라 포함 여부를 명시해야 합니다. 지역별 다른 SKU의 사진·구성 설명을 그대로 적용하지 않습니다. \[02\]

### 이름이 비슷한 제품과 구분

OMX, 구형 OpenMANIPULATOR-X, 상위 OMY는 별도 모델입니다. 특히 OMY-F3M의 D405 기본 구성이나 OMY의 6자유도 설명을 OMX에 적용하면 안 됩니다. OMY-F3M에 대한 D405 설명은 공식 OMY 페이지에 있습니다. \[01\]\[34\]

### 손목 카메라가 만드는 숨은 하중

설계 예로 카메라 20g + 브래킷·배선 영향 15g + 물체 40g이면 단순 질량 합계는 75g입니다. 그러나 이 값만으로 안전을 판정하지 않습니다. 무게중심 거리, 케이블 당김, 가속도, 관절 자세에 따라 모터가 받아야 하는 토크가 달라집니다. **“100g에서 카메라 무게를 뺀 값”은 보증 가능한 물체 하중이 아닙니다.**

D405 본체는 60g이므로 고정물·배선과 작업 물체까지 더하면 OMX의 완전 신장 여유가 빠르게 작아집니다. 가까운 거리에서 깊이를 잘 측정한다는 장점과, 작은 팔의 손목에 적합하다는 판단은 서로 다릅니다. \[03\]\[17\]

### 첫 작업은 이렇게 좁힙니다

20\~50g 불투명 부품 1종, 테이블 위 일정 높이, 손목 자세가 크게 바뀌지 않는 접근, 격벽 없는 넓은 트레이를 권고합니다. 위치 변화를 늘리기 전에 고정 좌표 이동·실제 도달 오차·파지 안정성을 측정합니다. 숫자는 제조사 보증이 아니라 본 보고서의 실험 시작 조건입니다.

## 04 ROS와 AI는 세 경로로 접근한다

| **경로** | **공식 기반** | **우리에게 주는 가치** | **주의점** |
| --- | --- | --- | --- |
| A. ROS 2 제어 | Jazzy, ros2_control, MoveIt, 공식 bringup \[04\]\[06\] | 기구학·TF·충돌 검사·센서 연동을 배우고 현장 시스템으로 확장 | 카메라 장착만으로 자동 파지가 구현되지는 않음 |
| B. ROS + Cyclo | ROS 토픽 기록, 데이터 변환, 추론 실행 \[12\]\[13\]\[15\] | ROS 관측과 시범 데이터를 같은 체계로 관리 | 학습은 Cyclo 외부에서 수행. 토픽 설정·GPU 이미지 호환성 확인 |
| C. Native LeRobot | omx_leader / omx_follower 공식 지원 \[11\] | ROS 없이도 직접 시범 수집·학습 실험 가능 | ROS 드라이버와 직렬 장치 동시 점유 금지. ROS 통합은 별도 어댑터 필요 |

### 권고 순서: A로 기준선을 만들고 B 또는 C를 선택

사용 목적이 “ROS까지 이해하고 자체 로직을 만드는 것”이라면 A를 중심으로 잡습니다. 모터 통신, 관절 피드백, 제한된 목표 이동과 카메라 좌표 변환을 확인한 뒤 모방학습을 추가합니다. 짧은 기간에 학습 절차만 경험할 때는 C를 별도 환경으로 운영할 수 있습니다.

B는 현재 공식 도구가 rosbag2 기록 → 검토·정리 → LeRobot v2.1/v3.0 변환을 지원하므로 연결 고리를 전부 새로 만들 필요는 없습니다. 다만 임의로 녹화한 모든 rosbag이 자동 변환되는 것으로 해석하면 안 됩니다. 공식 로봇 설정, 필요한 토픽과 타임스탬프 구조가 맞아야 합니다. \[12\]\[13\]

### 현재 버전에서 중요한 변화

조회한 open_manipulator 최신 릴리스는 5.1.2이고 변경기록 날짜는 2026-09-14입니다. 5.0.0부터 기본 통신이 Zenoh로 바뀌었습니다. 과거 Fast DDS 튜토리얼과 현재 컨테이너를 혼합하지 말고, 검증한 Git 태그·커밋과 컨테이너 digest를 함께 보관합니다. \[08\]\[09\]

> **캘리브레이션을 하지 않아도 된다는 말의 범위**
>
> OMX의 출고 모터 설정·오프셋이 준비되었다는 뜻입니다. 카메라 렌즈 보정, 카메라-로봇 위치 관계, 공구 중심점(TCP), 테이블 기준면은 별도로 보정해야 합니다. [11][23]

### 네트워크는 로봇팔이 아니라 제어 PC를 중심으로 구성

OMX의 호스트 연결은 USB-C입니다. 원격 제어 예제의 robot_ip는 본 구성에서는 **OMX를 USB로 연결하고 제어 컨테이너를 실행하는 PC의 IP**로 해석합니다. 인터넷을 통과하는 원격 GPU가 USB 모터를 직접 제어하게 만들지 않습니다. \[03\]\[08\]

현재 공식 컨테이너는 rmw_zenoh_cpp를 기본 사용하며 네트워크에 Zenoh 라우터가 필요합니다. 외부 클라이언트는 제어 PC의 TCP 7447 엔드포인트에 접속하도록 설정합니다. 관련 터미널·컨테이너의 ROS_DOMAIN_ID와 RMW 설정을 일치시켜야 합니다. \[08\]

### 기존 Pinky/DDS 환경과 연결하는 방법

1차 실험은 OMX 네트워크를 독립 구성합니다. 통합 단계에서는 관련 노드를 동일한 RMW로 맞추거나, 별도 작업 게이트웨이로 완료·요청 메시지만 연결하는 편이 단순합니다. 공식 문서에는 모든 관련 컨테이너를 Fast DDS로 바꾸는 절차도 있습니다. RMW 하나만 바꾸고 다른 컨테이너를 그대로 두지 않습니다. \[08\]

> **제어 주기와 AI 주기를 혼동하지 않습니다**
>
> 공식 소프트웨어의 관절 제어 루프는 100Hz 구성입니다. 카메라 30fps, 정책 추론 주기, 네트워크 지연은 별도 값입니다. “100Hz 제어”가 카메라부터 파지까지 10ms 안에 끝난다는 의미는 아닙니다. [04][15]

## 07 카메라보다 중요한 배치·조명·USB

### 상부 카메라: 작업영역을 재현 가능하게

초기 배치안은 테이블 위 약 45\~65cm에 고정 RGB 1대를 놓고, 파지 시작 구역과 목표 트레이를 모두 보게 하는 것입니다. 이 높이는 RGB용 설계 시작값입니다. D405의 7\~50cm 권장 거리나 다른 카메라의 최소 깊이에 그대로 적용하지 않습니다. 렌즈 시야와 실제 물체 높이를 보고 조정합니다. \[17\]\[18\]

시야 폭 W는 왜곡을 무시한 단순 모델에서 W ≈ 2h·tan(HFOV/2)입니다. 예를 들어 h=0.5m, 수평 시야각 70°이면 폭은 약 0.70m입니다. 판매 페이지의 대각 시야각(DFOV)을 수평 시야각(HFOV)으로 대입하면 안 됩니다. 이 계산은 배치 예시이지 특정 제품의 실측값이 아닙니다.

### 손목 카메라: 집게 끝을 보되 움직임을 방해하지 않게

파지 직전의 집게 끝과 대상이 보이는 위치에 작고 가벼운 모듈을 놓습니다. 브래킷을 포함한 질량을 저울로 측정하고, 모든 관절 자세에서 케이블 여유·당김·집게 간섭을 확인합니다. 손목 카메라를 장착한 뒤에는 외부 보정값과 학습 데이터 조건이 달라집니다.

| **항목** | **초기 설정 / 점검** |
| --- | --- |
| 해상도·프레임 | 학습·원격 영상은 우선 640×480, 실제 30fps를 목표로 시험. 작은 코드 판독은 별도 고해상도 원본과 조명으로 평가. |
| 초점·노출 | 고정 초점 또는 초점 잠금. 노출·화이트밸런스 잠금 가능 여부 확인. 카메라가 자동으로 밝기와 색을 바꾸는 변수를 줄임. |
| 조명 | 확산 LED, 반복 가능한 위치, 반사 억제. 이동 중 줄무늬나 밝기 변화가 없는지 실제 영상으로 확인. |
| USB 배치 | 깊이 카메라는 가능한 호스트 USB 3 직결. 두 RGB가 같은 허브를 공유하면 모드별 프레임 드롭 시험. |
| 장치 식별 | /dev/video0 번호만 고정하지 말고 serial/by-id 등 지속 식별자를 사용. 동일 저가 카메라의 식별자 중복 가능성 확인. \[12\]\[16\] |
| 수집 지속성 | 30분 연속 녹화, 재연결, 재부팅 후 카메라 역할이 뒤바뀌지 않는지 확인. |

비압축 RGB8 640×480×30fps는 1대당 약 27.65MB/s, 2대 약 55.30MB/s입니다. USB 전송 포맷이 MJPEG/YUYV이면 실제 버스 사용량은 달라집니다. 위 값은 메모리 내 RGB 데이터량 계산이며, 허브가 감당한다는 보증이 아닙니다.

## 08 픽셀을 로봇 좌표로 바꾸는 과정

> **물체를 찾는 것과 집을 수 있는 좌표를 구하는 것은 다릅니다**
>
> 검출 상자 중심 (u,v)은 화면 위치입니다. 로봇이 이동하려면 실제 거리·기준 좌표계·공구 끝 위치·접근 자세가 필요합니다. 모방학습으로 영상-동작을 직접 연결하는 경우에도 장착과 입력 조건의 일관성은 필요합니다.

| **보정 단계** | **저장할 값** | **확인 방법** |
| --- | --- | --- |
| 내부 보정 | 초점거리 fx/fy, 중심 cx/cy, 왜곡 계수 | 실제 해상도와 초점에서 보정판을 촬영. 촬영하지 않은 위치로 오차 검증. \[23\] |
| 고정 카메라 외부 보정 | 카메라 → 로봇 기준 변환 | 테이블 기준점과 로봇이 가리키는 점을 대조. 카메라·팔 베이스가 이동하면 재검증. |
| 손목 hand-eye | 카메라 → 공구/손목 고정 변환 | 다양한 자세의 영상과 대응 관절 자세를 사용. 현재 시각의 TF로 월드 좌표 변환. \[23\] |
| TCP·작업면 | 실제 집게 중심, 테이블 높이 | 툴 변경 후 재측정. 손끝 충돌 전에 충분한 여유 공간에서 검증. |
| 깊이 정합·시간 | RGB-depth 정렬, 깊이 단위, 시각 | 서로 다른 픽셀 좌표나 mm/m 혼동 방지. 움직이는 손목은 영상 촬영 시각의 자세 사용. |

### 두 가지 기하 경로

**고정 평면 RGB:** 렌즈 왜곡을 보정하고, 알려진 테이블 평면에 대한 호모그래피로 화면 점을 작업면 좌표로 옮깁니다. 높이가 바뀌거나 물체 윗면이 테이블에서 떠 있으면 같은 변환을 그대로 적용할 수 없습니다. \[23\]

**RGB-D:** 정렬된 깊이 Z와 내부 보정값으로 X=(u-cx)·Z/fx, Y=(v-cy)·Z/fy를 구하고, 카메라 점을 로봇 기준으로 변환합니다. 마스크 내부의 유효 깊이를 확인하고 경계·구멍·배경을 제외합니다. 한 픽셀의 깊이만 믿어 집게 높이를 결정하지 않는 방식을 권고합니다. \[23\]

### TF와 단위 원칙

ROS는 길이 m, 각도 rad를 기본으로 사용합니다. 일반 본체 축은 x 전방·y 좌측·z 위쪽이고, camera_optical 계열은 z 전방·x 우측·y 아래쪽입니다. 이름만 바꾸지 말고 올바른 회전을 포함한 변환을 연결합니다. \[24\]

초기 검증 제안: 작업면에 3×3 기준점을 두고 위치별 오차를 기록합니다. 보정 오차·깊이 오차·팔 오차·파지 여유를 분리하여 평가하며, 센서의 “밀리미터급” 광고를 전체 시스템 정밀도로 간주하지 않습니다.

## 09 시범 데이터 수집과 품질 관리

Cyclo Intelligence는 이미 발행 중인 로봇·관절·카메라 토픽을 rosbag2 에피소드로 기록합니다. 카메라 영상을 화면에서 볼 수 있어도 로봇 설정 파일에 등록되지 않은 토픽은 수집되지 않습니다. 새 카메라를 추가하면 노드 실행과 observation.images 설정을 각각 확인해야 합니다. \[12\]

| **반드시 구분할 데이터** | **저장·검증 기준** |
| --- | --- |
| 관측 observation | 팔로워 실제 관절 상태, 카메라별 영상, 각 데이터 시간. 명령값을 실제 관절 상태로 대체하지 않음. |
| 행동 action | 리더 또는 정책이 요구한 목표 명령. 축 순서, rad/degree/정규화 값, 그리퍼 정의를 명시. |
| 에피소드 메타데이터 | 작업 ID, 자연어 설명, 시작 조건, 물체 종류·질량, 성공/실패, 작업자·세션 구분. |
| 보정·버전 | 카메라 ID, 이미지 회전·크기, 내부/외부 보정, 로봇 URDF, 소프트웨어 커밋·펌웨어. |
| 동기 품질 | 실제 프레임율, 관절-영상 시간차, 중복·누락, 가장 느린 카메라 기준의 출력 FPS. |

### 공식 변환 도구를 활용하되 변환 결과도 검사

Cyclo Data Tools는 rosbag2 데이터를 검토·삭제·병합하고 LeRobot v2.1 또는 v3.0 형식으로 변환합니다. 액션·관측·카메라 타임스탬프를 목표 FPS에 정렬합니다. 목표 FPS는 실제 카메라 속도를 기준으로 해야 하며, 15Hz 영상을 설정만으로 실제 30Hz로 만들 수 없습니다. \[13\]

### 초기 데이터 설계안

먼저 정상 시범 10개로 카메라·관절·명령 정합을 확인한 뒤, 5\~10개 시작 구역에서 각각 반복해 **50\~100개 시범**을 수집합니다. 부족한 실패 조건을 보완하여 늘립니다. 이 개수는 실험 계획이며 성공률을 보장하지 않습니다. 프레임을 무작위로 쪼개 학습·평가에 섞지 말고 날짜·세션·시작 조건 단위로 분리합니다.

실패 시범은 원본 진단용으로 별도 보관하고, 정상 동작 모방학습 세트에는 검토 후 포함 여부를 정합니다. “집기 실패”와 “카메라 데이터 누락”은 같은 실패가 아니므로 구분해야 원인을 개선할 수 있습니다.

### 용량 예산

가정: RGB 카메라 2대, 각각 압축 영상 6Mbps, 에피소드 30초, 100회이면 영상 약 4.5GB입니다. 변환본·중복 기록·체크포인트는 별도입니다. SSD에 100\~200GB 작업 여유를 확보하는 것을 권고하며, 실제 비트레이트와 저장 중복 여부를 측정해 수정합니다.

## 10 모델 선택: ACT부터, VLA는 그다음

**추천 순서는 규칙 기반 제어 → ACT → SmolVLA입니다.** ACT는 영상과 관절 상태를 받아 여러 시점의 행동 묶음을 예측하는 모방학습 정책으로, LeRobot도 첫 모델로 권고합니다. SmolVLA는 영상·상태·언어 지시를 함께 사용하지만 우리 로봇과 작업 데이터에 맞춘 적응이 필요합니다. \[26\]\[27\]

| **단계 / 모델** | **우리의 목적** | **자원·운영 판단** |
| --- | --- | --- |
| 규칙 기반 / OpenCV | 고정 좌표·평면 인식·이동의 기준선 | 실패를 좌표·기구·파지 문제로 분리하기 쉬움. 모든 작업에 AI 학습이 필요한 것은 아님. |
| ACT | 한두 가지 짧은 반복 작업을 시범으로 학습 | HF 기획 가이드의 light BC 학습 범위: 대략 2\~6GB VRAM (batch 8 조건). 실측 필수. \[28\] |
| Diffusion | ACT와 행동 생성 방식 비교 | 동일 가이드 약 8\~14GB VRAM. 첫 실험의 복잡도 대비 이득을 비교 후 선택. \[28\] |
| SmolVLA | 언어 지시·여러 작업으로 확장 | 동일 가이드 약 10\~16GB VRAM. 동결 범위·배치·영상 수에 따라 변동. \[27\]\[28\] |
| Pi0 / 대형 VLA 계열 | 고도화 연구 | 수십 GB급 GPU 메모리와 학습 자원을 별도 산정. 현재 16GB 시스템 RAM PC의 기본 목표에서 제외. \[28\] |

VRAM은 GPU 메모리이며 시스템 RAM과 다릅니다. 위 수치는 Hugging Face의 대략적 학습 가이드이지 특정 OMX 구성·추론 속도·학습 완료시간의 보증이 아닙니다. \[28\]

### Cyclo의 현재 GPU 조건을 놓치지 않습니다

현재 공식 추론 문서는 **사전 빌드된 ACT·GR00T 정책 이미지가 Blackwell 기반 amd64/arm64 환경에 한정**된다고 설명합니다. 이는 ACT 알고리즘 자체가 Blackwell에서만 동작한다는 뜻이 아닙니다. 다른 GPU는 native LeRobot 또는 호환 백엔드 이미지 준비 경로를 검토해야 합니다. \[15\]\[26\]

Cyclo는 외부에서 학습한 모델을 불러와 시뮬레이션 검사 후 실제 명령을 발행합니다. 학습은 Cyclo 외부에서 수행합니다. 지원 모델 이름이 목록에 있다는 사실이 “OMX에 꽂으면 바로 물건을 집는 완성 체크포인트”를 뜻하지는 않습니다. \[14\]\[15\]

> **정책보다 먼저 준비할 것**
>
> 카메라 고정·조명 고정·상태/행동 정의·정지 규칙·평가 조건입니다. 데이터 조건이 바뀌면 더 큰 모델을 써도 원인이 해결되지 않을 수 있습니다.

### Windows/WSL을 버릴 필요는 없지만 역할을 나눕니다

### Gazebo → 필요시 MuJoCo → 목적이 생기면 Isaac

OMX 공식 문서는 Gazebo 실행 경로를 제공하고, ROBOTIS MuJoCo 저장소에도 OMX 모델이 있습니다. 먼저 관절·TF·접근 경로를 검증하는 데 사용합니다. Isaac의 사실적 렌더링이 필요한 합성 데이터 과제가 생기면 별도 자원으로 평가합니다. Headless가 RAM 최소요건을 자동으로 없애지는 않습니다. \[10\]\[29\]\[32\]

제안: 제어 30분 안정성 시험과 학습 1회 메모리 시험을 분리합니다. swap은 충돌 회피 수단일 수 있어도 시간 민감 제어 성능을 보장하는 해결책으로 취급하지 않습니다.

## 12 Pinky Pro·바코드·현장 시스템으로 확장

> **Pinky 위에 팔을 올리는 것보다, 역할을 나눕니다**
>
> 1차 구조는 “Pinky가 정해진 위치로 운반 → 정지·도킹 확인 → 고정 OMX가 작업 → 완료 확인 → Pinky 출발”입니다. 주행과 조작의 변수를 동시에 늘리지 않습니다.

Pinky Pro 공식 페이지는 110×120×142mm 크기, Raspberry Pi, 5MP 카메라와 LiDAR·IMU를 설명합니다. 해당 공개 사양에서 팔 탑재 허용 하중을 확인하지 못했습니다. OMX-F 560g 본체와 길게 뻗는 팔의 무게중심 변화를 감안하면 직접 탑재 가능하다고 단정할 근거가 부족합니다. \[03\]\[31\]

| **연계 지점** | **처리 방식 제안** |
| --- | --- |
| 도킹 확인 | Nav2 목표 도착만으로 작업 허가하지 않음. 근접 위치 기준·마커/센서·속도 0 확인 등을 조합하여 별도 작업 준비 신호 생성. |
| 작업 인터록 | arm_busy이면 주행 금지, base_ready가 아니면 파지 금지. 재접속 시 자동 재개 금지. 명령 ID와 완료 ID를 대조. |
| 좌표 관계 | 정지 작업대는 station 기준으로 보정. 이동 베이스 탑재 시 map/odom/base/arm/camera 변환과 시간 정합을 모두 다시 검증. |
| Pinky 카메라 | 주행·상황 관측과 손끝 정밀 작업의 요구가 다름. 5MP라는 숫자만으로 보정된 작업 카메라나 깊이 카메라를 대체하지 않음. |

### 세리텍 업무와 연결할 수 있는 실증 세 가지

**품목 식별 후 분류:** 바코드 판독 결과를 작업 ID에 묶고, 비전에서 선택한 대상 1개와 동일 물체인지 확인한 뒤 트레이를 결정합니다. 여러 물체가 보이는 경우 코드가 어느 물체의 것인지 연결하는 로직이 별도로 필요합니다.

**라벨 부착 전 부품 정렬:** 가벼운 부품을 정해진 지그에 놓고 프린터·작업자에게 다음 단계를 요청합니다. 라벨을 박리·흡착·부착하는 전체 기구까지 OMX 하나로 바로 해결하려는 범위는 피합니다.

**검사·저울 연동 데모:** 집은 대상의 품목·중량·검사 결과를 하나의 이력으로 연결합니다. 실패하면 물체를 다시 확인하거나 작업자를 호출하도록 설계합니다. PLC와 연결할 때도 작업 신호와 안전 정지 회로는 분리합니다.

위 흐름은 시스템 설계 제안이며 Pinky·OMX·스캐너·프린터 간의 완성 패키지 호환성을 의미하지 않습니다.

| 전원 차단 후 낙하 | 팔과 물체가 내려오는 영역을 비움. 낮은 높이·받침·수동 차단 수단 준비 | 전원을 끊는 것이 항상 가장 안전한 상태라고 가정하지 않음 |
| 허브·케이블·발열 | 재연결/연속 녹화/관절 자세별 배선 점검 | 동작 중단 후 장치 식별·초기 상태 재확인 |
| 원격 접근·데이터 유출 | 로컬망/VPN·접근 제한·비공개 데이터셋·비밀키 분리 | 외부 접속 차단, 로컬 기록 유지 |

### 소프트웨어 정지와 하드웨어 차단은 역할이 다릅니다

화면의 Stop 버튼, 명령 timeout, USB 연결 해제, 전원 차단은 동일한 기능이 아닙니다. 전원·토크 해제 후 팔이 처지거나 물체를 놓을 수 있으므로 실제 상태별 거동을 먼저 확인해야 합니다. 수동 차단 부품을 달았다는 사실만으로 인증 비상정지 또는 안전회로가 완성되었다고 표현하지 않습니다.

### 네트워크·데이터 기본 원칙

Zenoh 7447, 컨테이너 Web UI, 원격 화면을 공인 인터넷에 직접 노출하지 않는 구성을 권고합니다. 고객 코드·라벨·제품이 담긴 영상은 기본 비공개로 저장하고 외부 학습 서버 업로드 전에 반출 가능 범위를 확인합니다. 원본 데이터는 수정본과 분리하고, 모델·코드·보정 파일을 함께 버전 관리합니다.

### OMX 대신 다른 선택이 나은 경우

**SO-101 비교:** LeRobot 중심의 조립·보정·학습 경험이 핵심이면 비교 대상입니다. 공식 문서에 모터 구성과 리더·팔로워 캘리브레이션 절차가 있습니다. 국내 최종비용·부품 품질·지원 조건을 확인하지 않은 상태에서 OMX보다 싸거나 더 낫다고 단정하지 않습니다. \[33\]

**OMY 또는 다른 6축 플랫폼:** 더 자유로운 파지 자세와 다른 하중 범위가 요구되면 상위 플랫폼을 먼저 비교합니다. OMY는 6자유도 및 DYNAMIXEL-Y 계열 기반이고 OMY-F3M에 D405 구성이 명시되어 있습니다. 가격·하중·안전 등급은 별도 사양 검토가 필요합니다. \[34\]

**로봇팔이 불필요한 경우:** 물체를 이동시키지 않고 코드 확인·중량 판정·프린터 발행·신호 출력만 필요하다면 고정 카메라/스캐너와 PC·PLC가 더 단순한 해법일 수 있습니다. OMX 도입 목적을 “학습용 실험”과 “즉시 생산성 개선”으로 구분합니다.

> **최종 권고**
>
> 우선 OMX-AI 기반 소형 작업대를 구축해 제어·비전·데이터를 익히는 것은 권고합니다. 성공한 기능과 데이터는 유지하되, 하중·정밀도·안전이 병목으로 확인되면 카메라나 AI 모델이 아니라 로봇 플랫폼 자체를 교체하는 판단이 필요합니다.

## 17 현장 시작 명령과 버전 기록

아래는 공식 경로와 읽기 중심 점검 명령을 모은 시작점입니다. 설치된 패키지·컨테이너·장치 경로에 맞춰 확인해야 하며, 본 환경에서 사용자 로봇에 실행 검증한 스크립트가 아닙니다. **하드웨어 bringup은 초기 움직임을 유발할 수 있으므로 작업영역을 비운 뒤 실행합니다.** \[05\]\[06\]

### A. 장치와 ROS 통신부터 확인

```bash
# Linux host: serial/camera device inventory
ls -l /dev/serial/by-id/
v4l2-ctl --list-devices

# Inside the official open_manipulator container
echo "$RMW_IMPLEMENTATION"
echo "$ROS_DOMAIN_ID"
# Run in a separate terminal only if no router is running:
zenohd

# Inspect the graph in another terminal
ros2 node list
ros2 topic list -t
ros2 action list -t
```

### B. 공식 launch 이름: 모드별로 하나씩

```bash
# Simulation route (do not also start hardware bringup)
ros2 launch open_manipulator_bringup omx_f_gazebo.launch.py

# Hardware route: only after USB, power and workspace checks
ros2 launch open_manipulator_bringup omx_f.launch.py
# In a separate terminal after hardware is ready
ros2 launch open_manipulator_moveit_config omx_f_moveit.launch.py
```

공식 로봇 제어·Gazebo 경로 \[06\]\[10\]. 설치·포트 지정은 ROS 2 Setup \[05\]. 리더·팔로워 기록 모드는 Teleoperation \[07\]의 별도 구성에 따릅니다.

### C. 카메라와 LeRobot 식별

```bash
# Replace the video path with the verified capture device
ros2 launch open_manipulator_bringup camera_usb_cam.launch.py \
  name:=camera2 video_device:=/dev/video1

# Native LeRobot environment; stop ROS hardware drivers first
lerobot-find-port
lerobot-find-cameras opencv
```

카메라 launch 및 장치 경로 주의사항 \[12\], LeRobot 탐색 명령 \[11\]\[16\]. 카메라 번호는 예시입니다. 단일 장치가 여러 video 노드를 노출할 수 있으므로 실제 capture 노드를 확인합니다.

설치 기록에 OS·ROS·Git tag/commit·컨테이너 digest·GPU/VRAM·CUDA/PyTorch·모터 펌웨어·카메라 serial·렌즈 설정·보정 파일·작업 데이터 버전을 남깁니다. ROS와 LeRobot 사이의 관절 순서·단위·그리퍼 표현을 별도 매핑 표로 보관합니다.
