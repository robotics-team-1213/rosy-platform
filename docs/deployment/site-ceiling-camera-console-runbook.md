# 현장 천장 카메라 · 관제 운영 가이드

현장 운영자와 팀원이 천장 폰 카메라(Rosy Cam)를 현장 PC에 붙이고, 관제 화면에서 트랙이 사이트 지도와 맞는지 확인하고, 로봇을 관제에 붙이는 절차다. 설계 근거는 D-257, D-261, D-341(§9 CA 고정, §11 닫힘 코드), D-360, D-361, D-375, D-391(사이트 링크), D-193, D-369, D-364에 있다. 이 문서는 절차만 다룬다.

관제의 경기장 뷰, 차선 겹침, 지도 맞춤은 **표시 전용**이다. 관측 좌표, CameraMap, 주행 목표에는 쓰지 않는다 (D-360, D-375).

## 1. 전체 흐름

```text
Rosy Cam(천장 폰) --mDNS로 사이트 찾기--> 현장 PC (tls_host, 예: site-pc.local)
Rosy Cam --wss(사이트 CA 고정, tls_host 확인)--> 프록시 :8443 --> Vision(프레임 수신·맵 맞춤)
관제 브라우저 --https--> 프록시 --> Fleet(관제 화면·로봇 명단) --> 로봇 CORE
```

- 폰은 **IP를 저장하지 않는다.** 사이트 이름(`tls_host`)과 사이트 CA 지문만 저장한다.
- 연결하거나 다시 연결할 때마다 mDNS(`_rosy-overhead._tcp`)로 주소를 새로 찾는다. 그래서 현장 PC의 IP가 바뀌어도 다시 페어링하지 않는다 (D-391).
- Fleet은 영상을 중계하지 않는다. 브라우저는 Vision에서 짧은 임대(lease)로 최신 프레임만 읽는다.

## 2. 현장 PC 스택

1. 현장 PC를 로봇과 같은 공유기(AP)에 **먼저** 붙인 뒤 Docker를 켠다. Docker가 먼저 떠 있으면 컨테이너가 로봇 LAN에 닿지 못할 수 있다.
2. 사이트 인증서 파일은 **leaf + 사이트 CA를 한 파일로** 둔다. 폰은 CA를 고정하므로, CA가 빠지면 폰이 붙지 않는다.

   ```bash
   cat site.crt site-ca.crt > site-fullchain.crt   # site_cert 시크릿이 이 파일을 가리키게 한다
   ```

   인증서 SAN에는 `tls_host`(예: `site-pc.local`)가 있어야 한다. 폰·브라우저·발견 브리지는 이 이름으로 인증서를 확인하므로 IP SAN은 필요 없다. 수동 IP 링크(3항 2번)를 쓸 때만 그 IP SAN을 더한다.
3. **LAN 공개는 IP가 아니라 인터페이스로 한다** (`deploy/site/README.md` "LAN access"). 사이트 망이 192.168.1.0/24에서 10.16.36.0/24로 바뀐 날(2026-10-01), 옛 IP에 묶인 프록시가 "cannot assign requested address"로 못 떠서 관제·카메라·로봇·발견이 한꺼번에 멈췄다.
   - 사이트 환경 파일(`/etc/rosy/site/site.env`): `ROSY_SITE_BIND_ADDRESS=0.0.0.0`, `ROSY_SITE_LAN_IFACE=<LAN 인터페이스, 예: wlan0>`. LAN IP를 적지 않는다. 이 PC만 쓸 때(SSH 터널)는 기본값 `127.0.0.1` 그대로 둔다.
   - `rosy-site-firewall.service`와 `rosy-site-firewall-check.timer`를 설치하고 켠다(README "LAN access"의 명령). Docker 공개 포트는 ufw를 거치지 않으므로, 이 유닛이 Docker보다 먼저 `mangle PREROUTING`에서 공개 포트를 `lo`와 `ROSY_SITE_LAN_IFACE`로 들어온 연결만 받고, 이 PC로 오는 나머지는 버린다. 인터페이스 이름으로만 거르므로 주소가 바뀌어도 고칠 것이 없다. 브리지된 LAN이면 브리지 이름(`br0`)을 쓴다. 적용이 실패하거나 5분 점검에서 필터가 없으면 프록시를 멈춘다(포트가 닫힌 채로 남는다). 미리 보기: `sudo python3 /opt/rosy/candidate/deploy/site/site-firewall.py apply --dry-run`.
   - 스택 유닛이 기동 전에 점검한다. 이 PC에 없는 IP나 허용하지 않은 리터럴 IP로 묶였거나, LAN 공개인데 인터페이스 필터가 없거나, 사이트 인증서가 `tls_host`에 대한 엄격 검증(README "Site certificate profile")을 통과하지 못하면 이유를 남기고 뜨지 않는다(`journalctl -u rosy-site-stack`). `site.env`는 `KEY=VALUE` 줄만 쓴다(`export` 금지).
   - 발견 브리지(`rosy-mdns-bridge`)는 `/run/rosy-site/site-public.env`(방화벽 유닛이 Compose 설정에서 쓴 `ROSY_SITE_TLS_HOST`·`ROSY_SITE_HTTPS_PORT`)로 이 PC의 루프백(`127.0.0.1`)에 스캔을 보낸다. 옛 `mdns-bridge.env`(`ROSY_SITE_DISCOVERY_URL`)는 지운다. 브리지가 45초 넘게 스캔을 못 보내면 관제 **기기 연결 → 로봇 등록**에 빨간 **검색기 끊김**이 뜨고, 그동안 새 로봇 발견과 **새 주소로 옮기기**가 안 된다.
4. `deploy/site/compose.yaml`는 트랙 파일을 이미지에 넣는다. 다음 옵션으로 지도 맞춤과 차선 겹침을 켠다.
   - Fleet: `--site-lane-graph …/lane_graph.yaml --site-lane-paint …/road_lines.stl`
   - Vision: `--map-paint …/road_lines.stl`

   다른 트랙은 `ROSY_SITE_CONFIG_DIR` 아래에 파일을 두고 경로만 바꾼다.
5. `site-cameras.yaml`의 `corner_world_m`은 실제 경기장 크기(m)로 쓴다. 예: 2.81 × 1.26 m 트랙은 ±1.405, ±0.63.
6. **mDNS 광고:** Ubuntu 현장 PC에서는 `rosy-overhead-advertise.service`(avahi)가 `_rosy-overhead._tcp`를 광고한다. TXT에는 `role=overhead-camera`, `proto=rosy-overhead/1`, `tls=required`, `tls_host`가 들어간다. 광고가 없으면 폰이 사이트를 찾지 못한다. 방화벽은 UDP 5353 수신을 허용한다.
7. 확인: `https://<tls_host>:<포트>/healthz`가 `{"status":"ok"}`를 돌려준다.

## 3. Rosy Cam 설치와 페어링

1. 폰에 Rosy Cam(`io.github.livsbittt.rosy.cam`)을 설치한다.
2. 현장 PC에서 **이름으로, CA 고정** 페어링 링크를 만든다. 토큰은 셸 기록에 남기지 않는다.

   ```bash
   ROSY_OVERHEAD_TOKEN="$(cat <secrets>/phone_ingress_token)" \
     rosy-vision pair-link --host <tls_host, 예: site-pc.local> --port <포트> --source <카메라 이름> \
     --pin-ca <secrets>/site-ca.crt --pin-cert <secrets>/site-fullchain.crt
   ```

   - leaf만 고정하는 링크는 만들지 않는다 (D-341 §9). 도구도 거절한다.
   - `--host`에 IP를 주면 그 IP는 "수동 주소"가 된다. 수동 주소는 mDNS가 사이트를 못 찾을 때만 쓰는 예비이고, IP SAN이 필요하다. **이름을 쓰는 것이 기본이다.**
3. 폰에서 QR을 찍거나 링크를 연다. 확인 창에 나오는 `사이트 인증서 지문 sha256/…`이 도구가 출력한 `pin:` 앞부분과 같은지 보고 **저장**한다.
4. **카메라 켜기**를 누른다. 처음에는 카메라와 알림 권한을 허용한다. 정상이면 다음이 보인다.
   - "송출 중 · 3.0 fps · 건너뜀 0"에 가까운 수치
   - `주소: … (자동 찾기로 찾음)`

## 4. 카메라 위치

관제의 **맵 자동 맞춤**이 보여 주는 "지도 n% 보임"과 "…쪽 끝이 화면 밖입니다" 안내를 보면서 맞춘다.

- **목표:** 트랙 전체(차선 페인트 100%)가 화면 안에 들어오고, 긴 변이 화면의 긴 변을 따라 놓인다.
- **높이와 각도:** 기본 렌즈(1×)로 트랙을 곧게 내려다보려면 트랙 긴 변 × 약 0.85 이상의 높이가 필요하다. 2.81 m 트랙이면 약 2.4–2.5 m다.
  - 2.0 m라면 트랙 중심 쪽을 향해 15–25° 기울여도 된다. 기울기가 클수록 먼 끝의 해상도가 떨어진다. 실측으로 30°에서 양 끝 크기 차이가 1.7배였다.
- **넓게(0.5×) 렌즈:** 곧게 내려다볼 때만 쓴다. 같은 자리에서는 트랙 해상도가 약 절반이 되고 옆 트랙이 화면을 채운다. 기본값은 1×다.
- **각도:** 트랙이 화면에서 180° 돌아가 있거나 몇 도 기울어진 것은 문제가 아니다. 맞춤이 보정한다.
- 폰은 조명·햇빛 열을 피해 통풍되게 단다. 앱이 온도 경고를 띄운다.

## 5. 관제에서 트랙과 지도가 맞는지 확인

관제 `/console`에 운영자 이름으로 접속한 뒤 **관제 카메라** 패널에서 다음 순서로 한다.

1. **맵 자동 맞춤**을 누른다. 한 번 계산에 1–3초(부하가 크면 더 길게) 걸린다. 그동안 "맞추는 중…"이 뜨고 알아서 다시 묻는다.
2. **맞춤이 받아들여지면:**
   - 카메라 영상 위에 지도 차선 페인트(채움)와 중심선(점선)이 그려진다. 페인트가 실제 흰 차선 위에 겹쳐야 한다.
   - 아래에는 지도 좌표(m)로 편 영상이 나온다.
   - 상태 줄에 일치·정밀·"지도 n% 보임"이 나온다.
   - "이전 결과 · N s 전"으로 나오면 이전 계산 결과다. 수락할 수 없으니 새 결과가 올 때까지 기다린다.
3. **맞춤 수락**을 누르면 이 브라우저에만 표시 초안으로 저장된다. **경기장 자동 찾기**가 "field runs past the frame"으로 실패해도, 수락한 맞춤이 있으면 경기장 뷰가 나온다. 모서리가 화면 밖이어도 된다.
4. **맞춤이 거부되면:** 이유와 옮길 방향만 보여 주고 수락 버튼은 없다. 카메라를 안내대로 옮기고 다시 누른다.
5. **제안 버리기**는 지금 보는 제안을 버린다. **저장한 맞춤 지우기**는 초안을 지운다. 카메라 해상도나 사이트 지도가 바뀌면 저장한 맞춤을 쓰지 않는다고 알려 준다.
6. 레이어 켜기·끄기: **경기장 크기·레이어**에서 "카메라 위 차선"과 "지도 맞춤 평면"을 켜고 끈다.

실측 참고(2.81 × 1.26 m 트랙):
- 맞게 단 카메라에서 페인트 일치 0.83–0.96, 정밀 0.93–0.98.
- 지도 대비 오차는 전체 화면에서 수 cm, 부분만 보이면 최대 약 5 cm.
- 실제 테이프가 CAD와 몇 cm 다른 곳(횡단보도, 바깥 곡선)은 조금 어긋나 보인다.

## 6. 로봇을 관제에 붙이기

1. 로봇 코드 받기 (D-193):
   - **LCD:** `CORE_READY` 뒤 `Login ABCD-EFGH operator`가 표시된다 (카드 `login.boot_code`가 `off`가 아닐 때).
   - **LCD가 없거나 꺼져 있을 때:** 로봇에서 `sudo rosy-login-code --role operator --minutes 15`.
   - **관리자:** 로봇 대시보드에서 등록 코드를 발급한다 (5분).
   - 코드는 한 번만 쓰이고 제한 시간 안에만 쓸 수 있다. 다섯 번 틀리면 버려진다.
2. 관제 **기기 연결 → 로봇 등록**: 발견된 행의 **등록**을 누르거나, **주소로 추가**에 `IPv4:8080`을 넣고 코드를 입력한다 (D-361).
3. 로봇 카드의 상태 줄로 운전 모드를 확인한다.

| 모드 | 할 수 있는 것 | 못 하는 것 |
|---|---|---|
| CORE 전용 (core) | 상태 확인 | 모터 |
| 모터 벤치 (motor) | 저속 직접 제어, 정지 | LiDAR, 자율주행(Nav2), 목표·교통정리·대형 |
| 하드웨어 (hardware) | 전부 | — |

4. hardware로 올리는 것은 사람이 입회한 시험을 통과해야 한다.
   - **G4:** 바퀴를 띄운 모터·데드맨 시험.
   - **G5:** 제어된 매핑·주행 시험. 여기서 트랙 지도가 승인된다.
   - `/etc/rosy/approvals/*.approved`는 `mapping_approval.py approve`만 만든다. 손으로 만들지 않는다.
   - 절차는 [`pinky-pro-first-device-runbook.md`](pinky-pro-first-device-runbook.md)의 G4, G5 절을 따른다.
5. 로봇을 여러 사람(세션)이 함께 쓸 때는 움직이기 전에 누가 지금 명령을 보내고 있는지 확인한다.

## 7. 규칙 점검표 (관제에서)

한 사람이 트랙 옆에서 즉시 들어 올리거나 멈출 수 있을 때만 한다. 처음에는 저속으로 한다.

| 규칙 | 모드 | 하는 일 | 통과 기준 |
|---|---|---|---|
| 정지·제어 권한 (D-369) | motor 이상 | 관제 **전체 정지** → 해제 | 모든 로봇이 EMERGENCY로 멈추고, 해제 전까지 명령을 받지 않는다. 한 대가 응답하지 않으면 본문에 그 로봇이 나온다. |
| 모드가 막는 명령 | motor | 목표·대형·차선 자동을 보낸다 | 로봇이 거절하고, 관제가 이유(모터 벤치 모드)를 보여 준다. |
| 차선 지키기 (D-364) | hardware | 로봇 카드의 차선 모드를 켠다 | 차로 안을 지킨다. 원형 교차로는 반시계 일방통행이다. |
| 목표·교통정리·양보 | hardware | 두 로봇에 서로 엇갈리는 목표를 준다 | 늦게 온 쪽이 기다리거나 비켜선 뒤 둘 다 도착한다. |
| 대형 | hardware | 리더와 모양을 정해 시작하고, 리더에만 목표를 준다 | 따라가는 로봇이 슬롯을 지킨다. 리더가 실패하면 HOLD가 된다. |

## 8. 문제 해결

폰의 빨간 안내 문구 기준이다. 폰은 사람이 할 일이 없는 문제(수신기 바쁨, 사이트 확인 중)는 알아서 다시 연결하고, 사람이 고쳐야 하는 문제만 멈춘다.

| 폰 안내 | 원인 | 조치 |
|---|---|---|
| "사이트가 이 Wi-Fi에서 보이지 않습니다 — 같은 이름의 다른 Wi-Fi일 수 있습니다" + "지금 Wi-Fi는 …인데 페어링 때는 …였습니다" | 폰이 이름만 같은 다른 공유기나 핫스팟에 붙었다 | 현장 PC와 같은 공유기에 붙인다. 같은 이름을 쓰는 핫스팟이 있으면 이름을 바꾸거나 끈다 |
| "사이트가 자동 찾기(mDNS)에 보이지 않습니다" + "주소 범위가 페어링 때와 같습니다" | 현장 PC가 mDNS 광고를 하지 않는다 (광고 서비스 꺼짐, UDP 5353 차단) | 현장 PC의 광고 서비스와 방화벽을 확인한다 (2항 6번) |
| "Wi-Fi에 연결되어 있지 않습니다" | 폰의 Wi-Fi가 실제로 끊겼다 (아이콘만 켜져 있을 수 있음) | Wi-Fi를 다시 붙인다 |
| "주소: 수동 주소 … (자동 찾기로 못 찾음)"에서 계속 실패 | mDNS가 못 찾아 예비 IP로 붙는 중인데 그 IP도 틀렸다 | 이름 링크로 다시 페어링한다 (수동 주소가 지워진다) |
| 보안 연결(TLS) 실패 / 인증서 지문 불일치 | 프록시가 CA를 함께 주지 않거나, 사이트 CA가 바뀌었거나, 다른 PC다 | fullchain 파일을 쓰고, 새 CA면 새 링크로 다시 페어링한다 |
| "사이트 확인 중 — 자동 재시도" / "수신기가 바빠서…" | Fleet이나 Vision이 잠시 응답하지 못한다 (4503, 1013) | 기다린다. 오래 가면 현장 PC 스택을 확인한다 |
