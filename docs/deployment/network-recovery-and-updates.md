# 장치 Wi-Fi 복구와 업데이트

정상 CORE 화면에서는 관리자 계정으로 Wi-Fi 이름과 암호를 입력하고 변경을 확인한다.
준비됨은 접수 상태다. 실제 SSID·IPv4 관측이 committed가 되어야 완료이며, 접속이 끊기면
같은 작업 ID로 결과를 다시 조회한다. rolled_back은 이전 연결 복구, held는 수동 확인이
필요한 상태다. 운용 중이거나 정지 증거가 부족하면 변경을 거절한다.

첫 부팅 실패로 CORE가 열리지 않으면 로봇이 표시하는 복구 AP에 접속한다. LCD 또는
로컬 콘솔의 HTTPS 주소와 인증서 SHA-256 전체 지문을 확인한다. 인증서를 로컬 장치에
등록하고 지문 일치를 확인한 뒤 8문자 복구 코드를 입력한다. 인증서 경고를 무시하거나
HTTP로 접속하지 않는다. 코드는 해당 부팅/AP에 결속되며 10분, 최대 5회 시도다.
서비스 재시작은 시도 횟수나 만료를 초기화하지 않는다. 신원이나 인증서가 달라지면
현장에서 원인을 확인한다. 재발급은 로컬 root의 `rosy-network-recovery.py issue --renew`
로 명시적으로 수행하며 네트워크의 일반 사용자에게 이 권한을 주지 않는다.

복구 화면은 새 SSID 연결만 제공한다. 다른 보드에 옮긴 카드의 SETUP 승인, 모터 활성화,
재부팅이나 일반 관리자 권한을 제공하지 않는다. handoff 미지원 이미지는 진단만 가능하고
image_required를 표시한다. 지원 이미지에서는 실제 연결을 확인한 복구 결과만 첫 부팅에
인계하므로 원래 카드 번들의 오래된 Wi-Fi 설정으로 되돌아가지 않는다.

자동 업데이트는 기존 10분 timer와 서명·canary/wave·idle·배터리·claim·health 검증을 사용한다.
코드 수정 자체는 배포가 아니다. 서명된 ARM64 산출물을 만들고 canary를 수용한 릴리스만
전달한다. 기존 이미지의 장치 설정, 신원, 지도, 보정 자료는 덮어쓰지 않는다.

기존 장치에는 먼저 `ROSY_BOOT_SUPPORT=bridge`로 만든 준비 payload를 `payload-<id>`로
전달한다. 준비된 업데이터를 확인한 뒤 signed boot catalog를 포함한 기능 payload를
`payload-v2-<id>`로 전달한다. 구형 discovery는 최신 20개만 읽으므로 bridge를 그 범위에
유지하거나 새 bridge 릴리스를 발행해야 오래 오프라인이던 구형 장치도 돌아올 수 있다.
이를 보장하지 못하는 장치는 로컬 복구가 필요하다. 두 세대에 같은 release ID를 쓰지 않는다.

롤백은 새 조정자가 서명된 이전 릴리스와 inverse를 먼저 검증하고, native 전환 후 구형
sync 실행 전에 boot inverse를 완료한다. 정전·파일 변경·inverse 실패는 보류하며 성공으로
기록하지 않는다. OS·커널·파티션·Python runtime처럼 지원 migration이 없는 변경은
image_required이며 카드 재작성이 필요하다. 장치가 SD 전체를 자동 파괴적으로 다시 쓰지 않는다.

실물 수용은 별도다: 실패 부팅 → AP/TLS 지문 등록 → SSID 변경 → 재부팅 후 설정 유지,
구형 이미지 → bridge → 기능 OTA, 중단·롤백 후 기존 설정 보존을 실제 Pinky에서 확인한다.
호스트 회귀 통과는 이 수용을 대신하지 않는다.
