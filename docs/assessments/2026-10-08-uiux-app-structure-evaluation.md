# ROSY 앱별 UI/UX 구조 평가와 개선 순서

- 날짜: 2026-10-08 (Asia/Seoul)
- 기준 소스: 로컬 `main` `64d7a68a8`에서 분기한 문서 검토. 새 화면 실행·캡처·사용자 시험은 하지 않았다.
- 판정: **개선 방향 기록, 제품 전체 UI/UX HOLD**. 이 문서는 D-153의 G1/G2/G3 회차나 실물 수용을 대체하지 않는다.
- 범위: 사람이 사용하는 활성 앱·표면. 역할·조작 소유·최종 writer는 [표면 등록부](../../shared/web/surfaces.yaml), [앱·웹 역할 검토](2026-10-05-app-web-role-review.md), D-425를 따른다. 새 앱·API·권한을 제안하지 않는다.

## 평가 결론

화면을 하나씩 다듬은 기록은 많지만, **앱 안의 작업 시작점 → 판단 → 조작 → 결과 확인 → 실패 복구**를 같은 단위로 닫는 기준이 약하다. 특히 여러 화면을 거치는 설치·운용에서는 “같은 제품”을 같은 색으로 만드는 것보다 **각 화면의 책임과 다음 이동을 이해시키는 것**이 먼저다. D-280의 차분한 성격과 D-153의 정직한 증거·표면 질문을 그대로 적용한다.

개선 완료의 단위는 버튼이나 캡처 한 장이 아니라 **한 역할이 선언 상태와 화면 폭에서 실제 과업을 마치는 경로**다. 화면마다 아래 순서를 검토한다.

1. **진입:** 앱 이름, 대상 로봇/사이트, 현재 역할과 연결 상태를 알아볼 수 있는가.
2. **판단:** 현재 상태·근거의 출처/시각·영향을 먼저 읽고, 모르는 값은 모른다고 표시하는가.
3. **행동:** 이 화면이 소유한 주 동작이 한눈에 보이며, 권한·안전 차단 이유를 이해할 수 있는가.
4. **결과:** 요청, 접수, 실제 상태 readback을 구분하고 완료 또는 불확실성을 표시하는가.
5. **복구·이동:** 실패 뒤 재시도/확인/다른 앱으로 이동하는 경로가 보이고 입력·초점이 보존되는가.
6. **매체:** 전화·태블릿·PC·LCD 각각의 거리, 방향, 입력 방식에서 위 순서가 유지되는가.

## 공통 구조 결정

- **앱 간 연결은 과업 이름으로 설명한다.** Robot은 한 대의 상세·정비, Console은 사이트·Mission, Pilot은 직접 운전, Cam은 카메라 설치다. 다른 앱으로 보내는 버튼은 대상과 이유를 적고, 그 앱의 권한을 대신 행사하지 않는다.
- **공유할 것은 표현 규칙과 기초 부품이다.** 토큰, 상태 신선도, 입력/오류/확인 문법을 `shared/web`에서 사용한다. 로스터, 운전석, 페어링, 경기 필드를 억지로 같은 카드 레이아웃으로 만들지 않는다(D-425, D-280).
- **각 화면의 기본 정보 구조를 고정한다.** 상단: 대상·연결·안전. 본문 첫 부분: 현재 판단과 근거. 다음: 해당 역할의 주 작업. 상세 진단과 기록은 필요할 때 연다. 예외 표면인 Fleet과 영상 중심 Pilot/게임은 등록된 문법을 유지한다.
- **상태와 조작의 시간축을 함께 보여준다.** `fresh`/`delayed`/`disconnected`/`unavailable`, 요청/접수/실제 결과, 로컬 후보/설치본을 혼동하지 않는다. 임의의 성공 문구나 0값으로 빈 근거를 덮지 않는다.

## 실행 순서와 판정

1. **과업 지도 작성:** 각 행의 사용자 역할·진입 경로·주 동작·결과 정본·되돌아갈 곳을 현재 코드/화면과 맞춘다. 소유 중복 또는 빈 경로가 발견되면 해당 앱의 작업으로 기록한다. 기존 D-425와 `surfaces.yaml`이 기준이다.
2. **P0 여정부터 실제 화면 수정:** Robot 운용/절차, Console 관제, Pilot 연결·운전. 한 번에 전역 CSS를 바꾸지 말고 한 여정의 데스크톱/모바일, 정상/차단/복구를 닫는다. P1은 같은 방법으로 진행한다. 화면 변경 회차에는 코드·관련 브라우저/네이티브 시험·G2 캡처를 함께 남긴다.
3. **현행 후보 검증:** 후보 SHA를 고정하고 D-153 G1, 표면별 선언 상태×폭 G2, 사용자 역할별 G3 8항을 수행한다. 캡처 원본·실행 로그·SHA-256과 실패 셀을 `docs/validation/uiux-surfaces-<date>/`의 카드에서 연결한다. 적용되는 앱은 설치 이미지/APK·실물 장치 readback과 실제 작업 결과를 추가한다.
4. **완료 판정:** 한 표면의 모든 선언 셀이 있고 G1 통과·G3 위반 0이면 D-153의 표면별 GO를 검토한다. 그 앱의 현장 사용성을 말하려면 동일 후보의 설치본과 실물 결과도 필요하다. 하나라도 빠지면 셀과 이유를 적어 HOLD로 둔다. 전체 활성 표면이 닫히기 전에는 제품 전체 GO를 쓰지 않는다.
