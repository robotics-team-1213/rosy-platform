## 평가 결론

화면을 하나씩 다듬은 기록은 많지만, **앱 안의 작업 시작점 → 판단 → 조작 → 결과 확인 → 실패 복구**를 같은 단위로 닫는 기준이 약하다. 특히 여러 화면을 거치는 설치·운용에서는 “같은 제품”을 같은 색으로 만드는 것보다 **각 화면의 책임과 다음 이동을 이해시키는 것**이 먼저다. D-280의 차분한 성격과 D-153의 정직한 증거·표면 질문을 그대로 적용한다.

개선 완료의 단위는 버튼이나 캡처 한 장이 아니라 **한 역할이 선언 상태와 화면 폭에서 실제 과업을 마치는 경로**다. 화면마다 아래 순서를 검토한다.

1. **진입:** 앱 이름, 대상 로봇/사이트, 현재 역할과 연결 상태를 알아볼 수 있는가.
2. **판단:** 현재 상태·근거의 출처/시각·영향을 먼저 읽고, 모르는 값은 모른다고 표시하는가.
3. **행동:** 이 화면이 소유한 주 동작이 한눈에 보이며, 권한·안전 차단 이유를 이해할 수 있는가.
4. **결과:** 요청, 접수, 실제 상태 readback을 구분하고 완료 또는 불확실성을 표시하는가.
5. **복구·이동:** 실패 뒤 재시도/확인/다른 앱으로 이동하는 경로가 보이고 입력·초점이 보존되는가.
6. **매체:** 전화·태블릿·PC·LCD 각각의 거리, 방향, 입력 방식에서 위 순서가 유지되는가.

**유지할 점:** Robot·Pilot·Console의 정지가 첫 화면에서 살아 있고, Games의 [390px 지연 화면](../validation/uiux-surfaces-2026-10-06/captures/games-delayed-390x800.png)은 마지막 수신 위치를 현재 위치와 구분하면서 필드와 정지를 유지한다. Console의 3:2 지도/개입 열은 D-493의 의도된 비율이다. 단순히 모든 카드 폭을 같게 만들거나 게임·운전석을 일반 폼으로 바꾸지 않는다.

`impeccable detect --json`을 Robot·Console·Pilot HTML에 실행했다. Console의 `img` 두 개는 JS가 `src`를 채우기 전 `hidden`인 동적 영상 자리라 `broken-image` 경고를 곧바로 결함으로 보지 않는다. 소스 파일 단독 검사에서는 `/common/...` CSS가 정적 경로로 해석되지 않아 `flat-type-hierarchy` 등 색·타이포 결과가 불완전하다. 이 결과를 현재 렌더의 접근성 통과/실패 점수로 사용하지 않는다. 실제 브라우저와 네이티브 화면에서 글자 확대, 키보드/터치, 명암, 헤더·주 동작 위치를 확인해야 한다.

### 현행 Console 재촬영

현행 브랜치의 `operations/fleet/test/test_traffic_view_browser.py::test_console_traffic_layer_card_line_and_queue_row`를 `ROSY_RUN_BROWSER_TESTS=1`로 실행해 **1 passed**를 얻었다. 실제 Fleet 앱을 Chromium에서 열되 API는 합성 로봇·교통 응답이다. 1920×1080과 390×844 원본은 `X:/DevTemp/projects/rosy-platform/2026-10-08--150144--app-ux-layout-audit--191323/evidence/console-traffic-{1920x1080,390x844}.png`에 있다(SHA-256 순서대로 `058216736fb1e5d7e14731f46f267f5078dcc84ac0af371e53a86b2184636bc3`, `13b8f8cd26f806c922d50886542a23010d048e71245cca233a6724bed56ebf73`). 1920px에서는 지도와 개입 영역이 첫 화면 안에 들어오고 390px에서는 정지·주의·로봇 카드가 지도보다 먼저 보인다. **이 순서 자체는 맞다.** 단, 전화 첫 화면의 `관제 경로` 세 줄과 로봇 카드 상세가 지도 진입을 늦추므로 예외 상황에서 어느 정보가 기본 노출되어야 하는지 G3로 확인해야 한다.

이 픽스처는 `state.mode=LINE_FOLLOW`를 넣지만 CORE `RobotMode`에는 그 값이 없다. 화면의 `LINE_FOLLOW` 태그는 공유 `enumLabel`이 알 수 없는 값을 숨기지 않고 원문 표시한 결과다. 이를 현재 실제 CORE의 운용자 어휘 결함으로 계산하지 않는다. 픽스처를 유효한 모드·별도 차선 상태로 맞춘 뒤 같은 장면을 다시 평가해야 한다. `Vision 응답 404`도 이 합성 API의 응답이며 현장 Vision 진단이 아니다.

공유 `main`에서 Pilot 브라우저 회귀 `test_pilot_browser.py -k 'camera_keeps_aspect_and_controls_never_cover_it or lobby_empty_and_failure_fit_declared_widths'`를 실행했다. 실행 시작 때 관측한 HEAD는 `2fa5d896f0f6abc7645eac9394171ee91bb18c7b`이고, 결과는 **9 passed, 116 deselected**다. 원본 캡처와 실행 로그는 `X:/DevTemp/projects/rosy-platform/2026-10-08--155028--pilot-ui-review--cf4223/`에 있다. 2000×1200·1333×760·1200×2000·390×844·320×568 운전 화면과 로비 빈 목록/연결 실패 화면을 촬영했다.

390px 운전 화면과 2000px 운전 화면, 390px 로비의 빈 목록·실패 화면을 원본 크기로 확인했다. 영상과 조작 영역은 분리되어 있고 비상 정지는 첫 화면에 있다. 로비는 빈 목록과 실패를 구별한다. 390px 회전 조작은 조작 영역의 스크롤 뒤에 있으며 힌트가 보인다. 이번 화면 검토만으로 이를 결함으로 확정하거나 화면을 재배치하지 않는다. 실제 운전자가 첫 시도에 회전을 찾는지, 태블릿 설치 APK가 같은 화면인지, 연결·정지의 장치 readback은 여전히 G3/DEVICE/HOLD다. 공유 `main` 체크아웃은 다른 세션과 함께 쓰므로 실행 시작 SHA와 종료 SHA의 동일성은 별도 고정하지 않았다.

## 공통 구조 결정

- **앱 간 연결은 과업 이름으로 설명한다.** Robot은 한 대의 상세·정비, Console은 사이트·Mission, Pilot은 직접 운전, Cam은 카메라 설치다. 다른 앱으로 보내는 버튼은 대상과 이유를 적고, 그 앱의 권한을 대신 행사하지 않는다.
- **공유할 것은 표현 규칙과 기초 부품이다.** 토큰, 상태 신선도, 입력/오류/확인 문법을 `shared/web`에서 사용한다. 로스터, 운전석, 페어링, 경기 필드를 억지로 같은 카드 레이아웃으로 만들지 않는다(D-425, D-280).
- **각 화면의 기본 정보 구조를 고정한다.** 상단: 대상·연결·안전. 본문 첫 부분: 현재 판단과 근거. 다음: 해당 역할의 주 작업. 상세 진단과 기록은 필요할 때 연다. 예외 표면인 Fleet과 영상 중심 Pilot/게임은 등록된 문법을 유지한다.
- **상태와 조작의 시간축을 함께 보여준다.** `fresh`/`delayed`/`disconnected`/`unavailable`, 요청/접수/실제 결과, 로컬 후보/설치본을 혼동하지 않는다. 임의의 성공 문구나 0값으로 빈 근거를 덮지 않는다.

## 실행 순서와 판정

1. **과업 지도 작성:** 각 행의 사용자 역할·진입 경로·주 동작·결과 정본·되돌아갈 곳을 현재 코드/화면과 맞춘다. 소유 중복 또는 빈 경로가 발견되면 해당 앱의 작업으로 기록한다. 기존 D-425와 `surfaces.yaml`이 기준이다.
2. **P0 여정부터 실제 화면 수정:** Robot 운용/절차, Console 관제, Pilot 연결·운전. 한 번에 전역 CSS를 바꾸지 말고 한 여정의 데스크톱/모바일, 정상/차단/복구를 닫는다. P1은 같은 방법으로 진행한다. 화면 변경 회차에는 코드·관련 브라우저/네이티브 시험·G2 캡처를 함께 남긴다.
3. **현행 후보 검증:** 후보 SHA를 고정하고 D-153 G1, 표면별 선언 상태×폭 G2, 사용자 역할별 G3 8항을 수행한다. 캡처 원본·실행 로그·SHA-256과 실패 셀을 `docs/validation/uiux-surfaces-<date>/`의 카드에서 연결한다. 적용되는 앱은 설치 이미지/APK·실물 장치 readback과 실제 작업 결과를 추가한다.
4. **완료 판정:** 한 표면의 모든 선언 셀이 있고 G1 통과·G3 위반 0이면 D-153의 표면별 GO를 검토한다. 그 앱의 현장 사용성을 말하려면 동일 후보의 설치본과 실물 결과도 필요하다. 하나라도 빠지면 셀과 이유를 적어 HOLD로 둔다. 전체 활성 표면이 닫히기 전에는 제품 전체 GO를 쓰지 않는다.
