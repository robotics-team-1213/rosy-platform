# OMX 제한 작업대 물체·문맥 설계

상태: 제안. [실험 기록](../validation/omx-object-context-2026-10-15/result.md)의 실패에서 도출했다.
새 API·공유 스키마·모듈·권한을 승인하지 않는다. [통합 설계](2026-10-15-omx-learning-operations-design.md)의
첫 과제를 **흰 원형 용기의 딸기 꺼내기→임시 놓기→원래 용기로 복귀**로 구체화한다.

## 문맥을 네 가지 근거로 분리한다

| 구분 | 이번 값 | 갱신·사용 규칙 |
|---|---|---|
| 사용자 목표·역할 | 딸기 왕복, 흰 원형 물체=용기 | 사용자 출처·확인시각·revision 기록. 현재 장면 상태로 승격하지 않음 |
| 검증된 작업셀 설정 | 캡처 해상도·view 이름 | rig/camera/profile/calibration revision과 scope. 바뀌면 재확인 |
| 프레임 관측 | 외형 box·가림·관측시각·image hash | 장면 상태는 새 프레임에 종속. host receipt와 exposure 시각 구분 |
| 미확인 | 임시 구역·내용물·현재 단계·깊이·실물/모형 | null/unknown. 추정으로 필수값을 채우지 않음 |

일회 확인된 역할도 물체 이동·rig 교체 후 무조건 재사용하지 않는다. 프레임·view·영역과
의미를 연결하고 범위/유효기간/충돌 시 재확인 규칙을 정한다. TTL 실측값은 아직 미정이다.
불일치는 원인과 출처를 함께 표시하고 기존 근거를 덮어쓰지 않는다.
주입된 문맥은 명령이 아닌 데이터로 처리한다. 예상 물체 목록은 실제 검출을 강제하지 않는다.
미등록 물체·사람·장비 침범도 유지하며, 선택적 crop을 쓸 때 원본 변환과 전체 장면 확인을 남긴다.

## 작은 관측 루프

1. 신선도·해상도·노출/가림을 먼저 검사한다. 현재 top은 딸기가 경계에 걸리고 front는 전체 작업 관찰에 부족하다.
   우선 프레이밍을 바꾸거나 역할을 top=전체 작업, front=검증된 근접 관찰로 명시한다. 카메라 재배치 후 보정은 무효화한다.
2. 고정 제공자 좌표 규약과 JSON schema를 사용하고 별도 bounds/order/unique-id 검사를 한다.
   normalized_1000→실제 pixel→검증된 camera/workcell/robot frame 변환을 구분한다.
   기존 `ImageTransform`의 model image 크기를 가짜 1000×1000으로 설정하지 않는다.
3. VLM 외형·사용자 역할·색/윤곽/geometry 제안을 대조한다. 색만으로 딸기라고 하지 않는다.
   경계 접촉은 결정적으로 경고할 수 있지만 진짜 가림 정도는 독립 표식과 검수한다. 원래 모델 출력은 보존한다.
4. 새 프레임에서 target identity를 잇는다. 가림/화면 밖 이동 뒤 유사한 빨간 부품으로 재연결하지 않는다.
   양 시점 동기화·cross-view association이 검증되기 전 별도 증거로 유지한다.
5. 동일 이미지·문맥 revision을 묶어 제한된 1회 상대 검토를 하고 끝낸다. timeout·총 호출/토큰 예산을 정한다.
   모델 PC는 오프라인 평가, AI PC는 승인 버전 관측 후보를 담당한다. 상시 모델 PC 대화 서비스를 열지 않는다.
   같은 모델 동의는 통과 조건이 아니다. 실패시 unknown/재촬영/사람 검수로 돌아간다.

## 왕복 과제의 독립 판정

관측 이력은 `용기 안 확인→꺼냄 확인→임시 구역에 놓음 확인→원래 용기 안 복귀 확인`으로 평가한다.
이는 제안한 과제 검수 순서이며 새 운영 protocol enum이 아니다. 현재 단계는 미확인이다.
2D box 중첩만으로 inside를 확인하지 않는다. 용기의 벽/깊이·다른 시점·필요 센서나 독립 사람 확인을 정한다.
action terminal/그리퍼 닫힘은 물체 성공이 아니며 마지막 용기 안 존재만으로 꺼냄 이력을 만들지 않는다.
낙하·작업면 이탈·가림·다른 물체 파지·목표 소실·센서 stale은 각각 실패/미판정을 기록한다.
실물 사전 조건이 충족되기 전 이 관측 루프는 어떤 motion/action도 만들지 않는다.

## UI·학습 반영

기존 Fleet Cell에는 용기/임시 구역·근거 출처·현재 관측·미확인·단계별 증거를 보여 준다.
카메라별 frame age/가림/보정 상태를 구분하고 pixel overlay 옆에 metric 유효 여부를 둔다.
context 수정은 새 revision과 적용 범위를 검토하게 하고 완료 표시는 독립 task outcome에만 따른다.
Pilot 제어권·정지와 관측 검수는 구분하고 기존 episode review에 원본·모델 후보·사람 수정 이력을 둔다.
모든 표면 구현은 등록된 UI 목록을 먼저 대조한다. 새 별도 대시보드를 만들지 않는다.

IL에는 parent cycle id와 꺼냄/놓기/복귀 하위 outcome을 기록한다. 동일 cycle/연속 프레임의 split 누수를 막고
현재 장면·조명·배치만 외우지 않게 독립 held-out 조건을 정한다. 실패/개입/미판정 시연도 보존한다.
RL은 먼저 SIM에서 동일 과제와 독립 evaluator를 사용한다. 반복 집기·놓기로 보상만 얻기,
마지막 상태만 성공 처리하기를 검사하고 timeout truncated와 실제 종료 terminated를 구분한다.
VLM 대화/consensus를 reward 정답이나 실물 탐험 허가로 쓰지 않는다. D-427/L0–L3와 로컬 owner 경계는 유지한다.

반응형 IL/RL은 기존 계약의 작업셀 로컬 host, 모델 PC는 학습·평가, AI PC는 사실/Task 후보,
Fleet은 admission·원장, OMX local owner는 팔 실행을 소유한다. CORE의 최종 base `/cmd_vel` 권한도 유지한다.
새 runtime holder/schema/API가 필요하면 기존 ADR·SRS/API reference와 생산자/소비자를 같은 변경으로 확정한다.
