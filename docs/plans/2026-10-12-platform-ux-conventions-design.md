# ROSY Platform 사용 규칙 재정리: 계정·연결·탐색·작업

작성: 2026-10-12. 상태: **Fleet 계정 진입 D-683 · 첫 변경 D-686 · 기본 내 계정 D-689 채택/소스 구현 · 설치/실물 수용 별도**.

사용자 요구: 일반 서비스처럼 우상단에서 로그인과 계정을 찾을 수 있고, 모든 화면에서 정보와 행동의 위치를 예측할 수 있게 한다. 현장 운용·오류 복구 우선이라는 기존 목표를 유지한다. 이 문서는 기존 [운용 브리프](2026-10-12-field-ui-recovery-brief.md)를 보완한다. 기존 ADR을 자동으로 대체하지 않는다.

## 1. 진단: 규칙이 없는 것이 아니라 사용자가 기대하는 규칙과 충돌한다

검토 기준 소스: 작업 브랜치 `uiux/header-all-surfaces`, `addd5a982`. 소스 점검과 공식 문서 조사이며 이번 회차의 설치 화면/사용자 테스트는 아니다.

| 발견 | 직접 근거 | 사용자에게 생기는 문제 |
|---|---|---|
| 사람 로그인·토큰·화면 테마가 같은 펼침 안에 있다 | `operations/ui/console/index.html`의 `topbar-extra`, `password-login`, `token-access`, `theme-choice` | 계정 진입점이 일반 설정처럼 보인다. 로그인과 화면 표시의 목적이 섞인다 |
| 로그인한 이름·로그아웃이 접힌 상세에 들어간다 | `shared/password-login.js`가 `who`를 `topbar-extra`에 prepend; D-658 §7 | 누가 로그인했는지와 로그아웃 경로를 헤더에서 찾기 어렵다 |
| 연결과 권한을 한 상태 그룹에서 보여 준다 | `online-pill`, `user-role`, D-658 | 통신 장애·미인증·권한 부족은 다른 복구가 필요한데 ‘접속’으로 뭉치기 쉽다 |
| 표면별 접속 모델이 다르다 | Fleet D-519 쿠키 세션, Robot D-193 기기 인증, Pilot 접속 게이트 | 제품 이름이 같아도 인증 범위가 다르다. 같은 계정으로 모든 로봇에 들어갈 수 있다고 오해하기 쉽다 |
| 색·크기·헤더 계약은 있지만 계정/설정의 사용자 관례가 약하다 | `DESIGN.md`, D-641, D-658 | 기계 회귀가 통과해도 첫 사용자가 조작을 찾는지는 보장하지 않는다 |

판단: 앞선 개선은 오류 복구와 배치 안정성을 다뤘지만 **계정 발견성**을 충분히 다루지 않았다. 문서·시험의 존재를 사용자에게 익숙한 제품 경험의 증거로 쓰면 안 된다. 계약이 나뉘며 이런 결과가 생겼다는 것은 소스에 근거한 해석이며 개발 경위 전체를 확인한 사실은 아니다.

**우상단 계정은 ROSY가 채택할 관례**다. WCAG가 ‘로그인 버튼은 우상단이어야 한다’고 요구하는 것은 아니다. 장치 안전은 일반 사이트 예시보다 ROSY의 CORE·정지 계약이 우선한다.

사용한 스킬: `brainstorming`으로 문제·대안·범위를 정리하고, `impeccable`의 Operate 원칙으로 익숙한 조작·일관성·작업 발견성을 평가했다. 스킬은 평가 방법이며 API·권한 계약의 근거가 아니다. 이전 context 결과를 재사용했고 이번 문서 작업에서 디자인 detector나 공식 critique 실행을 새로 수행했다고 주장하지 않는다.

## 3. 권장 방향과 대안

**권장: 현재 인증 백엔드를 유지하고 사람 계정의 진입/복귀 흐름을 공통화한다.** Fleet은 우상단 계정 진입점에서 전용 로그인 화면으로 이동한다. 로그인 뒤 같은 자리는 계정 메뉴가 된다. Robot/Pilot은 같은 위치·어휘 원칙을 쓰되 실제 기기 연결/페어링 모델을 설명한다.

대안 A: 현재 펼침을 유지하고 이름만 바꾼다. 변경량은 작지만 사람 로그인과 작업 공간의 분리, 복귀 흐름을 해결하지 못한다.

대안 B: 플랫폼 SSO와 통합 계정 관리까지 도입한다. 인증 범위를 통일할 수 있으나 사이트·CORE·오프라인 장치의 보안/운영 계약을 새로 설계해야 한다. 이번 목표에 포함하지 않는다.

## 4. 무엇을 어디에 놓는가

| 정보/행동 | 자리 | 그 자리에 있어야 하는 이유 |
|---|---|---|
| 제품·현장·현재 장치 | 헤더 왼쪽 | 어느 대상으로 작업하는지 첫눈에 확인 |
| 현재 연결과 자료 신선도 | 헤더 상태 영역, 상세 근거는 본문 | 계정과 관계없이 현재 자료를 믿을 수 있는지 판단 |
| 로그인/계정 | 헤더 우측 유틸리티 영역, 안전 그룹 바로 앞 | 어느 문서에서든 같은 자리에서 인증/로그아웃을 찾음 |
| 비상 정지 | 독립 안전 그룹, 기존 위치/규격 유지 | 메뉴와 로그인 화면 전환 때문에 정지 접근을 잃지 않음 |
| 문서/역할 이동 | 기존 전역 탐색 | 현재 위치와 다른 업무로 가는 길을 표시 |
| 현재 작업의 주 동작 | 본문 작업 제목/도구 영역 | 어떤 대상에 어떤 작업을 하는지 함께 보여 줌 |
| 선택 대상의 근거/결과 | 현재 맥락 패널 | 전체 현장 상태와 선택 대상 상태를 혼동하지 않음 |
| 테마 | 화면 표시 메뉴 | 계정·장치 설정과 효과가 다름 |
| 장치/현장 설정 | 해당 역할의 설정 화면 | 로그인이나 단순 테마 변경과 달리 운영 구성을 변경함 |
| 로그/원시 응답/고급 토큰 | 진단 또는 명시적인 고급 접속 | 사람의 기본 업무를 기술 자격 전사로 시작하지 않음 |

넓은 Fleet 개념도: `제품·현장 | 연결 상태·권한 | 알림·화면 표시·계정 | 비상 정지`.
좁은 Fleet: 첫 줄 `제품·현장 | 비상 정지`, 둘째 줄 `연결·권한 | 계정·보조 조작`. 우상단은 화면의 무조건 최우측 픽셀이 아니라 안정적인 **우측 유틸리티 영역**을 뜻한다. 정지 위치를 계정 때문에 바꾸지 않는다.

기존 D-641의 아이콘 탐색은 유지한다. 계정 버튼의 표시 문구는 `로그인`/`계정`처럼 발견 가능한 이름을 권장하며 이는 D-641의 아이콘 단독 기본에 대한 **한정 예외 제안**이다. 전체 탐색을 글자 메뉴로 바꾸는 제안이 아니다. 좁은 화면에서 이름을 숨기게 된다면 접근성 이름뿐 아니라 첫 사용자 발견성 검토를 통과해야 한다.

## 5. 인증 흐름: 로그인·계정·장치 연결을 구분한다

Fleet의 사람 로그인 화면은 D-519의 기존 `/api/fleet/auth/connection`, `/session`, `/login`, `/logout`을 사용한다. D-683이 UI 경로 `/console/login`을 채택했으며 새 API를 만들지 않는다.

1. 미인증 사용자: 헤더에 로그인 진입점. 보호된 업무로 직접 진입하면 같은 로그인 화면과 돌아갈 업무를 안내한다. 오류 배지/빈 지도만 보여 주지 않는다.
2. 로그인 화면: 현장 이름, 아이디, 비밀번호, 기본 미선택 ‘이 브라우저 기억(30일)’, 로그인, 돌아가기. HTTPS·쿠키 등 기술 진단은 필요할 때 상세에 둔다.
3. 실패: 아이디는 보존하고 비밀번호는 지운다. 계정 유무를 구분하지 않는 오류, 속도 제한과 서비스 장애는 각각 다른 안내. 중복 제출을 막고 키보드로 완료할 수 있게 한다.
4. 성공: 입력을 비우고 **서버 세션 조회로 principal/role과 첫 변경 완료를 확인한 뒤** 기존 업무 위치로 복귀한다. 로그인 POST 성공만으로 운영자 표시를 만들지 않는다. D-686 초기 계정은 기존 로그인 화면에서 비밀번호를 먼저 변경한다. 초기 쿠키의 운영·프로필 API는 거절되며 변경 후 세션 재조회에서 제한 해제를 확인한다.
5. 로그인 후: 같은 자리의 계정 메뉴에서 현재 계정·역할·현재 현장·로그아웃과 **내 계정**을 제공한다. D-689의 `/console/profile`은 표시 이름 수정, 현재 비밀번호 확인 후 변경, 읽기 전용 ID·이메일·권한으로 한정한다. Map/Cell에서는 새 탭으로 열어 업무 입력을 보존한다. 사진·추가 연락처·권한 편집·비밀번호 재설정은 제공하지 않는다.
6. 만료: 보호된 조작을 막고 재로그인 경로를 보여 준다. 가능한 업무 초안/선택은 보존한다. 응답을 잃은 쓰기 요청을 로그인 뒤 자동 재실행하지 않는다.
7. 로그아웃: 서버 종료 확인 전에는 ‘로그아웃 완료’라고 표시하지 않는다. D-683에 따라 실패하면 현재 계정 표시를 유지하고 ‘로그아웃 확인 불가’와 재확인 경로를 준다. 다른 탭에서 종료된 세션도 다음 검증에서 반영한다.

복귀 주소는 허용된 same-origin 업무 경로만 받는다. 외부 주소/인증 화면 반복 복귀는 거절한다. 자격·비밀번호·쿠키를 URL/로그/임의 localStorage에 넣지 않는다. Bearer 우선·로그인 시 오래된 토큰 제거·HttpOnly/Secure/SameSite·CSRF·감사·기존 유효기간 계약을 보존한다.

| 상태 | 표시/다음 행동 | 하지 않을 일 |
|---|---|---|
| 통신 확인 불가 | 연결 확인 불가, 현재 상태 다시 조회 | 잘못된 비밀번호라고 단정 |
| 세션 없음/만료 | 로그인 필요, 로그인 | 로봇 전원이 꺼졌다고 단정 |
| 로그인했으나 권한 부족 | 현재 역할, 필요한 역할/관리자 문의 | 재로그인을 무한 요구 |
| 장치 미연결/페어링 필요 | 대상과 연결 방법/코드 입력 | Fleet 계정 로그인이 장치 권한을 준다고 주장 |
| 오래된 안전 자료 | 자료 미확인/지연과 조작 제한 | 초록 정상·운전 가능 표시 |
| 개발 연결 모드 | 개발 배지와 실제 개발 세션 표시 | 실명 계정 로그인 성공으로 표시 |

사람 로그인이 설정되지 않은 사이트에서는 동작하지 않는 로그인 폼을 만들지 않는다. 미설정 사유와 관리자 설정 안내 또는 기존 고급 접속을 제공한다. 개발 세션과 기계 Bearer 지원은 별도 진입점으로 유지한다.

## 6. 모든 표면에 도달하는 적용 표

등록 기준은 `shared/web/surfaces.yaml`. 같은 외형을 강제로 복제하는 대신 정보의 의미·위치·상태 어휘를 공유한다.

| 표면 | 적용할 규칙 | 인증/안전 예외 |
|---|---|---|
| Fleet 관제·설치·지도·Cell, 관제의 작업 보기 | 같은 계정 진입점/메뉴, 로그인·복귀, 연결/권한 분리 | 사이트 쿠키 세션. 작업 보기는 별도 계정 화면이 아님 |

## 7. 본문·작업·설정의 공통 규칙

- 업무 화면은 ‘대상 → 현재 상태/출처/시각 → 가능한 주 작업 → 막힌 이유/복구 → 실제 결과’를 따른다. 전역 헤더에 모든 진단을 쌓지 않는다.
- 한 작업 영역에는 주된 다음 행동을 하나 정한다. 삭제·초기화·구성 변경은 영향과 대상을 실행 전에 설명하고 원래 권한/확인 절차를 따른다.
- 읽기 로딩·첫 사용·자료 없음·조회 실패·권한 부족을 별도 상태로 만든다. 읽기 재조회와 쓰기 재실행은 다른 행동이다.
- 저장은 `저장 중 → 저장 확인` 또는 `저장 확인 불가`로 표시한다. 작업은 `요청 → 접수 → 실행 → 결과 확인`을 구분한다. 선택/포커스가 목표 지정 활성화나 실행 승인처럼 보이면 안 된다.
- 같은 의미는 같은 이름·아이콘·부품을 쓴다. 버튼은 행동, 링크는 이동. 필수 대상·위험·결과 문구는 아이콘 툴팁만으로 전달하지 않는다.
- 폼은 실제 라벨, 키보드 제출, 오류와 입력의 연결을 제공한다. 일반 업무 입력/초안은 실패 때 보존한다. 비밀 입력은 별도 처리한다.
- 메뉴/로그인 화면 전환에서 포커스 이동·복귀를 관리한다. 계정 메뉴 Escape 종료·트리거 복귀, 본문 건너뛰기와 보이는 포커스를 확인한다.

## 8. 문서·구현·검증 순서

1. **계약 정합화:** 새 ADR 번호를 도구로 선점하고 D-658 §3/§7의 접속 펼침·계정 위치, D-519 §6의 내장 폼, D-641 아이콘 기본에 대한 한정 예외를 명시한다. 옛 ADR을 조용히 고치지 않는다. 보안 API·권한·안전 범위는 유지한다.
2. **최소 Fleet 구현:** 공통 계정 트리거·로그인 화면·복귀·세션 확인·로그아웃 상태를 기존 모듈로 구현하고 네 문서가 함께 사용한다. 정적 로그인 자산의 Fleet 서빙 allowlist/패키징/배포 closure와 모든 호출자를 점검한다.
3. **회귀:** 인증 성공/실패/429, 계정 미설정/개발 모드, Bearer 우선, 쿠키·CSRF, 새 탭·만료·로그아웃 실패, 외부 복귀 주소 거절, 초안 보존·쓰기 비재실행을 원격 검사한다. 테스트는 사용자가 ‘설정’ 아이콘의 의미를 미리 알고 있다고 가정하지 않는다.
4. **표면 확장:** Robot/Pilot → Learning/Game/Cam/LCD 순서로 적용 표의 실제 계약을 읽고 필요한 부분만 바꾼다. 각 표면의 예외·소유 API·완료 근거를 기록한다.
5. **사용자 검토:** 첫 사용자가 도움 없이 로그인 진입점을 찾는지, 현재 계정/현장/권한을 구분하는지, 직접 진입→로그인→원래 업무→로그아웃을 끝내는지 관찰한다. 320/390/1366/1920px, 긴 계정명, 키보드/확대에서 안전 접근과 넘침을 확인한다.
6. **설치 검증:** G1 회귀·G2 캡처·G3 작업 검토, local/main/pushed SHA·CI·서명·설치 SHA·제공 자산을 각각 기록한다. 폰/태블릿/로봇 미접속은 실물 수용 미확인으로 남긴다.

최종 수용은 ‘처음 온 사람이 계정과 업무를 찾고, 상태를 오해하지 않으며, 복구 후 결과를 확인한다’는 작업 증거로 판단한다. 정적 헤더 동일성이나 로그인 폼 존재만으로 완료로 표시하지 않는다.

## 이번 회차 결과와 남은 일

공식 참고 조사·현재 소스 진단·플랫폼 적용 표·인증 상태/복귀 흐름·검증 기준을 문서화했다. 후속 구현에서 [D-683](../adr/D-683-fleet-account-entry-and-login-return.md)을 채택하고 네 Fleet 문서의 우측 로그인/계정, 전용 로그인 문서, 세션 확인 후 업무 복귀를 구현했다. 기존 인증 API와 CORE 권한은 유지한다. 로그아웃 확인 실패는 현재 계정 표시를 유지하고 재확인을 안내한다는 D-683 결정이 이 설계의 초안보다 우선한다.

새 인증 흐름의 원격 회귀와 설치/실물 검증은 [검증 기록](../validation/all-ui-workflows-2026-10-12/result.md)에 구분해 남긴다. 기존 관제 작업 회귀 `addd5a982`의 원격 **8 PASS**는 새 로그인 설계의 검증이 아니다. 소스 구현을 설치·사용자 수용 완료로 표시하지 않는다.

후속 확정 범위는 [D-686](../adr/D-686-fleet-first-login-password-change.md)과 [D-689](../adr/D-689-fleet-self-profile.md)다. 팀원 네 명의 사람 계정만 operator로 발급하고 초기 비밀번호는 사용자 요청대로 ID와 같되 첫 로그인에서 변경해야 한다. 기존 기계·업데이트·AI 자격은 보존한다. 이름 저장은 PATCH 뒤 GET 프로필, 비밀번호 변경은 POST 뒤 GET 세션·프로필로 결과를 확인한다. 설치 코드·제공 자산의 일치와 실제 초기 제한을 확인한 후 발급하며, 당사자의 최종 비밀번호 변경을 대신 수행하거나 완료로 추정하지 않는다.
