# Rosy Pilot 로비(게임방 입장)와 실시간 영상 경로 설계 (초안)

**상태:** 초안 — 사용자 승인 전. ADR 번호는 승인 때 잡는다(현재 브랜치 최고 D-338).
**관련:** D-323(pilot), D-331(다중 기기), D-193(토큰), D-12(최종 명령 기기 로컬),
[현장 LAN 발견 규칙 v0.1](../reference/site-lan-discovery-profile.md), 설계 §3.1·§10.

## 1. 왜

- 운전자는 기기 주소를 몰라도 "방 목록"에서 로봇을 골라 들어가야 한다(게임 로비처럼).
- 어느 기기에 먼저 붙든 거기서 다른 기기들이 보여야 한다 — 현장 PC 가 없어도.
- 2026-09-29 태블릿 실측: pilot 탭 52 개가 한 로봇을 동시에 폴링했고 그중 하나가 MANUAL
  주행 화면에 들어가 있었다. **한 로봇을 여러 조종 화면이 동시에 잡을 수 있다** — 로비는
  "로봇 1 대 = 운전석 1 개"를 보장해야 한다.
- 카메라가 초당 2~3 장(CORE 계약 0.4 s 하한)이라 게임 같은 조작감이 불가능하다.

## 2. 로비 구조

### 2.1 방(room) = 기기 하나

| 항목 | 출처 |
|---|---|
| 이름·종류(Pinky/OMX)·release·stage | mDNS TXT(공개 정보만, 규칙 v0.1) |
| 주소 | `<hostname>.local:<port>` — IP 가 아니라 호스트네임 |
| 온라인·배터리·모드 | 그 기기의 공개 상태 요약(아래 2.3) |
| 운전석 | 비었음 / 누가 운전 중(라벨만) / 내가 운전 중 |

### 2.2 방 목록의 출처(합집합, 호스트네임으로 중복 제거)

1. **지금 붙은 기기가 대신 찾아 준 이웃**: 브라우저는 mDNS 를 못 한다. 대신 각 CORE 가
   Avahi 로 `_rosy._tcp` 를 탐색해 `GET /api/v1/site/rooms` 로 돌려준다(공개 TXT 만).
   CORE 는 이미 `_rosy-fleet._tcp` 를 Avahi 로 찾는 코드가 있다(`fleet_agent/discovery.py`).
   → **어느 기기로 들어가도 같은 로비가 보인다**(현장 PC 없이도).
2. **현장 Fleet 이 있으면** 그 발견 결과(`/api/fleet/discovery/*`)를 같은 모양으로 더한다.
3. **기억된 방**: PWA 가 호스트네임·라벨만 기억한다. **토큰은 저장하지 않는다**(D-193).
   현재 "최근 접속"은 토큰을 localStorage 에 평문 저장한다 — 이 설계에서 제거한다.
4. **QR·직접 입력**: `http://<hostname>.local:8080/pilot/` (규칙 v0.1 이 허용한 진입 수단).

### 2.3 입장(join)

- 방을 누르면 **그 기기의 origin 으로 이동**한다: `http://<hostname>.local:8080/pilot/#join`.
  모든 기기가 같은 pilot 을 서빙하므로 CORS 를 열지 않는다(D-323 same-origin 유지).
- 인증은 기기마다다(origin 마다 sessionStorage). 빠른 입장은 D-193 로그인 코드(기기 LCD
  표시 → 입력) 또는 운영자 토큰.
- 들어가면 **운전석 요청** → 비었으면 앉는다 → 주행 화면. 차 있으면 "관전"(영상·상태만)과
  "양보 요청".

### 2.4 운전석(seat) — CORE 계약 추가 필요

- `POST /api/v1/teleop/seat` {client_id} → 임대(lease) 발급. teleop 이 임대를 연장한다.
- 다른 클라이언트의 teleop 은 `409 SEAT_TAKEN`. 임대는 teleop 이 끊기면(예: 2 s) 풀린다.
- 비상 정지는 좌석과 무관하게 누구나.
- 이것은 CORE API 변경이므로 API Ref 사이클과 SAF 요구 추적이 필요하다.

## 3. 실시간 영상 경로 — 권장: 인증된 MJPEG 스트림

| 안 | 지연·프레임 | 비용 | 판단 |
|---|---|---|---|
| 지금(JPEG 폴링, 0.4 s) | 2.5 fps 상한 | 0 | 게임 조작감 불가 |
| **MJPEG over HTTP** | 15~20 fps, 100~200 ms(LAN) | CORE 라우트 1 개, 새 의존성 없음 | **권장** |
| WebRTC | 30 fps, <100 ms | aiortc/GStreamer, 시그널링·NAT, 이미지 크기 증가 | 후속(필요 실측 시) |

- `GET /api/v1/vision/front/stream` → `multipart/x-mixed-replace`. 최신 프레임 저장소
  (`core_features/vision/store.py`)에서 새 시퀀스가 올 때만 내보낸다.
- 브라우저 `<img>` 는 Authorization 헤더를 못 보내므로 `fetch()` 스트림을 JS 로 잘라
  `createImageBitmap` 으로 캔버스에 그린다(토큰을 URL 에 넣지 않는다, D-193).
- **운전석 보유자만 고프레임**(예: 15 fps), 관전자는 기존 0.4 s 폴링 — 기기 CPU·대역폭 상한.
- 프레임 소스도 올려야 한다: 실기 카메라 파이프라인과 시뮬 릴레이가 15 fps 를 내야 한다
  (지금 시뮬은 gz 카메라 ~2 Hz — 호스트 부하 영향 포함).
- 끊기면 폴링으로 자동 복귀, HUD 에 "영상 지연 N ms"를 보인다.

## 4. 순서(제안)

1. 로비 UI + 기억된 방(토큰 저장 제거) + QR/직접 입력 — 프런트만, 바로 가능.
2. CORE `GET /api/v1/site/rooms`(Avahi 탐색) — 기존 discovery 패턴 재사용.
3. 운전석 임대 계약(API Ref) + CORE 구현 + pilot 관전 모드.
4. MJPEG 스트림 라우트 + pilot 캔버스 렌더 + 소스 15 fps.
5. 실기 2 대 + 태블릿으로 로비 입장·좌석·영상 지연 실측(DEVICE).

## 5. 열린 질문

- 빠른 입장 수단: 로그인 코드(LCD) vs 운영자 토큰 vs 둘 다.
- 관전을 허용할지(영상 대역폭).
- 현장 PC 없는 순수 P2P 로비만으로 v1 을 닫을지.
