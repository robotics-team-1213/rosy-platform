# CORE cumulative camera lane trial restriction

The user authorizes at most 0.20m TOTAL physical path, including reversing and coasting, across the authorization. This limits physical movement, not engineering scope. Human indexed mask approval is required only for NEW indexed training. Existing classical or already accepted model camera-to-lane control is independent of that approval. Connectivity is not accuracy or driving acceptance.

Reuse the existing camera geometry, line-follow policy, CommandManager, readiness/safety policies, PinkyTwistPort and sole CORE publisher. An optional private `BoundedTrial` restricts every selected manual/navigation/docking candidate immediately before port submission. No HTTP/API/schema/config flag arms it. The owner may inject the same object into the existing bridge's private `_bounded_trial_guard` only after existing field guards and independently validated measurement/stop evidence are satisfied. This source change alone performs no injection, deployment, mode change or movement.

One owner-controlled canonical ledger represents the entire user authorization, not a new ledger per robot, mission or retry. Its immutable identity includes trial, robot, boot, odom frame and complete measured bounds. SQLite FULL transactions preserve sampled path upper estimate and unresolved nonzero issuance before send. Every read/modify/write begins IMMEDIATE so another connection cannot overwrite STOP with an old read. Reopening consumes the trial and remains STOP; there is no automatic resume, budget reset or repeat. A failed/unknown send consumes the trial and attempts ZERO; that attempt is not physical stop acknowledgement.

The ROS adapter preserves original integer header timestamp and frame plus current ROS source clock. It never fabricates ROS2 sequence numbers. Invalid/future/repeated/backwards stamps, frame changes, receipt/source gaps, nonfinite positions, implausible speed or backwards monotonic time latch STOP. After STOP, valid samples still accumulate coasting evidence. Unknown gaps invalidate path coverage; a later valid sample cannot restore motion authority. Pose increments include backtracking; sampled chords require validated curvature/measurement underestimate bounds, never an assumed exact physical distance.

The owner-supplied `Bounds` is a PRIVATE evidence input, not an approval flag. Every positive bound and its evidence SHA must be independently validated for the selected device: actual path underestimation scale, total measurement uncertainty, actual speed/angular ceiling, minimum deceleration, worst-case control/transport/actuator latency, original-source freshness/gap and total trial duration. Nominal D-422/D-424 profile deceleration, synthetic tests, camera stamps, cmd_vel=0 or stationary wheel odometry do not establish these bounds. Source publisher/robot/boot/frame binding and artifact-to-device correspondence must be verified by the runtime owner before injection. Unknown actual evidence => no arming or motion.

Before each nonzero send the existing measured path upper estimate plus total measurement uncertainty, speed upper*(source age + worst-case latency) and speed upper squared/(2*minimum measured deceleration) must remain strictly below 0.20m. Equality stops. A final clock/STOP check follows the durable commit so slow storage cannot use stale evidence. Real operator stop capability, current navigation/readiness, calibration and obstacle/safety approvals remain separate required gates. Mask count is not consulted here.

Host tests use SYNTHETIC bounds/poses only. They cover current CAMERA_LINE manager -> CORE mux -> existing final send with guard and lane loss, reserve/backtracking/coasting, source freshness/reset/errors, mutation, restart, slow commit and lost acknowledgement. Existing geometry/fallback/sole publisher checks remain their existing suites. ROS bridge construction/installed device matching, actual accuracy/braking/physical distance and final stationary evidence remain independently unverified; no physical trial PASS is claimed.
