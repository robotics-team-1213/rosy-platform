# 카메라→지도 초안 자동 생성·상시 보정 파이프라인 설계 (draft)

Date: 2026-11-11
Status: **Draft — 승인 전** (승인 뒤 rosy-platform `docs/plans/`로 옮기고 실행 계획 작성)
작성: map-reality-check 세션 · 사용자 선택: **(a) 카메라가 초안을 자동 생성 + (b) 카메라가 틀어져도 지도를 계속 보정**

## 1. 목표와 이유

관제 지도(차로·장소·구역)를 **사람이 손으로 그리지 않고**, 사이트 카메라가 본 실제 바닥에서:

1. **초안 자동 생성** — 보정된 카메라 평면 한 장에서 차로/구역 후보를 뽑아 지도 초안을 자동으로 만든다.
2. **상시 보정** — 카메라가 돌아가거나(틀어짐) 바닥이 바뀌어도, 재촬영·재추출로 지도(또는 카메라 보정)를 계속 맞춘다.

왜: 오늘 만든 「지도–실제 대조」는 *이미 있는 지도*를 검증만 한다. 그 앞 단계(지도를 만드는 일)와 뒷 단계(계속 맞추는 일)를 카메라 데이터로 채우면 지도 만들기→검증→보정이 하나의 흐름이 된다. 로봇 주행 없이도 첫 지도를 만들 수 있다(주행 기록은 검증용 근거로만 쓰고, 없어도 초안 생성은 가능).

## 2. 이미 있는 부품 (재사용, 신규 없음)

| 부품 | 위치 | 이 설계에서 하는 일 |
|---|---|---|
| 그림→초안 추출 파이프라인 (D-825) | `site_map_routes.py` drawings/projections/extractions/validate + `drawing-import.js`·`extraction-review.js` | **본체**. 이미지 업로드→투영→정렬→추출→검증→초안 병합까지 이미 동작함. 지금은 올린 파일만 받음 |
| 카메라↔지도 변환 | 추적 보정(`tracking/`, `/api/fleet/calibrations`) + 카메라 평면(`camera-backdrop.js`, D-515 워프) | 카메라 프레임을 지도 좌표로 정렬하는 **자동 투영**의 소스. 사람이 손으로 정렬하는 걸 대체 |
| lane-paint 정합 (D-375) | `shared/map-fit.js`(순수 수학) + `map-fit-view.js` | 바닥 차선 그림에서 homography/차로 후보 계산. 표시 전용이던 것을 추출 입력으로 승격 |

| 로제이 캠 스트림 | `operations/site_ui`(media) | 프레임 획득 경로 (v1은 Fleet이 아는 보정 카메라 목록의 스냅숏) |

## 3. 설계

### 3.1 초안 자동 생성 — 「지도 만들기」의 새 절 「카메라로 초안 만들기」

```
보정된 카메라 선택 → 서버가 프레임 캡처(스냅숏)
  → 그 프레임을 D-825 파이프라인에 "도면"으로 투입 (새 entrance: source=camera)
  → 투영(projection)은 카메라 보정 행렬로 자동 계산 — 손 정렬 없음
  → 추출: 차선 페인트(Vision map-proposal API)로 차로 후보, 색 영역으로 구역(제외) 후보
  → 후보 검토 화면(기존 extraction-review 그대로): 운영자가 확인/수정
  → 수락하면 서버 기하 검증(validate) 뒤 **초안에만** 반영
```

- 여러 카메라를 이어 붙일 때: 각 프레임을 같은 절차로 돌리고 후보를 초안에 순차 병합(기존 병합 규칙 재사용).
- 프레임 캡처는 서버가 함(브라우저가 카메라 자격을 갖지 않게 — 기존 원칙).

### 3.2 상시 보정 — 「지도–실제 대조」 절에 카메라 근거 추가

오늘 만든 대조는 근거가 주행 기록(D-594)뿐이었다. 카메라 재추출 결과를 두 번째 근거로 넣고 **셋(지도·카메라·주행)을 삼각측량**해 무엇을 고칠지 분류한다:

| 비교 결과 | 판정 | 조치 제안 |
|---|---|---|
| 주행과 지도 불일치 + 카메라가 주행과 일치 | **지도가 틀림** | 초안에 강체 보정(v1.384 apply 재사용) |
| 주행과 지도 일치 + 카메라만 어긋남 | **카메라가 틀어짐** | 카메라 보정 갱신 제안(D-375 homography로 재보정 안내) |
| 카메라와 주행이 일치, 지도만 벗어남 | **지도 밀림** | 초안 보정 제안(apply) |
| 카메라와 지도가 일치, 주행만 어긋남 | **주행 기록 이상**(끊김·드리프트) | 지도를 고치지 않고 사람 확인 |
| 세 쌍 다 어긋남 | 판정 불가 | 사람 확인(기존 `mismatch` 경로) |

- 실행 시점: v1은 운영자가 「다시 대조」를 누를 때(수동). 주기 자동 재추출은 설정(`site-rules`/사이트 설정)에 두는 걸 v2로.
- 카메라 보정 갱신도 **제안만**: 적용은 기존 보정 승인 절차(tracking 승인 경로)를 따른다.

### 3.3 지키는 경계 (오늘 세운 원칙 그대로)

- 자동 생성·보정이 쓰는 곳은 **초안뿐**. 활성 지도는 운영자가 초안을 검토하고 활성화할 때까지 불변.
- 지도 편집은 로봇 명령을 내리지 않는다(D-2 무관).
- 카메라 프레임·추출 후보·판정은 모두 감사 사건으로 남긴다(기존 `site_map_events` 재사용).

## 4. 범위 밖 (v1)

- 활성 지도 자동 교체, 로봇 명령, 카메라 자동 발견/새 하드웨어 등록.
- 보정 없는 카메라의 프레임 사용(보정 행렬이 없으면 투영을 계산할 수 없음 — 등록·보정은 기존 절차).
- 사람 얼굴·물체 인식 등 비전 일반화. 차선 페인트·표시된 구역 색만.
- SLAM 점유 지도 결합(기존처럼 오프라인 도구로 유지).

## 5. 접근법 비교 (책임 소유 기준 — 2026-11-11 사용자 확정: **안 1**)

1. **안 1 — 계산은 Vision, 판정은 Fleet (채택, 사용자 승인)** — Vision이 이미 소비하는 카메라 프레임에서 "차로·구역 후보 JSON"을 내는 것(차선 페인트 정합 D-375 계산도 이미 Vision의 map-proposal API에 있음)을 확장. 프레임 캡처도 Vision이(이미 스트림 보유, Media 무변경). Fleet은 카메라 선택·검토·기하 검증·초안 병합·삼각측량·감사·활성화를 단독 소유. 카메라 틀어짐 보정은 Vision이 homography **제안**, 적용은 기존 Fleet 추적 보정 승인 절차. 제안/승인이 서로 다른 주체 — 역할표(Vision=파생 관측·후보, Fleet=승인·원장)와 정확히 일치, 새 권리 경계 없음. 제약: 초안 생성이 Vision 가용성에 의존(실패 시 이유 표시·재시도).
2. 안 2 — Fleet이 계산까지 자체(포팅) — 조정자가 관측 계산 소유로 역할표 위반·코드 최대. 기각.
3. 안 3 — 지도-관측 전담 신규 서비스 — 새 배포·권리 주체, D-427 정리 방향과 어긋남. 기각.

## 6. 빌더 검토 반영 — 정해진 답 (2026-11-11, 내 판단으로 정하고 표시)

1. **첫 지도 전제(그린필드)**: v1은 **추적 보정이 있는 카메라 ≥1대를 전제**로 한다(보정은 기존 실측 절차 — 두 점 거리 실측 등 — 로 세운다). 보정 없는 카메라에서 보정 자동 생성은 별도 과제. 이 전제를 UI에도 밝힌다("보정된 카메라가 없으면 먼저 보정").
2. **투영 변환 모델**: D-825의 유사변환 모델은 그대로 두고, **서버가 보정 행렬로 프레임을 하향 정사(rectify)한 뒤** 파이프라인에 넣는다. projection/survey 스키마·UI 픽셀 수학은 불변. survey 근거는 `source: camera + calibration revision`으로 새로 기록(실측 거리 필드 대신).
3. **차선 페인트 검출 주체**: 기존 **Vision map-proposal API를 호출**한다(X-Proposal-State·속도 제한 준수). Vision은 계산만, 흐름·승인·초안은 Fleet — §5.2의 기각(비전이 파이프라인 소유)과 모순되지 않는다. Vision 닿지 않으면 그 프레임은 추출 실패로 처리(폴백 없음, 이유 표시).
4. **삼각측량 표 수정**: 3행은 "**카메라↔지도 일치, 주행만 어긋남** → 주행 기록 이상(끊김·드리프트) → **지도를 고치지 않고** 사람 확인". 나쁜 주행 기록에 지도를 끌어맞추는 일이 없게 한다. "카메라↔주행 일치" 판정은 카메라 추출 기하↔주행 트랙 직접 비교(오차 문턱은 v1.384의 0.15 m 재사용).
5. **map-fit 경계**: D-375는 여전히 **제안 전용**. 바뀌는 건 없다 — 카메라 보정 갱신 제안이 **기존 추적 보정 승인 절차**로 흘러가고, 그 승인된 보정만이(이미 그래왔듯) 카메라 평면·투영에 쓰인다. ADR 불필요(권한 변화 없음).
6. **횡단보도**: v1 범위에서 뺀다. 기존 D-573 차선 그래프 유지를 그대로 쓴다(수용 종류도 road·stop_line·exclusion 그대로).
7. **다중 카메라**: v1은 **한 프레임(한 카메라)만** 초안 부트스트랩에 쓴다. 추가 카메라는 기존 업로드 절차로. 이어붙이기(초안 `drawing` 단일 슬롯의 근거 재기록 문제)는 v2 설계.
8. **프레임 보존**: 오늘 운영자가 카메라 스크린샷을 올릴 수 있는 것과 같은 노출 등급이므로 **도면 자산 저장소·보존 규칙을 그대로** 쓴다(해시+메타데이터는 감사 사건에). 사람이 상시 찍히는 현장의 프라이버시 정책은 사이트 운영 규칙 과제로 남긴다.
