## 1. 결론 — 두 평면

```
관제(Fleet 콘솔) ──명령──▶ [ESP32 컨트롤러] ──접점──▶ [신호등]
        │                                        │ 빛
        │                                        ▼
        └──교차 검증(불일치=faults)── [관측 서비스] ◀──프레임── [카메라]
```

- **제어 평면** = ESP32 컨트롤러(ROSY-SIGNAL-001). 접점을 누른다. 권한의 유일한 주체.
- **관측 평면** = 호스트 카메라 + 영상 처리. **읽기 전용 증거**이지 명령 경로가
  아니다 — 관측 서버에 명령 API 자체를 두지 않는다(경로가 없으면 해킹할 경로도
  없다).

이 분리가 바로 해결하는 것: 수용 계획이 인정한 맹점 **S-02/S-11** — "명령했는데
실제로 켜졌는가"는 접점 쪽에서는 원리적으로 볼 수 없다. 카메라가 신호등을 **바깥에서
바라보면** 제품을 개조하지 않고도 그 갈림이 보인다. 토이 제품(개조 부담)에 특히 맞는
비침습 해법이다.

## 2. 파이프라인 — 인터페이스가 축이다

```
캡처 → 분류 → 관측 API (GET /observed, 읽기 전용)
```

1. **캡처**: 웹캠/RTSP. 배치는 신호등 헤드 정면, 렌즈 3개가 프레임 안에 고정되게.
2. **분류 v1 — OpenCV 고전 기법 (기본)**: 렌즈 ROI 3개는 고정 좌표(장착 후 캘리브레이션).
   HSV 색 분할 + 밝기 임계로 렌즈별 `lit/꺼짐 + 색상군(적/황/녹-청록)`을 판정한다.
   **결정론적이고 학습 데이터가 필요 없고 설명 가능하다** — 3개의 큰 LED가 고정
   프레임에 있는 문제에 YOLO는 필요 없다.
3. **분류 v2 — YOLO (선택 단계)**: 장면이 복잡해질 때만 — 원거리, 다신호기, 배경
   혼잡, 움직이는 촬영. **같은 인터페이스 뒤에 끼우는 교체 가능 단계**로만 둔다.
   "인터페이스 먼저, 탐지기 나중" — 파이프라인을 YOLO에 결합하면 모델·학습데이터
   관리 비용이 구조에 스며든다.
4. **관측 API**: `GET /observed` →

```json
{
  "ts": 1770000000.0,
  "lamps": { "left": {"lit": true,  "group": "red"},
             "mid":   {"lit": false, "group": null},
             "right": {"lit": false, "group": null},
             "beacon": {"lit": false} },
  "confidence": 0.93
}
```

색상군(`group`)은 운영자의 사이클 지도(B0)와 대조하는 값이지 의미가 아니다 —
stop/go 해석은 Fleet 쪽 지도가 한다(v2 제안 §2.1과 같은 정신).

## 3. 교차 검증 — 이 구조가 존재하는 이유

Fleet 콘솔은 세 개의 말을 모은다:

1. 내가 보낸 명령(의도)
2. 컨트롤러가 보고한 상태(접점이 닫혔다고 주장)
3. 관측 서버가 본 것(빛이 실제로 켜졌는가)

1≠2면 **컨트롤러 불일치**, 2≠3이면 **표시 불일치**(배선 끊김, LED 사망, 전원 문제) —
원인이 다른 두 고장이 처음으로 구별된다. 둘 다 화면 faults 로 올라가고, 이것이
S-02/S-11 맹점의 해소다.

**착지 (2026-09-22):** `SignalConsole` 의 `verify` 행 — `cross_check()` 순수 판정 +
`poll_once()` 안의 관측 폴링. 상태값: `absent`(관측 없음)/`unreachable`(도달
실패)/`agree`/`controller_mismatch`(1≠2)/`display_mismatch`(2≠3)/`stale`(관측
`frozen` — 오래된 증거라 말할 수 없음)/`unmapped`(사이클 지도 없음 — 합격으로
그리지 않음)/`bad_response`. 램프→ROI 지도는 `signals.yaml` 의 `observer_map`
(운영자 기입 — 여기서 지어내지 않는다). 관측 `pending`(debounce 확정 전)은 침묵이다.

## 4. 배치와 경계

- **배치**: `signal/observer/` — signal 모듈의 증거 컴포넌트다. 독이
  `dock/firmware/` 를 품은 것처럼, 관측은 신호등 모듈이 품는다. Python + OpenCV,
  ROS import 없음, 작은 FastAPI/http 서버 하나.
- **경계 규칙**:
  - 관측 서버는 **명령을 받지 않는다**. POST 라우트 자체를 만들지 않는다.
  - Fleet 는 관측을 **근거로만** 쓴다 — 신호등 제어 결정의 입력으로 쓰지 않는다
    (관측이 고장 나면 표시 신뢰도가 같이 무너지는 결합을 만들지 않는다).
  - 관측은 로봇 안전 판단의 입력이 아니다(D-94 와 같은 원칙).
- **기존 자산과의 관계**: games overhead(D-94/95)는 경기 관측용이고 control 카메라는
  로봇 센싱이다 — 용도가 다른 관측을 한 파이프라인에 합치지 않는다. 패턴(호스트
  서비스, 최소권한, 증거 기록)만 재사용한다. 훗날 로봇이 신호를 "보고" 판단해야
  하면 이 관측 API 가 그 입력이 된다 — 그때까지 인터페이스가 고정되어 있으므로
  소비자만 붙으면 된다.

## 5. 시험 (합성 ≠ DEVICE 유지)

- 분류기 단위시험: 합성 프레임(단색 원형 ROI, 배경 노이즈 포함)으로 lit/색상군 판정
- 회귀 세트: 벤치에서 실촬 프레임을 수집해 고정 — 합성 통과만으로는 부족(D-94)
- 교차 검증 단위시험: 의도/컨트롤러/관측 셋이 갈릴 때 faults 매핑 — 가짜로
- 관측 서버 경계시험: POST 시도 → 405/404 (명령 경로 부재를 시험이 고정)

## 6. 카메라 역할의 분리 — 표시 / 계측 / 상태관측 (2026-09-22 운영자 지시 반영)

이 제품의 카메라는 **속도 확인(단속) 컨셉의 요소**다. 그래서 "카메라"라는 말이
세 가지 전혀 다른 역할을 가리킬 수 있고, 이 셋을 한 스트림·한 서비스에 섞는 순간
구조가 무너진다.

| 역할 | 하는 일 | 요구 | 만지면 안 되는 이유 |
|---|---|---|---|
| **표시 피드** | 운영자에게 카메라 화면을 **보여준다** | 낮은 지연, 압축 허용, 정확도 불요 | 화면용 스트림에 계측을 얹으면 압축·지연이 숫자를 오염시킨다 |
| **속도 계측** | 로봇의 속도를 **숫자로** 뽑는다 | 캘리브레이션(스케일·프레임레이트·왜곡), 결정론 | 표시와 섞여 "눈으로 보이는 속도"와 "계측 속도"가 어긋나면 단속 근거가 무너진다 |
| **신호 상태 관측** | 신호등 **빛의 실측**(이 문서) | 렌즈 ROI 고정, 색 판정 | — |

**속도의 출처 원칙:** 속도의 1차 출처는 **로봇 오도메트리**다 — Fleet 가 이미 N대
pose 를 모으고(D-59), pose 차분이 속도다. 카메라 속도 계측은 그것을 검증하는
**독립된 두 번째 출처**일 뿐, 1차가 아니다. 카메라 단독으로 속도를 만들면 조명·
가림·왜곡에 단일 실패점이 생긴다.

**조심 규칙 (운영자 지시 "조심해서"의 구체화):**

1. 한 스트림을 셋이 나눠 쓰게 하지 않는다 — 계측이 필요해지면 별도 파이프라인
   (해상도·프레임레이트·왜곡보정 요구가 다르다).
2. 계측 결과가 곧 제어가 되지 않는다 — 판정은 Fleet, 신호등은 표시(D-12·D-59 정합).
   "과속 → 적색"을 만들면 그 판정과 명령은 Fleet 가 한다.
3. 표시 피드는 관제 토큰 뒤로 — 카메라 화면은 현장 영상이라 권한 없는 노출이
   곧 문제다(D-52 최소권한 선례).
4. 제품의 카메라 프롭은 그 역할(속도 확인 컨셉)을 유지한다 — 관측 센서 마운트로
   재활용하지 않는다. F1 이 필요하면 별도 소형 마운트를 쓴다.

**속도 확인이 신호등과 만나는 시나리오** (미래 과제 — v1 밖, 별도 설계):
과속 판정(오도메트리 1차 + 카메라 검증) → Fleet 가 판정 → 신호등 `all_red`/적색
표시. 이때 새로 생기는 것은 판정 정책(임계값·측정 구간)과 이벤트 경로뿐이고,
신호등은 여전히 표시 장치다 — 역할이 늘지 않는다.

## 7. 비목표

- 관측 서버가 제어 권한을 갖지 않는다 (앞서 말한 경로 부재 원칙)
- 로봇 안전 판단 입력 아니다
- 도로용 인증 아니다
- v1 에서 YOLO 도입 아니다 — 기준(§2.3)이 넘어갈 때 별도 결정
