# 관제 유닛 첫 배치 확정 — R과 CELL-A

**상태:** 2026-10-29. [독립·상하위 관제 후속 목표](2026-10-23-composable-control-goals.md)의 N1(실제 배치 확정)을 마감한다. 사용자가 지시한 구조 — 각 셀의 조정 단에 관제가 붙고 위로 통합관제가 있는 모양 — 를 현재 장비로 처음 적용하는 배치다. 이 문서는 논리 유닛·자원·자격·private 설정 소유를 정한다. 실제 설치·PC 간 연결·장애 수용은 N2·N3로 남는다.

## 확인된 현재 상태 (2026-10-29, 현장 PC 읽기 조사)

- 사이트 스택 운영 중: proxy·Fleet·Vision 컨테이너 healthy, Fleet 이미지는 2026-10-28 빌드분.
- 관제는 **단일 Fleet 인스턴스**다. Pinky 로봇 2대(사이트 robots.yaml), 셀 팔 관측 토큰(`ROSY_ARM_A/B/S_TOKEN`, compose 오버레이), 천장 카메라가 한 인스턴스에 붙어 있다.
- **관제 유닛 계층은 배포된 적 없다.** `/etc/rosy` 아래 control-unit 설정·compose 오버레이·peer 서비스 자격이 없고 Fleet 환경 변수에도 관제 항목이 없다. 소프트웨어(I1–I6)만 main에 있다.
- OMX 셀 도구는 같은 호스트의 자동갱신 미러(`~/rosy-omx`)에 있고, 관측 bridge는 상시 systemd 서비스가 아닌 세션 단위로 돈다.
- 모델 PC·AI PC는 테일넷으로 접근되고, AI PC의 운영 추론 경로는 아직 활성화되지 않았다(기존 D-516 상태).

## 배치 결정

논리 유닛 2개를 호스트 1대로 시작한다(D-893 3항: 한 호스트에 여러 관제 인스턴스 동거 허용, 원장·설정·포트·서비스 자격 격리). 관측 영상과 셀 카메라는 소유 관제에 머물고 R에는 D-862 요약만 오른다.

| 유닛 | 역할 | 직접 자원(manifest `resources`) | 부모 | 호스트 | 원장·화면 |
|---|---|---|---|---|---|
| `R` | 통합관제 + 현장 주행 관제 | `robot:<robot-1>`, `robot:<robot-2>` (사이트 roster와 정확히 일치) | 없음 | 현장 PC, 기존 site 스택 | 기존 Fleet SQLite·`/console` 그대로 승계 |
| `CELL-A` | OMX 셀 관제 | `workcell:arm_a`, `workcell:arm_b`, `workcell:arm_s` | `R` | 현장 PC, 신규 격리 인스턴스 | 자체 SQLite·자체 포트·자체 users 파일·자체 `/console` |

세부 계약:

- `CELL-A`는 `share_information_with_parent: true`, `accept_parent_stop: true`를 명시 허용한다. R은 D-862 정보 수집·위임·명시 허용된 정지 중계만 하고 CELL-A의 승인·장치 자격을 대행하지 않는다.
- R의 직접 로봇 소유는 기존 로컬 승인·CORE 경로를 그대로 쓴다(후속 목표 N1의 명시 허용 형태). 주행 trip·교통정리·지도는 하나의 조정 범위이므로 R에 둔다.
- 팔 셋(arm_a/arm_b/arm_s)은 **하나의 조정 범위**라 유닛 하나(CELL-A)로 묶는다. 팔마다·AI마다 관제를 만들지 않는다(D-893: 조정 범위가 다를 때 나누고, 계산·연결만 다를 때는 호스트만 나눈다).
- 기존 site Fleet 환경의 셀 팔 관측 토큰(`ROSY_ARM_*_TOKEN`)은 N2 설치 때 R에서 빼고 CELL-A의 환경으로 옮긴다. 두 인스턴스가 같은 workcell을 소유하면 정지 소유 대조(`CONTROL_UNIT_LOCAL_OMX_OWNER_MISMATCH`)와 중복 소유 거절에 걸린다.
- 실제 주소·토큰·인증서는 승인된 private 위치에만 둔다(현장 PC `/etc/rosy/control-unit/`, 개발 체크아웃 `private/control-units/`). 이 문서와 공개 예제는 자리표시자만 쓴다(D-226).
- manifest revision은 `site-2026-10-29-r1`로 시작하고, 미완료 위임이 있으면 revision을 바꾸지 않는다(기존 구성 규칙).

## 단계적 확장

1. **지금(1단계):** 위 표. 두 인스턴스가 같은 호스트에서 TLS peer로 연결된다(루프백 origin).
2. **2단계(셀 전용 호스트 확보 시):** CELL-A 인스턴스만 그 호스트로 계획 전환한다(D-893 6항: 정지·진행 중 요청 조정 뒤 원장·설정 이동, 자격 회수, 재무장). 논리 유닛·자원·부모 관계는 불변.
3. **3단계(복수 현장·셀 추가):** 새 셀은 자기 조정 범위의 유닛(CELL-B, …)으로 R 아래에 붙고, R이 상위 통합관제의 서브 유닛으로 참여한다(D-850 2항).

## 연기하는 결정

- **팔 작업의 계층 간 위임:** D-855 범위(유한 navigation 위임)를 유지한다. R→CELL-A 팔 작업 위임은 D-851 후속 설계로 별도 계약을 연다. 첫 배치에서 계층 간 이동은 정보 수집과 정지 요청뿐이다.
- **통합관제 실시간 영상:** D-862 경로에는 영상이 없다. 셀 영상은 CELL-A 화면(소유 관제)에서 본다. R에서 실시간 영상이 필요해지면 별도 opt-in 계약을 설계한다.

## N2 실행 개요

상세 절차·실제 값은 `private/control-units/`(공개 저장소 밖)의 실행서를 따른다.

1. control-peer CA·양방향 서비스 토큰 생성, R·CELL-A 각각의 users 파일에 `role: service` principal 등록.
2. CELL-A compose 프로젝트 생성(자체 포트·DB 볼륨·users·roster `robots: []`), `--control-unit-config` 지정, 팔 토큰 환경 이전.
3. R에 관제 오버레이·설정 적용, 양방향 TLS 연결 확인(자식→부모 승인 전 조회 포함).
4. [관제 구성 안내](../deployment/control-units.md) 「검증 경계」 1–3: roster·DB·peers 대조, 인증·범위 거절, 같은 identity 재전달이 새 Task를 만들지 않음. 이 통과까지가 N2다.
5. N3는 같은 문서 4–5(단절·재시작·취소·실물 정지 관측)로, 실제 장치 작업 승인이 있을 때 진행한다.

## 기명 운영자와 남은 결정

- CELL-A의 기명 운영자는 CELL-A 자체 users 파일에 설치 시 등록한다. **운영자 이름 지정은 N2 시작 조건**으로 사용자가 정한다.
- R의 기명 운영자는 기존 사이트 계정을 승계한다.
- CELL-A의 typed stop이 붙는 셀 OMX owner·관측 서비스의 상시 서비스화는 진행 중인 셀 작업(관제 PC 셀 서비스)과 함께 맞춘다. 서비스화 전에는 CELL-A 정지 경로의 실물 수용을 완료로 세지 않는다.

## 검증과 보고

이 문서는 배치 정의이며 설치·연결 수용 증거가 아니다. N2·N3의 증거는 해당 날짜의 검증 기록으로 남긴다. 이 결정의 변경(유닛 분할·자원 이동)은 이 문서를 고치는 것이 아니라 같은 절차로 새 배치 결정을 기록한다.

CE: 해당 없음 — 배치 정의 문서이며 장애 원인·복구를 새로 검증한 사례가 아니다.
