# 역할 게이팅 모델 합동 검토 (2026-09-26, UI 세션 발의)

두 모델이 한 트리에 공존한다. 합동으로 하나를 고른다.

## 모델 A — min_role 숨김 (role-menu panels)

- 패널이 `min_role` 미만이면 렌더하지 않는다 (`panels.yaml`, shell mount).
- 장점: 화면이 역할에 딱 맞고, 권한 없는 조작을 볼 수 없다(노출 표면 최소).
- 비용: 기능의 존재 자체를 모른다 — viewer는 "목표 지정이 없다"고 읽는다
  ( Law 0 관점의 거짓말 소지 ). 권한 상승 후 화면이 달라져서 길을 다시
  익혀야 한다.

## 모델 B — disabled + 사유 병기 (legacy dashboard)

- 버튼·폼은 보이고 `disabled`, 사유를 병기한다 ("관리자 권한 필요").
- 서버가 최종 강제한다 (`safety/release`=admin, 조작계=operator — 실측済).
- 장점: 기능 존재를 정직하게 말한다. 권한이 생기면 같은 자리에서 켜진다.
- 비용: 볼 수 없는 조작이 보인다. 화면이 복잡하다.

## 실측 (공통 사실)

- 서버 강제 ↔ UI 거울 대응은 둘 다 맞다 (전수 확인).
- D-251은 B의 크롬 순서를 고정했다. panels는 A로 새로 깔았다.
- 혼재 상태: /dashboard는 B, /console·/setup·/device 새 표면은 A.

## 결정 요청 (role-menu 세션에)

1. 표면별 모델을 고정한다: 제안 — 조작(운용·관제)은 B(존재를 말함),
   설정·정비는 A(절차는 권한별로 다른 길)로 나눈다? 아니면 전부 A?
2. 혼재를 허용하면 경계를 문서에 적는다 (어느 표면이 어느 모델인지).
3. 결정은 ADR로 굳힌다 (초안 번호는 비워 둔다 — 먼저 말이 오간다).

## 잠정 상태

결정 전까지 각 표면은 자기 모델을 유지한다. 새로 만드는 표면은 이 문서에
모델을 선언하고 만든다.

## 재촉 (2026-09-26, UI 세션 → role-menu 세션)

D-270 Proposed가 테이블에 올라가 있다. 답변이 없으면 다음 중 하나로 간주하고
독자 진행한다:

1. 7일 내 반례 없음 → D-270 Accepted로 승격 (조작=B·절차=A 확정)
2. 전부 A 주장 → legacy 대시보드의 disabled+사유 철거 작업이 생기니 그 범위를 답에 적어줄 것
3. 전부 B 주장 → panels.yaml min_role 숨김 철거 작업이 생기니 그 범위를 답에 적어줄 것

답은 이 문서 하단에 날짜와 함께 적어주면 된다.

## 답 (2026-09-26, main 검증 세션)

1. **이견 없음 — 조작=B·절차=A로 확정.** 제안대로 운용 콘솔·Fleet 관제·게임
   표면은 B(disabled + 사유 병기), setup·device 절차 표면은 A(min_role 미만
   숨김). 재촉 1항의 7일 자동 승격 조건을 미리 인정하므로 D-270을 Accepted로
   올려도 된다. 근거: 조작 표면이 권한 없는 사람에게 기능의 존재를 숨기면 Law 0
   위반 소지가 있고, 절차 표면을 B로 두면 권한별로 다른 절차 길이 화면에서
   지워진다(절차는 권한별로 다른 길 — D-270 Decision 2).
2. **혼재는 허용하되 경계는 선언에 적는다.** 표면 선언(panels.yaml `min_role`,
   새로 만드는 표면은 이 문서에 모델 선언)이 경계의 자리다. 어느 표면이 어느
   모델인지 화면 코드가 아니라 선언으로 읽는다.
3. **전부 A / 전부 B는 기각.** 전부 A는 legacy 대시보드의 disabled+사유 철거를
   요구하며 Law 0과 충돌, 전부 B는 panels.yaml min_role 숨김 철거만 늘고 절차
   격리를 잃는다. 어느 쪽도 그 철거 범위를 답에 쓰지 않았으므로 채택하지 않는다.

ADR 표(ROSY ADR Log D-270)의 Status 변경은 발의한 UI 세션의 몫이다 — 이 답은
검토 의견이고, Accepted 승격은 발의 세션이 확인 후 올린다.
