# 앱 이름·작업·책임 경계 정리 설계

날짜: 2026-10-16. 상태: 검토용 설계. 사용자 합의는 앱 이름을 유지하면서 책임을 선명하게 하는 방향이며, 이 문서는 구현·배포·현장 수용 완료를 뜻하지 않는다.

## 목적

사용자가 자기 작업에 맞는 앱을 고르고, 다른 앱으로 이동해도 대상 로봇·현장·현재 작업을 이해하게 한다. 유지보수자는 화면 소유, API 소유, 사실의 정본, 실행 권한, 완료 확인을 구별할 수 있어야 한다.

기준 소스: `436d52a55`. 기존 D-370·D-377·D-425·D-487·D-741·D-757과 현재 `shared/web/surfaces.yaml`, `docs/reference/platform-folder-responsibilities.md`를 출발점으로 삼는다. 과거 계획의 `src/`, `middleware/ui`, `operations/ui`는 새 이동 대상으로 재사용하지 않는다.

## 접근 방식

| 방식 | 효과와 비용 |
|---|---|
| 권장: 현재 앱·서버를 유지하고 업무별 소유·탐색·중복 조작을 단계적으로 정리 | 기존 사용자 경로를 유지하며 화면과 실제 권한을 함께 검증할 수 있다 |
| 설명과 문서만 정리 | 비용은 작지만 중복 조작과 잘못된 이동이 남는다 |
| 앱·패키지를 일괄 개명하고 재배치 | 이름은 맞출 수 있지만 설치·호환 변경이 늘고 업무 책임 정리와 섞인다 |

## 앱별 사용자 약속

| 표면 | 설명 | 소유 작업 | 연결할 작업 |
|---|---|---|---|
| Rosy Fleet | 현장 운영 | 현장 감시, 지도, Mission·개입, 등록·보정, 계정 관리 화면 | 로봇 상세는 Robot, 수동 운전은 Pilot |
| Rosy Robot | 한 대 관리 | 상세 상태, 로컬 작업 준비·조작, 영구 설정, 정비 | 직접 운전은 Pilot, 현장 작업 조정은 Fleet |
| Rosy Pilot | 직접 운전 | 조종 입력, 운전 영상, 현재 조종 세션과 세션별 설정·기록 | 영구 설정·정비는 Robot |
| Rosy Cam | 카메라 송신 | 캡처·송신, 물리 설치와 연결 상태 안내 | 현장 승인·좌표 보정은 Fleet 설치 |
| Rosy Learning | 학습 자료 검수 | 현재 자료·객체·픽셀 검수와 승인 결과 export | 학습·평가·활성화는 해당 pipeline owner |
| Face | 로봇 상태 표시 | 이름·표정·부팅·연결 상태 | 입력·명령 없음 |

설명은 안내·앱 선택 문맥에 사용한다. 모든 앱 바에 새 부제를 추가하라는 뜻은 아니다. D-741의 공통 셸 자리와 기존 접근성·반응형 규칙을 따른다.

Rosy Fleet의 내부 id `console`, URL, 아이콘은 D-487 예외를 유지한다. Rosy Learning은 현재 작업 화면 이름이며 별도 런처·PWA 등록을 이번에 만들지 않는다. Vision은 관측 서비스, Account는 공통 신원 기반으로 설명한다. Games·진단·시뮬 표면은 도구 분류와 현재 활성 상태를 유지한다.

## 작업과 권한

작업별로 `화면 → API → 상태 정본 → 실행 owner → 완료 증거 → 다른 소비자/이행 조건`을 기록한다. 설정 저장·등록·조종 등 같은 쓰기 절차는 한 owner에 둔다. 상태를 목적에 맞게 여러 화면에서 읽는 것은 허용한다.

Fleet의 현장 원장과 장치 실행 결과는 별개다. UI가 요청 응답만으로 물리 작업 성공을 표시하지 않는다. Pinky 최종 주행 명령은 CORE가, OMX 최종 팔 명령은 해당 로컬 owner가 소유한다. Cam·Vision·학습 도구에는 장치 실행 권한을 부여하지 않는다.

운용 표면은 자기 범위의 정지를 직접 제공한다. 앱 간 링크로 정지 버튼을 대체하지 않는다. 대상, 요청 접수, 로컬 래치, 물리 정지 증거를 구별하고 기존 e-stop과 취소의 의미를 유지한다.

## 탐색과 중복의 이행

Fleet 안의 운용·지도·설치·작업·계정은 같은 앱의 업무 영역이다. Robot은 기존 운용·작업 준비·설치 정비를 유지하며, 직접 운전 진입을 Pilot으로 모은다. Pilot web/PWA/Android는 동일 업무의 제공 방식이다.

다른 앱 이동은 기존의 신뢰된 대상 발견·등록 정보를 사용한다. 주소를 포트 산술로 추정하지 않는다. 대상이 없거나 신뢰되지 않았으면 이유와 복구 경로를 표시하고 임의 호스트로 이동하지 않는다. URL에 토큰을 싣지 않으며 앱 전환이 조종 좌석 획득·운동·Mission 재시작을 일으키지 않는다. Fleet 브라우저에 CORE 토큰을 보관하거나 장치 조작 API를 직접 호출하게 만들지 않는다.

`console.teleop`은 D-370의 이행 항목이다. Pilot `progress.md`에는 2026-10-05 사용자 실기 확인으로 DEVICE GO가 기록되어 있으므로 미수용으로 되돌리지 않는다. D-323 Validation의 항목과 대상 로봇·릴리스 증거를 대조해 해당 범위를 명시하고, 충족한 범위에서 링크 패널로 전환한다. 다른 장치나 OMX SIM의 증거로 범위를 확대하지 않는다. 증거가 부족한 대상만 예외로 남긴다.

## 공유와 기존 계획

디자인 토큰·기본 컴포넌트·통신 도구는 공유한다. CORE/Fleet 계약 해석, 인증 scope, 조종 세션, Mission 복구 판단은 각 owner에 둔다. 두 소비자가 실제로 쓰는 중복만 추출한다.

Account의 사람 신원은 하나이며 대상별 권한·앱 세션은 구별한다. 공통 로그인 구현은 `2026-10-14-rosy-account-completion.md`가 소유한다. 이번 계획은 진입·복귀·권한 안내의 연결과 검증을 맡는다. 인증 자동 갱신은 운동 자동 재개가 아니다.

소스 위치는 현재 `middleware/robot_ui`, `operations/site_ui`, `operations/overhead`, `learning/curation/perception`, `shared/web`을 따른다. 새 서버·프레임워크·폴더 트리나 API를 선행 생성하지 않는다.

## 수용 기준

1. 주요 사용자 작업마다 하나의 화면 owner와 실제 API·정본·실행·완료 확인 경로가 대응한다.
2. Fleet → Robot/Pilot, Robot → Pilot/정비 복귀가 대상을 유지하고 자격을 URL로 전달하지 않는다.
3. 쓰기 권한 부족·대상 미등록·통신 장애가 구별되고 연결 복구만으로 운동이 재개되지 않는다.
4. 중복 조종 제거는 대상별 기존 실기 증거와 새 이행 검증에 연결된다.
5. 관련 자산이 설치 산출물에서도 제공된다. SOURCE·브라우저·설치·DEVICE·FIELD 결과를 따로 기록한다.

실행 순서와 작업별 파일·검증은 [실행 계획](2026-10-16-app-role-clarity.md)에 둔다.
