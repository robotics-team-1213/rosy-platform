# AI·Fleet·CORE 메시지와 영상 관측 계획

근거: D-623, D-629, D-632, `ROSY API & Protocol Reference.md`. 순서는 조회 화면 → 실제 교환 증거 검증 → 필요한 미들웨어 계약 보완이다. 기존 REST·이벤트 저장소·사건 기록을 먼저 사용한다.

## 1. 먼저 보여줄 화면

공통 Fleet 머리의 알림 버튼에서 오른쪽 알림 창을 연다. 현재 개입, 관제 요청 결과와 연결 변화 메시지, AI·CORE 사건 근거로 가는 링크를 모은다. 상세 근거는 기록·근거 탭에서 출처별로 검토한다. 현재 개입과 비상 정지는 창 밖에 유지한다.

| 확인할 내용 | 기존 데이터와 화면 | 증거의 한계 |
|---|---|---|
| CORE 문제 문의 | `/api/fleet/state`, `/api/fleet/line-stuck`의 열린 사건과 `inquiry` | 상태 스냅샷이며 전체 전송 원문 기록이 아니다. |
| AI 판단과 Fleet 판정·CORE 응답 | 열린 사건의 `ai_facts`, `ai_proposal`; 기존 개입 상세 | 수락은 실행 완료가 아니다. 응답이 없으면 미확인이다. |
| 사건 당시 CORE·Fleet·AI | `GET /api/fleet/incidents`, `rosy.incident.v1`의 `evidence`, `actions` | AI 사실·카메라의 ±5초 시간 결합은 정확한 요청 상관을 증명하지 않는다. |
| CORE 이벤트 | `GET /api/fleet/events?after_id=&limit=`의 영속 `audit_id`, `event_id`, `seq` | event store가 없는 배포에는 경로 자체가 없다. 현 버전 알림창에 전체 이벤트 구독은 추가하지 않는다. |
| 현재 앞 카메라 | 열린 사건의 `line-stuck/evidence?live=true` | 출처·sequence·촬영 시각/나이 확인, 3초 만료 후 숨김; 종료 후 보존되지 않는다. |
| Rosy Cam 관측 | 기존 관측 영상과 사건의 `source_id`, `seq`, `captured_at` | 사건 당시 영상 파일을 영속 보관한다는 뜻이 아니다. |
| AI에 전달한 정확한 프롬프트 | AI VLM의 기록 `evidence.prompt`: id·sha256·text·calls | 모든 사건 보고에 이 정보가 포함된다는 보장은 없다. 상세 연결은 2단계에서 확인한다. |
| 관제 메시지 | 기존 브라우저 `log` | 해당 브라우저의 최근 요청 결과이며 서버 영속 받은편지함이 아니다. |

읽음은 UI 표시만 변경한다. 처리·거절·취소·완료는 실제 기존 응답과 후속 CORE 이벤트로 판단한다. 영상이 없거나 촬영 나이를 확인할 수 없으면 이유를 표시하고 이전 그림을 현재 영상처럼 유지하지 않는다.

## 2. 실제 증거 연결과 미들웨어 경계

1. 로봇 CORE는 센서·문제 문의·명령 수신 및 완료 결과의 원출처다. Fleet ingest가 기존 event identity와 payload를 검증하고 저장한다.
2. Fleet은 기존 AI case에 문맥과 영상 참조를 전달한다. AI 서비스는 모델·프롬프트·영상 출처·판단을 기록하고 Fleet으로 반환한다. AI는 로봇 credential이나 직접 명령 경로를 갖지 않는다.
3. Fleet은 판단 전달 기록과 CORE 응답을 구분한다. CORE가 최종 실행·정지 권한을 가진다. 화면 조회, 읽음, 근거 열람은 명령 경로를 호출하지 않는다.
4. 관측 데이터는 Fleet 기존 읽기 API에서 제공한다. 별도 메시지 broker나 신규 서비스부터 설치하지 않는다. 프론트에 credential·원본 인증 헤더·전체 설정을 노출하지 않는다.
5. 먼저 실제 사건 하나의 문의·AI 프롬프트·판단·Fleet 전달·CORE 수신·CORE 완료가 어느 저장소에 있는지 조사한다. 기존 식별자로 연결되는 단계와 시간으로만 추정되는 단계를 명확히 나눈다.
6. 정확한 상관이 불가능한 단계만 API/SRS/ADR 개정 대상으로 삼는다. 이후 페이지 커서·재연결 중복 제거·보관 한도·인증·영상 참조/만료 계약을 확정한 뒤 구현한다. 이 계획의 표를 새 외부 프로토콜로 사용하지 않는다.

## 3. 실행 순서와 완료 증거

- 이번 변경: 디자인 법칙·규격·관제 위계·알림 진입점·현재 개입/메시지 조회·기존 근거/영상 접근을 구현하고 커밋·원격 시험·머지한다.
- 조회 검증: 두 테마와 1920/1366/390/320px, 네 Fleet 문서 진입, 읽음 후 반복 폴링의 중복 없음, 새 메시지 증가, 키보드·포커스·무명령 열람·공통 48px 비상 정지를 확인한다.
- 설치본 검증: 정확한 CI SHA와 서명 배포 SHA를 확인하고 실제 Fleet의 AI/CORE 기록 몇 건을 조회한다. 로봇 오프라인이면 새 교환을 증명하지 못했다고 표시한다.
- 후속 계약 단계: 실제 교환 예시의 요청·영상·응답·완료 연결 누락을 목록화하고 API/SRS/ADR 및 최소 회귀 시험으로 보완한다. 로봇암은 기존 장치 식별·명령 종류·실행 결과 계약으로 같은 조회 흐름에 합류하며 바퀴 명령으로 해석하지 않는다.

소스·원격 시험·CI·설치본·새 로봇 교환·실물 수용은 각각 보고한다. 기존 과거 기록 조회를 새 실물 시험 성공으로 표현하지 않는다.
