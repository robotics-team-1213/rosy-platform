# 도메인 중립 플랫폼과 업무 앱 분할 실행계획

> **For agentic workers:** `superpowers:executing-plans`로 작업별 진행한다. 이 문서는 Proposed ADR의 후속 계획이다. 각 작업의 계약 검토가 끝난 범위만 구현하며 API·장치 권한을 계획만으로 개방하지 않는다.

**Goal:** 업무 앱이 공통 실행·공정·장치 기능을 재사용하도록 계약을 정하고, 변경을 독립적으로 검토·검증할 수 있는 단위로 나눈다.

**Architecture:** 앱은 업무 목적과 제약을 제시하고, 재사용 공정은 절차와 필요한 근거를 선언하며, Fleet은 실행 원장·admission·배정을 소유한다. World와 장치 owner의 관측·실행 권한을 유지한다. 기존 내장 앱·외부 앱·direct 호환 경로를 구분한다.

**Tech Stack:** 기존 Python·HTTP/JSON·pytest와 플랫폼 원격 시험 도구. 새 서비스·SDK·workflow 언어·배포 방식을 선행 도입하지 않는다.

**Spec:** [D-827](../adr/D-827-domain-neutral-platform-process-application-boundaries.md), [D-828](../adr/D-828-execution-acknowledgement-and-physical-milestones.md), [D-829](../adr/D-829-domain-intent-and-resource-admission-boundaries.md). 모두 Proposed이며 구현·장치 수용이 아니다.

## 실행 순서

`W0 지원 계약표 → W1 상태·근거 → W3 외부 앱 조회·요청 → W4 기존 소비자 호환`

`W0 → W2 자원 소유·admission`

`W1 + W2 + W3 → W5 도메인 앱의 첫 흐름 → W6 통합·단계별 수용`

W1과 W2는 W0 뒤에 독립적으로 진행할 수 있다. W3의 API envelope 변경이 필요하면 W1·W2의 입력 계약 검토를 기다린다. W4는 기존 소비자 저장소의 별도 변경이며 W5는 업무 앱 저장소의 변경이다. 단계별 저장소·분기·검증 SHA를 따로 기록한다.

## Global Constraints

- D-427·D-429의 소유·API 방향과 D-430의 장치 권한·단일 writer·정지 경계를 유지한다.
- API 지원 목록은 현행 SRS/API reference·스키마·실제 구현과 대조한다. 필요한 필드만 별도 계약 변경으로 선점·문서화한다.
- 기존 공정·receipt·goal-evidence·Mission 진행 투영을 우선 사용한다. 새 계약과 기존 같은 의미의 타입을 독립 정의하지 않는다.
- 업무 앱의 계획·예약은 승인·물리 관측·장치 실행 권한이 아니다. 불명 상태를 자동 해제하지 않는다.
- 기존 앱·직렬 실행·dispatch profile·실물 승인 규칙을 유지한다. 구조 변경과 활성화·배포 변경을 같은 작업으로 묶지 않는다.
- 제품 테스트는 커밋된 SHA를 기존 원격 runner로 검증한다. 실제 browser·모델·장치·현장 시험은 코드 계약 시험과 별도 근거다.
- 독립 착지 가능한 작업만 나누고 한 작업에서 caller·fixture·계약·시험을 함께 전환한다. 단일 작업이 15개 파일을 넘으면 다시 분할한다.

## Review Focus

1. 접수·유예가 물리 완료로 보이는 입력은 W1·W4에서 막는다.
2. 다른 시도·오래된 관측·재시작 결과는 W1에서 검증한다.
3. 만료된 예약과 미확인 물리 점유는 W2에서 구분한다.
4. 외부 앱이 내부 import·DB·ROS에 기대는 경우는 W3에서 검증한다.
5. 일반 CI에서 통합 시험이 전부 skip인데 성공으로 보이는 경우는 W6에서 거절한다.

## W0 — 계약 기준선과 책임표

**책임:** 플랫폼 계약 담당. 런타임 변경 없는 첫 문서 변경.

**파일:** 생성 `docs/reference/application-contract-support.md`; 이 계획과 세 ADR의 상태·참조를 함께 관리한다. 현행 `ROSY API & Protocol Reference.md`·`platform_parts.yaml`·D-822·D-657은 읽기 기준이다.

**입력 → 출력:** 현행 공개 계약·실제 route·인증·consumer → 외부 앱이 쓸 수 있는 API/버전/상태 의미/권한/현재 지원 환경의 표.

- [ ] 업무 요청, 작업 진행·근거 조회, 취소·정지, 장치/자원 가용성에 필요한 호출을 실제 producer–consumer 경로로 대조한다.
- [ ] 기존 지원, 어댑터로 해결, 새 계약 필요를 구분한다. Python 내부 포트를 공개 HTTP 지원으로 기록하지 않는다.
- [ ] 필요한 milestone과 자원 상태마다 생산자·원장·소비자·권한·유효성·복구 책임을 적는다. 공통 장부와 업무 장부의 중복 정본을 찾는다.
- [ ] 외부 앱 계약과 내장 Fleet 조립의 예외를 명시하고 D-827~829의 검토 결과를 기록한다. 미채택 세부 계약은 구현하지 않는다.
- [ ] 링크·현재 소스 참조·ADR 색인·lint를 검사한 뒤 문서 변경만 커밋한다.

**완료:** 다음 작업이 사용할 기존 타입·함수·route와 반드시 바꿔야 하는 계약이 식별돼 있다. 단순 문서 검사만을 위한 새 pytest는 만들지 않는다.

## W1 — 단계 상태와 물리 근거

**책임:** execution 계약·Fleet 원장 담당. 공통 순수 계산과 Fleet 접속 변경은 별도 커밋으로 나눌 수 있으나 의미 전환은 한 지원 버전으로 묶는다.

**대상 파일:** `operations/site_execution/src/rosy/execution/site/{workflow,goal_evidence}.py`, `operations/fleet/fleet/server/missions/mission_progress.py`; 기존 `operations/fleet/test/test_mission_progress.py`와 goal-evidence 시험. wire 변경이 필요한 경우 W0에서 선정한 소유 schema·API reference를 같은 변경에 포함한다.

**입력 → 출력:** 현재 작업·시도·receipt·관측 → 접수/진행/목표 확인의 의미가 구분되고 재연결 가능한 결과. 기존 `project_progress(data, *, now)` 인터페이스는 의미 변경 검토 전 유지한다.

- [ ] 기존 표현으로 요청 접수·동작 결과·목표 검증을 매핑하고, 공정별 필요한 중간 근거를 정의한다. 단순 하위 단계로 표현 가능한 경우 새 상태 타입을 만들지 않는다.
- [ ] 현재 시험에 접수만 성공, 동작 성공/목표 미확인, 중복, 과거 시도, stale 관측, 재연결·재시작 사례를 추가하고 원격에서 실패를 확인한다.
- [ ] 기존 identity·revision·cursor·freshness를 재사용해 필요한 투영/조회만 구현한다. 요청이나 예상 상태를 물리 결과로 바꾸지 않는다.
- [ ] 관련 schema·consumer·fixture를 같은 계약 버전으로 전환하고 W0 표를 갱신한다.
- [ ] 커밋 SHA를 고정해 관련 원격 시험과 기존 실패 비교를 수행한다.

**완료:** 접수/유예/과거 결과로 물리 완료나 다음 동작 허용이 생기지 않는다. 기존 소비자는 호환 계약으로 계속 동작한다.

## W2 — 자원 소유와 admission

**책임:** Fleet 조정·각 자원 owner 담당. 새 중앙 자원 서버를 만들지 않는다.

**대상 파일:** `operations/fleet/fleet/server/ledger/{action_claims,charge_policy_admission}.py`, `operations/fleet/fleet/server/rightofway/traffic_reservations.py`, `operations/site_execution/src/rosy/execution/site/charge_policy.py`와 기존 해당 시험. 첫 설계 표는 W0 문서에 작성한다.

**입력 → 출력:** 업무 제약·검증된 자원/관측·기존 claim → 실행 가능한 후보 또는 근거 있는 거절·대기. 이 결과는 장치 grant가 아니다.

- [ ] 장치·공간·충전 자리별 실제 점유·예약·해제·불명 복구의 현재 소유자를 적는다. 서로 다른 물리 조건을 단일 lease 만료로 합치지 않는다.
- [ ] 같은 자원 동시 요청, 부분 확보 뒤 실패, TTL 만료 뒤 실제 점유 지속, owner 재시작, 충전 미시작 사례의 기존 시험을 먼저 보강한다.
- [ ] 빠진 공통 가용성 검사만 현재 admission 경로에서 보완한다. 필요에 근거하지 않은 전역 최적화·분산 잠금·별도 scheduler는 만들지 않는다.
- [ ] 업무 우선순위는 앱 입력으로, 설치 제약과 검증된 비용은 프로필/근거로 유지한다. 검증되지 않은 배터리·경로 예산은 대기/차단으로 처리한다.
- [ ] 같은 커밋의 원격 시험으로 중복 배정 차단·기존 정지·직렬 제한 유지·일관된 실패 정리를 확인한다.

**완료:** 실제 점유가 불명인 자원을 다시 배정하지 않고, 앱 정책 변경에 플랫폼 코드 수정을 요구하지 않는다. 병렬 운행·자동 충전은 이 완료 조건에 포함하지 않는다.

## W3 — 외부 앱 소비 경계

**책임:** 공개 API·인증·Fleet 조립 담당.

**대상 파일:** W0에서 확인한 `operations/fleet/fleet/server`의 소유 route·schema·auth와 관련 HTTP 시험; `applications/fleet/gateway`는 기존 내장 조립 보존 대상이다. 새 범용 endpoint를 이 계획에서 미리 선언하지 않는다.

**입력 → 출력:** 지원 버전·인증·업무 제약을 가진 외부 요청 → 기존 admission을 거친 작업 identity·조회 가능한 결과 또는 명시적 거절.

- [ ] 외부 소비자가 설치해야 하는 것은 앱 의존성뿐임을 확인한다. 플랫폼 Python import·직접 DB·ROS 연결을 사용하지 않는 최소 HTTP 소비 시험을 만든다.
- [ ] 알 수 없는 capability/버전·권한 부족·중복 요청·상태 재연결·서버 재시작의 실패 시험을 먼저 확인한다.
- [ ] W0의 기존 route로 충족하면 문서와 consumer만 정비한다. 부족한 계약만 해당 owner에 추가하고 API reference·스키마·양 끝 fixture를 전환한다.
- [ ] 요청 가능한 action/profile/승인·장치 근거를 기존 registry와 결속한다. 임의 함수명·shell·Python·driver 호출을 외부 요청으로 노출하지 않는다.
- [ ] 기존 내장 Fleet·외부 HTTP 시험을 커밋 SHA 기준으로 원격 검증한다.

**완료:** 외부 앱이 내부 코드를 설치하지 않고 지원되는 범위의 작업과 결과를 사용한다. 내장 앱·설치 identity·공개 기존 경로가 보존된다.

## W4 — 기존 업무 앱 호환 전환

**책임:** 기존 업무 앱 저장소 담당. 플랫폼과 분리한 변경.

**입력 → 출력:** W1·W3의 고정 지원 버전 → 기존 앱의 동작을 보존하는 어댑터·fixture·통합 시험.

- [ ] 성공 반환에 논리 유예가 섞인 호출과 실제 물리 결과를 구분하고, 변경 전 동작을 시험으로 고정한다.
- [ ] 기존 업무 모델·장부를 공통 플랫폼에 이관하지 않는다. 어댑터 또는 명시적 하위 단계에서 새 결과 의미를 소비한다.
- [ ] 가짜·계약 fixture·설정의 SHA를 함께 갱신하고 실제 고정 버전 서버와 통합 시험한다. fixture를 바꿔 가짜에 맞추지 않는다.
- [ ] 기존 direct 시연 경로·승인·정지·이동 한정 재시도를 유지한다. 새 경로 활성화는 별도 변경으로 한다.

**완료:** 기존 업무와 새 외부 앱 계약이 함께 검증되고, 공통화 때문에 기존 데이터 변환이나 전면 재작성을 요구하지 않는다.

## W5 — 첫 도메인 앱 흐름

**책임:** 업무 앱 담당. 구체 장비·업무 전략·데이터 모델·파일 경로는 해당 앱 저장소의 비공개 계획이 소유한다.

**입력 → 출력:** 합의된 업무 시나리오와 W1~3의 지원 계약 → 목표·제약을 요청하고 검증된 결과로 업무 장부를 갱신하는 첫 흐름.

- [ ] 업무 개체·작업계획 버전·선후관계·완료 조건을 앱에 두고, 공통 코드에 업무별 이름·정책 분기를 추가하지 않는다.
- [ ] 순수 업무 정책을 정상·대안 불가·오래된 관측·중복 지시로 검증한 뒤 HTTP 어댑터를 연결한다.
- [ ] 장치 identity는 배치와 후보 제약으로 주고, 플랫폼 가용성 판단과 실제 owner의 실행 검사를 건너뛰지 않는다.
- [ ] 하나의 정상 흐름과 중간 실패·정지·복구를 합성/시뮬 환경에서 끝까지 검증한다.

**완료:** 업무 정책만 바꾸어도 플랫폼 코드가 바뀌지 않고, 앱이 내부 DB/import 없이 자기 업무 장부와 실행 근거를 연결한다.

## W6 — 재현·기준선·단계별 수용

**책임:** 각 저장소 검증 담당. 하나의 거대한 착지 분기로 합치지 않는다.

- [ ] 플랫폼·공정·앱별 전체 SHA·계약 버전·아티팩트 digest와 각각의 시험 결과를 기록한다.
- [ ] 전용 통합 job은 고정 서버 버전으로 실행하고 시험 미수집·전체 skip을 실패로 처리한다. 일반 단위 시험과 구분한다.
- [ ] 기존 업무 회귀·새 업무 정상/실패/재연결·자원 경합을 따로 확인한다. browser·모델·실물 결과를 pytest 통과로 대신하지 않는다.
- [ ] 미확인 자동 기능은 비활성 상태로 유지하고 실물·현장 수용은 기존 승인·설치 관문으로 별도 진행한다.

**완료:** 각 변경이 개별 검토·착지·복구 가능하고 어느 SHA의 어떤 범위가 통과했는지 재구성할 수 있다.

## 실행 기록과 범위

계획 작성 시 플랫폼 기준 HEAD는 `45b2bfe064`였다. 구현 전에 실제 HEAD와 계약을 다시 확인한다. 이 변경은 ADR·계획·색인·거버넌스 기록만 작성하며 제품 코드·wire schema·capability·운영 설정은 변경하지 않는다. 시험 결과와 문서 검사 결과는 별도로 기록한다.

2026-10-21 후속 W0: `afa2d0373e`의 실제 route·원장·공정 경계를 [지원 계약표](../reference/application-contract-support.md)에 기록했다. 기존 계약과 앱 내부 정책으로 해결할 범위, 후보 배정·물리 근거의 후속 계약을 구분했다. W1~W3의 제품 변경과 실물 활성화는 아직 완료하지 않았다.
