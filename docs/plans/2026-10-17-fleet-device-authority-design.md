# 기기·실행 호스트·담당 Fleet 분리 설계

**상태:** 설계 검토 대기. 목표와 책임 분담은 사용자와 합의했다. 이 문서는 구현·운영 계약의 변경이나 실물 활성화를 선언하지 않는다.
**기준:** 2026-10-17, 로컬 main SHA `a458f7ec98d0bfbefbe73faf06840a1eb8eb5767`.
**작업 브랜치:** `docs/fleet-device-authority`.

## 1. 목표와 완료 조건

기존 관제의 기기 연결을 재사용하여, 실행 PC 배치와 관계없이 지정된 Fleet이 기기의 작업을 지휘한다. 각 기기의 로컬 제어기는 최종 실행·안전 판단을 유지한다. 사용자는 팔 세 대를 각각 PC에 연결하거나, 둘 이상을 한 PC에서 양손 작업에 사용하는 배치를 선택할 수 있어야 한다.

전체 구현의 완료 조건은 다음과 같다.

1. 기기·실행 호스트·담당 Fleet·작업대 구성을 별도로 식별한다. 호스트 주소와 컨테이너 이름이 기기 신원이 되지 않는다.
2. 한 호스트에 여러 팔을 등록할 수 있고, 같은 팔의 활성 실행 인스턴스 중복은 거절한다.
3. 관제는 발견·등록·담당 지정·연결·실행 가능·작업 실행을 구별해 보여준다.
4. 장치의 명령 수용 경계가 담당 Fleet과 유효한 권한 버전을 검증한다. 다른 Fleet과 이전 권한의 요청은 거절한다.
5. 진행 중 작업과 불명확한 실행 결과를 확인하지 않고 다른 Fleet이나 호스트로 넘기지 않는다. 연결 상실로 자동 인계하지 않는다.
6. 같은 호스트와 다른 호스트의 연결 모두 같은 작업 수용·중복 처리·결과 의미를 지킨다.
7. 아래 검증 표의 소스·원격 회귀를 통과한다. 실물 성능·정지·동시 작업 수용은 별도 증거로 남긴다.

## 3. 식별과 정본

아래 이름은 설계 개념이다. 새 공개 필드·경로·오류 코드의 확정은 해당 구현 단계의 SRS·API reference·ADR 변경에서 한다.

| 개념 | 책임과 수명 |
|---|---|
| 기기 | 독립 실행·정지 경계. Pinky의 기존 robot ID와 팔 신원을 각각 보존한다. 팔을 작업대에 묶거나 다른 PC로 옮겨도 신원을 바꾸지 않는다 |
| 실행 호스트 | 제어 프로그램이 실행되는 PC의 승인된 논리 신원. IP는 교체 가능한 연결 정보다 |
| 실행 인스턴스 | 특정 기기를 실제로 제어하는 프로세스의 승인된 설치 단위. 한 호스트가 여러 인스턴스를 가질 수 있다 |
| Fleet | 사이트 계정 권한과 구분되는 작업 지휘 서비스의 논리 신원. 재시작해도 유지하고 주소로 식별하지 않는다. 승인된 백업 PC로 옮길 때도 동시 실행을 허용하지 않는다 |
| 담당 지정 | 기기, 실행 호스트·인스턴스, 담당 Fleet, 권한 버전, 지정 상태를 묶는다. 장치의 명령 수용 경계가 영속 정본을 가지며 Fleet의 목록은 이를 확인한 투영이다 |
| 작업대 | 함께 작업할 팔·좌표계·공유 구역·보정·조율자 구성을 묶는다. 기기나 호스트 신원과 동일시하지 않는다 |

담당 지정 버전은 기기별로 증가하며 기존 `authority_epoch`·`dispatch_generation`과 구별한다. 서로 다른 Fleet에서 같은 epoch 숫자를 쓴다고 같은 권한이 되지 않는다. 명령은 담당 지정과 기존 dispatch fence를 모두 만족해야 한다.

담당 지정 정본을 두 Fleet의 SQLite에 각각 기록하는 것으로 독점성을 구현하지 않는다. 같은 기기의 명령을 받는 하나의 로컬 수용 경계가 비교 후 갱신을 직렬화한다. 교체된 호스트의 과거 프로세스가 물리 장치를 계속 소유할 수 있는 상태에서는 새 인스턴스를 활성화하지 않는다.

기존 설치 인벤토리의 Workcell 행과 새 협업 작업대는 같은 개념으로 합치지 않는다. 기존 행의 ID·소켓 경로·journal 상관관계를 보존하고, 그 행이 가리키는 개별 기기·인스턴스를 협업 그룹의 구성원으로 참조한다. 이행 계약이 없는 상태에서 기존 `workcell_id`를 양팔 그룹 ID로 바꾸지 않는다. 설치 파일은 배치의 출처이며, 장치가 실제 연결되어 있고 독점 소유됐다는 런타임 증거는 아니다.

## 4. 제어권과 자격

- Fleet은 작업 배정·승인·grant·lease를 맡고, CORE와 팔 owner는 최종 명령 및 현재 장치 조건 검증을 맡는다.
- 기명 운영자 자격, Fleet 서비스 자격, registry 읽기 자격, 장치별 실행 자격은 구분한다(D-302). Fleet 이름 문자열이나 UI 선택만으로 권한을 얻지 않는다.
- 지정할 Fleet의 논리 신원은 승인된 서비스 자격에 결속한다. 원격 호스트가 전달한 자기 주장 ID만으로 수용하지 않는다.
- 같은 Fleet의 논리 ID나 일반 등록 자격을 복사한 두 PC에 각각 유효한 실행 세션을 주지 않는다. 장치 측은 담당 Fleet의 현재 승인 실행 세션을 하나만 유지하고 승인 실행 호스트 및 세션 세대를 검증한다. 일반 Fleet 로그인만으로 기존 실행 세션을 교체하지 않는다. 재시작·백업 PC 전환은 이전 세션을 무효화하고 미확정 작업을 확인한 뒤 새 세션을 승인한다. Fleet 논리 신원은 이 과정에서 유지된다.
- 이 독점성은 승인 주체·세션 검증의 보장이다. 활성 세션의 비밀과 호스트 실행 상태까지 탈취·복제한 두 컴퓨터를 문자열 ID나 bearer 값만으로 구별할 수 있다고 주장하지 않는다. 실행 자격은 설치 이미지와 분리하고 호스트별로 발급·회수하며, 침해 시 현장 정지와 기명 복구를 적용한다. 비밀 복제 자체에도 견디는 물리 호스트 증명이 필요해지면 별도 하드웨어 신뢰 계약을 추가한다.
- 실행 요청의 수용·재시도·phase 진행 시 담당 지정 버전과 기존 dispatch fence를 확인한다. 진행 중 권한이 회수되면 기존 정지·HOLD 경로를 적용한다.
- 담당 지정 회수와 driver 제출은 같은 장치 측 배타 경계로 직렬화한다. journal 준비·capability 조회 뒤 실제 driver 호출 직전에 지정·세션을 다시 검사하고, driver 호출과 수락 기록을 기존 stop fence 안에 둔다. 제출이 먼저 완료됐으면 인계가 그 Action을 찾아 정지·결과 확인을 해야 하고, 회수가 먼저 완료됐으면 그 제출을 거절해야 한다.
- 로컬 정비·Pilot·학습 수집은 기존 owner와 같은 seat·장치 점유 규칙을 따른다. 담당 Fleet 지정을 우회하는 두 번째 writer를 만들지 않는다.
- 작업 지휘권은 안전 정지의 유일한 권한을 뜻하지 않는다. 기존 물리 정지, 로컬 운영자 정지, 승인된 작업대 조율자의 결합 정지는 유지한다. 정지 권한이 재무장·복구 권한으로 이어지지 않는다.
- 현재 허브 페어링에 관한 D-555의 수용된 신뢰 한계를 숨기지 않는다. 이 설계는 기존 등록 보안을 조용히 바꾸지 않으며, 그 자격만으로 새 독점 명령 권한을 증명했다고 표시하지 않는다.

## 5. 지정과 인계

담당 지정 상태는 미지정, 지정 준비, 지정됨, 인계 차단으로 구분한다. 이는 기존 로봇 모드나 Action 상태를 대체하지 않는 별도 관리 상태다.

### 최초 지정

1. 기명 관리자가 기존 승인 흐름을 통해 기기와 실행 인스턴스의 신원·장치 연결을 확인한다. 발견 결과만으로 지정하지 않는다.
2. 장치 측이 미지정 상태, 다른 제어 인스턴스 부재, 진행 중·미확정 작업 부재를 확인한다.
3. 기대한 이전 버전과 비교하여 담당 Fleet 및 새 권한 버전을 영속 기록한다. 동시 지정 요청 중 하나만 성공한다.
4. Fleet은 장치 측 readback과 자격 결속을 확인한 뒤 담당 지정 완료를 표시한다. 아직 실물 동작 수용이 없는 기기는 계속 실행 불가로 표시한다.

### 다른 Fleet으로 인계

1. 이전 Fleet과 장치 측에서 새 작업 접수를 차단한다.
2. 진행 중 작업을 종료·취소하고, 실제 정지 결과와 미확정 Action·claim을 확인한다. 요청 전송 성공을 정지 증거로 쓰지 않는다.
3. 장치 측에서 기존 지정과 실행 자격을 회수하고 권한 버전을 증가시킨다. 기존 연결과 지연 요청은 더 이상 유효하지 않다.
4. 새 Fleet 자격을 승인하고 장치 측 readback을 맞춘다. 명시적 복구·재무장 절차 전까지 정지를 유지한다.
5. 인계한 사람, 이전·새 Fleet, 기기·호스트·인스턴스, 권한 버전, 정지 근거, 결과를 원장에 남긴다. 비밀 자격은 기록하지 않는다.

이전 Fleet이 오프라인이면 인계를 완료로 간주하지 않는다. 로컬 기명 복구 절차에서 실제 정지·이전 자격 무효화·잔여 작업 확인을 마친 뒤 진행한다. 시간 초과나 네트워크 단절만으로 소유권을 넘기지 않는다.

호스트 교체도 같은 인계 절차를 적용한다. 장치의 영속 담당 정보와 인계 기록을 복구할 수 없거나 과거 버전으로 되돌아간 경우, 설치 기본값으로 다시 승인하지 않고 인계 차단으로 시작한다. 이전 실행기의 물리 장치 접근 철회와 새로운 배치를 사람이 확인한다.

작업대 구성 변경과 협업 팔의 인계는 관련 작업·barrier·claim이 모두 정리된 뒤에만 허용한다. 여러 팔을 한 번에 지정하는 중 일부만 성공하면 협업 실행을 열지 않고, 확정된 각 팔의 상태를 그대로 표시한다. 다른 Fleet에 속한 팔을 한 협업 작업으로 실행하지 않는다.

## 6. 같은 PC와 원격 PC의 연결

같은 PC에서는 기존 Unix socket과 서비스 peer 검증을 유지한다. 다른 PC에는 실행 호스트의 제한된 인증 게이트웨이를 두고, 승인된 기기별 owner로만 전달한다. 게이트웨이는 grant·lease를 새로 발급하거나 관절 명령을 직접 만들지 않는다.

원격 경계는 다음을 계약으로 확정한 후 구현한다.

- HTTPS 서버 신원 검증과 명시적으로 승인된 Fleet 서비스 자격. 승인된 endpoint만 사용하고 redirect·발견 주소로 자동 우회하지 않는다.
- 기기·호스트·인스턴스·담당 Fleet·지정 버전의 일치 검증. 단일 gateway UID로 여러 Fleet의 요청을 모두 같은 주체로 취급하지 않는다.
- 유한 요청 크기와 timeout, 기존 grant/receipt·correlation·중복 처리 의미 보존. 수락 응답 유실 시 움직이는 요청을 무조건 재전송하지 않고 기존 Action 조회로 확인한다.
- 지속 동작은 장치 측에서 확인하는 유한 연결·lease 유효성에 묶는다. 연결 상실의 감지 한계와 HOLD 적용 시점은 해당 장치 계약에서 정하고 시험한다. 관제 화면의 online 표시를 정지 보장으로 쓰지 않는다.
- gateway 장애·owner 재시작 뒤 기본 HOLD, 미확정 실행 확인, 명시적 복구. 수집 도구와 owner의 기존 배타 점유도 유지한다.

원격 경로가 준비되기 전에는 같은 호스트 구성만 실행 가능으로 표시한다. UDS를 네트워크에 노출하거나 SSH 터널을 운영 제어 계약으로 대신하지 않는다.

## 7. 배포와 작업 구성

| 배치 | 목록과 제어 의미 |
|---|---|
| PC 세 대, 팔 세 대 | 세 기기·세 호스트·세 인스턴스를 같은 Fleet에 지정 |
| PC 한 대, 독립 팔 세 대 | 세 기기·한 호스트·세 인스턴스. serial·카메라·ROS graph·상태 DB를 개별로 배정 |
| PC 한 대의 양팔 + 다른 PC의 단독 팔 | 세 기기를 유지하고 두 팔만 같은 작업대로 묶음. D-778·D-780의 같은 호스트 조율 조건을 유지 |

3대 이상의 협업 동기화는 기존 양팔 계약의 범위 밖이다. 세 기기 등록을 삼중 팔 협업 지원으로 표시하지 않는다. 해당 시나리오가 필요할 때 조율 계약과 검증을 확장한다.

Fleet 컨테이너와 팔별 native systemd 실행이라는 D-246·D-281·D-785의 경계를 유지한다. 같은 설치 산출물 버전을 여러 PC에 배포하고, 기기 신원·장치 연결·보정·자격·담당 지정은 인스턴스별 영속 설정으로 둔다. 이미지에 비밀이나 승인 상태를 굽지 않는다. 이미지 복제·재시작만으로 실행 자격이나 제어권을 얻지 않는다.

Docker 실물 제어 채택은 별도 배포 결정과 장치 수용을 요구한다. 이번 목표는 PC 수와 무관한 제어권 계약이며, 운영 팔을 컨테이너로 옮기는 것을 선행 조건으로 삼지 않는다.

## 8. 구현 단위와 완료 증거

이 표는 설계의 경계를 정한다. 파일별 실행 계획은 설계 검토 후 별도로 작성한다.

| 단위 | 변경 책임 | 끝난 기준 |
|---|---|---|
| A 등록·배치 읽기 | Fleet의 기존 registry/roster, OMX host inventory와 instance 설정을 출처가 있는 공통 읽기로 투영. contracts는 기기·호스트·인스턴스·Fleet 신원과 담당 상태 shape 소유 | 3가지 PC 배치 표현, 중복 장치·인스턴스·장치 포트 거절. 기존 Workcell 행·Action 상관관계 보존. 읽기 결과가 실행 권한을 생성하지 않음 |
| B 장치별 담당 지정 | 장치 측 영속 지정 원장과 비교 후 갱신, 승인된 Fleet 자격 결속, 지정·회수·인계. Fleet은 관리 요청과 투영 담당 | 서로 다른 Fleet의 동시 지정 중 하나만 성공. 오래된 요청·잘못된 Fleet·인계 도중 요청·재시작·DB 손실을 거절. 첫 통합 대상은 no-goal OMX |
| C 원격 실행 호스트 | 제한된 gateway와 Fleet transport를 기존 owner 포트에 연결. 임의 ROS/serial 제어 endpoint 없음 | 두 호스트에서 인증·조회·정지·응답 유실·단절 시험. 시뮬레이션 Action 계약을 확인한 뒤 실물 no-goal 조회·정지 연결을 별도로 검증 |
| D 관제 화면 | 기존 기기 연결 흐름에서 담당 Fleet·실행 호스트·협업 구성·차단 이유 표시 | viewer 읽기/관리자 변경 구분, 기명 인계·부분 실패·미확정 상태 브라우저 회귀 |
| E 실물 수용 | 각 기기의 실제 정지·복구 및 공유 호스트 동시 부하 확인 | 별도 승인한 장치 시험과 증거. 동작 목표 허용은 D-785 및 기존 장치 게이트 이후 |

새 공개 타입·경로·버전은 각 단위 시작 전 SRS·API reference·ADR에서 선점·정의한다. 이 문서의 개념 이름을 구현에 임의로 넣지 않는다. 안전 경로 변경은 D-430 독립 Safety-Review를 받는다.

## 9. 검증 표

| 상황 | 필요한 관측 |
|---|---|
| Fleet A 담당 기기에 B가 실행·재무장 요청 | 장치 수용 경계에서 거절, 동작/재무장 없음 |
| A와 B가 같은 이전 버전으로 동시 지정 | 영속 정본에 하나만 성공, 나머지는 충돌. 두 성공 응답 없음 |
| 같은 Fleet 논리 ID·일반 등록 자격으로 두 PC가 세션 요청 | 현재 승인 실행 호스트·세션 하나만 유효. 로그인만으로 기존 세션 교체 불가. 이전 세션의 요청은 거절하고 재시작으로 미확정 작업을 자동 재개하지 않음 |
| journal 준비와 driver 제출 사이에 담당 지정 회수 | 기존 stop fence와 같은 배타 경계에서 회수/제출 순서가 결정됨. 회수 이후 목표 제출 없음, 앞서 수락된 Action은 인계 정지 확인에 포함 |
| 인계 뒤 A의 지연 요청 또는 이전 자격 재사용 | 버전·주체 검사 거절. 새 Fleet과 같은 dispatch 숫자여도 거절 |
| 인계 중 timeout, Fleet/owner/gateway 재시작 | 지정·정지 상태 영속. 자동 재개·자동 권한 인계 없음 |
| 작업 실행·UNKNOWN 결과·협업 barrier 중 인계 | 차단 사유와 근거 표시. 미확정 claim을 timeout만으로 해제하지 않음 |
| 같은 PC의 여러 팔 | 각 serial·카메라·ROS namespace/domain·DB·소켓의 소유권 분리. 한 팔의 요청이 다른 팔에 전달되지 않음 |
| 기존 설치 인벤토리를 양팔 그룹 읽기로 이행 | 기존 Workcell 행·소켓·journal ID 보존. 한 팔의 과거 Action을 그룹 또는 짝 팔의 Action으로 잘못 읽지 않음 |
| 호스트 이동·DB 복원·설치 이미지 복제 | 이전 인스턴스와 stale 자격 차단, 권한 버전 rollback을 정상으로 수용하지 않음 |
| 두 팔 중 한 팔만 지정·연결·수락 성공 | 개별 상태 표시, 협업 시작 차단. 한 팔만 실행되는 협업을 만들지 않음 |
| 원격 인증 실패·잘못된 endpoint·응답 유실·연결 상실 | 우회 연결·새 목표 재전송 없음. 조회·HOLD·복구의 계약 결과 확인 |
| 비담당 Fleet 요청 차단 중 로컬/조율자 정지 | 기존 정지 경로 유효. 정지 주체가 재무장 권한을 얻지 않음 |

pytest는 커밋된 revision을 `tools/remote/remote_pytest.py`로 보내고 `test/known_failures.py`와 비교한다. 노트북 pytest는 실행하지 않는다. 브라우저·시뮬·장치 시험은 각각 별도 실행과 증거를 남긴다. 소스 시험 통과를 실제 정지나 성능 증거로 쓰지 않는다.

## 10. 기존 결정과의 관계

| 결정 | 관계 |
|---|---|
| D-427 | 새 최상위 폴더를 만들지 않는다. 현장 조정·장치 실행·설치 역할 안에서 구현 |

## 11. 이번 산출물의 검토 기준

설계 검토에서는 (1) 기기와 호스트를 별도로 유지하는지, (2) 지정 Fleet의 권한을 장치 측에서 검증하는지, (3) 양팔 구성과 인계 실패에서 부분 실행이 열리지 않는지, (4) 기존 등록·정지·로컬 writer를 보존하는지를 확인한다. 검토 후 단위 A부터 실행 계획을 작성한다. 이 문서만으로 제품 코드·실물 설정·제어권·운영 배치를 변경하지 않는다.
