# 독립·상하위 관제 최종 목표와 상세 설계

작성일: 2026-10-23. 기준 코드: ROSY Platform 로컬 main `a1d103b9f3`.

**상태:** D-850은 Accepted 구조 목표이며, [D-851](../adr/D-851-control-unit-delegation-and-recovery.md)은 세부 계약의 Proposed 설계다. 독립 검토를 마친 기본안을 기록한다. 새 API·실행 정책·장치 수용을 개방하지 않으며 기존 ADR·SRS·안전 계약은 계속 유효하다.

**다음 행동:** D-851의 세부 결정과 공개 위임 API·인증 결속·영속 transaction 경계를 확정한 뒤 P1부터 구현한다. 기존 [후속 목표](2026-10-23-composable-control-goals.md)의 G1–G5와 이 문서 P0–P5를 함께 읽는다. 독립·상하위·중첩 구성의 최종 목표와 세부 설계는 이 문서 한 곳에서 관리한다.

## 최종 목표

각 관제가 자기 범위의 업무·자원·실행 이력을 책임지고 독립 운영하면서, 필요하면 하위 관제를 포함하거나 상위에는 하나의 서브 관제로 참여한다. 상위가 없어도 승인된 독립 구성이 성립하며, 상하위 연결이 생겨도 장치 실행 권한과 안전 책임은 기존 소유자에게 남는다.

최종 수용은 다음 세 구성을 같은 책임·위임 계약으로 운영하는 것이다.

| 구성 | 확인할 결과 |
|---|---|
| 독립 A | 상위 서비스 없이 A가 자기 범위의 승인된 작업을 접수·조정·조회한다. |
| 상위 R와 하위 A·B | R이 업무를 A 또는 B에 위임하고 각 하위가 자기 원장·자원·실행 조건으로 접수·조정한다. |
| 중첩 R → A → A1, R → B | A가 A1을 조정하면서 R에는 하나의 서브 관제로 참여한다. R이 A1의 원장·장치를 직접 쓰지 않는다. |

기능 수용과 실제 장치·현장 수용은 분리한다. 문서 병합, 합성 결과, 요청 접수만으로 업무 완료를 주장하지 않는다.

## 접근 선택과 첫 범위

| 접근 | 판단 |
|---|---|
| 중앙 원장 하나에 모든 관제를 연결 | 중앙 장애와 독립 운영이 결합된다. 선택하지 않는다. |
| 관제 간 동등 연결과 자유로운 교차 실행 | 동일 자원·업무의 소유와 권한 회수 처리가 복잡해진다. 첫 범위에서 선택하지 않는다. |
| 각 관제가 자기 원장을 가진 상하위 트리 | D-850의 독립·중첩 구성을 표현하며 기존 실행 소유자를 유지할 수 있어 기본안으로 선택한다. |

첫 범위는 **동일 현장 LAN에서 서로 겹치지 않는 자원을 가진 관제들**이다. 한 업무의 첫 위임은 하위 한 곳에 맡긴다. 여러 관제에 걸친 동시 예약·자동 보상·전역 최적화·관제 이중화·WAN 다중 현장은 첫 구현에 포함하지 않는다. 업무별 순차 위임과 중첩 경계는 검증하되, 장치·공간을 여러 소유자가 함께 점유하는 자동 교차 공정은 후속 설계가 필요하다.

## 1. 관제 경계와 구성

각 관제는 고정된 관제 식별자, 직접 소유 자원, 허용 업무 종류, 부모·자식 관계와 구성 revision을 가진다. 이것은 논리 정보 목록이며 새 wire 필드 이름은 아니다.

- 직접 소유 장치와 물리 공간의 실행 소유자는 배치 전체에서 하나다. 상위가 하위 자원을 집계해서 보는 것은 직접 소유가 아니다.
- 한 구성 revision에서 부모는 0개 또는 1개다. 부모가 없으면 독립 루트다. 자기 자신·조상·같은 자원의 중복 직접 소유 등록을 거절한다.
- 첫 설치 검증은 3개 관제 수준(루트·서브·서브의 하위)까지다. 개념은 더 깊은 트리를 배제하지 않지만 수용되지 않은 깊이는 활성화하지 않는다.
- 첫 버전은 운영자가 검토한 전체 구성 manifest로 중복 소유·순환·깊이를 검사한다. 동적 전역 레지스트리나 자동 발견 후 실행 권한 부여를 만들지 않는다.
- 양 끝이 상대 신원과 동일 구성 revision을 확인한 관계만 위임에 사용한다. manifest가 다르거나 자원 소유가 충돌하면 해당 경로의 신규 위임을 막고 불일치를 표시한다.
- 재부모화·분리·자원 이관은 신규 업무를 막고 미완료·불명 작업과 점유를 대조한 뒤 양쪽 권한을 명시적으로 갱신한다. 불명 작업이 남으면 자동 이관하지 않는다. 링크 단절은 이관 사유나 단독 실행 권한이 아니다.

독립 구성과 상하위 구성을 서로 다른 제품으로 만들지 않는다. 동일 논리 단위에 승인된 관계와 범위를 적용한다.

## 2. 상태와 업무 완료의 소유권

| 정보 | 정본 소유자 | 상위가 보관할 것 |
|---|---|---|
| 고객·화물·재고 등 업무 의미와 최종 업무 완료 | 해당 업무 앱의 장부 | 앱 업무 ID와 결과·근거 참조 |
| 관제 간 업무 위임과 집계 진행 | 위임을 발행한 관제 | 자기 위임 기록, 하위 작업의 식별·revision·관측 시각과 조회 결과 |
| 하위에서 접수한 실행 작업·admission·점유 | 접수한 하위의 기존 Fleet transaction·원장 | 읽기 전용 결과 투영과 그 출처 |
| 장치 Action·현재 동작·정지 결과 | 해당 CORE 또는 OMX owner | 장치 owner가 낸 receipt·시도 식별의 참조 |
| 현재 관측·위치 | 해당 범위의 World·승인된 관측 생산자 | 출처·시각·revision이 붙은 관측 |

상위 원장은 하위 원장의 복제 writer가 아니다. 상위는 자기 위임의 진행 상태를 쓰고 하위 실행 상태는 출처를 붙여 투영한다. 도메인 업무의 성공 판정은 앱에 남긴다. 완료에는 작업·시도·계획 revision과 필요한 독립 물리 근거를 연결하며, receipt 성공만으로 화물 안착·퇴피를 확정하지 않는다(D-836).

## 3. 위임 접수와 중복 방지

아래는 목표 의미다. 기존 API에 없는 공통 위임 경로와 직렬화 필드는 별도 계약 변경으로 등록해야 한다.

1. 상위는 자기 업무 기록에 하위 대상·의도·제약과 고정된 요청 식별을 먼저 영속화한다. 시도 전 기록이 없으면 전송하지 않는다.
2. 하위는 인증 주체·직접 부모 관계·구성 revision·위임 허용 범위·업무 본문을 검증한다. 상위의 가용성 조회나 배정 제안은 하위 admission을 대체하지 않는다.
3. 논리 위임 식별은 발행 관제와 최초 위임 때 고정하며 관계 세대·구성 revision·재시작·재전송으로 바꾸지 않는다. 하위는 같은 발행 관제·논리 위임 식별에 같은 본문이 오면 같은 접수 결과와 작업을 반환하고 다른 본문이면 충돌로 거절한다. 인증 주체와 최초 관계 세대·본문도 보존한다. 현재 관계·권한 검증은 별도로 수행하며 과거 관계 요청은 새 접수로 바꾸지 않는다. 요청 식별은 자원 실행 시도 식별과 구분한다.
4. 영속 중복 방지 기록·접수 작업의 결합과 동시 요청 직렬화를 같은 transaction으로 보장해야 한다. 기존 소유 경로의 claim·admission을 유지하며, 새 공통 transaction이 필요한 경우 구현 전 설계한다. 상위 영속 기록 후 응답 유실·하위 재시작에서도 같은 요청을 재조회한다.
5. 상위는 응답 유실·시간 초과를 실패로 확정하거나 다른 하위로 재배정하지 않는다. 같은 식별로 조회·재전달한다. 접수 여부와 물리 점유가 불명인 동안 새 실행을 열지 않는다.
6. 완료·취소 뒤 같은 요청을 다시 받아도 재실행하지 않는다. 중복 방지 식별과 본문 digest·결과 참조는 작업/감사 보존 기간 동안 유지하며, 자동 만료로 같은 요청을 새 실행으로 해석하지 않는다. 첫 버전은 이 식별의 자동 삭제·재사용을 지원하지 않는다.
7. 실제 새 실행은 새 의도·새 요청 식별·별도 승인과 admission을 거친다. 관계 세대나 서비스 자격증명 교체는 새 의도가 아니다. 이미 접수된 업무를 다른 하위에 맡기는 것은 기존 작업의 종단·점유 해제 증거 확인 후 새 위임으로 기록한다. 자동 재전송이 새 key를 만들거나 최초 관계 세대를 현재 값으로 바꾸지 못하게 한다.

네트워크에서 정확히 한 번 전달을 주장하지 않는다. 반복 전달과 영속 중복 방지, 실행 소유자의 claim으로 중복 실행을 막는 것을 목표로 한다. 영속화 실패·DB 손상·감사 기록 실패 시 신규 실행을 열지 않고 기존 상태를 보존한다. 정지는 기존의 장애 중 정지 경로를 따른다.

## 4. 진행·취소·완료

설계상 단계는 준비, 접수 여부 불명, 하위 접수, 실행 중, 취소 요청 중, 재대조 필요, 종단 결과다. 새 wire enum을 선언하지 않으며 기존 상태에 의미를 보존해 매핑한다.

- 접수 응답은 실행 허가·물리 완료가 아니다. 하위의 실행은 기존 named operator·admission·claim·장치 검증을 거친다.
- 취소 요청 접수는 정지 완료가 아니다. 실행 전 취소와 실행 후 정지·종단 결과를 구분한다. 상위가 취소를 요청했다는 이유로 물리 자원을 해제하지 않는다.
- 완료와 취소가 경합하면 실행 소유자의 영속 순서와 결과를 사용한다. 완료가 먼저 확정된 작업을 취소 성공으로 덮거나 동일 시도의 실패·성공을 임의로 바꾸지 않는다. 취소 뒤 늦은 응답은 해당 시도의 이력으로 대조한다.
- 관제 identity·관계 세대·작업 identity·시도 identity·소유자의 단조 revision으로 응답을 결속한다. 과거 관계·다른 시도·낮은 revision의 결과는 현재 상태를 덮지 않는다. 늦은 결과가 기존 결과와 모순이면 재대조 필요로 남긴다.
- 관제 간 벽시계 순서로 승자를 고르지 않는다. 시계는 운영 표시와 출처에 쓰고, 권한·상태 갱신 순서는 각 소유자의 영속 revision으로 판단한다.

## 5. 권한·사람 확인·정지

상위 서비스는 자기 신원으로 직접 자식에게만 위임한다. 운영자와 원래 업무 출처는 감사 맥락으로 전하지만, 클라이언트가 적은 operator 이름을 인증으로 신뢰하지 않는다. 자식이 가진 장치 자격증명을 상위로 넘기지 않는다.

관계 등록과 실행 허용은 별도다. 인증 주체·대상 범위·허용 업무·유효한 관계 세대의 교집합만 허용한다. 첫 버전의 상위 요청은 후보·위임 접수까지만 만들며, 사람 확인이 필요한 작업은 하위의 인증된 named operator가 기존 승인 경로에서 승인한다. 상위 operator 이름·AI 응답·상위 승인 표시·공유 브라우저 세션을 하위 승인으로 신뢰하지 않는다. 상위의 사람 승인을 하위에서 소비하려면 대상·작업·계획 revision·승인 신원을 결속한 별도 계약을 먼저 정한다. 승인 전후 계획이 바뀌면 기존 revision 검사를 통과해야 한다.

권한 회수나 관계 revision 변경을 하위가 영속 반영한 뒤에는 과거 권한의 신규 접수를 거절한다. 이미 접수한 실행은 회수·정지 정책에 따라 별도 처리한다. 네트워크 분할 중 즉시 전역 권한 회수를 보장한다고 주장하지 않는다. 첫 버전의 관계/권한 변경은 접수 정지·양 끝 확인·진행 작업 대조 후 적용하며, 긴급 상황은 기존 현장 정지 수단을 사용한다.

상위 일괄 정지는 자식별 요청·응답·미확인 범위를 각각 기록한다. 일부 응답만으로 전체 정지를 표시하지 않는다. 상위 장애가 현장 정지와 물리 E-stop을 막아서는 안 된다. 래치 해제는 기존 장치·사이트 소유자의 명시적인 공개 경로만 사용한다. 어떤 관제도 안전 PLC나 물리 E-stop 회로를 대신하거나 우회하지 않는다.

## 6. 단절·재시작·재연결

| 상황 | 기본 동작 |
|---|---|
| 상위–하위 링크 단절 | 첫 버전은 현재 admission된 유한 Action의 기존 실행·정지 정책만 유지한다. 접수된 전체 계획을 계속 실행하는 허가가 아니다. 다음 Action·다음 하위 위임과 상위 응답·타 관제 인계에 의존하는 단계는 막고 대조를 기다린다. 더 넓은 로컬 연속 실행은 별도 허용 범위·admission 계약이 필요하다. |
| 하위의 로컬 운영자 요청 | 사전에 로컬 권한이 부여되고 상위 위임과 자원·업무가 겹치지 않는 범위만 기존 admission으로 처리한다. 단절로 권한이 확대되지 않는다. 불명 점유는 계속 잠근다. |
| 현장 Fleet–장치 링크 단절 | D-419·해당 장치 owner의 기존 정책을 적용한다. 상하위 관제 링크의 정책으로 대체하지 않는다. |
| 상위 재시작 | 영속 위임 기록을 읽고 미종단 작업을 하위에 조회한다. 조회 전 새 요청으로 재발행하지 않는다. |
| 하위 재시작·DB 복구 | 중복 방지·작업·claim·관계 세대를 복구하고 기존 장치 결과와 대조한다. 검증된 복구 전 신규 접수·점유 해제를 막는다. |
| 재연결 | 서로 신원·구성 revision을 확인하고 미종단 작업의 소유자 snapshot·revision·결과 근거를 대조한다. 승인된 작업·점유 대조가 끝난 범위만 신규 위임을 다시 허용한다. |

링크 상태는 응답 관측의 로컬 monotonic clock으로 측정한다. 첫 구현에서 링크 유실 감지 시간은 실행 권한·점유 해제·재배정의 자동 시한으로 쓰지 않는다. 표시 주기·backoff는 설치 조건에 맞춰 제한하며 별도 장애 측정으로 확정한다. 장치의 기존 watchdog 값은 바꾸지 않는다.

상위의 오래된 조회 결과는 stale로 표시한다. 이벤트 스트림은 조회 최적화이며 유실 시 소유자 snapshot으로 복구한다. 모순·누락·증거 부족은 불명으로 보존하고 사람이 확인한다. 연결 복구만으로 자동 재시작·래치 해제·권한 승격·자원 점유 해제를 하지 않는다.

문서/합성 시험과 실제 장치 수용을 구분하고, 모든 실행 증거는 코드 SHA·환경·수행/skip 수·원본 로그에 결속한다. pytest는 플랫폼 공식 원격 runner와 known failures 비교를 따른다. 현장 접근·실물 동작·서비스 재시작은 별도 승인 범위를 확인한다.

## 설계와 수용 상태

최종 목표와 G1–G5의 세부 기본안을 작성하고 독립 검토 지적을 반영했다. 문서 등록과 검토는 기능 수용을 뜻하지 않는다. D-851 세부 결정 승인·공개 API 등록·코드 구현·장치 및 현장 수용은 별도 증거로 닫는다. 원격 시험·병합 결과는 SHA에 묶인 착지 기록과 완료 보고를 따른다.

CE: 해당 없음 — 구조 설계의 정식 기록이며 새 장애 원인·복구 방법을 검증한 사례가 아니다.

## 독립 검토

새 검토자가 문서와 관련 ADR·작업/미션 소유 경로를 읽고 4건을 지적했다. 관계 세대와 무관한 불변 위임 식별, 단절 중 현재 admission된 유한 Action만 허용하는 기본값, 하위 인증 named operator 승인 경로, D-435의 Proposed 상태 구분을 반영했다. 이 검토는 구현·공개 API 전체·시험·장치 수용 검증을 대신하지 않는다.

수정 후 같은 검토자의 재검토에서 4건 모두 닫혔고 수정으로 생긴 중요한 모순을 발견하지 못했다. 제품 저장소 등록 시 문맥·연결 변경은 다시 검토한다.
