# 독립·상하위 관제 후속 목표

**기준:** [D-850](../adr/D-850-composable-control-units.md). 구조 목표는 Accepted이며 이 문서는 후속 설계·검증의 순서를 정한다. 완료 표시는 산출물과 검증 근거가 있을 때만 한다. 아래 계약·기능은 아직 구현 완료가 아니다.

**목표:** 관제 단위가 독립 운영하고, 하위 관제를 포함하며, 상위에는 하나의 서브 관제로 참여할 수 있게 한다. PC 배치는 논리 책임과 별도로 정한다.

**상세화:** [최종 목표와 상세 설계](2026-10-23-composable-control-design.md)에 G1–G5의 기본안과 P0–P5 실행·수용 기준을 기록했다. [D-851](../adr/D-851-control-unit-delegation-and-recovery.md)은 세부 계약의 Proposed 설계다. 독립 검토를 마쳤으며, 설계 기록·병합과 세부 결정 승인·기능 수용은 구분한다. 아래 체크박스는 승인·구현·수용 근거 없이 닫지 않는다.

## 진행 순서와 완료 기준

- [ ] **G1 — 첫 적용 범위와 관제 경계 결정.** 현장 내 공정·셀 또는 다중 현장 중 첫 범위를 정한다. 관제 식별·등록·관할 자원·부모 관계·순환 방지·지원 깊이를 설계하고 구성 예시를 남긴다. 완료 기준은 독립 A, 상위 아래 A·B, 자체 하위를 가진 A의 상위 참여를 모순 없이 설명하고 잘못된 포함 관계의 거절 기준을 정한 것이다.
- [ ] **G2 — 상태 정본과 업무 위임 계약 결정.** G1을 입력으로 상위 업무와 하위 작업의 대응, 각 상태의 쓰기 소유자·조회 출처·완료 증거를 정한다. 접수와 실행 완료를 구별하고 거절·취소·재시도·중복 요청·상위 교체 시 경합을 명시한다. 완료 기준은 정상·중복·응답 유실·취소 경합의 순서별 상태 전이와 소유자를 설명할 수 있는 것이다.
- [ ] **G3 — 권한과 정지 경계 결정.** G1·G2의 범위별 인증·위임 권한·사람 확인과 정지 요청의 전파·응답·실패 처리를 정한다. 완료 기준은 서브 등록이 구동 권한을 만들지 않고 상위 요청이 CORE·OMX owner의 검증을 우회하지 않으며, 무권한·범위 밖 요청·권한 회수 중 요청의 처분이 정해진 것이다. 안전·계약 경로는 해당 저장소의 독립 검토를 거친다.
- [ ] **G4 — 단절·재연결 정책 결정.** G2·G3를 입력으로 상위 단절 중 기존 작업·신규 요청의 허용 범위, 장치 연결 단절, 재연결 후 상태 대조·충돌 처리·늦은 응답 처분을 정한다. 완료 기준은 중복 실행 없이 상태를 맞추는 근거가 있고 링크 복구가 래치 정지 해제나 자동 권한 승격을 뜻하지 않는 것이다. 기존 단절 정책을 변경하려면 소유 계약을 별도로 개정한다.
- [ ] **G5 — 최소 구현 범위와 PC 배치 결정.** G1–G4 승인 후 현재 서비스·API·원장을 재사용할 부분과 필요한 최소 변경을 실제 호출 경로로 조사한다. 관제 서비스와 화면, 현장 조정, 모델·추론, 장치 실행을 호스트별로 배치하고 자원·네트워크 조건을 적는다. 완료 기준은 소유 파일·생산자·소비자·공개 계약·회귀 시험이 지정된 구현 계획이다. 역할마다 별도 PC나 새 서비스를 강제하지 않는다.
- [ ] **G6 — 구현과 단계별 수용.** G5의 구현 계획에 따라 변경한다. 독립·상하위 업무 흐름과 무권한·중복·거절·취소·단절·재연결을 검증한다. 중첩 구성은 G1에서 승인한 깊이까지 확인한다. 완료 기준은 커밋 SHA에 묶인 원격 회귀와 종단 증거이며 실물·현장 수용은 별도로 기록한다. 소프트웨어 시험만으로 장치 수용을 완료 표시하지 않는다.

## 소유 기준과 변경 위치

설계 시 아래 정본과 실제 호출 경로를 먼저 확인한다. 폴더 위치만으로 실행 권한이나 배치를 추정하지 않는다.

| 대상 | 현재 확인할 위치 | 후속 산출물 |
|---|---|---|
| 용어·구조 목표 | `CONCEPTS.md`, D-850 | 용어가 확정되면 용어집을 갱신하고 구조 결정은 ADR에 기록 |
| 작업·원장·조정 | `operations/fleet/`, `operations/site_execution/`, D-435 | G2의 상태·위임 설계, 소유 경로별 구현 계획 |
| 관측·상태 출처 | `operations/world/`, D-435 | 실행 결과와 관측을 구분한 출처·정합성 설계 |
| 관제 화면·접점 | `applications/fleet/`, 공개 API reference | 상하위 범위·상태를 표시하는 소비자 설계 |
| 장치·안전 | `middleware/core/`, OMX owner의 현행 계약, D-430 | 권한·정지·단절 검토와 소유자별 수용 근거 |
| 호스트 배치 | `deploy/`, D-434·D-516 | 실제 설치 구성과 자원·통신 조건 |

미결 계약을 API 필드나 실행 모드로 먼저 구현하지 않는다. accepted ADR의 기록은 보존하고 결정이 바뀌면 저장소 ADR 절차를 따른다. 구현 단계에서는 소유 경로의 AGENTS와 SRS·API reference를 읽고 영향을 받는 호출자·시험·설정·설치 경로를 함께 다룬다.

## 검증과 보고

문서 단계는 harness 생성·lint와 저장소의 문서 계약 시험으로 확인한다. 구현 단계의 시험 선택은 변경된 경로와 공식 affected selector에 따른다. pytest는 커밋된 SHA를 공식 원격 runner로 실행하고 모든 결과를 known failures와 비교한다. 안전·권한 검토, 실제 UI 종단, 장치 동작, 현장 수용은 각각 증거를 남긴다.

G1–G4는 설계 산출물의 승인, G5는 실행 가능한 구현 계획, G6은 기능·장치 수용의 증거로 닫는다. 이 목표 목록을 기록·병합한 사실만으로 어느 항목도 완료 처리하지 않는다.

CE: 해당 없음 — 후속 목표와 종료 조건의 기록이며 장애 원인·복구 방법을 새로 검증한 사례가 아니다.
