- **Status:** Active — 벤치(G-S1) 착수 전 판정 기준. 이 문서의 합격 기준을 통과한
  것만 "동작한다"고 말한다
- **Date:** 2026-09-22
- **Related:** `signal/README.md` (ROSY-SIGNAL-001),
  `docs/plans/2026-09-21-fleet-signals-integration-design.md` (G-S3 설계),

## 0. 왜 이 문서가 필요한가

지금까지의 증거는 전부 **호스트 소스 시험(E1)** 이다: 계약 시험 14건, fleet 시험
392건(2026-09-22, 교차 검증 포함). 이것이 증거하는 것은 "문서와 코드가 갈라지지
않는다"까지다. 다음은 아직 **증거가 0** 이다:

- 릴레이 접점이 실제 신호등 회로를 닫는가
- ESP32 가 부팅하는 동안 릴레이가 튕기지 않는가
- 관제 접촉이 끊기면 정말 10 s 뒤에 적색 점멸로 가는가
- 공유기가 재시작한 뒤 장치가 스스로 돌아오는가
- 구입한 신호등이 애초에 접점 방식과 맞는가(전압·배선·소비전류)

저장소 규칙 그대로: **합성 시험 ≠ DEVICE**(D-94), "A passing host pytest is not
device acceptance".

## 1. 증거 등급

| 등급 | 뜻 | 예 |
|---|---|---|
| E1 | 호스트 시험 | `test_signal_contract.py`, fleet pytest |
| E2 | 벤치 실측 — 계측·사진·시리얼 로그로 남은 것 | 멀티미터 연속성, 스톱워치+동영상 |
| E3 | 현장 관찰 — 설치 위치에서의 반복 관찰 | e-stop 연동, 장시간 무고장 |

**판정 규칙:** 각 수용 기준(AC)은 요구 등급 이상의 증거물이 `docs/validation/signals-<date>/`
에 기록될 때만 GO. 증거물 없는 "됐겠지"는 HOLD 다.

| W7 | **토큰 비교가 상수 시간 아님, LAN 신뢰 모델** | 코드 | 타이밍 공격 여지 — 실내 사이트에서 수용 가능 수준 | 문서화로 처분(계약 §인증). 필요 시 개정 |

| W9 | **버튼 인터페이스 불명** — "버튼을 눌러서" 맵핑한다고 했으나, 그 버튼이 본체 물리 버튼인지 유선 리모컨인지 무선(RF 433 MHz) 리모컨인지에 따라 아키텍처가 갈린다. RF 리모컨이면 접점 병렬이 안 되고 리모컨 기판 접점 병렬(리모컨을 우리 인클로저에 넣는 방식)이 된다. 또한 버튼이 "색 직접 선택"이 아니라 "모드 사이클"이면 현 계약의 `lamps` 직접 상태 모델이 성립하지 않는다(펄스 프리미티브 + 상태 재동기화 필요 → 계약 개정) | B0 특성화 시트 | 맵핑 아키텍처 전체와 계약 모양 | B0 가 세 갈래(§8)를 결정한다 |

## 5. 벤치 절차 (B0–B7, 순서가 계약이다)

- **장비:** 벤치 PSU(12/24V), 멀티미터(연속성/전류), USB 전류계, 스마트폰(동영상 타임스탬프), 예비 저압 램프/LED(1차 검사용), 공유기(전원 스위치 있는 것)
- **B0 신호등 입고 특성화 (W5, W8, W9) — 2026-09-22 실물 입고. §8 특성화 시트로 수행.** 개봉 → 배터리·버튼·배선 기록 → 버튼 회로 전압/전류 측정(AC-21) → 배터리 방전 곡선 준비. 여기서 맵핑 갈래(§8)가 정해지고, 계약 모양(state vs pulse)이 결정된다.
- **B1 릴레이 모듈 검사 (W2):** 3.3V/0V 인가 절동 확인, 트리거 극성 확인, 바이어스 저항 장착 확인 → 사진.
- **B2 펌웨어 플래시 + 부팅 글리치:** 플래시 → 10회 전원 사이클 → 등 관찰(AC-02, AC-06).
- **B3 하트비트/페일세이프:** 정상 명령 → 관제 정지 → 스톱워치(AC-11, AC-14).
- **B4 재접속/재단언:** 공유기 재시작 (AC-12, AC-15).
- **B5 e-stop 통합:** Fleet + 가짜/실 로봇 + 신호등 (AC-16).
- **B6 장시간:** 1 h cycle 측정(AC-10) → 4 h 연속(AC-19).
- **B7 운영 시나리오:** AC-18 수행자 기록.

증거는 `docs/validation/signals-<YYYY-MM-DD>/` 에 — `README.md`(절차·관찰) +
`result.json`(AC 별 GO/FAIL 수치) + 사진·동영상·시리얼 캡처. 기존 validation 폴더
관례를 따른다.

## 6. 이 계획이 증명하지 않는 것 (정직한 목록)

- 도로용 신호기 인증이 아니다 — EN 12675 는 원칙 차용일 뿐, 적용 대상 아님
- v1 에서 로봇은 신호등을 읽지 않는다 — "로봇이 신호를 보고 멈춘다"는 별도 과제

- 무선 간섭·금속 인클로저 환경 변수는 설치 위치마다 다르다 — AC-05 는 설치 시 재측정

## 8. 2026-09-22 업데이트 — 실물 확정(배터리+버튼 제품)에 따른 특성화 시트와 맵핑 갈래

구매 완료. 제품은 **배터리 구동**이고, ESP32 릴레이가 제품의 **버튼을 대신 누르는**
방식으로 간다. 이는 앞선 "릴레이로 램프 전원선을 직접 스위칭" 가정을 대체한다 —
전기적으로 더 안전해지지만(램프 전원을 만지지 않음), 두 가지 새로운 불명이 생긴다:
버튼이 무엇인가(W9), 배터리가 버틴다(W8).

### 8.1 B0 특성화 시트 (실물 앞에서 채우는 표)

> 동작은 **모드 사이클**(누를 때마다 빨강→초록→… 전환), 배터리는 **건전지 교체식**.

### 8.2 맵핑 갈래 — B0 가 하나를 고른다

**갈래 A — 본체/유선 버튼 병렬 건식 접점 (가장 단순, 1순위)**
버튼 단자에 릴레이 NO 접점(또는 논리 레벨이면 옵토커플러 PC817/AQY 계열 — 무음·무마모·무바운스)을
**병렬**로 연결. 사람 손과 ESP32가 같은 버튼을 누를 수 있다. 전제는 AC-21 통과
(버튼이 저전압 논리 회로)와 버튼이 "직접 선택"형일 때 깔끔하다.

**갈래 B — RF 리모컨 접점 병렬 (리모컨 방식 제품의 표준 해법)**
제품이 무선 리모컨으로만 제어되면, 리모컨을 우리 인클로저에 넣고 각 버튼 패드에
접점을 병렬 납땜한다. 리모컨 자체 배터리로 살아 있게 하고, 접점은 펄스(예: 200 ms
누름-이음)로 짧게 — 계약의 `lamps` 상태 모델이 아니라 **펄스 프리미티브**가 된다.

**갈래 C — 내부 수신기 출력 탭 (최후)**
개봉해 수신 디코더의 구동 라인을 옵토커플러 입력으로 탭. 가장 직접적이지만 제품
개조라 고장 시 수습이 어렵다. A·B가 모두 불가할 때만.

### 8.3 계약(ROSY-SIGNAL-001)에 미치는 영향 — 갈래가 정한다

| 갈래 | 계약 영향 |
|---|---|
| A + 색 직접 버튼 | 현 계약 유지 가능. `lamps` 는 "우리가 누른 마지막 상태"의 추정임을 문서화 — 제품 내부 상태기계가 색을 바꿔 버리면(더블프레스 등) 콘솔과 어긋난다 → AC-22 로 재현성 확인 |
| B 또는 모드 사이클 버튼 | **계약 개정 필요**: `lamps` 상태 명령 대신 `press(button, ms)` 펄스 프리미티브 + "상태는 추정" 선언 + 재동기화 절차(전원 사이클 또는 N회 프레스). 페일세이프의 "전 기능 적색"도 강제 불가 → "전원 차단 = 소등" 또는 "프레스 반복으로 적색 유도"로 재정의. Fleet 콘솔 UI 와 시험 전반 영향 — 별도 설계 문서로 |
| 어느 갈래든 | 페일세이프(침묵→점멸)는 **컨트롤러가 볼 수 있는 범위**에서만 유효하다. 버튼 제품에서 "점멸 패턴"을 제품이 지원하지 않으면 페일세이프 표시는 "전원 차단(소등)" 또는 "적색 유지"로 대체 정의해야 한다 — 이것은 장치 계약 §페일세이프의 개정이다 |

### 8.4 전원 아키텍처 (W8) — B0 숫자가 정한다

- 컨트롤러(ESP32+릴레이)는 하트비트 계약상 상시 가동 → **~0.5 W** (3.3 V 기준
  100–160 mA). 딥슬립으로 못 준다.
- 계산식: 런타임(h) ≈ 배터리 Wh × 0.8(효율) ÷ (컨트롤러 W + 램프 평균 W).
  예: 3.7 V 2.5 Ah(≈9.3 Wh) 배터리에 컨트롤러만 얹으면 ≈ 15 h, 램프 상시 점등이
  겹치면 크게 줄어든다 — **실측이 답**이고 AC-20 이 그것을 강제한다.
- 갈래: (a) 제품 배터리 공유(레귤레이터 필요, 제품 보증 리스크) / (b) 컨트롤러 별도
  전원(보조배터리·USB — 가장 깔끔, 충전 주기 분리) / (c) 대용량화. 기본 권장은
  (b) — 제품을 개조하지 않는 선에서 두 전원이 서로를 죽이지 않는다.
