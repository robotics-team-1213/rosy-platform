# remote

**Parent context:** `../AGENTS.md`
**Updated:** 2026-10-14

## Purpose

Run pytest for one commit on whichever of the model PC (OMEN), AI PC and site PC has headroom (D-568), instead of the Windows laptop, and tell Gazebo scripts which host to use (`--pick sim`). `tools/hooks/pre-push` and `tools/land.py` use it. `remote_sim.py` runs a headless Gazebo bench on the host that placement picks (D-571).

| `remote_job.py` | One pytest invocation as a job detached from ssh (`setsid nohup`, so the host needs `loginctl enable-linger` for the `systemd-run --user` scope; all three have it). The job holds `~/rosy-jobs/<run>.lock` with its own pid (also its process group id), which PROBE counts while that pid lives (the same pid also goes to `<run>.jobs/<k>.pid`, so liveness is per invocation); its EXIT trap writes the exit code to `~/rosy-test/runs/<run>.jobs/<k>.rc` (temp file then rename) and removes the lock, so the lock ends with the job even if the laptop never returns. `timeout --foreground -k 30 ROSY_TEST_TIMEOUT` (default 5400 s, exit 124) bounds it on the host. The laptop polls every 10 s over a short ssh call for log bytes after its offset (`tail -c +N`) and the exit code (read before the log, so a poll that sees it has the whole log) and prints the last 25 lines at the end, as before. A failed start or poll is retried after 5, 10, 20, 30, 30 ... s until `ROSY_TEST_RECONNECT` s (default 600) pass without contact; then that invocation and the rest of the run exit 255 with "lost contact with <host> for N s; the run continues there: <path>", and the job, its lock and its run directory are left on the host (no kill, no cleanup). The next SHIP on that host sweeps such runs: a `<label>-<6 hex>` run (never `sim-*`) whose `.jobs` dir has an exit code, no live pid (its `*.pid` and `~/rosy-jobs/<run>.lock`) and is older than 12 h loses its worktree (`git worktree remove -f -f`, prune), its `refs/remote-pytest/<run>` and its `.jobs` dir; nothing else under `~/rosy-test` is touched. A job that is gone without an exit code (host reboot, SIGKILL, START cut off) shows as no live pid and no code on two polls in a row: exit 254 with a note at the end of the local log (land.py stops on anything but 0/1). START is idempotent on the exit code or a live pid. Ctrl-C on the laptop, also during START's backoff, sends TERM to the job's process group (the job records 143), then cleans up as before. ## For AI Agents

### Working In This Directory

- Only the committed sha is tested; commit before running. There is no local fallback (D-584).
- A Gazebo script takes its host from `python tools/remote/remote_pytest.py --pick sim`, writes `echo "$$ sim 6 8" > ~/rosy-jobs/sim-$$.lock` on that host and removes it on exit; `remote_sim.py` does both itself. Never run a sim on a site host (`~/rosy-jobs/site`, D-571), even if `--pick sim` prints one. Before a demo or field drive, `touch ~/rosy-jobs/busy` on the site PC; remove it afterwards.
- The tool never installs: sim capability (`ros-jazzy-ros-gz ros-jazzy-navigation2 ros-jazzy-nav2-bringup ...`, D-568 5) is a sudo step a person does (`rosy-host-state install <model|ai> --approve sim`, D-571 2). The site PC (Ubuntu 26.04, system Python 3.14) needs `uv python install 3.12` (no sudo) for pytest; it has it since 2026-10-09 and carries the `~/rosy-jobs/site` marker. Put that marker on any host that runs live Fleet.
- Everything else on a host stays under `~/rosy-test` (sim runs too: `runs/sim-*`, `sim-pydeps/`; and `~/rosy-jobs` for locks). Do not install anything else there; another person uses the AI PC GPU and other sessions run Gazebo on the model PC.
- Other sessions run `~/rosy-test/venv/bin/python` directly. Keep that legacy environment intact. Never delete a hash-specific venv while its tests may run; prune unused hashes by hand.
- Not shipped by the venv: Chromium (a browser job installs it into `~/.cache/ms-playwright`; browser tests never run on the laptop, D-584), the Pinky raw tools and CPU torch (CI installs them only for those suites), and ROS (not sourced, as on the laptop).
